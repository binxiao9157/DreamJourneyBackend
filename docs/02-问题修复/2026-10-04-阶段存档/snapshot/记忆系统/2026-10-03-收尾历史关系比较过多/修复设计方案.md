# Live 收尾历史关系比较过多：修复设计

日期：2026-10-03。范围：既有发布链的性能修复；不重做会话协议或 UI。

## 问题与已证实原因

10/2 真机长场从冻结到发布约 451.63 秒，434 次请求中 374 次为历史关系提案/复核，约占 86%。正文已齐全；不能归因为手机上传缺失或模型容量报错。当前代码虽最多召回 8 个历史主题，却展开每个新事实页 × 每个旧事实页，分别提案与审核。“目标数量有界”未约束实际模型工作量。参考[原验收记录](../2026-10-02-短场主题更正类型冲突导致发布失败/2026-10-02发布修复部署与真机验收.md)。

## 修改方案

1. 保持同账号/档案/权限 epoch 的既有召回。多目标时先用已核验的主题标题、完整摘要与身份摘要做一次轻量筛选。返回每个目标的原 ID/版本/hash 和 possible/unlikely/uncertain，不能新增目标。请求仍走真实 Provider adapter 和持久化单元，不在内存里直接信任模拟答案。
2. possible 和 uncertain 均进入原事实证据分页核验。unlikely 只代表检索筛除，不能当成“已证明无关系”。精确事实指纹或相同 atom 命中的目标不得被筛选丢弃。单目标保留原路线，避免普通短场增加请求。
3. 筛选不产生合并、重复删除或正式更正权限。合并继续经过原关系提案、独立审核、成员/证据绑定、完整分页汇总以及提交时版本校验。目标不在前几位的关系仍可被选择。
4. 可选关系请求每个 run 最多 32 次，包含筛选、提案、复核及失败重试；在 memory 锁和 PostgreSQL run 行锁内预留时计数。跨 Worker、冷启动、重试不能重新获得 32 次额度。已完成单元校验后复用，不新增调用。该限额是此修复版本的附加上限，不提高原冻结总预算，不修改旧预算快照合同。
5. 用尽额度或筛选的可恢复模型失败时，沿用当前已验证主题的独立发布降级。未完整核验的部分关系不得用于历史写入。筛选回答的 ID/版本/hash 或 JSON 错误时整份丢弃并记录失败单元，不采用其中任何目标；不能因此阻断本场已核验主题。真实权限、数据库、持久化请求/响应缓存或原事实证据绑定错误仍失败关闭。筛除目标及筛选输入/响应 hash 入发布 manifest，区别于验证通过的 none。
6. 32 次仅是历史关系调用上限，不是整体收尾请求或秒数承诺。提取、主题归纳、安全审核仍使用原预算；大主题合并后的重新归纳也保持原预算。本地调用减少不能替代真实时延验收。

## 取舍

摘要筛选可能漏召回细节，只影响可选历史关联，可能留下两张待确认卡；不能因筛选而丢掉本场已验证事实。明确记录筛除而非宣称全历史去重。筛选偏向召回，不确定也做事实核验。超预算时保留归纳主题，不拆成一句一卡、不自动修改旧正式记忆。后续如真实误筛证据存在，再讨论检索改进。

## 验收

- 旧版同断言复现大量历史比较；新版多主题历史明显减少请求，验证全部本场事实/证据保留。
- 末位相关目标、精确重复被错误筛除、补充/更正、多个可能目标、筛选不确定均覆盖。
- 错 ID/版本/hash、遗漏/重复目标、异常 JSON、超容量、超时/429、预算用尽分别检查；模拟语义和真实 Provider 合同分开报告。
- 32 次上限以实际持久化 reservation 为准；并发、重新构造 Worker/仓库、完成结果复用均不绕过。
- 隔离 PostgreSQL：短 A → 逻辑十分钟 → 短 B；待确认、确认、正式记忆及新连接回读；非空历史且触发筛选。
- 真实合成模型检查只用新造内容，不读历史用户正文，不改业务数据；如未执行必须写 NOT_RUN。
- 本次不部署、不安装、不真机、不提交或推送。后续真机同版短场先过再跑自然十分钟，记录真实调用数和发布耗时；此前 UI 修复仍待真机。
