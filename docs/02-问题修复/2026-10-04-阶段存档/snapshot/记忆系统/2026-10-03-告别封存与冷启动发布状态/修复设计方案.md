# 告别封存与冷启动发布状态修复方案

日期：2026-10-03。范围：iOS 本地修复，不改变模型整理、主题合并、审核、权限与重试预算。不部署，不操作历史业务，不新增真实模型调用。

## 1. 事实、原因与未知

现场证据见 [上一轮真机记录](../2026-10-03-收尾历史关系比较过多/部署与真机验证记录.md) 和 [失败记录](../2026-10-03-收尾历史关系比较过多/十分钟告别与冷启动状态失败记录.md)。原始产物：`outputs/2026-10-03-live-relation-device/run-01`。

十分钟场完成 20 对问答、40 条正文。告别开始于 613.56 秒；625.20 秒测试捕获调度停顿。后续 Live 已关闭，但 capture 仍 live，没有 closeIntent，服务端仍 collecting。正常重开后 closeIntent 落盘，服务器发布两个待确认主题。首次故障原因和 0.56878 秒停顿的精确线程仍未证明，不宣称 SDK 或模型故障已定位。

新增只读手机证据 `natural10-b-current-phone-outbox.json`：本场 closeIntent 为 14:55:56 UTC；publication=published、themeCount=2、snapshotRevision=1，version=109，手机已保存服务器 14:56:44 的结果。因此第二个问题不是仅服务器成功而手机尚未收到。

源码明确存在两个缺口：
1. Controller 的 active Manager 停止分支只调用 stopDialog，业务 finish 依赖后续 onDialogEnded；Manager 可因上下文缺失直接返回，也可能在同步 SDK stop 或回调身份检查处不能送达 UI。关麦并不保证封存。这是确定的依赖缺陷，但现场究竟命中了哪种缺回调情形仍未证实。
2. 冷启动发现只在展示 session 为空时选最新场；历史恢复的 blocked 项又能覆盖已有展示归属。于是新场 published 已落盘，仍可能只显示旧场整理状态。现场内存中的展示归属未留证，需用同断言反例验证这条确定代码路径，不伪称已还原现场全部时序。

## 2. 收尾修复

在 Manager 封闭并封存原始 canonical 输入之后、调用外部同步 stop 之前，通知 Controller 输入已封闭。Controller 对原 capture 发起幂等 finish，持久化 closeIntent，继续使用已有队列、缺口补齐和发布流程。缺少 active engine/context 的路径也必须完成业务封存；已接受 handoff 不丢弃。语音结束回调只负责原有清理，可重复到达，不能成为唯一业务收尾触发。保持原账号/场次隔离；不让旧停止回调关闭新场。

## 3. 展示修复

当页面没有新的活跃 Live/文字会话时，由持久化的最新 closing 场次确定展示归属，立即重放其已发布状态；当前新会话优先，旧场和异账号不得覆盖。历史恢复 blocked 项不得覆盖已选择的新协议结果。候选按钮继续进入现有列表。读取仍是只读、有界观察，不发重试整理/重新审核请求，不改变用户三类状态约定。

## 4. 验收

先留修前源码和 dirty diff。以同断言验证：真实 Controller 活跃 Manager 停止时，在受控 SDK stop 返回/回调之前已封存；重复停止不新增正文或重新整理；冷启动读取实际磁盘快照时，旧场展示不遮挡最新 published，历史 blocked 晚到不倒退；活跃新会话与异账号仍隔离。

进行短场保存、十分钟告别尾轮、延迟 append、已发布单调性、账号及音频回归。普通模拟器与受控生产 Manager 配置分开记录，通用 iOS 无签名构建验证原生 SDK 编译。结果按真实执行报告，不把本地合成结果当真机十分钟通过。
