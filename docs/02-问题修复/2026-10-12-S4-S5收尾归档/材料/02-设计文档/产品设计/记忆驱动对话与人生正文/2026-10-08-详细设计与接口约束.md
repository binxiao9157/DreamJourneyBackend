版本：V1.0；日期：2026-10-08；状态：**设计待审阅，代码未开始，新增验收全部 NOT_RUN**。

产品依据：[整体方案](<2026-10-08-记忆驱动对话与人生正文持续更新设计方案.md>)。执行顺序和门禁见[分阶段实施与验收计划](<2026-10-08-分阶段实施与验收计划.md>)。本文件细化实现契约，不表示批准开发、模型调用、部署、真机操作或历史重建。若与整体方案发生冲突，先登记差异并修订设计，不在实现中自行改换产品规则。

## 3. 检索上下文契约

以下是拟定的逻辑字段，不是已经存在的API或新增物理表。实施优先映射既有字段，映射清单必须标明“复用/新增/不适用”。

| 字段组 | 内容与约束 |
|---|---|
| 身份 | account、vault/subject、authorityEpoch；由服务端授权上下文建立，不能信任客户端任意指定 |
| 对话绑定 | session、turn、topicGeneration、requestGeneration；只接收仍有效的返回 |
| 查询 | 当前表达、必要的最近相关指代、主题线索；不得默认发送全场或全账户正文 |
| 状态 | hit / no_match / unavailable；超时、权限过期、投影未就绪有独立内部原因 |
| 事实 | memoryId、versionId、内容hash、证据引用、主体、事件时间/精度、计划/否定/频率等限定 |
| 新鲜度 | requiredRevision、observedProjectionCheckpoint；确认后的最低可见修订可核实 |
| 预算与追踪 | selected/dropped计数、原因、Context摘要hash、实际回答请求关联ID、耗时 |

结果流程：

1. 权限核验 → 读正式事实/投影 → 主题检索 → 相关性与版本过滤 → 容量选择 → 构建Context。
2. 投影落后时不能返回“已查无记录”。在既有权限内执行有界刷新/受控正式查询兜底；仍无法满足则返回不可用，继续对话与保存。S0选择复用的具体路径，禁止新增无界全库扫描。
3. 容量裁剪以完整事实及限定信息为单位，不能截掉“不”“偶尔”“打算”或时间变化的一半。
4. 实际模型请求必须能对应Context版本与所选事实；“检索返回200”只证明读取，不证明注入或使用。
5. 查询内容和记忆正文作为数据引用，不能作为系统指令执行；用户材料里的指令不得改变权限或提示词规则。

会话内主题状态仅用于当前指代和查询，可随会话结束释放；不是未经确认的长期事实。主题切换、退出、切账号、切档案都使旧generation失效。取消网络任务是资源优化，返回时重新比对身份和generation才是正确性保证。

## 4. 自然追问与Live接入

文字回响先验证真实正式事实进入实际回答路径，然后加入追问策略。无旧记录时可问“是什么时候开始喜欢的”，不说“你以前不喝”；只有大学喝过的记录时，不补写停喝经历；用户更正主体后，本轮使用更正理解，但不直接改旧正式记录。

Live目前为sessionSnapshot。**不得直接假设有本轮动态注入API。** S2交付能力报告，逐项证明当前SDK/模型版本的更新入口、载荷限额、回调顺序、当前/下一轮生效时点、播放和打断影响。

- 能本轮安全生效：在现有回答时序内注入，不另外生成语音答案。
- 只能下一轮生效：本轮正常回应，下一轮使用已到达的证据；记录真实采用轮次。
- 不支持安全更新：S2阻塞，保留原有快照能力。不得把任意主题回忆标通过，也不偷偷切换回答架构。

每轮最多一个有效检索；同主题同修订可复用。500ms仅为整体方案中的**初始等待预算候选**，S0冻结测量方法、S2实测确定，不能通过拉长开麦/回答超时换取通过。晚到且仍属同主题的结果只有在SDK契约允许时供后续轮使用；跨主题/场次/权限结果丢弃。禁止在音频回调、UI主线程或正文保存队列同步检索。

提示词以版本归档：对话版负责依据与追问，主题版负责关系和限定，正文版负责指定主题的组织。提示词不能承担权限、幂等、版本冲突的唯一防线。

## 5. 主题与确认契约

新旧关系判断必须同时考虑主体、事件、时间范围和语义，不能只看关键词相似：

- 同事件同含义：复用既有去重/补证据路径。
- 同主题新细节：关联补充；不覆盖没有被更正的旧细节。
- 过去不喝、现在喜欢：可共存的时期变化；保留时间线。
- 明确纠正：生成现有更正提案，预览真正受影响的旧、新内容。
- 关系未定：保留独立准确陈述，不猜测合并；正文可先独立成段。

候选预览绑定候选版本、关联正式版本、变更内容hash。用户确认时沿现有服务端校验；版本变化先保留编辑并展示变化，再确认新提案。编辑内容保留ownerReviewed来源，不能冒充原转写。拒绝不会删除旧正式记录。

确认回执、正文更新状态、检索投影状态是三个内部维度；不增加用户“正在审核”状态。网络丢失确认响应时，先按既有幂等身份只读核实，不能为了正文生成再发一次确认写入。

## 6. 正文定位与产物结构

### 6.1 输入和输出

正文输入只能是已确认且仍有效的事实版本。逻辑输出至少包括：

- owner/vault、sectionId、稳定topicId、稳定paragraphId。
- 事实版本集合及sourceRevision、算法版本、提示词版本、模型配置版本。
- 标题、句子/段落、每句支持的事实版本、时间限定映射。
- 本次覆盖事实集合、未覆盖事实及明确原因、派生质量状态。

不能仅返回自由文本再靠UI猜主题；也不能仅有引用ID就宣称语义忠实。覆盖核对关注否定、主体、日期精度、频率、计划、变化和原因。无法可靠润色的已确认事实使用忠实独立短段，不通过省略掩盖失败。

### 6.2 定位步骤

1. 按明确主体与具体主题匹配已有topic；弱关联保持独立，不强合并。
2. 复用topic/paragraph稳定身份；标题改名和列表移动不改变来源绑定。
3. 同主题按可证实事件时间排序；未知时间保持中性叙述。保存时间、内部ID不代表人生先后。
4. 更新受影响段落；出生、家人等无关主题正文和hash应保持不变。概览只有依赖实际变化时才更新。
5. 使用事件粒度分段；不按固定三条事实切块。过长主题可有子段，但不能混入无关事实。
6. 相对时间绑定原表达日期与精度，不能把“最近两年”随系统日期滚动，也不能自动精确成某月某日。

咖啡例的验收依据是事实和关系，不要求模型逐字输出固定范文。只有明确“停喝”且后来恢复的证据才允许“又”。

### 6.3 提交、任务、并发与故障

逻辑顺序：正式事实事务提交 → 持久记录派生需求 → 检索投影与正文任务各自推进 → 校验最新修订 → 发布可读产物。

S0检查既有事件/outbox/任务设施。如果不存在可复用的可靠通知，需要最小事务内派生意图或等效持久机制：**事实成功后即使进程立即崩溃，重启仍能找回待派生工作**。不能依赖内存回调或单次异步投递。外部模型不进入正式事务。

- 任务按owner/topic合并最新修订；固定输入指纹复用已成功产物，重复通知不重复插段。
- 短事务领取任务 → 事务外生成 → 校验事实仍有效 → CAS提交。旧任务落后时丢弃或并入最新任务，不能覆盖新版本。
- 跨账号/档案不可共享缓存和任务身份。缓存键包含事实版本与算法/提示词/模型配置版本；仅事实hash不够。
- 模型等待期间不持有数据库长事务或锁；生成资源与采集、尾批、发布保留隔离预算。
- 超时/限流按单任务累计预算有限重试；永久非法输出直接忠实降级。重启不能重置已消耗预算。具体预算在S0/S4实测后、正式验收前冻结。
- 页面GET只读产物和当前有效性，不同步调用模型；高频刷新不增加生成次数。
- 删除/更正之后，读取必须验证旧段的事实版本仍有效。失效句不可继续展示；使用当前事实降级，不能“保留旧成功缓存”暴露已撤销内容。
- 多段产物按同一主题修订原子发布，避免新旧半段混合。其他主题不等待失败主题。

## 7. 兼容、迁移与回滚

新增逻辑字段尽量落在已有模型和任务体系；新存储字段采用向后兼容方式，旧客户端可忽略附加投影字段。S0列出实际schema/API变化与旧新版本组合，再决定是否需要迁移；不因设计图凭空建第二套记忆库。

开关分为文字检索策略、Live动态上下文、正文新派生三个层级，默认关闭，验收后逐项启用。复用既有配置设施；不要在用户UI增加技术开关。关闭新正文策略不能让已撤销内容重新出现；回滚时仍须保留事实版本过滤与忠实降级。

回滚不删除已确认事实，不恢复被用户纠正的旧版本，不回退用户编辑。需要测试“新产物存在但策略关闭”“旧客户端读取新投影”“确认已提交而正文任务未完成”。历史正文批量重建另行预览和授权，不随发布自动全账户重跑。

## 8. 观测与实现审查

默认记录脱敏身份、阶段、版本、数量、hash、预算和耗时；测试正文只在授权合成数据范围存放。不得在普通日志输出完整记忆、提示词、凭据。

每个阶段必须交付需求→实际调用点→断言→产物路径。特别检查：实际回答路径是否被绕过；模拟是否直接喂答案；只读GET是否变成模型入口；新校验是否误接到候选发布门禁；正文失败是否改变回响三种状态；任务重启是否绕过重试预算。

本次文档未修改业务代码。历史query-no-match的具体根因仍待S0定位；本设计不把假设写成已证实根因。
