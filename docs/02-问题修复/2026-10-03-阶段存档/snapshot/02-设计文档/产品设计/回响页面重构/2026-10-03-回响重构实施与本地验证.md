## 自动核对的实际规则

详见[状态修复记录](/Users/gaominge/Documents/liftora/02-问题修复/记忆系统/2026-10-03-回响发布结果自动核对/实现与核对边界.md)。

- 新协议使用原会话 `recovery action=status`；服务端该动作走 `repo.read`。不调用 authorize、close、append、end、ACK、admit 或模型重试。
- 绑定账号 lease、vault、原 session、thread、productSessionID；同场响应版本/快照不能倒退。新 Live、正在启动的 Live 及活跃文字场不被旧结果覆盖。
- 页面可见且 App 活跃时发现关闭场，最多保留最近两场观察器。磁盘扫描/恢复坐标持久化在独立队列。
- 首段 15 秒间隔，之后 60 秒，再降至 120 秒。已有 HTTP 在途时，15 秒 UI 等待阈值只更新辅助提示，不释放传输槽，不发重叠请求；实际传输仍受既有 Client 截止约束。
- 页面退出/后台暂停调度并废弃晚到响应，重新出现恢复读取。没有提高模型重试次数，也没有把本地观察超时当作后台失败。
- 旧协议继续用原 RecoveryCoordinator，只对已结束观察轮的未知/权限等待进行只读核对，不复位正在执行的轮。
- 部分发布归完成；空结果为“整理完成，本次没有新增记忆”；权威失败为“整理暂未完成”。未知/断网继续“正在整理”并说明暂无法获取进度。保存不确定时不承诺原对话完整保存。

当前仅凭绑定本场的权威 publication 结果显示完成，未读取其他场候选总数冒充成功。**这仍不是 ST-05 的完整验收**：缺少 Source/主题身份和确认后状态的查询闭环，不能证明完成提示时每张指定卡片均可访问。

### 首次失败与修正

1. 首轮编译发现新测试的 ID 初始化标签及类型标注错误，已修正；编译错误不算业务红测。
2. 首轮回归抓到新按钮把“连接中快速结束再开始”的第三次点击按旧 `.starting` UI 状态再停止。改为依据真实 activeVoiceLaunchAttempt 判断取消；四个 MIC-05 同断言原失败、最终通过，未放宽业务断言。
3. 旧文案与“核实整理”按钮断言不再符合已确认设计，更新为三态主文案、保留保存缺口辅助信息及自动只读核对；仍验证请求次数和迟到结果隔离。
4. 首轮 MIC-04 鉴权失败伴随 `OSStatus -34018`。原因在测试装配：无签名 Simulator host 无 Keychain entitlement。最终采用本地 ad-hoc 签名，同测试通过；没有修改鉴权产品逻辑。
5. 小屏截图发现状态文字被压缩。提高文字抗压缩优先级，并让中部内容滚动；最终状态可读，展开入口在小屏可通过滚动到达。

所有首次失败保存在 `regression-01.xcresult`、日志和基线副本，不覆盖。旧版180秒状态误报有既有现场证据；本轮可控时钟验证超过180秒继续读取成功，**未宣称已经补齐修前独立副本的同断言复现**。
