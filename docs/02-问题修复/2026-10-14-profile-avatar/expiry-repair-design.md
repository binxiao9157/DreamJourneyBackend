# 头像等待几分钟后保存失败：根因、范围与修复方案

2026-10-13；用户明确授权先分析归档、再修改和测试。真机仅USB直连，禁止镜像。沿用原账号，不登出、不清缓存、不清记忆。

## 现象与已确认链路

用户和真机均复现：资料页停留约5～6分钟后，保存头像提示网络失败。失败时未见POST /profile，旧头像仍在，选图仍保留；曾有一次单按钮保存成功，两次POST均200。现场策略缓存取回23:20:58、到期23:25:58，失败发生在到期后。

生产调用为 ProfileSettings.saveTapped → UserManager.saveAvatar → BackendClient.uploadProfileAvatar → requestJSON → profileSettings请求门禁。FeatureGateService.requestDecision会优先复用routeDecisions；FeatureGateEvaluator.revalidateForRequest在captured.expiresAt过期时直接返回capturedPolicyExpired。未捕获route时，过期策略缓存同样返回expiredPolicyCache。requestJSON在创建实际业务网络请求前返回featurePolicyDenied，没有资料写入口专属的策略刷新恢复。仅刷新缓存也不足：旧route决定仍可能过期/拒绝，因此提交新保存意图需要从当前策略重新取得请求决定。

另一个确定缺陷：UserManager头像失败分支丢弃Error，所有失败显示“请检查网络”。这把本地策略拒绝包装成网络问题。不是图片格式已被服务器拒绝，也不是必须同时点两个保存。

现场未录到此前每次失败的具体reason，不能倒推所有历史失败都是同一原因。本轮将用真实生产策略评估、HTTP请求方法、策略响应解码/缓存组成的修前红与修后绿，证明这一确定缺口；新请求增加不含图片/手机号/凭据的阶段诊断，真机等待超过真实TTL再核对。

## 修改边界及风险评估

只调整 BackendClient 的两个 /profile 写入口（头像、昵称/性别/地区）及 UserManager头像错误文案分类；补对应测试。服务器API、数据库、鉴权校验、TTL不改。统一底部保存和原子更新头像/保留资料合同不改。

不修改共用requestJSON恢复行为、FeatureGateEvaluator拒绝规则或全局捕获route；不放宽任何功能权限。Live、文字回响、记忆保存/候选/确认/检索、开麦与音频不变。避免在共用层无限刷新/重试写请求，是本次最重要的影响范围控制。

## 请求流程

1. 捕获本次保存的本人账号、sessionId和应用账号租约；跨账号或过期回调不能写入。
2. 从当前策略取得新的profileSettings请求决定，不复用进入页面的旧route。有效且允许时直接发送一次POST。
3. 仅对过期或缺失策略触发一次同账号、同audience/cohort的GET /v2/release-policy；不把明确拒绝、关闭功能、完整性损坏等当作可绕过的暂态。
4. 策略刷新最多等待15秒。失败/超时即结束本次保存，不发送POST。迟到的刷新结果不允许启动业务写入。
5. 刷新成功后再次检查账号租约、sessionId，重新评估当前策略。仍过期/不允许则拒绝；允许才发送一次POST。传入明确的新请求决定，仍走原requestJSON的鉴权、租约、运行策略和决定重校验。
6. 本次不新增POST重试，保留共用层既有401认证恢复行为。上传失败保留表单和选图；不把未经服务器确认的头像写入本机成功缓存。用户可点击保存发起新意图。
7. 记录traceID、阶段、reason及HTTP状态；不记录图片、资料正文、token。UI区分权限暂不可用、登录身份变化、网络错误与其他保存失败。

统一保存包含头像/基本资料两个原有写操作。首次刷新后基本资料直接使用当前新策略，不应再重复刷新。部分成功提示沿用现有规则。

## 验证与准入
