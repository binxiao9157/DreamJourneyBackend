# 真机测试方案补充：每场开始前清理旧测试记忆

日期：2026-10-04。依据用户要求：本场完成、下场开始前删除旧记忆，避免影响后续测试。本规则适用于后续执行的真机测试，优先于旧指导中“不清理账号数据”的历史限制；本次只更新方案，尚未执行删除或改动自动化代码。

## 1. 清理范围与时机

适用当前已授权的测试/演示账号及测试所属档案。清理历史测试生成的正式记忆，以及待确认主题/候选；仅删除正式记忆而遗留待确认候选，或只隐藏列表，均不算完成。其他账号、家人档案及非测试资料不在范围内。

每场测试结束后先完成保存、候选、正式确认及冷启动回查等已执行步骤的取证，保留失败原值、Source/runID、候选/正式记忆ID、时间线、报告和指纹。**下一场开始前必须完成清理及核验**。如果用户还要查看本场内容，可以在等待下场期间保留，但不能带入下一场。

第一次执行本规则时，同样先清理当前账号/档案已有的旧测试记忆。短场产生的记忆也属于下一场的旧记忆，不能作为例外留下。单纯换测试文案、名字或主题不能替代清理。

## 2. 执行顺序

1. 冻结并归档本场结果，完成必要的读取和取证；不能为腾空账号而中途删除正在验收的数据。
2. 核实本场已关麦，保存与候选发布已终结；异常场先完成既有有界恢复观察。若仍存在会产生新候选的在途任务，不直接开下一场，也不擅自重试旧任务。
3. 按账号/档案和测试Source清单确定删除对象，记录删除前待确认与正式记忆数量、目标ID及来源。范围不明确时先定位，不用全库删除代替。
4. 通过产品既有受支持的删除/拒绝接口执行：正式记忆删除；待确认候选按现有清理语义删除或拒绝，使其退出有效待确认集合。若只能逻辑删除，报告应如实写逻辑删除，不能声称物理擦除。原始对话、失败证据和本地归档保留，不清空App、不登出账号。
5. 核验服务端有效正式记忆与有效待确认集合中旧测试目标均为0；客户端重新读取结果一致。检索/记忆注入快照不得再包含已删除对象，不能只验证列表空白。存在异步索引更新时等待现有机制收敛后再验；未收敛不进入下一场。
6. 留存清理前后数量、操作结果、有效列表/检索核验、账号/档案范围和时间，生成独立清理记录；开下一场前再检查没有迟到发布的新候选。清理失败、状态未知或旧测试内容仍有效，均不得开始下一场。

## 3. 保留短场门禁

固定顺序：

**旧测试记忆清理并核验 → 新短场 → 短场完整验收与证据归档 → 清理短场生成的待确认/正式记忆并核验 → 同版本十分钟场 → 完成取证 → 下场前再次清理。**

短场凭证仍保留原源码、构建、设备、账号、有效期与单次消费约束。清理记录单独保存，不能改写旧PASS、重签过期凭证、抹掉失败或绕过原门禁。清理本身不改变已完成的短场历史验收；若代码/构建/账号或其他门禁依赖变更，仍须重跑短场。

专门验证“新旧记忆关联”的测试必须单独明确安排：从清理后的环境建立已知旧记忆夹具，并登记期望关联；不能把上次测试残留当作夹具。本轮普通保存/告别回归不引入这类旧记忆。

## 4. 清理验收记录

每次归档独立 `memory-cleanup-before-next-scene.json`（或等价报告），至少包含：

- 前场/下场标识、账号与档案脱敏标识、前场结果归档位置。
- 清理范围、Source及目标ID清单；正式记忆、有效待确认数量前后对照。
- 删除/拒绝的真实结果和未成功项；异步处理及客户端刷新核验结果。
- 旧目标未出现在有效检索/注入数据中的证据、清理后无迟到候选的复核时间。
- `PASS / FAIL / UNKNOWN`。仅PASS允许进入下场。

当前工具的 `lab.py run` 尚未内置自动删除和清理凭证强校验；后续执行者必须把以上步骤作为开场前置操作并留证，不能把文档更新宣称为已实现自动清理。需要新增工具逻辑时另行按影响范围开发、回归；不得为清理改动Live保存/主题归纳/审核业务规则。
