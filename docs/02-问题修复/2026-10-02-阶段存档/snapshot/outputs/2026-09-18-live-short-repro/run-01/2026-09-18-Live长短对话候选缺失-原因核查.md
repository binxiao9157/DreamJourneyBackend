# Live 长短对话候选缺失：原因核查

## 结论与范围

本轮是原因分析，未修改业务代码、部署、重新调用模型、重放业务写、清理历史或 commit/push。手机现场采集已经结束，后续不依赖手机连接。

当前证据将故障定位到“正文保存后的后台候选整理链”。不能再把候选没有增加笼统解释为 Live 正文未上传，也不能以改保存文案代替修复。

实际部署的候选整理接口为 `api.deepseek.com`，Live 语音接口为 `openspeech.bytedance.com`。二者是不同调用链。本轮没有证据将候选整理失败归因于火山 Live 语音接口。

但现有记录把多个错误统一归为 `candidateExtraction.responseContract.invalid`，未保留准确抛错检查点。因此，目前还不能在“请求前内部校验、DeepSeek 输出解析、独立语义复核、后续候选领域校验”中指定唯一触发点。

## 完整内容如何进入整理链

真实链路：Live 文字持续采集 → 本地 Outbox → 后台会话正文 → 结束封存 → ACK → admission 创建 Source 和异步任务 → Worker 调用 DeepSeek 组织草案 → 独立支持复核 → 候选入库 → 待确认记忆读取。

传给整理模型的是文字，不是 Live 录音。用户与助手文字均可提供上下文，但助手回答不能被当作用户事实。

**需要精确限定“完整”：**`owner_truth_interview_candidate_proposal.py:981–988` 用首条至末条用户消息的序号调用 `_conversation_turns_for_window`；`:1452` SQL 只取此范围。因此两场分别有 32/4 条接收记录，但整理 Source 是 31/3 条：全部登记的 16/2 条用户发言在内，最后一段助手回复在该窗口之外。不能说每一条助手回复也全部交给整理。此窗口与用户第二轮气泡未更新不是同一层问题，也没有证据证明省略末段助手回复造成契约错误。

代码会分块组织 Source 中的长内容，再拿该 Source 的全部 turns 和合并草案做支持复核。是否实际发出了两次模型请求、每次请求是否得到可用输出，现有诊断未记录。

登记内容全部确认、Source 存在、模型请求已发送、模型输入覆盖整场、候选入库成功是不同证据层。不能用任一前置成功替代后续成功。

## 已确认的内部问题

### 1. 错误分类丢失了真实失败阶段

`owner_truth_candidate_extraction_worker.py:956` 捕获整个消费链异常；`:145` 把任意 `ValueError` 标为 `responseContract.invalid / responseValidation / contract / retryable=false`。

它可能来自：请求前输入限制或配置、模型 JSON/字段/证据下标解析、语义支持复核、候选领域契约或领域写入冲突。`responseValidation` 是分类器写上的标签，不是“已经拿到模型响应”的执行证据。

HTTP 授权、额度、限流、5xx、超时与传输异常有独立分类。因此当前错误码不能翻译成“火山调用失败”，也不能翻译成“DeepSeek 服务不可用”。

现有日志没有保留具体校验原因、安全检查点、组织/复核各自请求阶段。Worker 循环还按 `(status, reason)` 去重日志，连续同类失败可能不逐任务打印。

### 2. 长文本组织与复核的输入合同不一致：另一个已证实缺口，本次现场已排除该触发条件

Worker `:562` 可分块组织；`:588` 独立复核却传原始整场。DeepSeek 适配器 `:1051` 复核构造仍调用 `normalize_turns`，限制为 200 turns、单 turn 4,000 字、整场 30,000 字。

无网络合成验证已经确认：超过上述任一限制的输入可以通过分块组织，却在整场复核 HTTP 发送前抛 ValueError。这是确定的内部缺口。**但本次两场的 turns 数、单条长度与总长均低于这三个上限，不能将它作为本次现场失败原因。**

历史提交：`a25b993` 已有分块；`f3ebc8a`（2026-09-15）引入整场独立复核，形成该不一致。不能将此直接归因于 9 月 18 日 iOS 认证恢复修改。

### 3. 语义复核失败会终结整场

`owner_truth_live_memory_support.py:108–141` 对 uncertain、遗漏事实轮次、事实未被最终草案覆盖等抛出 ValueError。因此接口即使返回 HTTP 200、JSON 可解析，也可能被本地判为整场失败。这是可证实的处理规则，尚不是本场具体命中项。

不能以删除 B7 证据保护、忽略失败、伪造成功或只保存部分草案来掩盖问题。

### 4. iOS 失败终态与成功终态共用恢复记录清理

`EchoViewController.swift:3279` 将 terminalFailure 交给相同 finish 路径；`:3313` 在观察落盘后删除 Outbox、follow-up、checkpoint，无失败保留分支。

冷启动只枚举这三类坐标。若清理完成，本场无法在下次启动被该恢复链重新发现。本次手机 follow-up 中短场记录确已缺失，只剩旧场；尚未单独核实另两份文件是否删除成功。

这些删除是客户端本地操作，不是服务端 DELETE，不能据此说后台正文被删除。

### 5. 历史任务 UI 归属和核实按钮绑定独立存在问题

历史多个 Coordinator 可以更新同一页面并覆盖 active 指针；核实按钮未稳定绑定当前展示场次。它能解释错误历史提示或查错任务，但不能解释为什么 Worker 没有生成候选。

长场 6 次轮询预算、短场明确失败、历史 UI 覆盖、短场气泡未更新应分别跟踪。延长轮询不能修好已经失败的 Worker。

## 本轮不能声称的结论

- 不能声称两场候选已生成只是 App 没显示。
- 不能声称 DeepSeek 已收到整场且完整返回。
- 短场错误码本轮已由服务器唯一关联确认，与长场同属 responseContract.invalid；相同宽泛错误码仍不证明两场命中了同一条具体校验。

- 不能通过再制造新真机会话、重放旧场整理或改状态文案来补缺失证据。
