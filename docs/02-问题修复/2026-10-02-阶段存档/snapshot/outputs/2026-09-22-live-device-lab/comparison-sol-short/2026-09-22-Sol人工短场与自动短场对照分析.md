## 1. 新场状态查询的确定错误

同一测试账号在北京时间 21:40—22:07 内只有一个新场，创建于 21:58:35，产品标识为 `echo_live_4c5837f370f642ba74be160c33e0499b`。服务器内仅对合成标记做布尔匹配，第二个 owner 消息包含开场与书房标记，进一步支持与本次人工场对应；未导出对话正文。

本场有四次 messages POST 201，服务器保留两个 owner 和两个 assistant。22:01:40，本场 `live-delivery-status` GET 返回 500，同一时刻栈定位到 `owner_truth_conversation.py:3375`，异常为 `psycopg.errors.UndefinedColumn: column s.thread_id does not exist`。

运行中 SQL 使用：

```sql
SELECT s.id, s.thread_id, ...
...
AND t.id = s.thread_id
```

实际表存在 `current_thread_id`，没有 `thread_id`。本地同一方法已使用 `s.current_thread_id AS thread_id`，JOIN 也使用 `s.current_thread_id`。这是可定位的查询实现错误；不要为了迎合错误 SQL 随意给数据库添加另一套 thread_id。

新人工场还没有 review batch，因此不能声称“新场也已 end/ACK 成功，只差 admission”。修好状态查询、推进关闭以后，还必须处理这个已知的后续阻塞点。

## 3. 两项应收窄或继续核查的结论

### 语音恢复

人工记录三轮均恢复聆听，属于本场人工交互 PASS。此前回调缺失只在静音 STREAM 自动化场景获得直接复现与二进制定位证据，不能扩展为所有普通麦克风路径均失败。自动化输入模式、观察回调开关、音频会话和真实播放状态的差异应单独核查，不能为了让自动化过关而改坏这条正常路径。

### 页面恢复文案

Sol 记录页面先显示“上次对话没有需要整理的表达”，核实与冷启动后显示“上次对话已保存，尚未确认开始整理”。本场服务器却仍 active、只有两个用户轮次，二者不构成“完整保存”的证明。

本地渲染代码中，后一文案对应 `.actionRequired(.acknowledged)`。可能显示了旧场次的 acknowledged 状态，也可能是当前场次恢复阶段归属错误；尚没有手机恢复坐标和实际页面绑定证据，不能直接定为历史覆盖。必须核对 productSessionID、capture generation、outbox、completion phase 与页面实际恢复对象。

## 4. 下一步优先级

1. 先核对现有本地修复是否全部进入实际发布包：至少涵盖 delivery-status SQL 与 admission authority 绑定。分别复现、验证，检查受影响模块回归与隔离数据库；不能只改 UI 状态或放宽成功条件。
2. 为本场保留恢复坐标，读取最小手机诊断，核清三轮输入为何只有两轮服务端记录、close intent 与排空停在哪里、恢复页面读的是哪个场。无需用户再说一轮对话。
3. 生成明确的 API/Worker 发布清单并在获部署授权后核对运行中版本。本轮只读对照不包含部署。
4. 修复后的新短场必须逐轮核对三轮输入、服务端覆盖、关闭、候选可见、审核与正式记忆；通过后才进行长场。普通人工语音与自动化 STREAM 结果分开记录。

目前没有新证据支持把本次失败归为火山或 DeepSeek 容量/超时。候选整理任务尚未建立，已确认的是内部后端错误及实际运行版本落后；正文覆盖与页面归属仍有待进一步定位的缺口。
