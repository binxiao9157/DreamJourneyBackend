# 原生 Live 保存入口回归引入点

日期：2026-09-16。仅本地只读源码、既有交付材料和真实源片段对照；未操作设备、未访问生产、未修改业务源码。

## 结论

**是，9 月 15 日的 canonical 接缝改造引入了一个新的原生 Live 保存回归：旧的 final ASR 直接采集入口被关闭，新入口却把 final ASR 保留为 interim，并等待现场没有可见记录的 QueryConfirmed。** 原来能够进入 owner 交付队列的同一条 final ASR，现在可以只留下不能封存的 canonical 槽位。

这不意味着旧版本完全没有缺陷，也不代表用户曾经每场都完整保存。9 月 15 日早间长会话漏记已先于这次改造存在；晚间复测所见“10 问都有 final，owner/queued=0、20 未封存”暴露了这次新增断点。不能把两者混成一个历史根因。

当前证据足以定位代码回归及其引入改造；尚不等于把所有历史成功/失败逐场绑定到设备二进制。

## 1. 修前存在怎样的保存路径

当前 iOS HEAD 是 `11d0d0051b9be3cce57822dd059472d1e2536866`，提交时间 2026-09-13 22:42:26 +08:00。其前一版本 `5fd061fd` 为 2026-09-09 23:59:51 +08:00。

实际入口函数名是 `onASRResult`，本次核对的这两个版本和当前相关文件中没有名为 `onUserSpeechRecognized` 的入口；用户语音通过 `viewModel.finishUserVoice` 更新交互状态，持久化随后独立调用。

| 层 | 9/13 HEAD 的实际行为 | 当时文件行号 |
| --- | --- | --- |
| Manager ASRResponse | parse 得到 `isFinal`；仍通过 delegate.onASRResult(text,isFinal) 传递 | DialogEngineManager.swift:4184–4242 |
| Echo onASRResult | `guard isFinal`，处理安全状态之后，无条件调用 `captureLiveOwnerTurn(text)` | EchoViewController.swift:12021、12031、12056 |
| provider 回答路径 | owner 已采集之后才 return，避免重复请求后端回答 | EchoViewController.swift:12057–12069 |

| persistAndEnqueue | 异步调用真实 Store.enqueue，再推进自然输入交付 | EchoViewController.swift:1218 |
| Store.enqueue | 立即建立 delivery、递增 clientSequence 与 ownerTurnCount、写磁盘 | OwnerTruthContracts.swift:14227 |

这里没有新增的 canonical finality 门槛，也不要求每问等待 QueryConfirmed。9/9 `5fd061fd` 的 EchoViewController.swift:10825 同样无条件采集 owner，之后才在 provider Live 分支 return。因此，9/15 新增门槛不能归为“原本一直如此”。

修前依然受合法账户、有效会话、自助手场景、安全状态、非空文本、重复去重、磁盘与后端状态约束；本核查没有声称这些条件永远成功。

## 2. 回归的两个必要改动点

### 2.1 旧入口被 provider 条件绕过

当前 [EchoViewController.swift:13905](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Echo/EchoViewController.swift:13905) 变成：

```swift
if DialogEngineManager.shared.answerAuthority != .provider {
    self.captureLiveOwnerTurn(text)
}
```

原生 provider Live 即使有 `isFinal=true`，也不再通过旧入口采集 owner；delegated/backend 路径仍保留旧入口。相同改造也包住 assistant 的旧 `captureLiveAssistantTurn`（当前 :13978）。

精确片段 diff：[capture-entry.diff](/Users/gaominge/Documents/liftora/outputs/2026-09-16-live-persistence-regression-audit/live/probe/capture-entry.diff)。头部包含历史/当前源行号；diff hunk 内行号是抽取片段的相对行号。

新入口是当前 `onCanonicalTranscriptEvent`（[EchoViewController.swift:14030](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Echo/EchoViewController.swift:14030)）→ coordinator.appendCanonicalTurn（:1443）→ Store.upsertCanonicalTurn（OwnerTruthContracts.swift:15421）。

### 2.2 新入口对 final ASR 增加了不成立的定稿门槛

当前 [DialogEngineManager.swift:4558](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DialogEngineManager.swift:4558) 在 ASRResponse 的 parser 之后，无论 `result.isFinal` 是什么，都发 `canonical.finality = .interim`。ASRInfo 的文本路径也是如此（:4460）。

唯一 owner.complete 发自 QueryConfirmed 成功解析非空文本后（:4648）；ASREnded 没有定稿逻辑。新增 Store 的 `flushCompletedCanonicalPrefix`（当前 OwnerTruthContracts.swift:15774）遇最前 interim 即停，不允许后面的完整 assistant 越过去。因此“停用旧入口”与“新入口不消费现场 final”共同构成此次回归。

ASR parser 本身在 HEAD 与当前逐字相同；这次断点位于解析之后的采集路由及 canonical 定稿规则，不是把语音是否 final 解析坏了。

## 5. 现场记录如何支持这次回归

恢复的原 Sol 真机输出已按 provider 场次分开：长答场 2 问各 1 个 final；整场 10 问各 1 个 final，均早于停止。整场 850 个 ASRResponse 中 final=true 恰 10 个，而 QueryConfirmed 的可见日志及其 question 观察入口均为 0；之后 owner/queued=0、unsealed=20。

来源与白名单汇总：[historical-live-whitelist-summary.json](/Users/gaominge/Documents/liftora/outputs/2026-09-15-device-blockers-analysis/live/evidence/historical-live-whitelist-summary.json)。这支持“final 已到，改造后的采集路径没有按 final 封存”，而非“用户始终没说到可保存内容”或“SDK 一直没给 final”。无可见 QueryConfirmed 不等于 SDK 在所有配置中绝不发送；未取原 Outbox，也不能直接断言 20 条恰好是哪 10 owner/10 assistant。

9/15 报告的 620 项本地测试没有证明真实原生接线通过。其 [A16 检查项](/Users/gaominge/Documents/liftora/outputs/2026-09-15-dreamjourney-live-continuous-capture-playback-fix/run-2026-09-15-01/reports/A01-A19-checklist.md:22) 明列：真实 manager 到 durable 接缝的单次性组合未完整执行。这正是旧入口退出、新入口终态不匹配能漏过局部绿测的边界。

## 6. 修复含义

应修正新 canonical 入口对真实 final ASR 的接纳与身份/定稿规则，补从 Manager 到真实 Echo/Outbox 的同事件回归；不要简单同时重新打开旧入口与 canonical 入口，造成重复 owner/assistant、重复候选或两套关闭水位。也无需因此撤回已经真机通过的长答播放/主动打断修复。

本核查只定位原生采集入口回归，不将它混为 B7 语义过滤、B8 admission 或跨历史 UI 仲裁的根因；也不宣称修复前的全部长会话保存已被验证正常。
