## 1. 结论强度

**蓝牙是必须覆盖的现场条件，目前不是已证实根因。** 用户补充为：连接车载蓝牙；长回答首几个字后无声而文字继续变化；本人没有说话、操作或其他已知声源；下一条短回答正常。上述信息支持按“无主动打断的长回答停音”设计反例，不支持直接认定回声、HFP/A2DP 自动切换、音频焦点抢占或 SDK 自动打断。

**源码已确认：正常原生 Live 的句段/整答回调没有直接执行 AVAudioSession 停用或强制路由切换。** 保持同一 owner/scope 时获取 lease 返回 unchanged，跳过实际 activate；provider 分支 onTTSFinished 只推进 UI/轮次状态然后返回。句级 finish 被当整答的风险不能因此直接写成“它关闭了蓝牙播放”。真正可停播的客户端指令、系统 interruption、SDK 内部播放器行为必须分别定位。

**已确认的诊断缺口**：当前 route/interruption 记录不能恢复当时实际输入/输出端口、音频硬件参数、SDK 播放活动与打断指令的完整顺序。没有这些信息，不能回答“声音还在 SDK 播放而车机没出声”还是“播放器本身已被停止”。

## 3. interruption 与 route-change 实际处理

`EchoViewController` 监听 interruption 和 routeChange。[注册:7519](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Echo/EchoViewController.swift:7519)

- 当前日志只有 result、requestedOwner、activeOwner、transitionCount、reasonHash，缺少实际 route。route reason 被放进字符串再 hash，排障不如白名单枚举可用。[diagnostic:7482](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Echo/EchoViewController.swift:7482)

## 4. Apple 与火山合同：可用结论与缺口

1. HFP 支持双向语音；A2DP 是偏高带宽的立体声输出协议。对 playAndRecord，允许 A2DP 需要额外选项；同设备同时允许 HFP/A2DP 时 HFP 可优先。当前代码不能推定实际车机端口，更不能将“蓝牙已连接”直接写成 A2DP。[Apple allowBluetoothA2DP](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/allowbluetootha2dp)、[Apple allowBluetoothHFP](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/allowbluetoothhfp)
2. HFP 输入/输出选择具有配对关系；选定 HFP input 会使 output 跟随对应 HFP 设备。不要设计“始终用车机蓝牙输出，同时任意指定手机麦克风”并假称该组合在 HFP 下必然成立。[Apple allowBluetooth](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/allowbluetooth)
3. **voiceChat 模式本身不能证明 AEC 已生效。** Apple 明确要求 Voice I/O Audio Unit 或开启 voice processing 的 AVAudioEngine 才有相应语音处理；仅模式没有该保证。当前 `enableAEC=false` 的注释声称硬件 AEC 已生效，证据不足；SDK 是二进制库，本轮未取得实际 I/O 类型/voice processing 启用状态。不能因此反向断言“AEC 一定关闭”。[Apple voiceChat](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/voicechat)、[源码注释:1876](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DialogEngineManager.swift:1876)
4. Apple 要求区分 route-change reason、previous/current route；路由变化后采样率、通道、buffer/latency 可能变化，应读取实际值。中断结束后的 shouldResume 是恢复判断的一部分，不是 SDK 声音已经继续的证明。[Apple route changes](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes)、[Apple interruption](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions)、[Apple audio guidelines](https://developer.apple.com/library/archive/documentation/Audio/Conceptual/AudioSessionProgrammingGuide/AudioGuidelinesByAppType/AudioGuidelinesByAppType.html)
5. 本地火山官方 SDK header 将 `SEPlayerStartPlayAudio=3019` 描述为从句子开始播放有效音频，`SEPlayerFinishPlayAudio=3020` 描述为在句子结束后播放完有效音频；**没有说明它必定是一整轮答案只发一次的终态**。`TTSEnded=3011`、ASRInfo/Response、QueryConfirmed 只有简短事件名称，没有定义全部 payload/时序或声学证据保证。[header:1527](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/Pods/SpeechEngineToB/pod/classes/SpeechEngine/SpeechEngineDefines.h:1527)
6. `SEDirectiveEventClientInterrupt=3010` 是客户端命令；现有 App 在 AI speaking + 非空 ASRInfo/Response 下主动发送，该机制能改变播放器/对话状态，但**非空 ASR 不能证明用户新开口**，也不能因文本相似就判回声。[header:1337](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/Pods/SpeechEngineToB/pod/classes/SpeechEngine/SpeechEngineDefines.h:1337)、[App ASR:4095](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DialogEngineManager.swift:4095)、[App ASRResponse:4190](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DialogEngineManager.swift:4190)
7. 火山主文档 `https://docs.volcengine.com/docs/6561/1597646?lang=zh` 本轮 web 工具未能读取，终端公开 HTTP 读取也受网络沙箱阻止；没有为此索取额外授权。不能引用未读正文证明“SDK 已自动 barge-in，因此可以无条件删除 App 打断”。SDK 精确自动打断合同仍 `NOT_VERIFIED`，应在保持原生路径的受控实测中分别统计 provider 自发变化、App 显式 ClientInterrupt、SDK send 返回码及播放后果。既有本地架构稿建议“自动优先、显式兜底”只是项目设计意图，不是 SDK 行为证据。

## 5. 建议 Sol 的最小修改范围

先补可测边界和确定性事件修复，不先切 A2DP、强制 speaker、升级 SDK、开另一套 AVAudioEngine 或重放 PCM。正常 Live 保持单一 SDK recorder/player 与现有 echoCapture lease。

- 在 manager 接收 SDK 事件、实际发送中断/停止指令、以及 coordinator 物理 activate/deactivate 前后分别记录安全事件；SDK 回调到达、App 接受/丢弃、UI 更新三层不能合成一条“播完”。
- 将句段 finish 与整答 synthesis-end、播放器 drain/可验证终态分开；没有 SDK 可用 drain 合同时不能发明完成回执，也不能靠固定等待时长标成功。该状态修复应由主音频事件设计负责，路由层只保留连续 lease。
- ClientInterrupt 使用经验证的当前 session/question/reply/generation 和明确触发源；客户端显式按钮可以形成用户意图，纯非空 ASR、晚到 final、identifier-only、文本重复都不能单独形成新的声学打断证据。是否完全交给 provider 自动处理，必须先验证 SDK 原生 barge-in 和“用户明确说停”仍正常。
- interruption 和真正的 route 丢失应进入独立的音频中断/待恢复状态；恢复时只在原 Live 意图仍有效、同 lease/generation 且系统允许的条件下操作。恢复 AudioSession 成功后仍需 SDK playback/capture 活动证据；不能假装长回答已经全部播完、自动重新问模型或把旧回复重新读一遍。
- route 变化先采集实际端口与硬件格式；同一路由的 categoryChange 通知不应触发无限重配。不得在每个句子开始/结束时 deactivate/activate。
- AEC 能力校验仅使用 SDK 支持的公开选项/官方证据；没有证据不盲开软件 AEC、不 dump 用户音频、不并行插入第二音频链。

| BT-D06 | 经授权在长答中断开车机、重新连接，单独测试 | 记录 previous/current port、实际 interruption；UI说明播放中断；不偷偷整答重放或新建对话；恢复/用户返回行为明确。此项与无操作现场分开，不能借故障注入证明现场发生过断连。 |
| BT-D07 | 经授权制造可恢复与不可自动恢复的系统 interruption，分别在扬声器与车机测试 | 丢失/恢复状态正确；原 intent、lease和generation守卫有效；结束会话后迟到通知不自动开麦/播旧答。 |
| BT-D08 | 靠近既有策略过期边界持续对话，再进行长答；与未过期场次对照 | 采集策略失败不能被擅自转成音频完成；音频问题与记忆持久化分别计数、分别验收；不得用延长凭据修声音。 |

每项至少保留：路由与版本基线、输入条件、SDK/App/system 有序事件、配置/停止指令次数、用户实际听到的首末句核对、前后状态、结果与证据路径。若服务端回答长度不满足用例，记 `INVALID_TEST_INPUT` 并重新构造，不能将短答冒充长答测试。

若无法在原车机复现：可交付 `AUDIO_LOCAL_CONTRACT_PASS`（仅在真正执行本地门禁后）、`READY_FOR_CAR_BLUETOOTH_RETEST`；`CAR_BLUETOOTH_DEVICE_RETEST=NOT_RUN`，现场根因仍 `UNCONFIRMED`、问题仍未关闭。扬声器/其他耳机通过分别登记，不能写“蓝牙已修复”。修复版原车机没有再次出现只能表述该次数范围内未复现；若旧版也未能重现，则不得声称已证明唯一根因。
