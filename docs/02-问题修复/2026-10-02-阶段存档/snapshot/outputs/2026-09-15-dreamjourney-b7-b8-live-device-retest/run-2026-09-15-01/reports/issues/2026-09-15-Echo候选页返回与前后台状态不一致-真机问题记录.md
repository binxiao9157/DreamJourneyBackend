# Echo 候选页返回与前后台状态不一致

问题编号：DJ-ECHO-STATE-01\
状态：FAIL\
范围：回响页历史会后任务恢复状态展示\
记录日期：2026-09-15

## 现象

从待确认记忆页面返回回响页后，页面显示：

> 上次对话已保存，尚未确认开始整理，可再次核实

并显示“核实整理状态”按钮，文字回响入口不可用。

切换到微信，再切回 App 后，同一个回响页变为：

> 上次对话已进入待确认记忆

同时文字回响按钮重新出现。用户没有在两次显示之间执行审核或整理写操作。

## 复现步骤

1. 在当前登录态进入待确认记忆。
2. 返回回响页。
3. 记录页面状态和可用按钮。
4. 将 App 切到后台并进入微信。
5. 再切回 DreamJourney。
6. 对比页面状态和文字入口。

## 实际结果

- 第一次返回时显示 action-required 样式状态，文字入口不可用。
- 前后台切换后显示 pending-review 样式状态，文字入口恢复。
- 设备诊断中观察到多个历史恢复 workflow 的只读结果交错返回：一个 workflow 提交 `actionRequired`，其他 workflow 提交 `pendingReview`。
- 本轮捕获范围内，这些状态变化对应的是 GET/只读恢复，没有观察到自动业务写 POST。
- 同一 action-required workflow 还出现多轮读取与 generation 增长；是否违反既有有界单飞规则仍需用请求触发证据验证。
- 在另一场整场采集失败且三条合成事实均未形成候选后，彻底重启 App，页面稳定显示“上次对话已经入待确认记忆”，同时仍提供“核实整理状态”按钮。该文案不能证明它属于刚失败的场次，暴露出页面未向用户说明当前 workflow 身份和状态归属。

## 期望结果

- 页面应按照明确的当前任务选择规则展示一个稳定状态。
- 导航返回、前后台通知和旧回调不能通过到达顺序互相覆盖。
- 历史任务的 actionRequired 不应无条件遮蔽当前已进入候选状态的会话。
- 状态恢复不能永久阻止用户进入新的文字会话；如确需阻断，应说明具体任务与可执行动作。

## 初步定位边界

现有证据支持“多个恢复结果竞争 UI 提交权”的假设，但尚未证明具体代码根因。不能据此直接认定为：

- 服务端状态错误；
- 某一历史 workflow 应被删除；
- FeatureGate 或认证失败；
- 必须重放 end/ack/admit。

## 对 Astra 的分析要求

1. 核对 EchoViewController 页面订阅、前后台恢复入口和 registry/coordinator 复用规则。
2. 明确多个历史 workflow 的选择、优先级和 UI 提交所有权。
3. 为每次页面可见周期建立 generation/request ownership，迟到结果只可丢弃，不能覆盖当前状态。
4. 核对重复 GET 的来源、单飞边界和整体期限，不通过删除历史任务或重放写操作解决。
5. 保持新 Live/文字会话与旧关闭任务严格隔离。

## 修复验收

- 从候选页返回和前后台切换后，当前业务状态一致。
- 旧 workflow 迟到结果不能改变当前页面或入口权限。
- 重复进入和生命周期通知不会形成读取风暴。
- 阻断状态提供真实、可执行的只读核实入口；可返回且不会永久锁死。
- 不新增任何自动业务写请求。
- 冷启动显示的状态必须能够绑定到当前被展示的 workflow；不能用某个历史任务的 pendingReview 覆盖刚失败场次，也不能以笼统“上次对话”混淆两者。
