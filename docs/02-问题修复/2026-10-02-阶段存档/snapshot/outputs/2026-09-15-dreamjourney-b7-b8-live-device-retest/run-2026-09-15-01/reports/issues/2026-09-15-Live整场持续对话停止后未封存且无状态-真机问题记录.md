# Live 整场持续对话停止后未封存且无状态

问题编号：DJ-LIVE-CAPTURE-01\
状态：FAIL\
范围：Live canonical transcript 持续采集与最终关闭交接\
记录日期：2026-09-15

## 独立问题定义

同一场 Live 中，开始、中段、结束三条合成事实均被正确识别并获得有声回应，普通问答也持续正常。用户只手动关闭一次后，页面没有显示任何“已保存、等待整理、正在整理、进入待确认或失败保留”状态。

诊断显示该场仍有 20 个未封存回合，但 owner、persisted 和 queued 计数均为 0，关闭交接没有建立。

本问题只描述 Live 整场采集和关闭交接，不把它与 B7 语义过滤或 B8 文字关闭链路合并为同一根因。

## 测试输入

同一场中依次陈述：

1. 开始标记为“红叶一号”。
2. 中段标记为“青石二号”。
3. 结束标记为“白帆三号”。

三条陈述之间各有普通问答。整个过程未关闭麦克风、未切换 App，系统每轮均有声音并自动恢复聆听。

## 用户侧实际结果

- 三个标记都被系统正确复述或确认。
- 开始、中段和结束之间 Live 没有中断。
- 最后一轮回答结束后仍继续聆听。
- 用户点击一次停止后，页面完全没有会后状态。
- 没有自动重新开启麦克风，也没有可见错误或持续转圈。

## 已证实

- SDK/Live 交互至少持续到 `turnSequence=10`。
- 页面上三条合成事实均被正确听到。
- 停止时存在 20 个未封存回合。
- canonical 会后采集计数为 0，未进入正常关闭状态机。
- 页面没有呈现会后交接状态。
- 随后只读刷新候选列表，数量保持 45 条；“红叶一号”“青石二号”“白帆三号”均为 0 条。

## 尚未证实

- 未封存发生在 SDK canonical transcript 适配、事件身份关联、持久化队列还是关闭水位确定。
- 不能仅凭没有看到 end 请求就断言服务端从未收到请求。
- 不能把本场候选是否增加作为该缺陷的唯一判断依据。

## 对 Astra 的分析要求

1. 从 SDK question/reply identity 到 canonical transcript store 核对同一场 10 轮事件的登记与定稿规则。
2. 解释为何 UI 能持续对话，但 `ownerTurnCount/persistedOwnerTurnCount/queuedTurnCount` 全为 0。
3. 核对 `unsealedTurnCount=20` 的成员构成、排序、定稿条件和关闭水位。
4. 关麦时应先保存关闭意图，再排空已登记内容；不能因某个回合未定稿而静默跳过整个交接。
5. UI 必须展示与本场关闭状态对应的结果，且不能被历史 workflow 覆盖。
6. 失败恢复只能基于磁盘坐标和只读状态核实，不重放未知写。

## 修复验收

- 同一场至少 10 轮对话的 canonical transcript 有序、无漏采、无重复、无跨场混写。
- 开始、中段、结束三条用户事实均被登记并持久化。
- 手动停止后形成明确关闭水位，并显示可观察状态。
- end/ack/admit 使用同一 session/batch，重复回执幂等。
- App 重建可以只读恢复未完成任务，不启动麦克风或写重放。
- 候选读取能够证明三段事实的来源和同场归属。
