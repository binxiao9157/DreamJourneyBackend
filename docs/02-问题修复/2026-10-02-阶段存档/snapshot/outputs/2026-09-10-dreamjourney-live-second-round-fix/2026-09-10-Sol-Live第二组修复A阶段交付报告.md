## 3. 五项问题结论

### L2-01 未审核 Source 使正式投影失效

**已证实根因**：旧触发器对任意 Source INSERT/UPDATE/DELETE 都将 memory/search checkpoint 置为 rebuilding，未区分 Source 是否被当前正式 MemoryVersion 引用；同时没有持久化重建意图。

**Astra 复核发现**：0120 仅检查 `MemoryVersion.source_id`，合并记忆的其他 `payload.evidenceRefs[]` 变化可能漏失效；重建请求也只有手工脚本，没有长期自动消费者。

**补齐改动**：

- 保留已执行的 0120，新增 `0121_owner_truth_source_dependency_recovery`，不修改旧迁移。
- INSERT 未审核 Source 不再触碰正式投影。
- UPDATE/DELETE 同时检查当前 MemoryVersion 主 `source_id` 和全部 `evidenceRefs[]`，覆盖 OLD/NEW、版本与权限边界。
- `source_projection_rebuild_requests` 增加 lease、attempt、availableAt、heartbeat、lastError、completedAt。
- Memory Projection Worker 在普通任务空闲时自动 claim 请求，支持心跳、幂等完成、有限重试、崩溃租约恢复和不可恢复阻断；不直接把 checkpoint 改为 ready。
- 正式投影重建会逐一复核全部证据来源；证据缺失或越权时 fail-closed。

**测试**：最终镜像在随机临时 PostgreSQL 中创建两个 Source，将其合并为同一当前 MemoryVersion；分别验证未审核新增不失效、主来源变化、次要 evidenceRef 版本变化/撤销、权限边界、0120 历史升级和 Worker 自动消费。结果 `schemaHead=0121 ... sourceProjectionBoundary=true ... legacy0120Upgrade=true`。

**结果**：`PASS`。未来新增正式证据依赖类型时仍必须同步扩展依赖判定，不能重新使用“任意 Source 变化全量失效”。

### L2-02 Live 正式记忆没有形成可验证闭环

**已证实根因**：旧快照存在字符截断导致 65 条事实只覆盖部分内容；客户端角色构造受本地默认 Prompt 条件影响；缺少从服务端 role 到 SDK 最终字段路径的同值校验。

**尚未确定部分**：真实火山模型在当前 iPhone 会话中是否始终按正式事实回答，必须由 B 阶段多次新会话和打断后问答验证，不能由 token 200 或 SDK ACK 推断。

**改动**：

- snapshot contract v3 全量绑定合格正式事实；超预算时 fail-closed，不静默丢事实。
- role 正文、memory revision、checkpoint、authority epoch 和 context hash 由服务端统一生成。
- API/proxy contract v7 校验相同 role/hash/ticket/session 绑定。
- iOS `DialogProviderLiveStartConfigBuilder` 把服务端原文写入实际 SDK 路径 `dialog.dialog.system_role`。
- JSON 错误包装、错误 role、缺 runtime/正文均拒绝启动假成功会话。

**SDK 证据边界**：Pod 锁定为 `SpeechEngineToB 0.0.14.6.1-bugfix`，启动指令仍为 `SEDirectiveStartEngine`，未改变原生 Live 音频链路。当前自动化只能证明服务端 role/hash 与 iOS builder 输入一致，无法证明 SDK 内部最终交给 `SpeechWsClientProtocol.sendData` 的控制帧字节。该静态库只在实际 iOS SDK 运行环境中可做受控客户端捕获；本轮明确禁止 iPhone 安装和测试。

**结果**：`BLOCKED`。缺项是实际 SDK 出站帧的字段路径、正文和 `providerContextHash` 同值证据；自建 JSON、token 200、SDK ACK 和模拟器构建均不替代。真实回答质量、声音和打断仍归 B 阶段。

### L2-03 会后整理失败原因丢失并被假成功掩盖

**已证实根因**：旧 Source intent 最大尝试数为 1；顶层异常压成通用失败；Provider/JSON 错误可走原文拼接 fallback，导致问题或转写原文被当 Candidate；真实 Live 的助手开场还会被误判为“必须由用户开始”。

**改动**：

- Source Candidate Extraction 最大 3 次；瞬时错误按约 5 秒、20 秒退避并带 jitter。
- 401/403、402、404、429、5xx、合同/证据/JSON 错误分别归类；只对瞬时错误重试。
- 保存 value-free `failureCode/failureStage/failureType/providerStatus/retryable`。
- 删除 Provider/JSON 失败后的原文 Candidate fallback。
- 长会话分片必须含用户证据；允许助手开场，但助手建议不能作为事实。
- DeepSeek Live prompt 明确 V5 factType/dimension 枚举；无效 taxonomy 由安全适配器丢弃，再由用户证据派生合法类型。
- 0121 为 `async_effects.job_attempts` 增加 `terminal_reason_code`：`error_code` 保存首次/最终原始失败，`terminal_reason_code` 单独保存重试耗尽。
- status contract 升为 v3，分别输出 `firstFailureCode/failureCode/failureCategory/terminationCode`；类别覆盖 authorization、quota、rateLimit、timeout、contract、transport/configuration。
- iOS 严格解码 v3，同时保留严格 v2 兼容；错误展示不读取正文、Prompt、凭据或原始供应商响应。

**全链路故障证据**：最终镜像在随机临时 PG 中创建真实测试登录会话，注入 Provider 401，经 Worker -> `job_attempts` -> 实际 FastAPI 状态路由返回 v3；结果 `failureCategory=authorization`、`firstFailurePreserved=true`、`terminalReasonPreserved=true`、`statusAPI=200`，且正文与供应商原始响应未保留。另有错误分类矩阵覆盖 401、402、429、timeout、contract 和 transport/configuration。

**结果**：`PASS`。

### L2-04 状态显示与恢复不准确

**已证实根因**：客户端把查询失败、前台轮询超时、retry wait、终态失败和 unknown 汇总为同一句“请稍后重试”；页面生命周期承担进度，退出后缺少可靠恢复坐标。

**改动**：

- status v3 暴露 job state、attempt/maxAttempts、retryable、原始失败、失败类别、终止原因和 review batch 状态。
- UI 分离 queued/running/retry/noChange/reviewReady/terminalFailure/unknown。
- 前台超时只停止主动轮询，不伪造服务端终态失败。
- follow-up store 只持久化 account-scoped 的 session/source/operation/reviewBatch 等不透明坐标，不保存转写正文。
- 返回页面或重启后继续查询同一后台任务；旧会话不会阻塞新 Live。

**残余风险**：真实前后台、断网重启和通知到达时序仍需 B6 真机验证。

### L2-05 退役 Archive text 重复提交

**已证实根因**：旧本地档案同步逻辑会对所有未 synced text 重试 `/archive/items`，永久 409 在重开页面和重启后仍可能再次触发。

**改动**：普通 text 不再具备 public backend sync eligibility；仅保留仍有效的 timeLetter 公共同步能力。未重开退役接口，未把 409 当瞬时错误。
