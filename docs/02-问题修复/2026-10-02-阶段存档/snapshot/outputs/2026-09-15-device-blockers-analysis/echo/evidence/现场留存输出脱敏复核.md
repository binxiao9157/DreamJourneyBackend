## 可确认及不能越过的边界

可确认：同一份原任务留存中有 3 个可区分 workflow 的恢复结果，且 UI 的 actionRequired / pendingReview 以两种相反顺序出现；W-3 在多次读取后继续返回 readyForAdmission。结合源码 `readyForAdmission → actionRequired(.acknowledged)` 映射和无选主的直接 render，支持多个历史任务竞争状态区的解释。

这是“真实输出顺序 + 当前源码机制”的证据。将行 87 的 UI 精确归给 W-3，或行 95 的 UI 精确归给 W-2，仍属于基于相邻事件和源码的关联推断：uiCommitted 没有 workflow、controller、selected owner 或 pageGeneration。没有这些字段就不能把每条 UI 身份闭环写成观测事实，也不能把两窗口擅自命名为某次具体导航或前后台通知。

47 次 readAttemptStarted 和 W-3 的 21 次读取证明多轮读取发生，不证明同一 workflow 物理 GET 同时在飞、违反 deadline/6 GET 预算或形成请求风暴。现有输出还缺完整 triggerReason、网络开始/完成时间、取消结果及物理请求归属；generation 包含状态结束/挂起递增，不能当作请求数。requestAlias 是日志相关值别名，部分可能是统一占位符的 hash，不能误认成真实请求 ID。

本提取只筛选 Recovery 结构事件，不能据“没有 POST 字段”推出整个会话零业务写。零自动业务写仍需专门的路由/方法计数验收；原现场“捕获范围内未观察到自动业务写”不能扩大成全生命周期承诺。
