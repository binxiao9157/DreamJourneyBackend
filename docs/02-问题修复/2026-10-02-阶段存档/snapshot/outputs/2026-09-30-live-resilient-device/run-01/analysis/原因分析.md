# 本场失败原因分析 · 2026-09-30

范围：仅本次SHORT_A和LONG20。只读服务器、检查已部署代码和本地证据、重放已保存响应；没有新调用模型、重试任务、操作手机或修改产品。用户要求先分析讨论，本文不构成实施方案。

## 结论与证据等级

本场有两个独立失败阶段，不能用一个“长对话容量/超时”解释所有表现。

1. **待确认记忆没有发布：已定位到具体的模型合同与内部处理链。** 长场批内关系输出把8个事实各自指向自身；这份结果被过早标记completed，随后上层才报forwardBatchTarget。程序转入安全复核，而安全复核开启json_object却缺少提示词中的JSON声明，不符合供应商公开接口要求。3个此类请求均被立即拒绝；已通过的主题因此全部被拦截，最终包装为noReliableThemes。
2. **17分19秒真机停场：直接触发器确定，但性能首因未定。** 自动工具在主线程送20ms音频，检测到0.542664秒间隔超过0.5秒即停止。不能把工具错误码当作火山服务端超时。失败前保存队列已落后；整文件持久化/校验以及高频SDK诊断是具体性能嫌疑，但没有CPU栈/锁等待/任务耗时的现场闭环证据。
3. **数据没有持续停留在“服务器少收”的状态。** 已完成36轮的72条正文后来补到服务器；消息ID（UUID规范化）、角色、正文哈希72/72一致。正文保存改善与候选发布失败同时成立。

## 一、记忆发布的具体失败链

### 1.1 跨批关系判定产生非法的自引用，内部完成判定过早

本场 `relationReviewBatch` 的唯一已保存结果共8项，每项incomingIndex都等于existingIndex，relation均为duplicate。对于批内比对，生产代码明确要求目标只能是更早的事实。

- 生产提示词已说明不能指向自身/更晚事实，说明此次模型回答不满足业务合同，不是原对话没有事实。
- `_relation_batch_page` 的结构验证只检查目标是否在页内，没有验证批内相对索引约束。它先把provider attempt记为responseAccepted、unit记为completed。
- 调用者 `_resolve_cross_batch_relations_batched` 随后才检查 `target >= incoming_index`，抛出 `candidateExtraction.live.relationValidate.forwardBatchTarget`。
- `RecoveryThemeAssembler.assemble` 捕获该合同失败后，保留原事实并要求额外的全上下文纠正安全复核。
- 用本场保存的关系结果运行生产批内解析方法，无网络/数据库写入，稳定复现forwardBatchTarget。第二个快照仍复用这份completed关系结果，故该前置失败不会靠新增快照自然消失。

证据：[模型结构化记录](model-audit.json)、[生产方法离线复现](local-causal-probe.json)。
源码：`owner_truth_candidate_extraction_worker.py` 的 `_relation_batch_page`、`_validate_relation_batch_results`、`_resolve_cross_batch_relations_batched`；`owner_truth_live_recovery_worker.py:341`附近的关系失败隔离。

### 1.2 主题已经整理出来，但安全复核请求违反供应商公开要求

保存响应重放结果：

| 恢复快照 | 事实数 | 安全复核前可靠主题 | 额外安全复核触发 | 安全复核后 |
|---|---:|---:|---|---:|
| revision1 | 36 | 2 | 关系解析失败；另有1个事实的主题支持被否决 | 0 |
| revision2 | 40 | 1 | 关系解析失败；本次主题分组本身无遗漏/否决 | 0 |

不是模型完全没有整理出主题，也不是所有事实都不可靠。失败在更后的请求。

`DeepSeekLiveThemeProvider.prepare_safety` 使用 `response_format={type:json_object}`，但system提示词和本场user材料均没有 `json` 一词。DeepSeek官方JSON Output说明要求在system或user prompt包含json并给出格式示例。其他正常主题归纳/支持复核提示词含“只输出严格JSON”；安全复核漏掉了这个声明。

对3个历史安全复核请求进行了重建：**完整请求body的SHA256与当时数据库中的requestHash全部一致**，同时promptContainsJSON全部false，因此不是拿近似请求推断。

- 请求body分别8832、12247、14597字节，实际max_tokens1024。
- 3次均 `themeSafetyRequest.requestRejected`，分别约0.143、0.138、0.160秒结束。
- 该错误由HTTP错误分类产生，不是主题复核模型回答unsupported。
- 适配器把401/403、402、404、429、5xx分别映射为其他码；requestRejected不能直接还原成唯一HTTP状态，**不能在没有原始证据时写成已确认400**。

**证据界限：** 不符合公开JSON模式要求是已确认的请求构造缺陷，且与3次立即拒绝高度吻合；现有诊断丢失了底层状态/供应商具体错误消息，无法将“供应商这次明确因缺json而拒绝”提升为已直接观测事实。没有为证明猜想新增真实模型调用。

证据：[精确请求重放](request-contract-replay.json)、[HTTP日志脱敏核对](http-log-metadata.json)、[模型调用摘要](model-audit-summary.json)。
官方依据：[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)，2026-09-30核对；源码 `owner_truth_live_theme_provider.py` 的 `prepare_safety`。

### 1.3 最终错误掩盖了底层拒绝

安全复核HTTP错误进入 `_call` 后，被记为failed unit，再转换成RecoveryThemePageFailed；`guard_partial_themes`因复核无法完成而排除主题。所有主题都经过同一错误分支，因此全部被挡住，之后上层抛noReliableThemes。

拒绝不可靠内容本身应保留；这里暴露的是请求构造和失败诊断问题，不是应当跳过证据校验。此次快照failure_code还为null，必须通过job_attempts→model work unit才能找到更具体错误，增加了排查困难。

## 二、为什么短场和本地验收没发现

- 本场短A事实少，走relationReview/relationSupport，没有themeSafety；完整短场通过不能覆盖长场批内8事实关系和部分结果安全复核。
- 本地四场及部分失败场虽然经过真实业务代码/PG，但模型是受控响应。`recovery_four_scene_server.py`与`recovery_partial_provider_pg.py`根据请求中context/themes直接返回合法安全复核JSON，并未检查供应商JSON模式对prompt的约束。
- 批内模型自引用这种“结构合法但语义非法”的实际输出未在本次验收中阻止unit过早completed。
- 因而本地PASS确实证明了受控响应下的链路，**不足以证明实际Provider合同及长时真机调度可靠**。我此前的测试没有覆盖到这两个关键分支，不能以本地测试数量多代替现场修复完成。

## 三、手机保存滞后和送帧中止

已确认：

- 25轮前逐轮送达；26轮开始落后，36轮时瞬时确认57/58条，落盘回调仅29用户轮，而语音已完成36轮。
- 1—12、13—24、25—36轮的ASR完成中位时延约1.58/1.57/1.60秒，助手文字约1.62/1.62/1.65秒；未出现随时长增长明显变慢的已完成轮响应趋势。
- 工具的 `startAudioClock` 运行在MainActor，0.5秒门槛是本地工具设置，未读到火山将本场因时长/容量主动断开的证据。
- 手机队列副本约2MB，73 canonical成员对应5692个持久化handoff，其中owner4908、assistant784。
- 每个persistCanonicalHandoff都会读整份Envelope、验证、修改、再验证并写整份文件，随后再次读回验证。验证还遍历累计handoff、查找成员并创建序号集合，负担随会话增长。
- SDK保存的4096条环形诊断中3989条为providerCallback。DialogEngineManager每个回调都记录诊断（含播放器音频3018）；诊断每事件读写整个环形文件。环形限制了留存条数，并不等于每次记录成本低。
- 工具失败后仍在主线程调用诊断queue.sync导出，具有拖延异步停止/持久化回调的风险；这发生在音频失败之后，不能倒因为此前的音频失败唯一原因。

当前合理判断：客户端事件/持久化处理吞吐不足是保存落后的强嫌疑，工具主线程送帧可能放大了同一负载压力。但没有现场线程栈，**仍不能确定哪项操作占据了本次0.542664秒**，也不能等同宣称真实麦克风一定在同一时刻失败。

证据：[分段时延](device-timing-comparison.json)、[手机原件和摘要](../LONG20/device-evidence/outbox-summary.json)、[SDK事件](../LONG20/device-evidence/diagnostic-events.json)、[逐轮记录](../LONG20/result.json)。

## 四、供应商容量、超时与内部预算核对

- 本场使用api.deepseek.com，模型记录deepseek-v4-flash。
- 86请求：83responseAccepted且finish_reason=stop，3rejected均安全复核，recovery请求0。
- 已接受响应实际最大prompt_tokens10290、completion_tokens1984；未见finish_reason=length。拒绝请求小于本场部分已成功请求，耗时不足0.2秒。
- 这些证据不支持“本场因20分钟、上下文装不下、生成输出耗尽或模型超时”这一解释。请求被拒绝也属于外部交互问题，但主要线索指向我们请求不符合合同，而不是供应商服务容量故障。
- 不把其他火山RTC/ASR产品的公开限制直接套到本场SpeechEngine端到端Live。官方实时接口页本轮网页读取失败；因此不填写未经核实的会话时长上限。火山侧仍以本场真实错误事件和契约为准，当前未发现时长上限触发证据。

## 五、另发现的潜在一致性问题（不是本场首因）

重建已保存themeSupport响应时，语义input/proposal哈希能通过，但9个themeSupport请求body字节哈希不能原样重现；归纳与3个安全请求哈希均能重现。原因候选是嵌套proposal被JSON序列化成字符串时未排序，而PG JSONB不保留原键顺序。已单独保留原始重放结果；需要作为恢复时重复模型调用/预算判断的独立风险继续核对，不能说它已造成此次现场失败。

## 未决项与讨论边界

1. 安全请求缺JSON声明已证实；供应商精确拒绝正文没有留存。
2. 批内自引用导致forwardBatchTarget以及错误结果先completed已复现。
3. 手机性能首因尚缺现场耗时/栈证据；不需要用户立即重测来重复制造同一结果。
4. 本场不能证明9月10日以来每一次短/长场故障都由这些原因引起。历史seq5等仍未关闭。
5. 本轮停在原因分析；不调大阈值、不放松校验、不做业务重放、不再部署，待用户讨论。
