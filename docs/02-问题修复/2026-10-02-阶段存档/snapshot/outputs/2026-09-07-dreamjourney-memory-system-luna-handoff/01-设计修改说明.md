# 记忆系统 B 增强版：设计修改说明

版本：1.0，2026-09-07。执行入口：[README](README.md)。本文件定义目标合同；标注“新增/建议名”的对象尚不存在，不得当成现有实现。

## 1. 必须达成的产品结果

| 需求 | 目标 |
|---|---|
| MEM-01 统一来源 | 本人素材、Live、文字及在世家人授权贡献，最终进入同一审核与正式事实体系 |
| MEM-02 结构记忆 | 保存谁、说了什么、何时/何地、什么依据、确定到什么程度，不只是每条记录附标签 |
| MEM-03 增量维护 | 每次新内容与旧事实比较，区分重复、补充、变化、更正、争议，不盲目增加独立碎片 |
| MEM-04 唯一正式权威 | PostgreSQL 内现有 MemoryVersion 体系仍是唯一事实权威，历史不等于分叉 |
| MEM-05 整体阅读 | 正式页是中性、连贯的整体概况及维度内容；内容记录页保留每次输入和处理历史 |
| MEM-06 自然检索 | “饮食偏好”“爱吃什么菜”能找到东坡肉事实，不要求问题必须含杭州 |
| MEM-07 Live 保留 | 火山原生听说与打断不重做，正式记忆背景确实生效，不恢复逐轮 DeepSeek→TTS |
| MEM-08 文字保留 | DeepSeek 自然文字回答、不朗读，支持新话题与连续追问 |
| MEM-09 整场沉淀 | 用户打开到关闭/已定义空闲结束是一个产品会话，逐回合保存、整场一个审核批次 |
| MEM-10 真实性与权限 | 正式记忆不润色，回复可温柔；家人、推测、历史情绪不冒充本人当前事实；撤权和删除能传播 |
| MEM-11 可维护 | 复用单后端、PostgreSQL、对象存储和 Worker；可恢复、可追踪、有成本与性能证据 |

不包含：逝者账户/档案控制权、声音克隆供应商切换、数字人重建、其他历史模块清理、完整人格诊断、每人训练一个基础模型。本版不安装多套开源记忆服务。

## 2. 当前缺口与设计选择

当前已有 Source、Candidate、审核回执、MemoryVersion、PostgreSQL 和派生投影，不是从零建库。本次修复这些基础之间的语义和可靠性缺口。

| 当前证据 | 设计修改 |
|---|---|
| 家人 Source 的来源语义在整理后变为 firstPerson/recalled | 来源身份由服务端证据合同贯穿，不让整理器默认补成本人 |
| 历史喜欢、现在不喜欢被同槽规则判成冲突 | 把有效时间、场景、肯否和更正意图纳入比较 |
| 近义问法漏召回、文字检索未用前文消歧 | 有界会话话题解析 + 结构/关键词/向量融合 + 回源 |
| 当前归并主要为规则分组和代表记录 | 审核变更集持续维护事实，受影响的维度生成整体文本 |
| Live 快照原文/摘要对限定和争议传递不足 | 统一读取资格，结构化事实压缩；验证 SDK 接收与实际回答 |
| 客户端会话依赖内存队列、可能误复用旧会话 | 持久发送箱、产品会话身份、回合幂等、结束水位及唯一批次 |

上述分别来自代码、内存探针和静态风险，不能一概认定生产数据已经损坏。详细证据见[原证据文档](../../03-架构与评审/记忆系统专项/2026-09-07-dreamjourney-memory-special-review/02-代码证据与验收计划.md)。

## 3. 一份正式记忆与三个派生用途

```text
素材 / Live / 文字 / 获授权家人材料
  → 原始证据 → 类型化候选 → 与当前事实对齐 → 差异审核
  → 原子提交 MemoryVersion 和当前事实集版本
  → 派生：整体正式文本 / 检索与 Live 背景 / 自传事实底稿
```

统一正式记忆是一个人物的当前有效事实集合，不是一行巨型 JSON 或一个无限长 prompt。历史版本、索引、自传和画像不是第二份可写事实权威。

事实集合的版本与投影版本必须分开：事实提交成功后，索引/概览可以仍在更新；不能把“概览旧 checkpoint”宣称为“最新正式事实”。单次读取绑定一个一致事实集版本，不混合提交前后数据。

## 4. 结构模型及现有数据映射

### 4.1 身份与出处

每份来源区分 `vaultId`、`memorySubjectId`、`claimSubjectId`、`speakerPersonId`、`contributorAccountId`、`reviewerAccountId`。这里是逻辑字段名；与当前 ownerSubjectId/personId 的映射要在数据库设计中列明。

- vault/memorySubject：这是谁的档案；claimSubject：具体句子讲谁。
- speaker/author：实际说话者/作者；contributor：谁上传，不等于谁说。
- 服务端由已认证账户和有效授权确定可操作档案，不能相信客户端自报的 owner/reviewer。
- 材料中的“我”、名字或声音不能自动证明身份。未知说话者保留 unknown，必要时审核澄清。
- 在自己档案记述父亲，不会自动创建/写入父亲档案；跨库入库需要独立授权和审核。
- 家人说“爸爸喜欢东坡肉，我很难过”：第一断言谈父亲，第二感受属于提交者。后者默认只服务本场聊天，不能悄悄跨库写入。

### 4.2 十个维度，少量类型

维度多选、类型单选；维度只是产品组织与检索入口，不是十个独立库。

| 维度 ID（新增合同） | 展示 | 主要 factType | 必要限定 |
|---|---|---|---|
| identity | 身份与背景 | attribute | 人物、属性、实体、时间 |
| lifeEvents | 人生经历 | event | 事件、参与者、发生时间、结果 |
| relationships | 家庭与社会关系 | relation | 两端、方向、时期、来源；不授予权限 |
| knowledgeSkills | 知识、技能与经验 | knowledge | 命题/方法、领域、适用条件、掌握程度的原话 |
| preferences | 偏好与兴趣 | preference | 对象/类别、肯否、程度、是否明确最、时期/场景 |
| habits | 习惯与生活方式 | habit | 频率、条件、持续区间；一次行为不是习惯 |
| emotions | 情感与联结 | affect | 感受者、对象、触发、时间、表达者 |
| values | 价值观与原则 | value | 表达者、适用范围、自我认同证据 |
| traits | 性格与应对方式 | traitReport | 自述/他评/假设、情境；不自动诊断 |
| goals | 目标与当前关切 | goal | 想法/计划/进行/完成/取消、期限与证据 |

另设 `other`/`unknown` 承接无法可靠分类的内容，不能为了结构完整强制补值。兼属经历与偏好的事实只存一次，多维引用。

保留当前 `memoryKind=experience/knowledge/emotion` 作为现有宽分类字段；在下一版类型化 payload 中新增 `factType` 和 dimensions，不同时新增一套 claim 可写库。宽分类不是真实性或当前性的依据。旧 reflections、personality 等 facet 由版本化映射转换；无法对应的不丢弃或强推新含义。

### 4.3 类型化事实合同

建议下一版 payload schema 使用 `owner-truth-v5`，开工先检查是否已占用。以下为合成示例，不是当前 DB 内容；ID 应换成项目实际合法格式。

```json
{
  "schemaVersion": "owner-truth-v5",
  "memoryId": "11111111-1111-4111-8111-111111111111",
  "memoryVersionId": "22222222-2222-4222-8222-222222222222",
  "memoryKind": "experience",
  "factType": "preference",
  "dimensions": ["preferences", "lifeEvents"],
  "memorySubjectId": "person-owner",
  "claimSubjectId": "person-owner",
  "statement": "本人回忆，在杭州时特别喜欢吃东坡肉。",
  "predicate": "likes",
  "object": {"entityId": "entity-food-1", "label": "东坡肉", "category": "food"},
  "qualifiers": {
    "polarity": "positive",
    "strengthExpression": "特别喜欢",
    "superlativeAsserted": false,
    "place": {"entityId": null, "label": "杭州"},
    "validTime": {"start": null, "end": null, "precision": "unknown", "expression": "在杭州的时候"},
    "currentApplicability": "unknown"
  },
  "provenance": {
    "mode": "selfReport",
    "speakerPersonId": "person-owner",
    "evidenceRefs": [{"sourceId": "33333333-3333-4333-8333-333333333333", "sourceVersion": 1, "turnId": "turn-7", "relation": "supports"}]
  },
  "review": {"state": "accepted", "receiptId": "44444444-4444-4444-8444-444444444444"}
}
```

合同约束：

1. statement 只能中性转述、去重或有依据合句；不得增加“始终”“最”“仍然”“擅长”等原文没有的含义。
2. `recordedAt` 与 `validTime` 分开；“今天”绑定来源时区/记录日期，“在杭州时”无日期则不编起止日。未知时间与确定的开放区间要区分。
3. `provenance.mode` 至少区分 selfReport、familyReport、documented、observed、inferred、unknown；证据表达确定性与机器提取置信度分开。与当前 perspective/epistemic 枚举显式映射，不直接把新字符串写入旧 CHECK 约束。
4. 审核 accepted 表示用户同意收录，不自动把 reported/inferred 变成 observed 或“绝对真实”。他人评价可作为带归属的评价保存，不是人的客观性格定论。
5. `affect` 类型必须另有 experiencer、target、trigger、emotionExpression、validTime、reporter；无依据的强度/诊断为 null，不自动把过去情感当作现在状态。
6. 学校、食物等 entity category 可以辅助索引，但不能据此自动扩充新的个人喜好。别名有作用域和出处，同名人物不能自动合并。
7. 审核/版本/权限字段由服务端控制，客户端 JSON 不能自行生成 receipt 或提升事实等级。

### 4.4 数据库存储选择

| 逻辑对象 | 复用/扩展位置 | 约束 |
|---|---|---|
| Source / evidence | owner_truth.sources、source_links、extraction_results、私有对象存储 | 版本/hash、原文跨度或音频片段/页面定位；转发链不算独立证据 |
| Candidate / ChangeSet | memory_candidates、interview_review_batches 及已有 decisions/receipts | 补操作、目标版本、base revision、依赖和来源，不另开平行审核系统 |
| Claim | memories + memory_versions | payload 类型化；每 memoryId 一个当前版本，查询聚合来自同一正式提交版本 |
| 多证据/实体 | 若现有实体不能承载，新增最小的 evidence link 与 entity/alias 表 | vault 约束、复合外键、支持/反驳角色及独立来源组；不要复用登录 identity alias 表 |
| 时间和冲突关系 | memory_relations + 新版本状态/限定 | temporalChange/correct/dispute 的新 relation enum 必须同步迁移及校验 |
| 当前事实集版本 | 复用可证明等价的当前版本机制，否则 vault 新增 memory_revision | 审核事务内递增；与权限 epoch、派生 checkpoint 分开，不新增完整事实镜像 |
| 展示 | memory_projection、person_memory_projection_versions | 绑定正式 revision、生成版本、句子引用，过期可检测、可重建 |
| 检索 | 现有 search projection 演进，Postgres + pgvector | 绑定 vault、版本、contentHash、模型/维数；不使用独立向量服务作为权威 |
| 会话 / 任务 | conversation_threads/messages、interview_sessions、async_effects | 稳定产品会话、可靠水位、幂等任务和回执 |

DDL、Python 合同、DTO、Swift decoder 和 fixtures 必须一起演进。不得直接覆盖历史 SQL migration；新增下一个未使用版本并校验升级顺序。索引为派生数据，不能反过来更新事实。

## 5. 统一接收、提取与匹配

### 5.1 接收与提取

来源接收返回可靠 receipt、source/session ID 和 processing 状态。原文未持久化不能显示已保存；已接收不等于已整理或已正式收录。

文字、OCR/ASR 后的媒体文本和对话都进入同一类型化整理合同，保留不同来源身份与定位。不得因 origin 不同就悄悄退回“原文一条候选”并谎报结构化成功。模型不可用保留材料与可重试状态，默认不伪造规范候选。

仅提取有用户表达/材料证据支持的个人命题；问句、建议、假设、助手答案不单独变事实。用户“是的”可与明确问题共同支持候选，须同时引用两回合，不能只把助手问题当证据。短答/指代不清时需要澄清。

### 5.2 与已有正式事实匹配

先限定人物与授权，再按实体/类型/关系和时间找有限候选，最后比较语义。建议初始匹配候选上限 20、相关关系扩展 1 跳；这是可调预算，不应全库两两 O(n²) 重算。

比较输入必须包含：主体、谓词/对象、肯否、程度、时间重叠、场景、证据类型、明确更正语句。向量相似度只能候选召回，不能决定合并、覆盖或真假。

| 操作 | 处理 |
|---|---|
| add | 新的独立事实，审核后新建 memoryId |
| addEvidence | 同一命题的新独立证据，不重复增加人生段落；证据支持变化有版本/回执 |
| refine | 填补原来未知信息，显示字段差异，审核后新版本 |
| temporalChange | 分时状态均保留；新当前偏好不抹掉历史偏好，时间不明则先澄清 |
| correct | 用户明确原记录错误，指向确切旧版本；审核后旧版本不再是当前事实 |
| dispute | 同一主体/时间/场景仍矛盾，保留两方证据；经审核的争议不得作为确定答案 |
| duplicate | 同一输入/转发/回执重放只返回原结果，不增加证据数量和费用 |
| noPersonalFact | 整理完成但无新候选，显示“未发现需新增的记忆”，不是失败 |

审核前不能因 AI 新提案而静默重写正式事实。若涉及权限撤回/删除，访问阻断按权利流程立即生效，不等待语义审核。

## 6. 审核、事务与唯一版本

每个 ChangeSet 包含 `changeSetId`、来源批次、baseMemoryRevision、操作集合、每操作目标版本/证据/差异、依赖关系和幂等 commandId。这里是逻辑新合同，不要求恰好同名的新表。

用户能查看“新增/补充/更正/变化/争议”和前后事实，接受、修改或拒绝。允许逐项决策；相互依赖的操作必须组成一个原子审核组，不能只应用删除旧事实却漏新增事实。整个会话批次不要求一次全部确认。

单个审核组的事务：验账号及用途 → 锁定 vault 当前 revision → 比较 base revision/目标版本 → 校验操作和证据 → 写新版本/关系/当前指针 → 写唯一审核回执 → 递增正式 revision → 写已有 Outbox → 提交。模型、网络、embedding 和概览生成不进入数据库事务。

重复 commandId 同载荷返回原回执；同键不同载荷拒绝。并发旧提案返回明确冲突（建议 HTTP 409），客户端重新展示差异，不最后写入者获胜。只读/拒绝操作不制造新的正式事实版本。

同一 memoryId 的旧版本和新版本不能同时 current；不同时间的有效事实可分别为当前版本，例如“过去喜欢”和“现在不喜欢”。这不是分叉，检索必须按时间回答。

## 7. 两个页面与自传

第一页复用正式记忆页，展示“整体概况 + 十维正文”；并非一条条卡片按维度分组。只增量重写受影响段落；每句绑定实际支持的 memoryVersionIds，保留时期/来源/不确定性。无法合句时分段，不为了连贯创造因果或人格。

第二页复用内容记录入口，显示每次素材/整场会话、接收与整理状态、候选批次、审核决定和正式版本链接。显示原始输入是为了追溯，不是用它替代正式概览。

审核事务成功但概览失败：明确“事实已更新，概览整理中”，可读取当前有效事实，不能误报审核未写入或以旧概览充当最新。重试不重复提交事实。

自传只消费正式事实底稿并绑定写作版本，文学表达不能反向入库；原事实更正/撤回使相关章节标为待更新，权限失效时阻断相关内容。作品固定版本不等于另一个正式事实权威。

## 8. 共用的事实读取合同

建议在现有服务层形成逻辑 `AuthorizedMemoryContext`，不要新建独立服务进程：

- 身份：viewer、target、vault、用途、Owner/发布域和有效 grant 范围。
- 一致性：memoryRevision、authorizationEpoch、projectionCheckpoint、contextHash；发布域另有 publicationVersion。
- 事实：eligibleFacts（含类型、时间、肯否、来源和证据）；争议/未知作为不能确定回答的限定，不混入确定事实列表。
- 完整性：coverage（已含/省略的范围及原因）、检索/索引状态；没覆盖与没有记录分开。
- 临时上下文：本场用户表达和助手聊天上下文分区，不能升级为正式事实。

服务端先授权过滤，再检索/构建背景；回源时重验当前有效版本。缓存键至少含目标、读取域、grant 范围版本、正式 revision 和权限 epoch。不能全库发给模型后用 prompt 要求它保密。

调用方使用同一个事实资格合同，但不同消费策略：文字按问题相关检索，Live 开场/更新用紧凑背景，正式页用中性聚合，自传用允许的写作事实底稿。

## 9. 文字检索和回复

`/echo/answers` 继续提供文字答案。建议扩展 productSessionId、turnId、questionSequence；旧字段与新增字段的替换计划由合同表明确，不能客户端/服务端各猜一种。

检索前使用服务端已收到且不晚于该问题的本场回合解析指代，不读取未来消息。若当前消息尚在持久发送箱，可在本请求携带受大小限制的必要本场上下文，明确它是未确认对话；它不能更改目标/授权或触发正式写入。已有 recentTurns 不是长期会话库。

处理链：绑定身份/版本 → 识别个人事实需求和追问意图 → 结构、关键词、向量召回 → 有界关系补充 → 融合排序 → 回源验权/版本 → 生成 Context Packet → DeepSeek 自然回复。

初始建议每路最多 20 条、融合最多 50 条、最终最多 8–12 条证据单元，总 token 预算必须实测；不能截断一句事实丢失“不是/以前/听说”。引用是真正支持答案的版本，不固定拿组里最长记录。

初期每人几千条事实，优先测授权人物范围内精确向量检索；近似索引是否必要由压测决定。中文分词/别名要测试，不把英文全文检索配置冒充中文方案。embedding 模型、维数、版本未在本交接锁定，必须先用合成中文集选型，不默认调用任何现有聊天模型充当 embedding。

向量服务不可用时显式降级为结构/关键词，校名精确查询仍应可用；近义召回指标没有真实 embedding 验证不得记 PASS。降级不能回退到无授权本地资料或旧记忆库。

回复规则：个人事实受正式证据和本场用户表达限制；一般知识可以自然聊。未知则简短说明并适时询问，不每轮固定推动。只知道“在杭州时特别喜欢东坡肉”时不能回答“你现在最爱东坡肉”。文字不播放语音，不触发火山朗读。

## 10. Live 记忆连接与体验保留

正常 Live 保持火山原生回答权威，最终 ASR 用于会话记录，不再逐句转入 `/echo/answers`。不修改音色、采样率、音频/VAD/打断状态机来解决记忆问题。

后台在正式更新后预生成有预算的 Live 事实背景：核心事实 + 按维度的紧凑证据；不重复全文与同内容摘要。不在点击麦克风时同步调用 DeepSeek 压缩整个人生。

事实背景必须保留时间、来源、争议、否定及程度。注入日志只能记录版本/hash/条数/容量/错误码，不记录私人正文。必须分别验证：后端构建 → iOS 序列化 → SDK 正确字段与长度 → 供应商接受 → 实际问题可正确回答。一个“token 成功”或 contextHash 一致不代表最后两步成立。

详细事实不在已注入范围时，优先验证当前 SDK 的工具调用或安全更新能力，用同一后端事实合同补查；工具查的是我们的正式记忆，不是外部互联网。未验证能力不得臆造 SDK 字段，不得用恢复逐轮 DeepSeek→TTS 作为兜底。

版本策略：本人开场拿最新已提交事实集；普通更新目标是在自然回合边界应用最新版本后再回答相关个人事实。删除/撤权/切人物必须及时失效；不能仅注入“忽略旧事实”来假装已清除旧上下文。若无法安全清除，停止该受影响会话并明确说明，安全事件不是普通播放超时。

**供应商热更新、连续体验、始终最新若不能同时满足，应报告阻断，由产品决定是否接受明确降级；Luna 不得自行批准“本场一直旧、下场更新”。** 该阻断不影响继续实现结构模型、文字检索和可靠会话等任务。

本场新内容可继续交流，后续由 DeepSeek 整理；正式背景只约束个人已知事实，不禁止对“今天刚发生的事”自然讨论。助手生成的事实不能作为训练/记忆证据。

## 11. 整场会话与持久化合同

### 11.1 身份及状态

`productSessionId` 标识一次用户打开到结束；providerSessionId 只是供应商连接，不作为整理批次身份。另有 captureChannel=live/text，不能仅靠旧 entryMode.live 恢复会话。

状态链：open → closing → awaitingTurns（缺消息时）→ queued → organizing → pendingReview / completedNoChange；任务可处于 retryableFailure，不能用轮询超时替代真实任务状态。review 的 accepted/rejected 与会话整理状态分开。

原生重连继续同 productSessionId；用户重新打开是新 productSessionId。旧会话仍可后台补传，但不能混入新会话。换人物结束旧作用域，重建身份绑定；不合并两个人物的上下文。

### 11.2 回合落地

最终用户转写及助手上下文进入受 iOS Data Protection 保护、按账户隔离的持久发送箱，然后异步传输。不得在音频实时回调中同步写盘、做网络或等数据库；放到串行后台处理队列。

消息合同至少包含：productSessionId、turnId、sequenceNumber、role、text、capturedAt、channel、contentHash、commandId。助手回复另保留对应用户 turn 的关联，SDK 能提供的原始 turn/event ID 一并映射；不能仅按回调到达顺序把回答配给错误的问题。role 中的助手不能作为事实来源；说话人身份需服务端与材料证据校验。

客户端序号是采集顺序，当前服务端分配的到达 sequence 不能直接替代它。可新增 clientSequenceNumber 并保留内部序号，或一次性迁移为共同逻辑序号；必须在 API/DB/Swift 明确映射。重复转写不得重编号，部分转写不当新消息，最终修订需 revision/去重规则。

回执返回已接收消息 ID 与**最高连续采集水位**，不能把 MAX(sequence) 当消息已齐。同键同 hash 重放成功，同键异载荷拒绝。助手打断前已展示的文本也可作为上下文保存，但不据此认定用户听完或认可。

文本提交失败与消息持久化失败分开显示。对已可靠接收的回合可以保证进程重启后可恢复；未接收/未本地落盘的语音无法承诺零丢失。

### 11.3 结束与审核批次

用户主动关闭或有效空闲达到 60 秒后，提交固定 lastSequenceNumber 与 endCommandId。空闲计时只计算真正可聆听且无人输入的时间；用户讲话、助手播放、服务处理和暂停/重连不能因等待被错误关场。不要改变现有原生打断逻辑。

关闭先进入 closing，不立即销毁保存协调器。停止接受新回合后，给已开始的采集/最终转写一个可验证的排空边界，再确定 lastSequenceNumber；无法确认边界时显示保存中/待恢复，不能仅因当前队列为空就宣告完整。具体 SDK 完成信号和有界等待策略要在 W02/W06 联测，不将等待放进音频回调。

服务端缺回合时返回 awaitingTurns/缺口，客户端补传；消息齐全后幂等创建整场唯一整理任务和审核批次。重复 end、不可靠回执及 Worker 重试不能增加批次。结束后的供应商迟到事件不写进新会话；若确属遗漏，走同会话显式修订/恢复流程，不偷偷重开已完成批次。

会话很长可分块，最终跨块统一人物、时间、重复和证据，汇总一个审核批次。无新个人事实显示 completedNoChange；整理超时/余额不足/格式错误显示可重试，禁止直接套原文假装规范整理完成。

会话转写上传沿用已授权用途；家人材料、媒体新增出网范围、保留期限不能从“本人同意 DeepSeek 整理”推导为全部授权。未授权只完成本地/自有后端流程并报告限制。

## 12. 权限、删除和降级

在世家人材料按现有贡献授权提交到目标 Owner 的审核。材料处理授权与事实确认可同一工作台呈现，但不能把接收一张照片等同于批准其全部 AI 推断。

Family/Visitor 不是私人域全量读取通行证。发布副本绑定已授权 publicationVersion，并不自动追随私人最新修改；两种对话在同一授权域/版本下保持事实范围一致，不能统一成读取对方全库。

删除/撤回沿 Source→证据→事实资格→索引/概览/Live/自传传播。多个独立来源支持同一事实时，按剩余证据和用途重验；派生摘要不算独立证据。先阻断使用再异步清理，已有他人看到/听到的内容不能宣称可追回。

建议错误合同（逻辑名称，复用或映射现有错误码）：`STALE_BASE`、`AWAITING_TURNS`、`AUTHORIZATION_REVOKED`、`PROJECTION_UPDATING`、`MEMORY_NOT_COVERED`、`ORGANIZATION_RETRYABLE`、`COMPLETED_NO_CHANGE`。明确哪些允许重试、是否已可靠接收，不能统一弹“提交未完成”。

## 13. 运维与实施限制

复用现有 Worker、Outbox、租约和退避，幂等 job key 绑定源版本/输入 hash/算法版本。每人物限并发、公平排队，增量 embedding 和聚合；不每回合重写整个人生，不为十维开十个 Agent。

模型上下文、输入长度、一次候选数量、循环重试均有上限和可观察状态。长任务可分块；达限不截掉剩余数据后伪称完整。

监控最小集：来源接收成功率、未补齐会话、最老队列年龄、整理失败/重试、审核错误、投影落后、检索命中及降级、Live 上下文覆盖、删除积压、DB 连接池和模型费用。只记录安全关联 ID/hash/指标。

AI 可协助诊断、幂等重试、索引重建和生成恢复步骤；生产删除、权限扩大、不可逆迁移仍需要明确授权和负责人。性能目标及完成判定见[验收文档](03-测试迁移与交付验收.md)。
