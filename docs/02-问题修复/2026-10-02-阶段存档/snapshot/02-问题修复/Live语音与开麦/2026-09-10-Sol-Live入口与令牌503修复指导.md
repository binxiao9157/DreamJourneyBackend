## 0. 先读结论与执行顺序

本次有两个相互独立的主问题，不能用一个原因解释全部现象：

1. **B-DEV-001：文字会话结束后，Live 入口停在不可点击的勾。** 当前代码存在完整可解释路径：文字回复设置 `.replied`，结束文字会话未重置交互状态，而非 Live 的 `.replied` 将麦克风渲染为禁用 `checkmark`。后台整理状态只更新提示文字，不会解锁该按钮。
2. **B-DEV-003：重启后可以点击麦克风，但 `/voice/realtime-token` 连续返回 503。** 故障发生在火山 `startDialog` 之前。现存日志没有 HTTP 响应中的业务错误码，不能认定为某个快照字段、模型余额、麦克风或 TTS 故障。

另有 **B-DEV-002：该文字会话整理进入 Dead Letter、没有 Candidate**，见第 7 节。它不是按钮保持禁用的必要条件，也未证明是令牌 503 的原因；必须保留单独状态。

推荐顺序：

`复核版本与原证据 -> 001 的失败回归与局部修复 -> 补安全诊断取得 003 实际错误码 -> 按实际分支修复 -> 自动化与构建 -> 必要后端部署 -> 用户配合真机复测`

001 修复和 003 取证可以分别推进。不要等待所有历史数据/全平台 readiness 关闭才定位这两个问题；也不要以 B 阶段为由跳过相关自动化测试或安全检查。

## 3. 修复任务 L01：文字交互结束后释放 Live 入口

### 3.1 要实现的状态合同

将“当前交互是否可以开始”和“上一场记忆是否整理完成”作为两个独立维度处理，优先沿用已有 ViewModel 和 coordinator，不要求另建复杂状态框架。

| 事件 | 交互/麦克风 | 后台记忆采集 |
|---|---|---|
| 用户结束文字会话 | 结束当前文字交互，恢复可启动状态 | 已接收内容继续可靠发送/整理 |
| 上一场仍 organizing | 可以启动新 Live 或新文字会话 | 原 coordinator 继续工作，关联原 productSession |
| 上一场 pendingReview / completedNoChange / unavailable | 不重新锁住新入口 | 如实保留各自结果；失败不假装有候选 |
| 已开始新 Live 时旧文字回调到达 | 不覆盖新会话状态、回答或麦克风 | 属于旧场的持久化结果仍按旧会话处理 |
| 换人、退出登录或授权失效 | 不能跨身份重置/更新 UI | 按既有账号边界处理，不投递到新人物 |

### 3.2 实现要求

1. 在结束文字会话的明确路径收尾交互，复用 [resetEchoViewModelToIdle](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Echo/EchoViewController.swift:3258)及 ViewModel 的账号校验。不能仅强行把 UIKit 按钮设 enabled 而留下旧交互状态。
2. 核对 [invalidateDigitalHumanInteraction](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Echo/EchoViewController.swift:3462)或现有同等机制，使已结束文字交互的迟到 UI 回调失效。选择副作用最小的交互级失效，不随意拆掉整个人物/SDK 生命周期。
3. 保留待整理 coordinator 与可靠回合 outbox；不能为恢复按钮清空它们、丢掉尚未持久化回合或把每回合重建成一场。
4. `render(.idle)` 会隐藏 voice status，注意调用顺序和展示优先级。恢复入口后仍须准确显示上一场整理结果，或保存在对应记录/通知中；不能按钮修好而整理失败提示被无条件抹掉。
5. 原 coordinator 终态回调只能操作自己持有的对象和原会话状态，不能清空新 coordinator 或覆盖新文字回答。当前 retained identity 判断可复用，但需新增“旧场回调遇到新场”的真实控制器测试。
6. 重复结束、结束时仍有回答在途、页面切换/前后台转换必须幂等。不能把所有 `.replied` 全局改成 `.idle`，影响仍有含义的其他回响状态。

建议收尾顺序为：捕获并验证当前文字会话身份，失效本交互的旧 UI 工作，将原采集交给后台完成，恢复交互 idle，最后按会话归属更新整理提示。具体顺序以现有异步依赖验证，不将此建议当作可直接复制的补丁。

### 3.3 最少回归

- 一轮和三轮文字问答后结束，均可直接点击 Live，无需重启。
- 整理四种结果：仍处理中、有候选、无新增、失败，入口均按新交互状态工作。
- 结束按钮重复点击，后台只结束/整理一次。
- 回答在途时结束，迟到回复不把新 Live 改回 `.replied` 或 `.error`。
- 旧场整理完成/失败时，新 Live 和新文字会话各自不被污染。
- 换人/退出登录后旧回调无效，已有账号安全断言不退化。
- 实际模拟器/控制器流程连续至少 10 次“文字 -> 结束 -> Live 入口恢复”。不能只做字符串源码检查或 `build-for-testing`。

## 4. 修复任务 L02：先取得 503 的实际业务错误码

### 4.1 最小诊断改动

在 Echo 的 Live 配置失败回调保留 error，通过已有分类接口提取 HTTP status、业务 code。不要直接打印 `localizedDescription`、error/context 的整体对象或原始响应体，因为它们可能带私人文本、服务返回内容或敏感信息。

建议安全诊断字段：

| 字段 | 约束 |
|---|---|
| event | 例如 `voiceRuntimeConfigUnavailable`，沿用已有诊断框架 |
| stage | 受控枚举：request/auth、capability、targetAuthorization、snapshot、binding、ticketStore、responseDecode、sdkConfigure 等 |
| httpStatus | 数字或明确 unknown；不得把 HTTP 200 blocked 当成 HTTP 503 |
| businessCode | 本产品已知代码白名单；未知值统一标 unknown，不原样输出任意后端字符串 |
| requestCorrelation | 复用已有请求关联机制并脱敏；没有则新增有界、不可携带凭据的关联 ID |
| snapshot metadata | 仅确有必要时记录数量、字符/字节长度、状态、字段校验布尔值和版本/hash；不记正文和完整票据 |
| retry classification | 来自可信合同或受控映射；未知原因不自动无限重试 |

检查 PrivacySafeDiagnostics 对 states/counts/correlations 的规范；能复用就复用。JSON detail、网关 HTML 503、无 body、网络超时、401/403、200 blocked、200 畸形响应分别测试。

后端按需要补局部、脱敏阶段日志：捕获业务异常的路由可记录 code；同一 `formalMemorySnapshotUnavailable` 内部细分 `stateNotReady`、`rightsInactive`、`checkpointMissing`、`entriesInvalid`、`eligibilityInvalid`、`revisionInvalid`、`statementMissing` 等受控失败原因。对外是否保持原错误码以合同兼容为准，不随意暴露内部字段给用户。

若需要新的关联 header/字段，先核对现有机制。不要为了日志重构所有接口的错误协议，也不要在源码或测试里固定某个生产账号。

### 4.2 如何取得生产同类证据

1. 优先只读查已保存安全日志及同一时间范围的服务器结构化日志。旧 access log 没有 body 时承认历史信息不可恢复，不能从 HTTP 503 推测 detail。
2. 不把调用 `POST /voice/realtime-token` 说成只读操作：即使不启动火山，也可能创建短时票据或占用并发名额。
3. 需要复现时，在用户已授权的 B 会话或合成测试账号上做一次受控启动，记录安全元数据。真实用户账号/材料的调用用途、安装和生产变更均按已有授权核对；不要求用户把 bearer token 或火山密钥贴进聊天。
4. 若配置失败时留下票据/会话，按实际生命周期验证过期和撤销，不全局删除其他会话或清空配额。
5. 响应实际 code 和对应服务端阶段取得之前，L02 只能写“诊断已补齐，生产根因待证”，不能写“503 已修复”。

## 5. 修复任务 L03：根据实证选择后端修复分支

以下是调查分支，不是要求把所有可能性都修改一遍。

| 实际观测 | Sol 核查与修复方向 | 禁止的绕过方式 |
|---|---|---|
| `formalMemorySnapshotUnavailable` | 比较当前合法人物的 projection 状态、rights、checkpoint、memoryRevision、entries 和 eligibility；与文字上下文读取路径对照，定位产生不合格值的模块。优先修生产者/迁移/装配合同，补真实 PG 再现 | 删除状态/权限/版本校验；把无效投影伪装成 ready；随便丢弃坏条目或退回本地旧资料 |
| `formalMemorySnapshotTooLarge` | 同时测快照、完整 sessionContext 及传输编码的字符/字节预算；核对已存在的维度覆盖、选择与截断逻辑，保留否定、时间、程度和 provenance 等关键限定 | 无上限加大预算；截断成无效 JSON；移除关键限定；有事实却改为空快照冒充成功 |
| `realtimeVoiceFormalMemoryBindingInvalid` | 对比同一次构建产生的 checkpoint/hash/revision 与签发参数，核对类型、序列化、配置/代码漂移和竞态；保证来自同一当前快照 | 接受客户端自填背景；关闭 binding；用零 revision 或任意 hash 填充 |
| `realtimeVoiceSubjectUnavailable` | 查 principal、auth session、人物/Vault 与票据存储使用的身份合同及状态；与文字路由的身份解析对照，判断迁移问题、主体失效还是校验器错误 | 自动激活被撤销主体；归给超级用户；以新的合成 subject 偷换真实身份 |
| capability blocked / URL 类错误 | 区分 200 blocked 与 503；核对已有代理开关、合法 URL 结构、路径前缀和凭据是否配置，不输出值。对照当前版本为何走该返回分支 | 将配置 descriptor 改为永远 ready；直发长期凭据；更换未经批准的供应商或接口 |
| 中间件/DB/UoW/未知 503 | 先确定请求是否进入路由、实际错误处理器和脱敏堆栈；核对池、事务、schema 与部署版本。不要把所有 503 都收窄到 snapshot | 对异常统一返回 200；跳过真实数据库或改用内存 store |
| 配置返回 200，但随后 SDK/WS 失败 | 作为下一阶段故障单独定位，保留令牌成功与连接失败两组证据 | 将 HTTP 200 当成 Live 能发声、可打断或用了记忆的证明 |
