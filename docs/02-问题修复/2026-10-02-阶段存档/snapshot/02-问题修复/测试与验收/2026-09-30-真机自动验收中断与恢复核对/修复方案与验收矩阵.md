# 真机自动验收中断与恢复核对：修复方案与验收矩阵

日期：2026-09-30；版本v1；DJ-LIVE-LAB-RECOVERY-20260930。

**原方案记录；用户已于后续明确授权实施。完成情况见 [实施与验证记录](实施与验证记录.md)。以下“本轮不实施”等表述属于制定方案时的历史边界。**

前置阅读：[问题记录与原因分析](问题记录与原因分析.md)。目标是让失败后的真实保存和记忆结果可以被准确验收，不把测试工具错误误报成记忆业务失败，也不掩盖真实语音问题。

## 1. 范围与不可退让项

优先只修改`tools/live_device_lab`中的运行器、只读核对、隔离注入及相应测试；不重写已通过的产品采集、保存、冻结、主题整理、关联复核、审核入库协议，不改模型提示词/预算/数据库结构来迁就工具。

- 第一失败和时间线不可覆盖；恢复结果独立记录。
- 真实SDK输入、真实ASR与PCM、真实Source/候选/确认/冷回查继续保留。
- 不伪造ASR/final/播放完成，不把合成脚本作为实际保存正文，不把候选直接灌入数据库。
- 当前账号仅确认本次新建、来源匹配的独立新增候选。旧主题关联、已有正式记忆目标、权限变化及未知业务写继续禁止自动重试。
- 本次说的“确认准备/已发送/结果未知”只是测试运行报告阶段，不给产品新增“正在审核”业务状态。
- 每次长场前独立同版短场。20/40分钟，65分钟不新增测试。没有手机不能阻塞本地工作。
- 媒体静音非硬要求；不扩大静音工具工程。

## 2. A：分开输入、完成验收、持久化和发布事实

### A1. 不再从完成轮数推导保存消息数

保留`completedTurns`含义为完整通过交互验收的用户回合，仅用于交互质量与长场门禁。新增或重用不同观察量，不能混用：

| 数据 | 含义/来源 |
|---|---|
| 输入计划与已发送输入 | manifest及实际PCM发送；计划不证明ASR已产生 |
| final ASR观察 | 原生实际回调，含operation/question身份与revision/hash |
| 完成验收回合 | 文字、核心事实、实际音频播放及聆听均满足 |
| 手机持久化消息集合 | 本场真实canonical→message/sequence/role/hash绑定 |
| 服务器接收集合 | 本场恢复进度与数据库实际消息 |
| 快照发布集合 | 指定snapshot revision/hash及其Source收录消息 |

不得假设一轮恒有两条消息。用户正文已保存但助手没有最终正文、迟到修订、打断等情况，实际集合可能为奇数。

### A2. 把ASR观察账本与成功回合账本分开

`observeASR`一收到本场final观察即保存有界证据；不等待整轮PASS后才记录。同question修订保留revision链，不直接拼接多个final成多个事实。以产品已封存的canonical消息及hash选择被保存版本；观察版本与持久化版本不能对应时明确UNRESOLVED，不猜测“取最后一条”一定正确。

隔离工具只读取产品已经存在的标识/摘要；需要桥接字段时限定DEBUG与LIVE_DEVICE_AUTOMATION，不向生产模型输入插入测试身份，也不将助手文本当用户事实。

内存有界；异常时落盘最小证据，不能为了日志每20ms重写整场全文。普通报告保留哈希、数量和脱敏身份；原始合成fixture继续单独保存，真实用户正文不批量导出。

## 3. B：统一主机与手机的来源证明

### B1. 先核对明确快照，再允许确认

建议统一版本化binding对象，至少绑定：run/launch、设备与构建、账号scope hash、session、productSession、snapshot revision/hash、Source、发布状态、已知结束水位/缺口、实际收录消息ID/sequence/role/content hash。

流程：

1. 手机发布本次恢复观察坐标及本地消息身份摘要。主机核对当前run/launch，而非接受任意同目录文件。
2. 只读服务器按相同账号、session、productSession、指定snapshot读取。若版本已变化则在既有等待预算内重新取得新坐标；不能随意拿“最新”Source配旧证明。
3. 校验账号、Source归属和快照哈希，再逐条比较手机封存消息、服务器消息、Source消息。数量相等不足以通过；角色错、重复ID、hash错、跨场消息均拒绝。
4. 完整发布要求结束水位及实际集合一致、无缺口；恢复部分发布则明确PARTIAL，按快照实际收录集合核验，未收录/缺失集合另列。不能为了通过把Source完整性检查删除，也不能以最高序号代替条数。
5. 手机再次核对binding的身份、revision、Source及本地账本后，才读取本场候选并执行既有独立新增保护。

本轮最小必修是现场的“completed=0、完整收录2条”场景。部分发布若现有元数据不足以证明收录集合，只做只读验收并标确认BLOCKED；不能自行扩业务协议或自动确认不明子集。

### B2. 有界重试、可辨错误

- 尚未发布或暂时网络不可达：GET-only，沿用既有deadline；不增加业务调用预算。
- 账号/Source/hash冲突：明确bindingMismatch等安全错误码，终止确认，不循环120秒掩盖同一稳定错误。
- 文件传输失败：只允许重传已核实且未过期的同一证明；本地存在文件不代表手机已收到。手机需匹配schema/run/launch/revision。
- 将`LiveDeviceLabError.check(code)`的安全code写入报告；不再仅写Swift类型名，不输出原始服务器正文/密钥。
- `confirmationPreparation`与`confirmationCommandSent`分别记账。业务请求尚未发送时标NOT_RUN，并附准备失败；发送后响应未知标UNKNOWN_WRITE，不自动重试。

## 4. C：事实与语音质量分别验收，避免挂住或假通过

### C1. 修复恢复事实集合的来源

恢复时从“本场已观察且被封存、并已被当前Source收录”的用户事实集合选择可核验项。不得直接使用`acceptedASRByTurn`，也不得仅将脚本中的全场requiredMemoryTerms逐字过滤后把剩余部分宣称完整覆盖。

每个预定义测试事实须分别记录：计划输入、是否实际输入、ASR是否正确、是否封存、是否收录、候选是否支持、是否确认/冷回查。未发送的第二轮不应要求出现在恢复候选；已发送但识别错的事实仍是语音准确性FAIL，不能默默从整体验收排除。

本场例如：周六读书可独立核对；“星桥/新桥”名称需要保留识别偏差。恢复可证明实际识别内容没有被丢弃，但不得因此称正确记住原计划专名。候选含错误关键事实时不自动确认整张主题卡；当前工具不应自动编辑或拆分卡片来凑正式记忆通过，记录BLOCKED即可。

### C2. 有界结束本轮的交互判定

把`asrContent/uiText/answerAudio/playbackDrain/listening`分项记录，给出各自首次证据及未满足原因。在当前question的有效final已与封存身份对应、真实回复及播放生命周期闭合后，核心事实仍不匹配则明确`asrFactMismatch`，按现有公共停止路径结束并观察收尾；不额外等待90秒希望错误文本自行变对。

若final尚可能修订或生命周期未闭合，则继续既有90秒上限，保留当前条件快照。不要凭一个临时final立即判错，也不新增固定睡眠或伪造完成事件。

### C3. 测试材料调整

新场仍明确“另一个独立场所，不是旧场所改名”。run/session/Source作为身份硬门禁，随机口述名称不能承担来源隔离职责。

优先选读音清楚的常见词及有区分的描述；名称需要辨字时，脚本主动提供释义或汉字说明。不得添加“星桥=新桥”的单例替换或泛化同音容忍。数字、空格归一化已有实现，避免重复修复不存在的问题。

修改合成材料后做真实TTS→火山ASR检查，保留每次结果；不得反复生成、试到一份成功再只报告成功。正式记忆准确性与传输正确性仍分开。

## 5. D：调度停顿先补测量，再决定实现改动

不将本次0.606秒直接归因于保存代码，也不先大改产品性能。

### D1. 最小有界诊断

测试模式记录环形时间点：计划帧deadline、调度到达、送帧开始/结束、帧类型（语音/静音）、输入ordinal及PCM偏移、实际样本数、队列深度、MainActor观察延迟。firstFailure冻结当时证据，另存此前已完成播放器proof，避免停止后计数归零使证据消失。

环形数据平时只在内存有界累积，按阶段或异常汇总；禁止每帧同步写盘。仅在可复現短时窗口采集线程耗时；先比较测试时钟/报告任务、SDK feed及已有保存/诊断成本，避免启用长时间原始控制台采集。

### D2. 实现选择的条件

- 先用单调时钟的目标deadline消除“处理耗时+相对sleep”累计漂移；保留单一生产者，不突发补发多帧假装没有间隔，不丢语音样本以追赶。
- 如证据显示主要是主线程竞争，才考虑独立串行时钟与预分配缓冲。**移动feed执行队列前必须核对锁定SDK文档/源码及Manager生命周期约束。** 当前bridge显式要求主线程，不能删MainActor/precondition就完成迁移。
- 无法证明SDK跨线程安全时保留正确调用线程，只改善已测得的工具开销并报告未决瓶颈；不把分离计时器但仍堵在主线程称为已解决。
- 停止/账号变化/engine释放须先停止生产并等在途调用结束；不允许旧operation或旧账号继续投喂，frame返回错误须保留。
- 保留0.5秒原检查和首错记录，不因本次超限就提高阈值。即使发生调度失败，也进入有界收尾观察；后续恢复PASS不发短场通行凭据。

如果测量指向产品保存或SDK缺陷，另列证据和小范围产品修复，再经讨论决定；本方案不预授权重写保存链。

### 6.1 非真机验收必须执行到实际主机路径

1. 在隔离副本保留旧版，用同一测试材料和断言取得R01/R04的修前红、修后绿；旧版失败不能来自fixture没启动。
2. Python单元负例可mock网络；但集成验收必须运行`recovery_binding`同一读取/校验函数，连接隔离API、默认Worker和真实PostgreSQL。允许注入安全的本地传输地址，禁止复制另一套宽松校验器。
3. Simulator实际Runtime/Controller用事件观察积累ASR账本，不能预填`accepted: texts`来证明R04；binding由真实主机验证器产生，不能测试代码直接写现成正确scene-binding绕过。
4. 执行候选可见→本场主题→确认→正式记忆→新进程只读回查，核对Source、fact集合和既有正式数据未变。
5. 模型受控返回必须明确标明；可注入正/负例和网络超时，不宣称是供应商现场行为。
6. 最终依赖变更后重新冻结，执行短A→逻辑20→短B→逻辑40；每次逻辑长场前独立短场，检查xcresult通过数、跳过原因、实际底层断言与源码指纹。

### 6.2 真实模型与真机阶段

本轮不执行。实施后按当轮授权开展，不能借用“模拟器通过”代替：

- 若只改工具，不需为本缺陷更改DeepSeek提示词或重跑无关所有模型分支。合成语音材料改动必须观察真实TTS/火山ASR；记忆闭环通过实际DeepSeek验证。
- 若实施扩至模型提示词/合同，按既有规则先给定合成材料、固定调用矩阵与预算，保留失败；不能只用fake返回验收。
- 新stage/build，旧工具指纹和short receipt失效。物理顺序仍短A→20分钟→短B→40分钟；不重用本次失败场或替换原结果。
- 短场至少两轮，第二轮补充第一轮；核心内容识别和显示、输入稳定、实际播放、逐条保存、待确认主题、确认及冷回查全部通过才可进入长场。
- 长场物理时长和输入数量依既定profile，不能压缩虚拟时钟。失败后先保留第一错误，再观察有界修复/补缺/发布；不重开场次制造替代成功。
- 剩余声学硬件环节单独记录，由用户主动安排，不能把STREAM测试当作麦克风/扬声器验收。

## 8. 交付与关闭标准

实施交付应包含：变更文件及原因、每项红绿原始产物、真实主机→手机证明合同、完整场与恢复场分项结果、准确的业务写次数、源码/工具/二进制指纹、四场复用或重跑依据、各环境NOT_RUN。

- 本地断言与四场全部满足，可记工具LOCAL_PASS；无手机不能阻塞本地交付。
- 现场短场完整闭环通过，才可说短场门禁通过。若仅恢复发布通过，维持整场FAIL。
- 物理20/40未运行或失败，持续保留对应状态。历史0.52/0.54秒及本次0.606秒具体耗时原因没有证据，不合并宣称找到统一首因。
- 原部署和记忆业务代码保留。没有新实现前，本方案状态始终DESIGN_ONLY / FIX_NOT_IMPLEMENTED。
