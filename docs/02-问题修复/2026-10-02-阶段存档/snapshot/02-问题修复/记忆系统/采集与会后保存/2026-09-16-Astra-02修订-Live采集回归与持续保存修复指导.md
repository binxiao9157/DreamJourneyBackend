## 3. ASR 解析和终态必须有显式证据

### 3.1 先纠正当前实现事实

[parseASRResult](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DialogEngineManager.swift:5156) 当前两处 `is_interim` 缺失使用 `?? true`，取反后是 isFinal=false；旧格式 definite 缺失默认 0。**当前不是“缺字段默认 final”。** 实际问题是 `(text,isFinal:Bool)` 抹去了“明确 interim”和“缺失/无效标志”的区别；新修复不能为了补 final 把默认值改成 false 或用事件名推断 final。

### 3.2 解析结果契约

用明确值类型表达解析结果，具体命名可调整，但至少包含：text、textSource、finalityEvidence（explicitFinal / explicitInterim / unknown / invalid）、evidenceSource（例如 resultsIsInterim / legacyDefinite / absent）、字段是否存在/有效。未知或无效数据允许保留为未定稿材料，不能成为完整 owner delivery。

| 输入证据 | 必须得到的结果 |
| --- | --- |
| results[0].text 非空且 JSON 布尔 is_interim=false | explicitFinal；合法身份下 owner.complete |
| 同结构 is_interim=true | explicitInterim；owner.interim |
| is_interim 不存在、null 或类型错误 | unknown/invalid；绝不 complete |
| is_interim 为字符串 "false"、数字 0/1 | 不能靠 Swift/NSNumber 桥接当作 JSON 布尔；按无效处理，除非另有明确版本化供应商合同 |
| 受支持的旧格式 definite 明确为合法整数 1 | explicitFinal；记录 legacyDefinite 来源 |
| 受支持旧格式 definite 明确为 0 | explicitInterim |
| definite 缺失、null、其他值或布尔值 | unknown/invalid；不得通过 `as? Int` 的宽松桥接默认接受 |
| extra.origin_text 作为兼容正文 | 只有与同一结果明确绑定的有效终态标志才能 final；不能因为有原文就 final |
| identifier-only ASRInfo，无正文 | 登记身份，不生成空 owner turn，不当识别失败，也不定稿 |
| ASREnded 但没有已收到的明确 final | 记录识别窗口结束和缺口，不把最后 interim 升格 |
| 元数据相互矛盾、正文/标志属于不同结果 | 明确冲突/未知，不猜最方便的值 |

保持现有受支持格式的兼容；不把任意 extractAnyText、LLM回答、UI完成、超时、下一问开始或关麦动作作为 owner final 证据。若兼容解析仍给 UI Bool，需要另保留 canonical 的证据类型，不能再次丢失 unknown。

## 4. 身份登记与不可变回调上下文

### 4.1 绑定单位

canonical owner 的业务身份至少由 account/vault/authority scope、productSession、provider engine/operation epoch、questionID 共同界定；assistant 另含其绑定 questionID 与 replyID。对外的 canonicalTurnID 可以使用有界稳定编码/散列，内部保存可验证字段。不能只靠拼接字符串后再从字符串猜作用域。

同一问题 interim/final/重复确认必须命中同一 ID；新的 question 即使正文相同也必须是另一条合法表达，不套旧的近似文本/短时间窗口去重。capturedAt 与 captureOrdinal 在首次有效正文登记时固定，后续 final 更新不重置。空的 identifier-only 登记也要能参与关闭边界，不伪造正文槽位。

### 4.2 现场格式的主路径

现场每问都是前置 identifier-only ASRInfo 带 questionID，后续 ASRResponse/ASREnded 不带 questionID。按该前置事件登记一个 ASR 接收窗口；在原始 provider 回调有序接收入口，解析并确定本条事件的身份/序号，随后冻结到事件上下文，再异步投递。

不可在 Echo main.async 执行时重新读取 `currentQuestionID` 或 active coordinator。现有 `enqueueProviderMessage`（DialogEngineManager.swift:4091）先异步投 main、`emitCanonicalTranscriptEvent`（:3900）再读当前 correlation，canonical event 又在 Echo 排队；新代码必须明确在哪个串行/锁保护入口完成登记、序号分配和冻结。

建议冻结结构至少带：captureSessionID/productSession、scope/lease 身份、provider epoch、question/reply identity、identitySource（payload / registeredWindow）、ingressOrdinal、eventType、finalityEvidence、首次捕获时间。该结构只为采集持久化提供来源，不授予过期账号新的写权限。

### 4.3 迟到、缺 ID 和无法区分的情况

| 情况 | 处理契约 |
| --- | --- |
| 当前登记 Q1 的无 ID ASRResponse | 在有序、唯一开放的 Q1 接收窗口内冻结 Q1；后续异步任务不得改成 Q2 |
| Q1 事件先接收/已冻结，主队列执行前 Q2 已登记 | 仍归 Q1；不触碰音频当前问题状态 |
| 显式携带已知 Q1 ID 的迟到 final，当前已是 Q2 | 只更新对应已登记 Q1；不把全局 currentQuestion 回滚；不能变成 Q2 final |
| 没有前置登记，也没有可验证问题 ID | 保留不可关联事件/缺口诊断，不猜 `turnSequence`，不建立完整 owner delivery |
| 新 epoch 或换场后旧回调 | 按冻结 epoch/scope 拒绝，不映射到新场 |
| 两个可能的接收窗口/矛盾问题身份 | ambiguous，保留缺口；不选“当前的那个”凑结果 |

必须修掉当前字符串 fallback `question-(providerTurnCorrelation.turnSequence)` / `reply-(providerTurnCorrelation.turnSequence)`；只补字符串插值仍不满足身份契约。

**信息边界：** SDK 若在 Q2 已登记之后才交付一条完全无 ID、无可验证边界的 Q1 迟到原始包，它可能与 Q2 正常包不可区分。冻结上下文能解决已接收事件的异步错配，不能创造原包没有的关联信息。依赖 SDK 的有序窗口约定必须明确写入实现/验收证据；存在可观察歧义时 fail closed，不能用相似文本、长度或固定延时声称消除了全部旧 Q 风险。不要把此问题交给音频打断 reducer 猜测。

## 5. canonical 定稿、去重与冲突契约

原生 owner.complete 的主入口是合法问题身份下的 explicitFinal ASR。QueryConfirmed 可以作为受验证协议下的补充确认来源，但不是必达事件、不是唯一门槛；不能重新要求它出现后才派送。

| 槽位现状 → 到达事件 | 存储/派送结果 |
| --- | --- |
| 新/已登记 owner + interim/unknown 正文 | 保留可修订内容，未定稿，不生成 delivery |
| interim + 合法 explicitFinal | 同 ID 更新为 complete；有序前缀允许时生成一次稳定 delivery |
| complete + 相同正文 final/Confirmed | 幂等 no-op：新增 canonical=0、delivery=0，不得因重复事件新增网络业务写；不阻断既有可靠未曝光队列的合法首次派送 |
| complete + 迟到 interim/unknown，无论正文是否不同 | 不降级、不覆盖、不新增记录；记录 staleNonFinalIgnored；不是新的 owner 表达 |
| complete + 不同正文 final/Confirmed | 显式 immutableFinalConflict；不覆盖已 seal/已 ACK 内容、不另起第二个 owner；保留原身份与冲突诊断供恢复/人工核实 |
| 已 seal/已 ACK + 相同 final | 仍幂等，ACK 后保留的 canonical 元数据继续生效 |
| 新 Q 与旧 Q 正文恰好相同 | 两个身份两条表达，不能用正文去重跨问题合并 |

“相同正文”使用已声明、前后一致的确定性规范化（如现有首尾空白裁剪）；不得使用语义相似度、前缀相似或近似词过滤。第一次封存后的正文与稳定命令不可被后续事件静默改写。

每条冲突/无法关联必须被作为具体回合的质量/覆盖问题保留，不能因一次 canonicalTurnConflict 把整场后续合法采集静默关掉；也不能忽略冲突却声称全场完整。已远端确认的内容不能通过本地覆盖“撤销”，本轮不引入自动业务纠正写。若现有 schema 不能表达该状态，以兼容的本地 gap/conflict 记录补足，版本迁移必须保留旧 outbox/checkpoint。

## 6. assistant 文本与音频保持分离

assistant 按已绑定 reply 聚合一次；句子开始/结束只更新同一 reply 文本，不作为整答 completed，不再次调用旧 native captureLiveAssistantTurn 形成双写。

文本 completed 由已验证的 Chat/TTS 文本流终态决定，和播放器 drained/用户听完是两个字段。播放中断不能改写已确定的完整文本；文字还未完成则只保留已收到内容并标 partial/gap。禁止按屏幕翻页、字数、固定等待、isAISpeaking=false 或一次 PlayerFinish 来定稿 owner 或 assistant。

保留 assistant 仅为 context 的现有 B7 语义；不能把它转换成 owner 证据。不修改 SDK 内置播放器控制、已有长答播放/主动打断规则来使存储测试通过。

| 传输类型差异 | Backend `11717/11833` start/append 为普通 Result，未传 exposure tracker，未显式禁止共用 transport 的刷新重发；`11773/11889` end/ack 已有 typed outcome、tracker、allowsRefresh=false。 | “start/append 已 typed”不成立。`requestJSON` 默认 allowsRefresh=true（16090），其 401 分支可递归同 method/payload；恢复派送前应补窄范围写保护。 |

当前 `OwnerTruthLiveDeliveryStatus` 已有 `startInterviewSession/endInterviewSession` operation、commandIDHash、thread/session、resultState（Contracts:9560）；现只有 end 的 `confirms/confirmedEndedReceipt` helper（9780/9799）。新增 start 原命令匹配应优先复用这个现有只读合同；不得为绕过缺 receipt 改成新建 start。


### 7.2 先固定本场采集权与派送状态

本场用户主动开启 Live 的采集同意、原 subject/vault/authority、productSession、provider epoch、关闭边界保持不变。正常同场 canonical 先落受保护磁盘，不因请求授权快照过期或临时断网停止落盘；UI 真实说明“本机已保存，待同步”。

这不是永久授权。用户关场/撤销、真实新策略明确 deny、原账号/authority 失效、录音或存储边界变化，按既有冻结语义停止新增材料并显示原因。单纯 TTL 过期与权威 deny 必须分开，禁止把 deny 当可重试的网络过期。不得把旧 FeatureDecision 延期或视为本地采集同意。

为原场每个业务命令记录明确的 dispatch 状态；“存在 queuedTurn”本身不能说明它是否已暴露网络：

| 状态 | 可做动作 |
|---|---|
| durable prepared，且有可靠未曝光证明 | 新鲜请求授权和原用户意图仍有效时，发送**原命令**一次。 |
| mayExpose / outcomeUnknown | 仅按原坐标只读核实，当前执行器禁止重发 POST。 |
| committedMatch | 持久记录原命令已确认，前移对应水位；才能考虑下一条确知尚未发送的队尾。 |
| serverRejected | 保留拒绝原因及原命令，按明确合同处理；不能统一等价为未发出，也不能自动刷新到允许为止。 |
| bindingMismatch / decode-invalid after exposure / unresolved scope | 保持 unknown 或冲突阻断；不得新建 ID、跳序、搬账号或清队列。 |

旧 V1/V2 记录缺少可靠曝光信息时采用保守 unknown，不反向补写为 notSent。不能用此轮本地修复自动补发历史记录；本轮也不实现旧设计里的“新用户恢复意图后重放未知 start/append”分支。

### 7.3 为 Live start/append 补 typed 传输与 durable 原命令

限定在 Live natural-input 的 start/append 路径，采用既有 `OwnerTruthInterviewWriteTransportOutcome` 与 exposure tracker 的模式，保持通用文字/其他业务调用合同可兼容；不要全局重写 requestJSON 或关闭整个 App 的认证恢复。

1. start 在 task 可创建/恢复前，原子保存原 commandID、threadID、sessionID、productSessionID、entryMode、scope 和可验证的 payload 语义。append 保存已有稳定 delivery 身份、内容/时间/角色/序号与实际 attempt 的 CAS；不得每次 prepare 再造 commandID。
2. 增加与原命令绑定的发送 attempt 记录。task.resume 可能执行之前先持久标 mayExpose；持久化失败零网络曝光。这个标记应保守，不因后来取消就自动倒退成 notSent。
3. 使用真实 transport 生命周期分类 notSent/outcomeUnknown/serverRejected/committed，而不是从 `Error` 类型、日志缺失或是否拿到回执猜。任务已创建但未 resume 是否能证明未曝光，须依真实库合同；不能凭主观认为“刚取消应该没发”。
4. Live typed start/append 的业务 POST 显式禁用 transport 内部自动刷新再发；认证/策略准备放在首次曝光前的有界过程。已曝光 401/5xx/断连/解码失败按 typed 分类，不能递归重发同一 POST 当恢复查询。
5. 回调提交必须绑定原 scope、command、attempt/generation 和 receipt。单纯旧 UI route 到期不应抹掉可绑定的已提交回执；真正账号/scope 失效不能把回执提交到新账号，原命令保留 unknown/待核实。不要让共用 `canCommit` 在写后根据旧 route 将它改成“未发送”。
6. prepared/结果/checkpoint 保存失败均需明确阻断。只有可靠 committed 可以清待发送正文，canonical 去重元数据与不可变 command 身份按既有规则保留。

已有 append CAS 例外只按已核实服务端合同使用：attempt 的乐观版本可按明确规则重取，原 command/message/sequence/role/text/capturedAt 语义不能变。start/end/ack/admit 不继承该例外，本次也不靠改 expectedVersion 解冲突。

### 7.4 再贯通新的请求授权，不刷新全局旧 route

1. 在本场 dispatcher 增加局部、单飞的 request-authority 准备流程，键绑定原 scope/productSession/当前原命令/attempt。异步等待期间不换场、不换账号 lease。
2. 从当前权威 policy 捕获新的 `.request` decision；可用则继续。只有真正可恢复的 policy 缺失/TTL 等原因允许一次有界 refresh，完成后重新检查原 scope 与当前 policy 并捕获新 decision。建议每个准备意图最长 15 秒、最多 1 次 refresh、同场并发 1；clock 注入便于验证。超时后旧完成失效。真实 deny、authority/账号变化直接阻断，不能无限循环刷新。同一失败条件下 ASR 新回调不能不断创建新准备意图；只在既定网络恢复、权威 policy 快照变化或用户明确同场继续等有效触发时再开有界意图。
3. 新鲜 FeatureDecision 作为这次 attempt 的显式输入传到实际 transport；下层只验证这份 decision 的 scope/版本/期限，不能再调用 naturalInputTransport 去拿旧 route 将其覆盖。
4. 同一授权过程覆盖 Live 初始 current/start、逐条 append、已请求关闭后的 end，以及承接该场 ended 的 inbox/ack 发前接缝。各业务阶段仍有自己的请求/命令身份；不能把一个 decision 永久跨 20 分钟沿用。
5. 已修的 B8 admission authority 和 B8-S01 status reader 各按本来的阶段合同消费。不要把 live 写授权复用成候选审核/正式入库权限，也不要改全局 FeatureGateEvaluator 的 captured expiry/deny 语义。
6. 用户手动关闭只冻结已接受场次和 N；TTL 到期不能触发提前 end。队列中只派送最小可发送 sequence，同场只有一个业务写 in-flight；ASR 高频事件只唤醒 dispatcher，不各自开启 refresh。

仅做第 2 步“refreshPolicy 成功”不算修好；测试必须证明实际 POST 收到的授权就是新 decision，且下层没回退到旧 route。

### 7.5 只读命中与未命中必须分开

append unknown 的 GET 需要按原 productSession、session、scope、sequence、messageID、commandIDHash、role、capturedAt、规范化 contentHash 精确匹配。命中只能确认这些原项，不能把未返回的队尾整体当作已保存或未发送。

把队列分为已确认、unknown、可靠 prepared/notExposed。只有原 in-flight 已确认且前缀连续时，后面的 prepared 项才可按当前有效采集/结束意图继续首次发送。当前实现“只要剩队列就全部 statusUnknown”的保守暂停可避免重放，但不能证明持续派送恢复；修改时应依据新持久状态逐项判断，不能简单删除该 guard。

GET 缺项、404、暂未观察到、部分窗口、超时或丢响应均不证明未曝光，保持原 unknown。只读恢复没有发 POST 的权力；恢复 start/append/end/ack/admit 时尤其不得以“读不到，所以重新来一遍”分支代替。

### 7.6 start 未知而还没有 bound receipt

start 的 prepared command 本身已有原 thread/session/product 坐标。未知时按该持久坐标调用现有精确只读状态路径，不依赖尚不存在的 `lastBoundNaturalInputReceipt`；原作用域仍要通过校验。

只有现有 status 的 start operation 与原 command hash、thread、session、product、scope 匹配，并满足明确 lifecycle/boundary 合同，才可确认该 start 已提交并恢复本场下一步。别的 active session、裸 current 命中或仅存在同名 product 不足以替代原 command 绑定。

原 start 没有可靠准备记录、status 不能找到对应 operation、scope/authority 无法安全确定、状态窗口不够、GET失败，均明确显示“无法核实，原记录保留”并停止派送。**禁止生成新的 start command/session，也不能把 current 查询为 nil 当作未知 start 未发送的证明。** 若现有 read contract 无法完成精确匹配，本轮报告该能力 BLOCKED，不擅自扩后端或伪造 receipt。

## 8. 停止时冻结、排空、封存水位

停止是一个与 provider ingress 同步排序的边界，不能等同于把全部回调立刻视为过期：

1. 用户停止时原子冻结 capture scope/productSession/epoch、已登记问题/回复成员和最后已接收 ingressOrdinal，立即进入本场“正在保存”状态；麦克风/播放及时停止，不为等 final 延长录音。
2. 将冻结边界内的首次 Store 槽位登记排在同一持久化队列的 closeIntent 之前；或者用版本化的 durable 关闭成员清单表达资格。现有 Store 在 closeIntent 后禁止新 ID，不能把停止前已接收但尚未落槽位的合法事件误判成新事件。
3. 持久化 closeIntent，N 可以未知。依冻结成员/epoch 将已接收有效事件交给 retained closing capture sink，而非要求当前仍有 activeVoiceInteractionToken、Live=true 或 active coordinator 指针。
4. 严格区分“UI/音频已停”与“已验证来源的采集事件排空”；只有已登记身份及有效账户作用域可补终态。不能全局取消回调租约检查，也不能复活已撤销账户授权。停止后新问题、跨场及旧 epoch 均拒绝。
5. 完成持久化 barrier；没有 gap/conflict、没有待写、所有被冻结成员已作明确终态决策后，再冻结正常 clientSequence 水位 N。接收序号/turnSequence/槽位数量不是 N。
6. 首 gap 不得跳过。保留连续前缀封存，未定稿达到有界截止后保留 partial/gap 与清楚状态；固定延时不等于获得权威 final。已有不可关联/未定稿材料时不能因为 owner=0 就显示空场。
7. 交付仍调用当前 B8/B8-S01 链。发送结果未知时保存原坐标，只读核实；不重建 command、重放未知 POST、清理待恢复记录或自动开麦。重建只恢复 durable capture/close 状态，不恢复语音采集。

## 9. 同场停止后的局部 UI 修复

当前 onDialogEnded 的手动结束分支先 finish capture、再 resetToIdle；coverageGap renderer 与 idle renderer 操作同一个 voiceStatus，idle 会隐藏它；相同 coverageGap 再赋值被状态去重压掉。修复本场状态投影，不能依赖回调碰巧先后再补写 label。

mic 可以回到可开始状态，同时保留当前关闭场次的 saving/queued/organizing/gap/unknown 状态。idle 分支不得无条件清空已有本场关闭结果；同一状态重复渲染也应稳定可见。仅在精确绑定本场原 session/batch 的权威只读状态确认 `reviewReady`（按现有状态合同）时显示进入待确认；单个 start/append/end/ack/admit 写入成功回执不作此证明。日志 `coverageGapPresented` 不是用户可见性的证明。

这里不实现历史多个 coordinator 的全局优先级、候选页返回或前后台历史状态仲裁；若被这些问题挡住，要独立记录为第 3 项，不扩范围。

## 11. 持续派送门禁：注入 clock 跨 TTL 并推进至逻辑 20 分钟


实施时仅使用合成事件/假网络/隔离磁盘和现有真实授权 evaluator/真实 UseCase/transport 代码接缝。不要新开真实场次；不要通过 `naturalInputPolicyAvailable={true}` 跳过待测 gate。没有执行的门禁保留 NOT_RUN。

| 门禁 | 输入与注入点 | 必须断言 |
|---|---|---|
| TTL-L01 | 真实原 route 在 t=0允许；clock 推到 t=301s；当前 fresh policy 已允许 | 原 route 仍拒绝；本场请求取得新 decision；真实 transport 消费它；原 scene/product 不变。 |
| TTL-L02 | t=301s 当前 policy 也过期；并发 10 次 ASR/唤醒 | 一次有界 policy refresh、一个派送单飞；刷新成功继续可靠 notExposed 原命令；失败保留本地队列，不循环刷新。 |
| TTL-L03 | t=301s 成功刷新为明确 deny | 新增采集按既定真实边界冻结并提示；零业务 POST；旧文件保留；不得再次刷新直到允许。 |
| TTL-L04 | 时钟分段推进至 20 分钟，期间多次 TTL 到期和短暂断网 | 同场全部合法 complete 持续落盘，按原序列有界恢复首次派送；未提前 end；最终关麦才固定 N。逻辑20分钟通过不能标真机20分钟 PASS。 |
| TTL-L05 | 原命令 durable prepared，preflight拒绝/持久 mayExpose 前取消 | 可证明 notSent；同意图仍有效且新权限允许后原 command 仅首次曝光一次；不重造ID。 |
| TTL-L06 | append 已曝光，服务器已提交但回执丢失；GET精确命中 | append原命令网络曝光次数仍为1；持久committed并清对应项；其后可靠未发送队尾可各送一次。 |
| TTL-L07 | append已曝光，GET missing/404/timeout/部分响应；原POST随后才提交 | 原命令保持unknown，零重发；不跳序，不新建命令，不把missing当notSent。 |
| TTL-L08 | start已曝光但无回执、没有boundReceipt | 从原prepared session/product读取；精确start-operation命中才绑定；未命中或读失败保持阻断，start POST不增加。 |
| TTL-L09 | start普通成功回执到达时旧route刚过期；另测append同情况 | 可绑定receipt不会被旧route判成未发送；真正scope失效仍隔离；不可借此给新账号提交。 |
| TTL-L10 | 关麦时echo权限过期，end/ack随后也跨TTL | close/N先持久；end/ack阶段贯通各自新decision且原command不变；admit/status承接已独立验收代码；unknown仍零重放。 |

| TTL-L12 | 账号/vault/authority变化、旧policy刷新或写回调迟到、重启缺曝光旧记录 | 不换lease续写、不跨场搬数据；旧材料保留且unknown保守；不自动恢复历史POST。 |

这些门禁与 ASR final→canonical→真实 Outbox 的装配门禁必须连接：不能下游永远手工构造 `.complete`，上游 gate 永远 mock true，然后把各自局部绿拼成20分钟持续采集通过。
