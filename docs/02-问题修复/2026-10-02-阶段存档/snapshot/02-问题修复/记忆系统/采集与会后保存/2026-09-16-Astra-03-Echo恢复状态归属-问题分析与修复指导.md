## 3. 可以重复验证的竞争机制

设 W-A 最终为 `actionRequired`，W-B 最终为 `pendingReview`；两者属于同一个有效账号。现有代码可以形成：

| 回调次序 | 最终状态区 | active 恢复指针 | 最终复用按钮 |
|---|---|---|---|
| A checking → B checking → A actionRequired → B pendingReview | B 的 pendingReview | A | 核实 A |
| A checking → A actionRequired → B checking → B pendingReview | B 的 pendingReview | nil | 新文字入口 |
| B checking → B pendingReview → A checking → A actionRequired | A 的 actionRequired | A | 核实 A |

这里没有任何业务状态改变，只有回调顺序改变。第一行还证明状态文案与核实按钮可同时指向两场；第二行说明指针清空也不能代表所有历史任务都已终结。这是多源对同一 UI 的逻辑竞争，不需要假设 Swift 数据竞争或服务端发生倒退。

它与已恢复原任务输出中的两向 UI 变化相符，但合成反例不能补出原 UI 日志缺失的场次、按钮归属和生命周期身份。不要宣称“切到微信修复了服务端状态”。

## 4. 修复目标和明确范围

本项交付是**展示状态及交互入口的归属修复**：同一已选场次的状态、文案、核实动作必须来自同一份展示快照。导航/通知/回调到达顺序不能改变选择。历史任务不能夺走有权限的新文字入口。

可改：Echo 控制器的展示仲裁、订阅/可见代次、恢复读取触发合并；本地只读展示 metadata；独立按钮与 UI 测试入口；隐私安全诊断；必要的纯函数展示 selector / reducer。

不可借本项改：B8 原 command/receipt/unknown 写恢复规则；Live canonical 采集/去重/封存/close/end 业务算法；服务端提取/审核/入库；SDK 语音协议/音频路由；历史任务的数据删除或静默迁移清理。不得为了恢复按钮重新 POST end/ack/admit/start/append。

## 5. 建议实现：每场缓存、一个展示所有者、一次原子渲染

### 5.1 分开 workflow 状态与页面展示

引入窄范围 `EchoMemoryPresentationStore` 或等价 reducer；不要求新建通用全局状态管理框架。所有变化在 MainActor / 主队列串行归约。

每场缓存 key 至少为 `(subject, vault, authorityEpoch, productSessionID)`；内部保留原始稳定身份，日志只用安全关联。条目包含：业务观察 state / blockedReason、planRevision、coordinatorIdentity、单调 observationRevision、本地场次时间及来源、读取 fresh/checking/stale 标志、可执行只读 action。不能仅缓存一段字符串。

`blockedRecords` 也是缓存条目；缺关闭 checkpoint、未封存、格式无法验证等，不等于 empty/pendingReview。绑定不可信的材料不合并、不读取其他场次句柄；用“另有未能核实的历史记录”独立表达，不能假造身份和时间。

completion terminal 可以解除轮询订阅、释放临时对象，但应保留对应展示快照和持久原记录；不能把“移除 observer”写成“删除 workflow”。缓存也是观察值，不得生成本地候选/正式记忆。

### 5.2 稳定选择，不按成功状态或最后回调选择

1. 用户当前新开的 Live/文字交互拥有主交互区。它结束后，本次 productSessionID 继续作为会后状态的明确 owner，即使只有 blocked/unsealed 状态。
2. 用户明确选择查看的历史场次按原 ID 固定；候选页返回不以“最后收到哪个结果”重新选择。用户启动新会话才显式转移当前交互归属；两种动作都必须在本地记录选择原因。
3. 冷启动且无本次交互/有效显式选择时，对可信的全部本地场次投影选择最近一场。优先使用已有 outbox 的创建时间，缺失时用 checkpoint/follow-up 的可信场次记录创建时间并标明来源；同时间用稳定 key 作确定性 tie-break。不要用回调时间、lastRecoveryObservation 或轮询产生的更新时间排序。
4. 时间缺失或无法比较的历史材料单独标“时间未知”，不伪称“最近”；不能因此把有可靠时间的最新失败场次从候选集合排除。状态 `.pendingReview` 不获得优先权；`.actionRequired` 也不获得全局阻断权。
5. 同一显示期间选择保持稳定。服务器真实的新观察只更新被选条目的 state/freshness，不自动跳到另一条。需要显示其他历史情况时使用明确的历史状态入口或简短次要提示，不在主状态区轮播多个任务。

展示用用户可读的场次时间/“本次对话”标签区分；不要把 UUID、hash 或端点名显示给用户。显式选择若跨控制器重建/冷启动保存，只保存账号隔离的选择 metadata，验证场次仍存在且绑定有效；不得改 workflow 业务记录或把选择当作写恢复授权。

### 5.3 UI generation 与请求 generation 分工

保留 coordinator 已有 requestID/generation/account commit 验证。另建立 controller 的 `presentationGeneration`：离开页面、进入后台、账号/authority 变化时先失效旧 UI 权；重新可见时只建立一个新的可见代次。

每个 UI 订阅持有 `presentationGeneration + scope + coordinatorIdentity + planRevision`，事件带 `workflowKey + observationRevision`。在更新缓存和 UI 时分别验证：

- 请求/账号/plan 已失效：不进入当前缓存或 UI；不得根据迟到内容重建指针。
- 当前 workflow 的有效业务观察可以保存在它自己的缓存；旧页面订阅提交无权直接 render。新页面读取缓存/当前 coordinator 快照后按本页代次提交。
- 旧 observationRevision 不可覆盖较新的同场观察；页面隐藏时不执行 UI commit；旧 UI 代次的排队 closure 不可跨后台/导航边界提交。
- 渲染只能由一个入口拿当前已选 owner 的完整 `PresentationSnapshot` 原子更新文案、核实按钮、动作绑定和新文字入口状态。任何单场回调不得直接 render 或设置全局 active 指针。
- 当前 capture 的状态也走同一个 owner 仲裁，仅调整其展示接缝。Live/文字交互期间，历史观察更新缓存不能改当前交互提示、键盘入口或当前会后场次。

新订阅已 terminal 的 coordinator 时保留缓存观察和明确“正在核实”标志；仍按 B6 在真实重入时做一次新鲜只读验证。不要以 `.discovered/.checking` 覆盖最后确定观察，也不要把旧缓存冒充刚成功 GET。测试应同时断言观察值和 freshness。

### 5.4 独立核实按钮与文字入口

保留原文字入口的独立 accessibility ID、权限判断和正常用户点击入口；历史恢复状态不再参与它的可见性/点击分发优先级。新增/独立的历史状态操作只绑定当前选中的 workflow snapshot。

文字入口可用前提仍是当前账号/FeatureGate/交互状态允许；本项不是绕过真实权限拒绝。允许新文字交互时，它必须创建属于新显式用户意图的新 productSessionID，不能复用未知历史 workflow 的命令、outbox 或关闭序列。

历史核实操作只做 GET；按钮文案说明它是“核实状态”。`actionRequired` 如需业务继续，展示真实原因和“暂不处理/开始新文字”的出口；本项不得把核实自动升级成继续整理，也不得先 POST 再通过 GET 宣称安全。用户点击历史核实不等于授权未知业务写。

## 6. 读取触发与有界单飞

已存在的正面约束必须保留：`start/verifyStatus` 拒绝 activeRequestID 非空的新请求；receive 校验 requestID/generation；后台 suspend 取消；每轮 deadline / GET 上限及跨发现 batch 的同一 context 预算。

需要新增的是**触发意图的合并和明确归属**，不是根据日志 generation 增加就重写整个网络层。将 viewDidAppear、foreground、didBecomeActive、readiness、policy-refresh-completion 收敛到同一页面刷新入口；事件附 triggerReason，不能由每个入口各自对全部历史 coordinator `startsNewRound: true`。

建议最小规则：

| 情况 | 规则 |
|---|---|
| 同一可见/激活周期的多个自动通知 | 使用相同 refreshIntentID；相同 workflow+plan 的 in-flight 直接复用。任务即使很快完成，也不能在同一个 intent 下因第二个通知又开新轮。 |
| 真正离开后再进入 / 下一次前台激活 | 可建立一个新的有界只读刷新意图；缓存先展示并标明核实中。不要通过 subscriptionEpoch 自增次数定义用户新意图。 |
| 被选场次 | 一次自动刷新意图最多打开该场一个 round，保留不超过 30 秒、资源 GET 不超过 6 的既有限制；handle discovery 与 status 继续共享总预算，policy/auth/runtime 沿用已实现的次数约束。 |
| 未选历史场次 | 可以扫描其本地记录、维护缓存；本页不因为每次通知自动为所有历史条目启动远端轮询。已经合法发出的只读结果可完成到自己的缓存，禁止抢占 UI。若另有独立 owner 的恢复读取，不由本页重复启动。 |
| 用户连续点击核实 | 同场正在读取时 join/禁用；不能累积无界 trailing 队列。超时或终态后的新显式点击可发起新有界读意图，不允许转成写。 |
| plan/账号/展示选择变化 | 旧请求 owner 失效或取消；旧完成只释放自己的 in-flight，不能清掉新任务的锁或覆盖其 cache。选择改变后读新场必须与新 snapshot 绑定。 |

如当前完整读取层还需要屏幕级并发/总量上限，先给出 source-backed 计数再加最小限制。本项必须用测试证明同一自动 intent 的 read round 数和资源请求计数；不要仅断言日志 generation “看起来少了”。

## 7. 最小诊断与隐私

原 `uiCommitted` 缺场次归属，不能用于证明跨 workflow 正确。补充安全结构事件：`presentationSelected`、`recoveryTriggerCoalesced`、`observationCached`、`presentationCommitAccepted/Rejected`、`verifyTapped`、`textEntryTapped`。

字段限：processRun 的安全关联、pageGeneration、refreshIntent 安全关联、workflow/selectedWorkflow 安全关联、planRevision 安全关联、coordinator/request 安全关联、observationRevision、triggerReason、state、freshness、rejectionReason、textEntryEnabled、GET/round计数。HTTP 层只记录路由类别、方法、safe code，不记录完整 URL。

不输出原始账号、会话、batch、command、设备标识、token、文字、语音、正文 hash 或错误 message；日志即使已有隐私问题也不能原样复制进验收文档。对本项只输出 W-A/W-B 这种合成别名或经现有诊断组件处理的关联字段。

“无自动业务写”在专用网络 spy/隔离端到端计数中分别覆盖 start、append、end、ack、admit、候选审核/正式记忆等业务写。policy/auth 刷新可能是控制面请求，需独立计数，不能将它混称业务写或把它藏掉。无请求不等于新文字可用；新文字可用要另验显式入口。

## 9. 单项交付与停点
