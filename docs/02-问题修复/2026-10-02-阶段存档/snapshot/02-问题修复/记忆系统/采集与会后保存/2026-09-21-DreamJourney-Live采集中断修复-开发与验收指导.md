## 1. 目标、事实与交付边界

### 1.1 本轮必须交付什么

修复真实存在的采集中断：正常 SDK 重复事件、合法终稿修订、Chat/TTS 交错不能让 Live 在仍然有声音时停止保存后续对话。正常短场、密集长场必须持续落盘，停止后完成原有 end → ACK → admit → 待确认候选链，审核后进入正式记忆。

不能以“异常后不崩溃”“改了文案”“增加一个状态”“所有长场统一变成 partial”作为完成。不可无歧义解决的真实冲突和真实磁盘故障必须有诚实的降级；这与正常事件最终完成保存是两套验收。

本轮开发范围以 iOS 记忆事件适配、持久化、采集生命周期、停止交接和关键诊断为主。已有后端分批整理、证据校验、合并纠正撤回和正式记忆合同保持。不得用调大 DeepSeek 参数代替修复客户端断链。

### 1.2 不能改写的现场结论

- 用户完成 33 个回合，OwnerTruth Outbox 和服务器均只有前 13 用户回合 / 26 条消息；队列为空，没有 close intent 或 end。
- 后半场仍有火山 SDK 回调；首批 DeepSeek 组织与支持复核成功。
- 本地已复现“单条 canonical 终稿冲突 → unavailable → Controller 移除采集入口 → 后续回合和停止交接丢失”。
- 首次现场错误窗口被日志覆盖，**尚未唯一证明来自哪条 ASR/TTS 回调或某次磁盘错误**。开发可据已复现缺陷推进，不必等待重做真机；报告不得虚构唯一现场触发。
- 不能保证手机所有其它存储里都没有后半场内容。旧 ConversationMemoryManager 不是完整兜底，也不能自动导入本场。

## 4. D1：生产与测试共用记忆事件适配器

### 4.1 共享生产逻辑，保留音频路径

从 DialogEngineManager 中抽出一个平台无关的记忆事件适配组件。原生 `handleProviderMessage` 和本地测试都调用同一生产 dispatcher/组件。组件负责身份归属、观察版本、封存边界和记忆事件输出，**不控制播放**。

原生 SDK 薄桥只转换 enum/raw code 和 payload envelope。不能在 Simulator 重新手写一套 TTS 拼接或 final 判断，再把它的绿测称为原生分派通过。至少覆盖 SDK 3012、3013、3014、3021、3008、3009、3011、3015、3016；按当前 header 明确核对数字，不混用 WebSocket API 的事件编号。

必须提交生产调用图和原生编译证据，证明实际回调接入共享组件，旧记忆提交路径已去重。普通音频分支照常执行；不能为隔离记忆来源而跳过原有音频 delegate、租约、打断或状态更新。

### 4.2 原始入口冻结与排空

每个被接受的观察包和结束边界，在原始回调入口冻结：账号/租约、productSession、engine generation、question/reply 身份、角色、来源、严格 final 证据、callbackOrdinal、观察 ID。

不能到主线程执行时才取 currentQuestionID；不以 capturedAt 排序替代入口顺序。无 questionID 的合法 ASR 包只能使用入口当时已绑定的 ASR 窗口；身份有歧义则隔离，不猜给下一轮。ASREnded 无正文，不得凭它制造用户正文。

当前 `reservedCanonicalHandoffIDs` 只覆盖首次 member，不能代表同 member 的多份 final 和 boundary 均已处理。必须按每个已接受观察/边界跟踪排空，停止冻结 ingress watermark。观察完成是“成功落盘或明确登记失败/缺口”，不能仅表示异步任务已入队。

### 4.3 用户输入来源规则

| 情形 | 必须行为 |
|---|---|
| ASRInfo / 合法 ASR 身份 | 登记同一 question 的 member；非 ASR、普通音频事件不能制造用户 member。 |
| interim / 未知 final 证据 | 保存观察正文和准确证据；不得生成已封存 delivery。非法类型保持非法，不能宽松转换为 true/false。 |
| explicit final | 保存可信 final 观察；**不降回 interim**，也不立即等同于不可变投递。 |
| 同来源、同 question，封存前合法 final 版本更新 | 按冻结序号选择最新可信完整快照，保留先前版本来源和必要证据。允许真实识别修订，不能 first-wins。 |
| ASREnded | 在该身份此前已接受观察排空后封存已取得的最新可信 final；本事件本身不是正文或落盘回执。 |
| final 已有，但缺 ASREnded | 可靠的下一 question 边界或用户停止排空屏障可封存已有 final；不能无限等待不存在的结束事件。 |
| final 的原始入口早于 ASREnded，但主线程执行晚 | 以入口序号和交接屏障纳入该 final，再封存；不能按主线程执行顺序丢尾段。 |
| ASREnded 的原始入口确实早于 final | 没有 final 时只持久化 boundarySeen，不立即伪造 complete 或认定永久缺口。同一尚未封存 member 后来收到严格 final，且身份及入口准入有效时才封存。已封存正文不得重新打开。 |
| 只有 interim 时停止 | 保留既有 partial 行为，不能自动补成 final。 |
| QueryConfirmed | 仅确认可绑定的本地文本输入请求，正文来自该已登记文本请求；不能将任意 ack 中猜取的字段当作语音第二份权威终稿。 |
| 无对应文本请求的 QueryConfirmed | 不改写 voice 正文，不创建语音回合，记录受控原因；后续合法回合继续。 |

“合法 final 版本更新”必须满足同账号/场/generation/question/角色、同一已选来源、已支持的完整快照 payload 合同、入口序号递增且尚未封存。它是一次输入的识别版本，不是把任何两个不同事实都按最后一个覆盖。不同分段、无法判断累计/增量的 payload、冲突身份不能套用此规则。保留多版本观察，并以 typed issue 处理无法确定的情形。

跨下一 question 才收到旧 question 的 final 时，只能依靠包内明确旧身份及仍未封存的已登记 member 完成交接；不得把无 ID 的迟到包猜回旧 question，也不得改写已封存正文。停止后则严格遵守已冻结观察清单，水位外新收到的 final 不得偷偷加入已结束场。上述顺序分别测试，不混称为“迟到都允许”。

跨 question 的用户真实补充、纠正、撤回仍是不同回合，全部保存，交由已通过的后端跨批语义处理；客户端不得靠相似度提前去重。

### 4.4 助手正文只选一条记忆来源

在 reply 所属的模式确定记忆正文来源，禁止“哪个事件先到用哪个”。

- 当前 provider 原生 Chat 模式：ChatResponse/ChatEnded 为记忆正文来源。TTS 句段及 TTSEnded 不再向同一记忆缓冲追加正文或第二次提交 complete；它们的播放行为保持。
- 只有确实存在、可从配置确定的 TTS-only 模式才使用独立 TTS 记忆流；不能因 Chat 暂时迟到临时改成 TTS-only。没有该模式则不新增它。
- ChatEnded 全文已形成后，再到 TTS 第一/第二句，结果必须仍是原全文，不能变成全文加已朗读的中间句。
- Chat/TTS 的先后互换、句段重发、不同 reply 交错不能改变已选来源或串正文。
- 单一合法来源完成后不等待另一条非必需来源。缺必要正文/终止证据则保留局部缺口，不能伪造内容或因等 TTS 延时关掉整场。
- 原生、腾讯/委托回答模式分别沿其已有合法记忆来源；不得改变 answerAuthority 或音频路由来绕过测试。

## 5. D2：持久化观察、封存与冲突处理

### 5.1 在创建 delivery 前拆开语义

当前 `upsertCanonicalTurn` 会立即 `flushCompletedCanonicalPrefix` 并分配 deliveryMessageID。必须在这个动作之前分开“观察 final”和“封存 canonical”。仅放松字符串比较会破坏已冻结命令，禁止这样修。

推荐在当前账号/场次 Outbox 的原子保存单元中增加向后兼容的观察、封存与 issue 字段；可以使用独立类型，但必须保持原子一致性。至少能重建：

- identity / role / source policy / 入口序号；
- 当前观察正文、严格 final 证据、可信 final 版本、选中版本与选择依据；
- seal status / boundary / sealed observation ID；
- unresolved capture issues、受影响 ordinal、最后成功持久化水位；
- close intent 与停止 ingress watermark；
- 已有 delivery、命令、曝光状态和确认状态。

未封存观察应在磁盘上，但不分配可曝光 delivery。封存与生成 canonical/delivery 必须原子且幂等；崩溃重建不能重新分配不同命令。已有持久化 complete 不因新增观察语义而一律变回 interim。

保留可信正文与必要的版本变化证据；高频、被新版本覆盖的 interim 可以安全合并，但不能丢失 member、严格 final、冲突和停止屏障所需记录。正常长对话不能因一个新的小条数上限被截断；诊断配额和故障缓冲配额不能成为整场会话次数限制。

### 5.2 已封存后的差异分类

| 分类 | 数据与生命周期行为 |
|---|---|
| 完全相同正文、相同身份 | 幂等 no-op，不增加 member/delivery/command/候选。 |
| 已确定低优先级的另一来源 | 只作为来源观察；不得覆盖已选来源。Chat 模式的 TTS、voice 场中的未绑定 QueryConfirmed 属于此类。 |
| 极窄的格式等价 | 可判重复，但保留原封存正文和命令。等价规则必须可审计、带版本和反例；不得普遍去标点/数字/空格或用相似度。 |
| 实质不同或无法证明等价 | 保留原封存正文、新观察及争议；继续后续合法回合落盘，不能改原 command，也不能伪造第二个用户回合发出去。 |

格式等价 v1 的允许范围：已有首尾空白规范化；同来源、同身份的两份文本仅相差末尾单个中文句号 `。`，其余 Unicode 内容完全一致。正文不进行该变换，只用于等价判断并留诊断依据。不得扩展为移除问号/叹号/引号/小数点、修改内部标点、数字、否定词、实体或日期。若当前业务合同对该特例有明确相反要求，保留更严格策略并在交付说明；不得悄悄扩大到通用去标点。

可执行定义：规范化后仅允许 `a == b + "。"` 或反向，较短串必须非空且不以 `。` 结尾；禁止循环 trim。`你好。/你好。。`、`好吗？/好吗`、`3.5/35`、`甲。乙/甲乙` 均不是这种等价。这是本产品明确的格式容差，不是供应商保证任意标点差异都语义相同。

真正冲突不得被 catch 后直接忽略。需要独立的未解决 issue 计数参与完整性判断，**即使原正文已有 deliveryMessageID 且 pending=0，仍不能认为全场没有缺口**。

本轮不新增“更改已曝光消息”的后端协议。未解决的曝光后语义争议：本地保留全部可接收后续正文和 close intent，阻止完整 end/admit，沿既有不完整/受阻恢复表现交付。不得为了正常重复通过而把所有正常事件归入此分支。后续若要对争议正文自动修订服务器，需独立协议设计；不是本轮偷偷增加替代 POST 的理由。

### 5.3 兼容与恢复

- 旧 envelope 的已有正文、ID、hash、序号、曝光和关闭坐标原样保留；无新字段不能被推断为不存在历史缺口，更不能因此自动重发历史业务。
- 新字段迁移须原子，有明确版本；重建、旧文件读取、损坏文件、迁移中断均有测试。无法安全降级的新文件不能交给旧 writer 静默丢字段。
- `recoverableProductSessionID` 必须识别新增观察待封存和未解决 issue，覆盖“旧正文全送达但后来采集出错”的场景。
- 不从旧 suffix(20) 聊天缓存自动补写 OwnerTruth，不处理本次真实失败文件或历史场次。所有迁移验证使用隔离夹具。
- 磁盘和诊断分离：业务正文只能进入现有受保护的本地存储；诊断不包含正文。

## 6. D3：生命周期、停止和恢复所有权

### 6.1 不能由一个 UI 状态决定对象生死

在本场内部明确区分：允许接收新回合、是否请求停止、正在排空的观察/写盘、同步状态、完整性问题、是否已完成关闭或安全移交。

`onStateChange` 可以继续驱动页面，但 `state.isTerminal` 不得单独触发清空 active/retained coordinator。也不能反过来把所有 unavailable 全局改成永久非终态。

| 情形 | 新回合 | 停止与释放 |
|---|---|---|
| 正常重复/合法修订 | 继续 | 正常封存关闭，完成后释放 |
| 单条真实争议 | 继续保存后续合法内容 | 停止写 close intent，保留 issue，安全移交恢复；不能完整成功 |
| 网络暂停/未知写 | 磁盘正常时继续 | 使用原有只读核实和原命令预算 |
| 单次磁盘故障 | 有界暂存，明确未保存 | 恢复后持久化准确事件/缺口再推进 |
| 持续磁盘故障/损坏 | 不能无界接受未保存内容 | 记录能记录的停止事实，诚实失败；不得声称完整可恢复 |
| 旧场/旧账号回调 | 拒绝该回调 | 不改变当前场状态 |
| 账号归属真正失效 | 隔离旧场，禁止旧授权发送 | 保留已落盘资料；不复活旧场、不跨账号恢复 |

活动所有权必须有唯一场次。用户停止后，可恢复关闭工作须有确定持有者；不能依赖页面恰好存活，也不能永久 retain 每一个失败场。安全移交后取消计时器/观察器，旧回调通过账号、场次、generation 校验后丢弃。

只修当前场 Coordinator 的所有权与绑定，不开展历史任务全局 UI 仲裁重构。

### 6.2 停止顺序

1. 在原始入口冻结本场停止水位，幂等设置 stopRequested，关闭水位外的新回合入口。
2. 原子保存 close intent、水位以及停止前已接受但尚未排空的观察/边界清单，或有证明等价性的连续水位加缺口账本；需包含精确身份、观察ID、ordinal和处理结果，能保留的未落盘观察正文一并保存。最大ordinal本身不足以在崩溃后重建未完成任务。其含义是用户已要求停止，**不是已经完整封存**。
3. 排空水位内每个已接受的观察、final 版本和结束边界。不能只等 member Set 清空。
4. 若停止前已预约但尚未落盘的 member 稍后交接，必须能按冻结清单中的账号/场/generation/身份/观察ID写入；close intent 不得把它误判成停止后新成员。不得只凭ordinal小于水位放行从未接受的身份。
5. 对已取得严格 final 的合法观察按边界封存；只有 interim、missing body 或未解决争议保持准确缺口。
6. 完整性通过后才冻结 delivery close sequence，排空上传，调用既有 end → ACK → admit；任何一步保留原命令和原曝光预算。
7. 有缺口仍保留恢复坐标和所有已保存内容。不能跳过缺口拼接一份“完整 Source”，不能让 Worker 发布仅前半场却说全场完成。
8. 重复 stop、页面离开重进、主线程迟到不产生第二套关闭命令。安全移交完成后按明确条件释放。

close intent 已落盘但 drain 未完成就崩溃时，重建必须识别清单中的未完成项；原观察无法恢复就保留缺口，不能因内存队列消失而当成已排空。

修改 `finish()` 的进入条件：不能因之前 `isCaptureOpen=false` 直接 return；应按本场是否已请求/完成停止决定幂等行为。若账号已切换，旧回调无权借 stop 再发业务写。

邻近必须修正的生命周期路径：只读确认队列排空后，不得先临时赋 unavailable 再重建 UseCase，导致 Controller 抢先关闭采集。它不是本场已证实的首因，但属于同一所有权合同，必须加真实组合回归。

## 7. D4：磁盘异常和首错诊断

### 7.1 精确错误与有界恢复

至少区分语义冲突、身份/角色不匹配、读取失败、解码/校验失败、原子写/替换失败、确认落盘失败、close intent/watermark 失败。不得全部变成 persistenceRejected；错误描述只输出安全枚举，不能含路径原值、正文或服务器原始响应。

member 首次登记写失败时，下一次成功写入必须先原子补记缺口或补回准确的原事件，再写后续正文。不能让磁盘因为“从未登记过丢失 member”而看似完整。

本地未落盘暂存必须有明确条数/字节上限、去重身份和恢复触发。建议初始上限为 128 个待持久化观察或 4 MiB（先到为准），只适用于故障暂存，不是正常会话正文上限。完整 final 和成员身份不能被普通 interim 覆盖。达到上限时停止继续接受未保存正文，保留能保留的缺口范围，并复用既有不完整/保存失败提示；不能继续假装全量保存。

缓冲耗尽后即使磁盘恢复，也不能清掉 overflow/漏采区间并正常 end。只有准确原事件仍存在且全部补回，才能关闭对应缺口；无法补回的区间必须继续阻止完整成功。

只允许对**相同本地持久化操作**做有界、可证明幂等的恢复；若写入返回不确定，先读回核实。不要把本地重试变成 start/append/end/ACK/admit 的新 POST。明确持续写失败不会无限循环、无限内存积压。

磁盘完全不可写时，诊断也可能无法落盘，报告必须承认这一边界；不得删除旧 envelope 或生成空文件掩盖损坏。

### 7.2 首次关键失败独立保留

新增或扩展一个独立于音频高频 ring 的关键诊断记录，账号/场次/generation 隔离。每场固定保留第一条关键失败；后续普通回调不能覆盖它。同时保留有界关键状态变化、最后成功水位和错误类别计数。

记录白名单：阶段、typed error、来源/事件码、入口 ordinal、身份哈希、角色、最后成功落盘/确认序号、持久化/待写/issue 数、是否已请求停止、是否已移交。正文、音频、token、密钥、原始账号和原始 payload 禁止进入诊断。

建议每场不超过 512 KiB、关键事件窗口不超过 256 条，固定首错摘要不参与循环淘汰；普通 SDK 高频日志保持原策略。对新诊断数据设置有界总配额并保护活动场。不得顺手清理既有真实场次文件。

诊断失败只能尽力记录，不能递归触发诊断、改变音频或新增网络请求。首错后追加 10,000 个普通事件、再重建，首错仍可定位。

### 7.3 UI 只反映真实保存情况

不新增一套用户可见“处理中”状态掩盖问题，复用现有状态/提示组件。会中真实保存故障不能继续被 `isLive` 的渲染早退完全隐藏；以简短保存风险提示呈现，不能改变麦克风/播放状态。

完整成功只来自当前场真实状态；部分保存不能显示“整场原对话已保留”。已持久化部分、仍未落盘部分要按事实表达。现有已通过的“已保存收到的内容，部分内容尚未完整记录”分支保持；不能把严格 final 回归成 partial 来套这句文案。

受控 HTTP 必须核对账号/场次、命令和 message ID、顺序、水位、正文摘要及请求次数，不能见任何请求都返回通用成功。断言来自重开磁盘、网络记录和真实 Controller 行为；禁止由测试强持有失效 Coordinator 掩盖生产释放。

### 9.2 CAP-15 不能用无关大 Source 代替

至少一份两轮补充短场和一份逻辑65分钟/150+用户轮的密集长场，应把**本次客户端适配器、真实 Controller 和 Outbox 产出的正文与命令序列**接入隔离后端，而非另造一个同样大小的 Source 宣称端到端通过。

可使用本地服务直连，或将合成测试的完整命令记录按原身份/水位输入真实后端 Runtime/HTTP 和隔离 PostgreSQL；禁止人工拼补遗漏正文。真实 extractor、请求构造、parser、验证器、Worker、事务和审核路径继续执行，仅外部模型 HTTP 使用受控合成响应。

优先让客户端实时接入隔离本地HTTP，由真实后端生成动态会话ID、回执和状态再驱动客户端继续。记录桥接必须处理这些真实响应依赖，不能把HTTP桩伪造的ACK回执或任意重映射后的ID当真实合同证据。**CAP-15不得直接播种已结束会话、已ACK批次或Source，绕过真实messages/end/ACK/admit。** 现有数据库smoke的已ACK批次种子可用于保留后端专项回归，不能代替这一条客户端闭环。

逐项断言：

1. 客户端封存正文、后端消息、admission Source 的身份/顺序/正文摘要一致；没有只保存前13轮。
2. 事实真值表覆盖首中尾、多维内容、跨批重复/补充/纠正/撤回、纯问题和助手排除；不是只核对总候选数。
3. 从同 Source 生成的候选经本地合成审核后成为正式 Memory/Version；重建 Store 后仍可读，没有重复。
4. 保留此前 F-65（73,728字/301条消息/150用户回合）同源链及 run04 语义/证据负例回归。数字来自夹具，不能称物理65分钟或真实模型效果。
5. 本轮若没有触及的既有环境基线失败，必须用原基线对照记录；不能改断言假绿，也不要求顺手修复无关范围。

若失败，先保留独立首错及相应水位，不自动再开一场、不重发业务、不清理历史；由新增证据定位首个失败阶段。本地交付不会因为本清单尚未执行而中断。

## 12. 新增强制要求：每次长场验证前先通过短场完整链路（2026-09-21）

这是用户本轮明确补充的验收要求，优先于此前仅将短场列为普通回归项的安排。**短场是每次长场组合、压力或真机验收的前置门禁，不得因上一版本曾经通过而跳过。** 本节同时适用于 Sol 后续开发和 Astra 独立复核。

### 12.1 本地阶段必须实际执行

1. 每次启动长场组合/压力验收前，先在同一份最终源码、配置、接口和迁移版本上运行独立短场。修改采集、持久化、关闭、认证、整理、候选读取或审核相关实现后，旧短场结果失效。长场修复完成后必须重跑短场，再启动长场。
2. 短场至少两个用户回合，第二回合补充第一回合。例如先说“我小学参加过校园合唱演出”，再补充“那次演出的测试代号是松塔七号”。使用合成数据，不读取或重处理用户历史场次。
3. 必须经过共享生产事件适配器、真实 Controller/Coordinator、临时磁盘、FeatureGate、BackendClient、本地 HTTP、真实 Backend/Worker 和隔离 PostgreSQL。真实后端响应返回原客户端并驱动后续操作。只替换外部模型 HTTP；不能用手工播种候选或直接写 Source 代替这条链。
4. **进入待确认记忆的判定必须读取本场候选正文和来源绑定**：第一轮事实和第二轮补充均存在，绑定本场 Source，合并后没有重复候选。上述固定短场夹具预期为一条含两个标记的候选；其他夹具按其事实真值表断言，不能将所有短场都限制成一条记忆。
5. UI 文案、pendingReview、HTTP 201、Worker 有进程、候选总数增加，均不能单独证明通过。还要完成既定的隔离本地审核→正式记忆→重建 Store 回查，内容完整、无重复，原命令幂等。
6. 短场失败即停止后续长场验收，记录失败阶段并继续本地修复；不得为了取得长场结果而绕过门禁。修好后重新从短场开始。针对缺陷的单元反例可先运行，不应把这些诊断冒称长场验收。
7. 测试入口必须落实顺序和阻断：优先独立 short 测试/命令生成带源码与配置指纹的结果，long runner 核验本次短场通过后才运行。不能仅在 Markdown 报告写“先短后长”，也不能在短场只等到 pendingReview 就立即启动长场。

### 12.2 真机阶段独立，由用户主动发起

用户安排真机验收后，**每次普通20分钟、密集20分钟、未来65分钟长场之前，各自先跑一场短场**，检查两轮内容及补充实际进入本场待确认记忆，再按既定要求审核到正式记忆并重启回查。若更换客户端、后端、模型参数或认证配置，应在新组合上重新通过短场。

本地没有手机不是阻断条件；本地开发、短场完整链、长场组合、回归、构建和交付都应连续完成。真实 Provider、部署、手机安装、物理时长测试和真实候选审核仍由用户主动发起，未执行就分别保持 NOT_RUN。

### 12.3 每次交付的最小证据

| 项目 | 必须记录 |
|---|---|
| 版本 | iOS/Backend/测试/配置/迁移指纹；不能沿用修复前结果 |
| 执行顺序 | 本次 short 的开始、结束和结果；随后 long 的启动时间与场景编号 |
| 内容证据 | 同场 Source、候选第一轮事实和第二轮补充、去重和来源绑定断言 |
| 正式链 | 隔离审核结果、正式记忆内容、重建读取及幂等断言 |
| 失败阻断 | short FAIL 时 long 为 NOT_RUN，不调用后续长场入口 |
| 环境边界 | local、真实 Provider、真机短场/20分钟/65分钟、部署分别记状态 |

不允许为通过短场而关闭长场整理、放宽证据/B7/未知写/预算保护，也不允许为修长场破坏已通过短场。受影响模块必须列入测试矩阵并实际运行。
