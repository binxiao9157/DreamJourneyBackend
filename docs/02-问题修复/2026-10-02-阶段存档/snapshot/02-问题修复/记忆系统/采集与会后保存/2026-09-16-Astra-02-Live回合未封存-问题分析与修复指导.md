## 1. 结论与证据边界

恢复出的当次真机执行输出已证实：整场 10 问每问都有一次 `liveASRResponseObserved isFinal=true`；该场没有可见的 `liveQueryConfirmed` 或 question stage=`queryConfirmed` 记录。当前源码却仍将这些最终 ASR 文本适配为 `canonical.interim`，owner 的唯一定稿入口依赖 `ChatTextQueryConfirmed`；Outbox 遇到最前面的未定稿条目便停止封存后续内容。现场 final 已到达与当前适配缺陷已有直接证据，不再只是合成输入假设。界面正常识别、回复和播放，与这条记忆采集通路相互独立，所以持续交谈正常并不能证明整场记录可交付。

另外，关麦流程先排队显示 coverageGap，再排队执行 idle 渲染，后者无条件隐藏同一个状态区域。异步关闭意图落盘后仍为相同 coverageGap，状态去重不会再次通知界面。因此存在“日志记录 coverageGapPresented，但屏幕没有状态”的直接代码链；无需用历史 workflow 解释本场停止后的消失。

**仍保留三项限制。** 无可见 QueryConfirmed 入口记录不等于 SDK 在任何情形下都不发送该事件；当前源码与当时安装二进制尚未逐行绑定；尚未取得该场原始 Outbox，因此不能直接列出 20 个槽位的成员与首 gap 的 ordinal/角色。缺口机制已明显收窄到“现场逐问 ASR final 已到达，但当前 canonical 终态适配仍拒绝定稿”；身份错配、停止边界丢回调等额外缺陷仍应防护，但不能再把“现场可能根本没有 final”作为同等可能的解释。以下 probe 证明当前代码机制，不是新做的真机复现。

## 3. 20 个槽位如何形成，为什么交付计数仍为 0

### 3.1 SDK → canonical 适配

当前 [DialogEngineManager.swift](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DialogEngineManager.swift:5156) 的 `parseASRResult` 能把 `results[0].is_interim=false` 解析为 `isFinal=true`。

但随后：

| 原生事件 | 当前 canonical 行为 | 当前源码位置 |
| --- | --- | --- |
| ASRInfo | owner 永远 interim，包括 isFinal=true | DialogEngineManager.swift:4460 |
| ASRResponse | owner 永远 interim，包括 isFinal=true | DialogEngineManager.swift:4558 |
| ASREnded | 只观察 question、打印结束，不提交 final | DialogEngineManager.swift:4606 |
| ChatTextQueryConfirmed | 成功解析非空文本后才发 owner.complete | DialogEngineManager.swift:4614、4648 |
| TTSSentenceStart/End | assistant 按 reply 聚合，发 interim | DialogEngineManager.swift:4704、4745 |
| TTSEnded | 聚合文本非空才发 assistant.complete | DialogEngineManager.swift:4760 |
| ChatEnded | chatBuffer 非空才发 assistant.complete | DialogEngineManager.swift:4950 |

`ChatTextQueryConfirmed` 名称及代码注释不足以证明每次原生口语 ASR 都必有该事件、字段结构、发生时序与定稿保证。恢复现场已提供反例证据：12 问逐问可见 final ASR，却没有可见 QueryConfirmed 入口。当前 SDK header 只列出事件名称，没有必达承诺（SpeechEngineDefines.h:1535–1553）。修复不能继续把这个未经保证、与现场记录不符的假设当作唯一 owner 终态合同。

### 3.2 ID 与槽位

`emitCanonicalTranscriptEvent`（DialogEngineManager.swift:3900）以 `engineGeneration + role + providerTurnID` 生成 ID：owner 优先 questionID，assistant 优先 replyID；缺失时回退当前 correlation ID。

Outbox 的 `upsertCanonicalTurn`（[OwnerTruthContracts.swift:15109](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:15109)）按 canonicalTurnID 找现有槽位；新 ID 获得递增 captureOrdinal。重复片段只更新同一槽位；完成且已封存的文字不能被不同正文覆盖。同 question/reply 的终态必须命中此前的同一 ID，否则旧 interim 会永久留下。

另有一个确定存在但**尚未证明参与现场**的缺陷：fallback 写成字面量 `question-(providerTurnCorrelation.turnSequence)` / `reply-(providerTurnCorrelation.turnSequence)`，没有 Swift 插值（3915、3919）。不能仅补反斜杠就认为身份已正确：缺 provider ID 的多条事件仍须在同一已登记问题/reply 内稳定关联，迟到回调不能用届时的“当前问题”猜身份。

### 3.3 首 gap 阻断连续前缀

`flushCompletedCanonicalPrefix`（OwnerTruthContracts.swift:15461）按 captureOrdinal 遍历，遇首个尚未投递且 finality 不是 complete 的条目立即 `break`。只有穿过此处的条目才创建带稳定 commandID/messageID 和 clientSequence 的 delivery；ownerTurnCount 也只在这里增加。

`unsealedCanonicalTurnCount`（15392）数的是 **deliveryMessageID == nil 的 canonical 槽位**，里面既可能有 interim，也可能有被前面的 gap 挡住的 complete。因此：

- 20 不等于 20 个都没最终文本，也不等于 20 次用户发言。
- 在“10 个 owner interim + 10 个 assistant complete、首条 owner 未完成”的序列里，20 个槽位已落盘，但 owner=0、pending=0、lastSequence=0。
- 现场 turnSequence=10 与这组 10+10 构成一致，但现有摘录不足以证明它就是现场的准确角色分布。
- coordinator 的 persistedOwner 是服务端已确认 owner delivery 的计数（EchoViewController.swift:1846 附近）；它为 0 不等于原始 canonical 文本没有落盘。

保留连续前缀限制是正确边界。**禁止通过跳过首 gap、给后续完成条目重排序号，或把所有 interim 在关麦时强制改成 complete 来让数字变绿。**

## 5. 当前关闭装配没有真正接上“已登记回调排空”

现在 `stopVoiceCapture`（EchoViewController.swift:13615）先关闭 isUserControlledLiveSessionOpen，然后释放音频 lease、失效交互 token，再 stopDialog。关闭该标志也清掉 liveProductSessionID（4056）。Manager 的 stopDialog（2647）同步 StopEngine 并注销 active operation；停止期间 isEnding 还会丢弃非连接/会话结束事件（4243）。

另一方面，`onCanonicalTranscriptEvent` 在 main queue 上再检查活跃交互 token 和 Live 开启标志（14010）；在此之前已经收到但还排队的有效 canonical 回调，也会被关麦后的 guard 丢弃。`finishLiveMemoryCaptureIfNeeded` 又先清掉 active coordinator 指针再 finish（12165）。保留字典仍持有 closing coordinator，但 canonical 回调不会按关闭场次路由给它。

所以现有 Store/Coordinator “允许 finishing 接受已有槽位 final”的能力，**并不等于真实 Echo → Manager 装配能在关闭后送达它**。现有测试直接调用 coordinator.appendCanonicalTurn，绕过了这里的失效和路由边界（OwnerTruthContractsTests.swift:479、505，以及 :622 的 Store 首 gap 测试）。

关闭计数为 0 并不应发送 N=0 的正常 end。`persistCloseRequestIfReady` 目前要求 closeIntent 已落盘、pendingPersistence=0、unsealed=0、owner>0（EchoViewController.swift:1632）；本场按这些条件不会建立正常 N。缺口场必须有明确可恢复结果，不能悄悄伪装空场。

## 6. “日志呈现缺口，用户看不见”的局部 UI 原因

手动结束分支 `onDialogEnded` 依次执行 finishLiveMemoryCaptureIfNeeded（14364）、Conversation summary、resetEchoViewModelToIdle（14370）。

1. coordinator.finish 把 state 变成 coverageGap；onStateChange 在主线程排队显示（12018）。
2. resetToIdle 也通过主线程排队触发 viewModel 的 idle 渲染（4847）。
3. `renderLiveMemoryCaptureState(.coverageGap)` 先让 voiceStatusView 可见，随后记录 coverageGapPresented（12264）。
4. `render(state:.idle)` 无条件 `renderVoiceStatus(text:nil,isVisible:false)`（6422），覆盖同一 view/label/height（10703）。
5. requestClose 落盘成功后再次赋值相同 coverageGap（1705 附近），state.didSet 的 oldValue==state 判重跳过通知（1304），不能恢复被隐藏的文字。

这条同场 FIFO 路径由代码确定；本轮未跑 UIKit 重现，不声称已捕获现场每一次 render 的精确时间。它与安全摘录和人工屏幕观察一致，是本项需要修复的局部显示缺陷。历史 coordinator、历史 pending-review、候选页返回及前后台谁有展示权，交给第 3 项，勿在本项扩建全局 UI 仲裁器。

## 7. 给 Sol 的最小修复范围

### A. 先补一轮可裁定的安全诊断，锁定原生 owner final 合同

采集 SDK 接收事件 → canonical 决策 → Store 快照三个边界，仅记录本次合成场次。至少记录：productSession 哈希、scope/authority/engine epoch 哈希、回调接收序号、事件类型、question/reply 哈希及来源（payload/current/fallback）、isFinal 字段是否存在及值、文本长度/同场去重哈希、canonical ID 哈希、revision、finality、接纳/拒绝原因、captureOrdinal。

关麦时输出首 gap 的 ordinal、角色、当前 finality、最后事件类型/序号、缺口类别、后方 completedBlockedCount、registered/persisted/unsealed/delivery 四组计数、pendingPersistence、closeIntent/N。避免只报总数或仅使用含混的 persisted 命名。不得记录原始主体/账户/provider ID、凭据或私人正文。

不能期待历史 23:43 场再生事件；该场只作只读恢复对象。历史记录已经证明该次 10 问每问都有被接收方识别的 final ASR；新受控合成场应补 canonical 决策→原 Outbox 成员→关闭 N 的装配证据，并验证实际采用的 final/QueryConfirmed 关联合同，不应重复把“现场有没有 final”当成尚无答案的问题。

### B. 修正 canonical 适配，不改已通过的音频控制

对有协议或真实 SDK 序列支持的原生 final ASR，使用其真实终态，禁止无条件降格到 interim、永久等待未保证存在的 QueryConfirmed。临时 ASR 保持 interim。若 ASR final 与 QueryConfirmed 代表不同阶段，明确“识别稿终态／提交给模型的确认”语义，制定有证据的单一提交规则；不能首次 complete 投递后再用不同正文覆盖同一条已封存 delivery。

将 canonical 身份/修订/终态归一化为独立适配职责，仍由 question/reply identity 与 provider epoch 绑定。重复 final 幂等；无 ID 或迟到不同问题的确认不能随手套当前问题；关联不成立进入明确 gap。修掉字面 fallback，并保证后续片段/终态仍命中同一槽位。assistant 仍按 reply 聚合为 context，completed 指文本流权威终态，不表示声音已经全部被用户听完。中断/缺终态只能保留已收文本并标明 partial/gap，不能伪造 complete 或写成 owner 事实。

若最小版本不扩展后端 partial 合同，partial/gap 只保留本地诊断/恢复记录并阻止“全场完成”，不得按完整消息绕过当前连续前缀约束。

本项不得改 ClientInterrupt 判据、providerReplyPlaybackState、播放器/SDK配置、音频 lease、AEC/蓝牙路由或自动翻页以解决记录问题。已通过的长答自然播放与主动打断是必须保留的真机基线。

### C. 正确冻结关闭场次并排空真实已接收内容

用户按停止时，先在采集串行入口冻结 immutable CaptureSessionContext（scope、productSession、provider epoch、已登记 ID 集合和接收序号边界），立即显示本场“正在保存”。在持久化串行队列写 closeRequested 意图，N 此时可以未知；在同一串行因果链上排空停止前已经接收/登记的 canonical 事件，然后执行磁盘 barrier，再根据连续封存结果冻结 N。

要区分“SDK 已接收/入口已登记”和“Store 已有槽位”：现有 Store 在 closeIntent 后禁止新 ID。因此冻结边界内的首次登记必须先在同一持久化队列排入、先于 closeIntent 落盘；或者用有版本的持久化关闭清单显式声明其冻结成员资格。不能先 requestClose、再把尚无 Store 槽位的合法队列成员当作新 ID 丢掉。关闭清单固定后只允许其中已有身份补充终态。

停止录音/播放仍应及时执行。记忆排空不能靠延迟 stop 麦克风来等待更多用户输入，也不能更改音频回调以换取 final。将 closing capture sink 与活跃声音 UI token 分开：同 scope/epoch、已登记身份的迟到 final 才能路由至被保留的 closing coordinator；新问题、跨场、旧 epoch 或账户变化仍拒绝。严格关闭窗口与拒绝原因可观察；禁止移除全部生命周期 guard 或把所有关闭后的回调统收。

对 SDK 从未提供的 final，固定等待几秒不能制造 drain 证明。已有 partial 达到有界截止后必须留下首 gap、已收到范围和缺口状态；不能 freeze 一个越过 gap 的正常 N，更不能把 pending=0 当作全场为空。进程中断后的恢复只使用 durable context/outbox/checkpoint，不恢复麦克风。

注意两个序号职责不同：接收序号证明停止前队列排空，clientSequence 是实际可交付连续前缀。不要用 turnSequence=10 或 unsealed=20 直接推导 end 的 N。

### D. 修复本场关麦状态的单一显示入口

将本场 retained closing capture 状态作为 idle 后应展示的状态输入；mic 变回可开始状态，不应顺带清掉正在保存/缺口/等待整理等状态。统一从本场状态快照 render，或在 idle 分支调用明确的本场状态 renderer，而非依靠回调先后补写文字。验证未变化的 coverageGap 也不会被 idle 清空。

本地只接收到部分内容时使用准确文案，例如“已保留收到的内容，部分对话尚未完整记录”。只有本场 server receipt/checkpoint 支持时才显示进入待确认；不借用历史结果。本项只修本场关闭局部覆盖，不解决多个历史 workflow 的优先级策略。

### E. B8 依赖与未知写

B8 的 ended receipt → batch acknowledgement → admission/recovery 合同先修，是本项端到端验收的前置条件；但 B8 不能解释 canonical 的 first gap 与 owner delivery 无法形成。先按本项把 canonical/freeze/N/本场状态做正确，再调用 B8 已验证路径，身份必须保持同一 productSession/server session/batch。

任何 append/end/ack/admit 的返回未知，先持久化命令身份与 unknown checkpoint，再只读核实。不得因缺少日志、UI 无结果或冷启动而重发未知写、创建新场次、清掉 outbox 或重启麦克风。已知未发送与发送结果未知必须分开；重试策略复用第 1 项的确定合同，勿在本项另写“失败就重放”。
