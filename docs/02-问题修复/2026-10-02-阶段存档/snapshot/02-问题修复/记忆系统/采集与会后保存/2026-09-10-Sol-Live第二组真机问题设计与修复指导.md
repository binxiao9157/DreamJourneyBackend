## 1. 结论与修复范围

这不是一个单纯的“提示词不够好”问题，也不能用增加等待时间、换模型或补几条假 Candidate 解决。

本次必须处理五个问题，其中第一个是本次独立核查新增发现：

| 编号 | 优先级 | 问题 | 证据结论 |
| --- | --- | --- | --- |
| L2-01 | P1，阻断 | 新增尚未审核的 Source，使整个正式记忆和搜索投影失效，且缺少对应恢复任务 | 生产触发器、任务时间、引用数量及代码已核实 |
| L2-02 | P1，阻断 | Live 正式记忆从服务端到供应商实际上下文未形成可验证闭环；还有快照裁剪遗漏事实的问题 | 用户现象与代码风险成立；原测试的最终供应商上下文尚未取得 |
| L2-03 | P1，阻断 | 会后整理第 1 次失败即终态，异常原因被丢失；部分失败又被原文拼接降级掩盖 | 生产任务、代码和离线反例已核实；历史首次异常仍未确定 |
| L2-04 | P1 | 客户端把等待超时、查询失败、任务终态失败统一为“请稍后重试” | 状态映射代码已核实 |
| L2-05 | P2 | 旧 `/archive/items` 写入仍在重试，制造 409 和错误状态 | 旧重试路径已找到；不是本轮 Candidate 失败的已证实原因 |

**目标不变：** 火山负责原生 Live 的快速语音交互、持续聆听和打断；DeepSeek 负责文字问答和会后整理；两者共用同一正式记忆事实权威。正式记忆内容保持客观，口语修饰只发生在回答层。

不得恢复逐轮 `ASR -> DeepSeek -> TTS`，不得让每轮语音回答等待会后整理，也不得重新引入另一套本地事实库。

- 正式记忆仍为 65 条，`memory_revisions.revision=66`。
- 正式记忆 checkpoint：`state=rebuilding / entry_count=65 / memory_revision=66`。
- 搜索 checkpoint 也为 `rebuilding`。
- checkpoint 的更新时间与上述失败任务 Source 的创建时间完全相同：`2026-09-10 04:04:38.879954+00`。
- 该 Source 没有被任何正式 Memory 引用，引用数量为 0。
- 当前没有该账户的待执行/租赁中/退避中的投影重建任务。历史失败投影任务不能被当成当前补偿任务。
- 通过正常读服务构造当前 Live 快照返回 `formalMemorySnapshotUnavailable`；读服务返回 `state=rebuilding`，并非数据库里 65 条事实被删除。

生产实际启用的触发器是：

```sql
CREATE TRIGGER owner_truth_sources_invalidate_derivatives
AFTER INSERT OR DELETE OR UPDATE OF
    owner_subject_id, state, source_version, content_hash, authority_epoch
ON owner_truth.sources
FOR EACH ROW
EXECUTE FUNCTION owner_truth.invalidate_memory_derivatives();
```

该函数不判断 Source 是否支撑正式事实，就把整个 vault 的两个 checkpoint 设为 `rebuilding`。Source 创建路径只排入 `ownerTruth.source.created` 整理任务，并不同时创建正式投影重建任务。

**机制结论明确：仅增加待审核素材就足以使旧正式记忆读模型失效，并可能永久停在重建中。** 这解释了当前新会话可能再次无法取得快照；它不能反向证明原测试首次 Live 已连上时答不出学校的原因相同。

## 3. 目标链路与边界

### 3.1 Live 会话

1. 用户开启 Live，后端鉴权并取得当前可用正式事实版本。
2. 后端生成有版本、覆盖范围和 hash 的模型上下文，并签发短期会话票据。
3. iOS 按已验证的 SDK 合同将上下文送入同一个火山会话。
4. 火山原生完成语音理解、自然回答和声音输出，保持打断能力。
5. 转写异步逐回合持久化，使用 `turnId / sequenceNumber / productSessionId` 去重及隔离。
6. 用户关闭或既定无输入超时结束后，封口完整会话，只启动一个逻辑整理任务。
7. 整理结果进入候选批次，用户审核后才改变正式记忆。

这里“一场”是打开至关闭；多轮、分片和失败重试不能变成多份互相独立的整理结果。

### 3.2 文字会话

文字继续使用 DeepSeek 和当前正式记忆进行回答，不朗读。沿用同样的逐回合持久化、整场整理、审核写入规则。

文字和 Live 可以表达不同，但事实、身份范围、有效时间和否定含义必须一致。不能拿“文字能回答”作为 Live 已接通的证据。

### 3.3 四种内容要分开

| 内容 | 用途 | 能否直接成为正式事实 |
| --- | --- | --- |
| 已确认正式记忆 | 跨会话个人事实权威 | 已经是 |
| 本场用户新陈述 | 当前交互上下文、会后候选证据 | 不能，必须审核 |
| 本场用户问题 | 意图与话题上下文 | 不能仅因是用户说的就入库 |
| 助手回答/建议 | 解释代词、问题背景 | 不能当成用户自述事实 |

“只以正式记忆回答历史事实”不应被解释成不能听懂用户刚说的话。允许回应本场新陈述，但必须与已确认长期事实区分；冲突时不擅自覆盖旧事实。

## 4. L2-01：修复投影失效边界

### 4.1 行为合同

| 事件 | 对已有正式记忆与搜索投影的影响 |
| --- | --- |
| 新增不被正式事实引用的 Source | 不失效，不改变正式修订号 |
| 为该 Source 整理、重试、失败或生成待审核 Candidate | 不失效已有正式事实 |
| 拒绝尚未写入正式记忆的 Candidate | 不使已有正式事实不可用 |
| 审核接受/更正导致正式事实变更 | 同事务更新修订号、失效相关派生物、创建持久重建任务 |
| 删除/撤销正式事实的依据 Source，或变更其有效版本/权限 | 必须立即失效受影响派生物，不能继续使用旧事实；同时具备可恢复重建或明确阻断记录 |
| 权限撤回、账户状态或 authorityEpoch 变化 | 保持现有 fail-closed 行为，不能为了可用性跳过 |

### 4.2 实施要求

1. 新增版本化迁移修正 Source 触发器；不要修改已经部署执行的 `0119` 文件和旧迁移摘要。
2. 对无正式依赖的新 Source INSERT，不触发全 vault 失效。
3. 对 Source UPDATE/DELETE，按照现有正式事实资格与证据依赖关系判定影响；必须覆盖多来源支持、旧新 vault/资源边界及删除前 OLD 行。不能只用一个随意的 `memories.source_id` 判断代替完整依赖检查。
4. 保留正式 Memory/MemoryVersion/rights/revision 的防陈旧机制。不得整体关闭触发器，不得伪造 `ready`。
5. 凡真正使读模型失效的命令，要核对是否在同一事务创建可恢复重建意图。幂等键绑定 vault、目标修订和权限版本，避免每个候选生成一次全库重建。
6. 回滚、Worker 崩溃或重复投递时不能漏任务、重复激活或使用新权限下的旧结果。
7. 对当前受影响账户，只允许经过验证后使用正常投影重建流程恢复派生数据。先确认当前修订与依赖，再重建正式投影、搜索文档、必要向量；不要修改 65 条事实或重新导入。
8. 将恢复范围和执行结果写入交付报告。新代码不能自动重放历史整理 Dead Letter，不能因为本次派生重建而恢复旧正式记忆。

### 4.3 必须使用真实 PostgreSQL 的回归

- ready 正式投影 + 新未审核 Source INSERT：两个 checkpoint 仍可用、修订号不变。
- 同一 Source 整理失败：已有文字检索和 Live 快照仍可读取。
- 正式事实依据 Source 被撤销/版本变化：旧内容不可用，重建任务确实存在。
- 用户审核新增事实：旧票据按原规则失效，新版本重建后可查询。
- 并发 Source 插入与候选审核：不会用旧修订覆盖新 checkpoint。
- 事务回滚：正式版本、状态和 outbox 均一致。

仅检查 SQL 文本里有某个单词，或只运行 migration contract mock，不能验收触发器行为。

## 5. L2-02：Live 正式记忆上下文设计

### 5.1 先取得真正的供应商输入证据

目前 iOS `performStartDialog` 构造：

```text
StartEngine 参数
  dialog
    asr
    tts
    dialog
      system_role = fullPrompt
```

这是代码形状，不是本文件认可的供应商合同。需要区分 SDK 包装层与最终 WebSocket StartSession 层，**不能凭看到两个 dialog 就直接删一层，也不能因为有声音就认定嵌套正确**。

Sol 必须核实当前锁定 SDK 的官方说明、对应官方 Demo 或受控模拟上游捕获，证明最终供应商收到的角色字段路径与内容。普通 TTS、RTC 智能体和原生实时语音不是同一个接口，不能混用文档。

官方资料入口：[端到端实时语音接口](https://www.volcengine.com/docs/6561/1594356)。本次网页读取遇到重定向失败，浏览器读取超时，尚未独立证实当前 SDK 的包装规则与输入上限。火山的[历史发布说明](https://www.volcengine.com/docs/6561/1329505%3Flang%3Dzh)提到系统提示词限制调整，但这不能推导为当前版本无限长、自动无损记住全部事实。

禁止在未证实前写死“火山只支持 4000 字”等数字，也不能把本项目 `32768` 字符预算当作供应商上限。

### 5.2 统一构造，不依赖本地默认 Prompt

当前 `if !config.systemPrompt.isEmpty` 包住整个正式快照注入，是明确的脆弱条件；默认非空意味着它未必是本次现象的实际触发点。

建议把 Provider-owned Live 的请求构造独立为可测试纯函数/适配器：

1. 判断 `answerAuthority=provider && lifetime=userControlledLive` 后进入唯一 Live 构造分支。
2. 使用已鉴权 runtime 的身份、正式上下文与风格，不能再依赖本地 `systemPrompt` 是否为空。
3. 明确区分“正式记忆确实为零”与“非空上下文丢失/解码失败/修订不匹配”。后者不得静默启动无记忆 Live。
4. JSON 编码失败应返回明确错误，不使用只有 bot_name 的兜底 JSON 冒充成功。
5. 新会话、SDK 重连和引擎重建统一使用同一构造器；正常打断不重新开一个丢失上下文的会话。
6. 新产品会话隔离旧供应商对话标识；不得把上一场的助手输出当成正式背景。

### 5.3 分离权限封装与模型阅读文本

不要把携带大量重复字段的完整审计 JSON 原样当成人类记忆正文。建议增加明确的模型输入投影，但不建立第二套正式记忆库：

- 权威封装保留 `targetPersonaId / authorityEpoch / memoryRevision / projectionCheckpoint / contextHash` 及事实到版本的映射。
- 从同一合格正式事实集合确定性生成 `providerRoleText`，其中包含事实规则、身份说明、精简事实文本及必要限定。
- 新增 `providerContextHash`，对服务端最终角色字符串的 UTF-8 字节计算 SHA-256；模型正文、客户端实际提交和受控上游收到的字符串使用同一规则。
- 不要比较 Python/Swift 默认 JSON 编码后的整串 hash 来猜测一致性。要么使用明确定义的跨端 canonical JSON，要么传递服务端最终字符串，避免客户端重排/重建后散列不一致。
- `contextHash` 表示事实与权限绑定，`providerContextHash` 表示模型实际输入；两者不能混为一个指标。

以上新增字段是本次建议合同，当前代码尚未实现；变更时更新后端响应、iOS DTO、票据绑定/校验、测试与合同版本，不能只改一端。

模型阅读文本可以类似下面的合成示例：

```text
当前是在和记忆主体本人交谈；“我毕业于哪里”指用户，不是 AI。
已确认事实：
F01 本科：2010-2012 在国内甲大学；2012-2014 在国外乙大学；2014 毕业。
F02 硕士：2014-2015 在丙大学学习信息系统管理。
F03 当前职业：产品经理；仍在职，未决定辞职创业。
F04 过去在杭州特别喜欢东坡肉；未声明它是终生最喜欢的食物。
F05 截至记录日期，当前最喜欢的家常菜是清蒸鲳鱼。
```

服务端持有 F01 等到确切 MemoryVersion 的映射，编号仅在本快照内使用。正式表不保存润色版本；模型输入不能创造本科授予学位机构、排名、动机、收入等未提供信息。

### 5.4 解决覆盖遗漏，而不是把遗漏说成“库里没有”

当前实现先每个维度取一条，再按稳定顺序补充，以完整 JSON 字符预算二分截取前缀。这能说明取舍，却不保证学校、职业等关键事实存在；单条 statement 还有 420 字截断，也可能截掉句尾的否定或时间条件。

本轮选择：**先做确定性无损精简与全量覆盖验证，不新增每回合 DeepSeek 查询。**

1. 去除模型不需要的重复审计键、冗余编号列表和重复空值；缺省值必须有合同定义，不能把 unknown 当成无条件成立。
2. 保留人物主体、谓词/客体、否定、强度、有效时间、地点/场景、来源是自述还是转述及冲突边界。
3. 当前 65 条规模，要求全部合格事实进入有效模型上下文，或明确给出经过测量的不可行证据。不能以改成固定前 20 条或只留学校职业来验收。
4. 单条超长事实按可追溯且语义完整的片段拆分；不能按字符硬切，使“没有”“当时”“现在”等限定丢失。
5. 分别测量事实文本、最终 role、SDK JSON 与线上帧的字符数和 UTF-8 字节数；如供应商有 token 限制，记录其适用版本和计算方式。
6. 覆盖计数从实际模型输入构造结果计算，不能沿用未发送集合的计数。完整覆盖必须是 eligible=included，不能只看 envelope 里的数字。
7. 超出已验证容量时返回明确 `coverage=partial/unavailable` 和运行限制，不能继续向用户承诺全量正式记忆可查，也不能让模型把“未装入”说成“没有记录”。
8. 超大记忆的按需检索仅作为独立后续扩展，需验证当前原生 Live 支持的上下文补充/工具机制，再单独评审延迟与权限。此次不顺手增加另一套 RAG、联网搜索或供应商数据库。

### 5.5 供应商握手与事实闭环

至少形成这些关联事件，名称可适配现有日志：

| 事件 | 安全字段 |
| --- | --- |
| snapshotBuilt / ticketIssued | trace、产品会话关联值、修订号、eligible/included/omitted、正文大小、上下文 hash |
| runtimeDecoded | 同一修订、大小、覆盖与上下文 hash 校验结果 |
| promptPrepared | adapterVersion、providerContextHash、最终 role 字节数、事实计数 |
| startDirectiveReturned | 本地 SDK 返回码；不能命名为模型已接受 |
| upstreamStartSessionObserved | 受控 SDK 适配测试观测的字段路径、role hash、字节数；不打印原文 |
| providerSessionStarted | 供应商 ACK 类型、会话关联值；只能证明握手，不证明逐条语义理解 |
| bargeIn / resumed / reconnect | 会话关联值、generation、是否重启、重注入版本 |

后端当前透明转发帧，只做票据授权和版本复查，**并不校验客户端实际发出的角色内容**。即使票据绑定了 `contextHash`，也不能把它当成上行 Prompt 已校验的证据。

最小处理：先用锁定 SDK + 受控上游建立真实帧合同测试。若增加代理对建会话/配置更新帧的验证或服务端注入，只处理已验证控制帧、设置解码/解压上限、保持音频帧透传；不自造整套音频协议。验证实际上行 role 与票据关联的服务端正文相同。若该能力无法在本轮证实，明确列为开放边界，不得声称已实现防篡改。

不能把连接成功、StartEngine 返回 0、客户端准备了 hash 或模型答对一道题，单独作为完整 Grounding 验收。

## 6. L2-03：会后整理可靠性与事实质量

### 6.1 先留下首次失败原因

在以下阶段形成固定枚举的失败记录：

```text
intentLoad -> sourceRead -> inputValidate -> chunkBuild
-> providerRequest -> responseParse -> typedCandidateBuild
-> authorityRevalidate -> candidatePersist -> effectCommit
```

记录 `failureStage / errorType / businessCode / retryable / providerStatus / attempt / maxAttempts / modelId / promptVersion / schemaVersion / operationId`。

要求：

- 用 allowlist 构造安全错误码，不直接记录 `str(exc)`、HTTP body、完整 URL、请求头、用户原话或完整 Prompt。
- 已知合同校验错误记录校验规则代码和字段路径，不记录出错字段值。
- 首次原因与最终收口原因分开保存；`candidateExtractionRetriesExhausted` 不能覆盖最初失败分类。
- Source 读取、模型等待、写回保持现有短事务分离；保留租约心跳、取消、权限复查。
- 安全诊断失败不能改变业务结果。

对历史这次任务，原异常可能已不可恢复。应明确写“历史首次异常未知”，通过同类合成会话和真实受控模型验收取得新证据，不得编造旧根因。

### 6.2 显式重试策略

只对 Source Candidate Extraction 设置重试策略，不把所有异步任务的全局默认值从 1 一起改大。

建议起始配置：总尝试 3 次，失败后约 5 秒和 20 秒退避，加有界随机抖动。429 尊重有界 Retry-After；单次 Provider 超时和整场总时长需显式设置、记录并验证。该数值是本项目初始设计，不是供应商 SLA。

| 错误 | 策略 |
| --- | --- |
| 连接失败、可确认的网络超时、429、502/503/504 | 有限退避重试，记录原因 |
| 请求发送后响应丢失 | 保持应用侧幂等；承认可能重复计费，不能承诺供应商 exactly-once |
| 401/403、缺凭据、余额/额度明确不可用 | 配置/额度阻断，不能忙重试；告警并显示需处理 |
| 不支持的模型/请求参数/合同版本 | 终态配置错误；先修合同 |
| 模型 JSON/结构内容无效 | 单独分类；如实现一次受限修复请求，必须沿用用户证据、重新全量校验，且计入总预算 |
| 证据指向助手、越界索引、主体错误 | 拒绝/隔离，不能补假证据或删掉校验 |
| 权限撤回、Source 删除/版本变化、租约丢失 | 保持阻断/取消，不写入结果 |
| 临时数据库冲突 | 依现有事务与幂等规则重试；永久约束失败应保留可诊断终态 |

重试仍是同一个 logical operation。每次不能创建新的 Source、review batch 或重复候选。长会话分片重试只重做失败部分，所有片片结果最终对应一个整场审核批次；部分成功不能伪装成全场完成。

### 6.3 删除“失败就拼原文成功”的语义降级

当前 Live Extractor 捕获 `httpx.HTTPError / ValueError` 后直接调用 Deterministic Extractor。该路径会把纯问题变为 EXPERIENCE 候选，且无法保证多个维度结构化整理到位。

本次要求：

1. 模型或合同失败保持真实的 retryable/blocked/terminal 状态，Source 原文继续保留。
2. 不把未经语义处理的拼接摘要标为 `succeeded` 或“待确认记忆已生成”。
3. 不把问句、寒暄、助手建议、用户仅复述旧答案自动当新事实。
4. 若产品以后需要“查看原始对话并人工整理”，单独作为原始内容恢复入口，不冒充本次三类候选/多维结构化结果。
5. 检查现有两个断言 transport/invalid-response fallback 成功的测试。它们固化了旧行为，必须按新合同替换；不是简单删测试或改成永远通过。
6. 用户确实新增事实才生成候选。只查询已有记忆且没有新陈述，可以正常完成为 `completedNoChange`，0 Candidate 是正确结果，不是失败。

### 6.4 整场封口与持久化

保留逐回合持久化与本地 outbox，不能把它移到模型回答前作为阻塞前提。

- 结束前等待已采纳用户终稿持久化，使用现有 last sequence watermark 验证完整性。
- 同一次关闭、重连回调、重复 admission 和重试都关联同一个产品会话。
- 长会话分片必须覆盖全部用户终稿，不能只取最后一句、前 N 轮或固定 800 字。
- 助手文本可以帮助理解代词，但候选 evidence 只绑定对应用户证据；含糊“对”不能自动确认助手编出的事实。
- 缺序列时显示补传/等待，不先整理不完整数据后声称全场已完成。
- `/end` 成功只说明会话已封口，不说明候选已经生成。

## 7. L2-04：状态合同与用户界面

### 7.1 不再用一个 unavailable 表示所有情况

可复用现有状态 DTO 并扩展缺失字段，无须另造大框架。至少区分：

| 服务端/客户端状态 | 用户看到 | 后续行为 |
| --- | --- | --- |
| 正在补传、等待结束回执 | 对话正在保存 | 补传同一会话；不重复新建 |
| accepted / queued / running | 对话已保存，正在整理 | 后台继续，用户可离开或开新会话 |
| retryWait | 整理暂时受阻，系统正在重试 | 展示受控状态，不让用户反复点击新建 |
| succeeded 且有 Candidate | 已进入待确认记忆 | 可跳转准确批次，刷新通知与数量 |
| completedNoChange | 本次没有新增可保存的记忆 | 正常结束；不推送虚假审核通知 |
| 查询超时/离线，但任务状态未知 | 暂时无法获取整理进度，对话已保存 | 恢复后重新读同一 operation |
| failedTerminal / deadLetter | 本次整理失败，对话已保存，需处理后重试 | 有准确状态详情；不持续显示整理中 |
| quarantined / rightsBlocked | 内容暂不能整理/需处理 | 依据安全错误码给最小必要说明 |

“对话已保存”只能在服务端封口/持久化回执成立时显示，不能一律用于本地写盘失败或缺消息。

### 7.2 持久化进度，不依赖页面活着

当前 `EchoLiveMemoryCaptureCoordinator` 在约 60 次轮询后转 unavailable，终态后会被页面移除。应保存轻量 follow-up 记录：产品会话、reviewBatch、operation/admission 标识与最新服务端状态，不保存另一个事实副本。

App 重启、回到档案、收到通知后可以重新读取后台进度。60 次前台轮询结束只代表停止主动刷新，不等于 Worker 失败。自适应退避，后台不持续高频轮询；服务端状态为准。

保留已修复的文字结束返回 idle/麦克风可用行为。上场整理失败不能禁用下一场麦克风，下一场也不能覆盖上场的进度。

## 8. L2-05：停止退役 Archive 写入重试

当前可确认调用路径：

```text
MemoryArchiveViewController 生命周期刷新
-> syncPendingPublicArchiveItemsToBackend
-> item.isPublicBackendSyncEligible（text / timeLetter）
-> 对所有非 synced 项再次置 pending
-> postArchiveItem
-> 409 后统一置 failed
-> 下次刷新继续重试
```

因此，进入记忆档案后的 409 可能来自历史本地条目的重试，不一定是 Live 关闭时做了双写。

要求：

1. 查清每条调用的来源，记录调用点和安全原因；不要猜测后直接重开旧后端路由。
2. V2 普通文字素材只走既定 Source 入口；停止旧 text 条目的自动公共 Archive 重试。
3. `legacyArchiveAuthorityRetired + retryable=false` 是永久合同结果，不得在每次出现页面时重新尝试。
4. 不将 409 当成功，不删除历史原文、不自动迁移/重放旧素材。
5. 需要保留的其他内容类型按现有产品边界独立处理，不能为了 text 清理把媒体/时光信等相关代码全部误删或开启。
6. Live 整理状态由 V2 operation 决定，不能被旧 Archive 状态覆盖。

## 12. DFX 与不回退要求

以下是本轮建议工程目标，需要实测，不是“与豆包/GPT 一样”的承诺，也不是供应商 SLA：

- 语音实时链路不增加逐轮 DeepSeek/embedding 等待；会后整理不阻塞下一场 Live。
- 在相同设备、网络、记忆集、发言条件下比较修复前后：建连耗时、用户停止说话至首音、打断至停播、停播至可采纳新语音。至少 30 个有效样本/条件，报告 p50/p95、样本数与异常值，不能从两轮体验断言性能无损。
- 正式上下文新增处理开销目标不超过同条件基线 20%；保留绝对耗时。超过则先定位序列化、网络、SDK 或模型，不把总延迟都归给检索。
- 对适中会话（例如不超过 30 轮、用户文本不超过 1 万字），正常供应商情况下暂定会后可审核 p95 目标 60 秒；不满足应报实测并优化，不能通过提前显示成功达标。
- 失败有界：尝试次数、单次网络超时、分片数和全场总耗时受控；客户端等待窗口不决定服务端终态。
- 幂等性：重复上传/关闭/admission/重试后，一个逻辑会话不生成重复来源和候选。
- 可用性：新未审核内容与其整理失败，不影响已有正式记忆；正式依据撤权后不能继续使用缓存。
- 保持小型部署：不新增数据库、常驻模型或复杂消息基础设施；复用 PostgreSQL、pgvector、已有 Worker/outbox、DeepSeek 和火山接入。
