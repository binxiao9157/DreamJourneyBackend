## 2. 必须保留的产品与架构边界

- **唯一正式事实权威：**同一人物的当前有效正式版本集合在 PostgreSQL 中；pgvector、画像、整体正文和自传是可追溯派生，不另建可独立改写的正式记忆分支。保留版本历史不算分叉。
- **写入边界：**素材和用户对话进入 Source/Conversation，再整理为 Candidate；用户确认后才成为正式事实。用户纠正应更新对应结构和证据，拒绝不得写入正式事实。
- **客观性：**不在整理时增加经历、情感、关系、程度或时间。回复可以温柔、口语化，自传可以有文学表达，但都不能反向污染正式事实。
- **统一事实、不同交互：**文字由 DeepSeek 回答且不自动朗读；Live 保留火山原生持续会话、打断与续听。两者措辞可不同，人物、权限和事实版本必须正确。
- **会话语义：**每回合可靠保存；从用户开启到主动关闭或既定有效空闲结束算一场，整场只整理一次。多条候选不等于多次整理；没有新事实允许 `completedNoChange`。
- **授权边界：**本人、在世家人贡献和授权查询保留各自边界。Visitor 读取被授权的独立发布版本，不自动改为私人域最新事实。本轮不扩大逝者场景。
- **检索降级：**结构和关键词是有效基线；向量增强有超时、故障和回退观测，不允许模型异常造成已接收内容丢失或退回无授权旧资料。
- **保持轻量：**优先修正已有 PostgreSQL、Worker、模型适配器和测试。不要为通过清单擅自新增独立向量库、图数据库、常驻大模型、复杂监控集群或替换 BGE-M3。

## 5. S02：三入口沉淀和事实消费一致性

### 5.1 统一追踪链

### 5.2 非设备必测矩阵

| 场景 | 由 Sol 验证的后台与客户端结果 |
|---|---|
| 记忆档案新建文字素材 | 成功回执对应已持久接收；整理完成出现可审核候选；通知与真实状态一致 |
| 当前已开放的图片/文档 | 走实际已开放处理路径；未开放时入口/错误明确，不假装上传成功后永远等待，也不擅自开启能力 |
| 文字多回合新增经历，结束 | 每回合可恢复；结束后整场只整理一次；候选覆盖用户事实，不吸收助手猜测或建议 |
| 文字只查询已有学校事实 | 可以正常结束；无新增事实不误报“整理未完成”，也不复制已有事实制造新候选 |
| Live 元数据多回合、关闭 | 模拟器/协调器按真实客户端合同投递，后台以同一会话接收；关场后可整理，不能只运行直接插表脚本 |
| 网络重试、乱序、重复关闭、缺少回合 | 同回合不重复生效；有缺口不得先显示“整理完成”；补齐/超时失败/恢复都有明确状态与重试路径 |
| 候选更正、拒绝、依赖组成组确认 | 前后端合同一致；只激活批准内容；原子提交，冲突或失败不留下半组正式事实 |
| 在世家人合法贡献及越权 | 作者、记忆主体、审核者分清；不把家人第一人称默认认作本人；审批不绕过正式事实确认 |
| 正式事实修改或撤权后再查询 | 文字、Live 快照、整体正文和自传输入遵守同一范围的当前版本；失效派生不能继续当当前事实 |

### 5.3 Live 需要证明到哪一步

在 A 中检查真实装配、序列化后的快照、人物/授权 epoch、正式 revision、checkpoint、context hash、内容预算和传给 SDK 的位置。证明学校等关键事实没有在摘要/截断中消失，不能只看到 ticket 创建成功就写“Live 已使用记忆”。

不得为了统一答案强迫 Live 每轮再次调用 DeepSeek，也不得恢复文字自动朗读。优先保持现有原生语音速度与打断体验。

## 7. S04：补齐恢复的技术证明

### 7.1 三个词对应的具体工作

- **身份归属校验：**恢复后能用既有身份系统证明某 Vault/事实属于哪个合法主体，而不是因 ID 相似就认领。
- **异步任务归属校验：**能证明哪个已接受业务操作产生了哪个任务，任务仍有权限执行，没有被删除/撤权或重复完成。
- **恢复回放：**备份之后合法接收的新增、更正、删除和任务结果，从可靠记录恢复到目标边界；不能拿一个时间戳、LSN 或手工空文件假装已回放。

沿用现有事务、幂等、outbox、身份及证据机制补齐。不要求新建重型事件平台；若现有架构无法满足，先给最小设计差异、数据格式、成本与批准项。

### 7.2 操作与演练要求

1. 查明原恢复记录中身份根/任务归属证明缺失、未分类表和 `replayBundleMissing` 各自源头。分清代码缺失、生产配置缺失和数据政策依赖。
2. 在隔离真实 PG 中，由实际应用业务操作产生有依据的恢复证据，覆盖备份 cutoff 之后的新事实、更正、删除、撤权、已确认回合和排队任务。不要手工编造成功回执。
3. 恢复到独立目标，前向迁移至目标 schema，应用经核验回放并启动相应 API/Worker；通过应用路由验证事实、权限和任务状态。
4. 重复回放、中断续跑和迟到回调必须不重复写入、不复活删除内容、不串账号。派生向量/缓存可按现有机制重建，但不能把旧派生当正式权威。

### 7.3 验收边界

候选目标沿用原文 RPO <=15min、RTO <=2h。RTO 必须量到目标数据和必要服务真正可恢复使用，而非只算容器启动或数据库导入；未通过完整性时不能用原记录 `34s` 宣称满足完整恢复 RTO。RPO 以可恢复的已接受操作边界衡量，不只看备份文件时间。
