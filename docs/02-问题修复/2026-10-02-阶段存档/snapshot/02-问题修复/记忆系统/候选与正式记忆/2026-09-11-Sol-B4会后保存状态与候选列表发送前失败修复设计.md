## 4. 会后状态与幂等设计

### 4.1 最小实现组织

保留现有协调器、自然输入 UseCase、ack/admission/status UseCase。允许局部提取可测试的状态归约器和存储/客户端协议，不引入新后台服务或通用工作流框架。

- 所有协调状态、世代和回调验收在主线程或单一 actor 上串行执行；磁盘仍走现有串行 persistenceQueue。
- **先校验回执身份和处理阶段，再更改 UI 状态**，不能在 guard 前写 saving。
- 明确分离“本场结束是否已消费”“ack/admit 进行到哪里”“状态观察是否在运行”“本地收尾是否完成”。不要仅靠一个不可复位 Bool 管所有情况。
- 展示仍可沿用现有 enum；内部增加最小 `closePhase` / `observerGeneration` / `cleanupPending` 等等价字段。禁止用状态 enum 的全局数值大小比较阶段，queued/retryWaiting/organizing 之间存在合法往返。

### 4.2 身份与重复结束规则

会后任务身份使用：合法账号/空间/authority 边界 + `productSessionID` + 服务端访谈 `threadID/sessionID`，冻结 batch 后再绑定 `reviewBatchID`。**访谈 sessionID 与认证 sessionId 是两种身份，不要混用。** 临时 requestId、continuation 内容、认证 token 变化不构成新场次。

| 收到事件时的状态/阶段 | 相同已验证 ended receipt | 不同场次/不匹配 receipt |
|---|---|---|
| 首次合法结束，逐轮数据已持久化且 close fence 匹配 | 原子记录结束处理身份，推进一次 ack；saving 仅描述真实保存/提交阶段 | 拒绝，保留当前任务，记录 mismatch，不选择另一会话 |
| saving，end/ack 已发出 | 不重发新命令，不重置超时；必要时观察同一个进行中动作 | 丢弃并诊断 |
| queued、organizing、retryWaiting、statusUnknown | 状态不回退；ack/admit 不重复；已有观察者继续，确实失活时只恢复同 batch 状态读取 | 丢弃并诊断 |
| pendingReview、empty、terminalFailure、quarantined | 业务终态不变，不重新生成候选，不重新写 saving | 丢弃并诊断 |
| unavailable / 暂停恢复 | 不凭回执直接恢复权限；先走当前账号、策略与恢复门禁，合格后恢复同一任务 | 禁止恢复 |

对相同场次但版本、close 序号或关键回执内容不一致，不一概当重复成功；记录合同冲突并读取当前状态核验，不能覆盖先前身份。完整比较只在内存/受保护工作流数据内进行，日志不输出回执。

### 4.3 完整状态转移

| 当前阶段 | 事件/条件 | 下一状态与动作 |
|---|---|---|
| live | 用户结束或既有闲置结束规则触发 | mic 按既有原生链路停止；后台 flush 同场 outbox，不等待整理才恢复入口 |
| closing/flush | 没有用户表达，且无待持久化用户输入 | empty，表达“本次没有可整理的用户内容”；不能把磁盘错误当无内容 |
| closing/flush | 待发轮次未齐 | 继续保存，不发送越过缺口的 end；恢复仍沿用稳定 turnId/sequence/command |
| closing/flush | 所有轮次完成持久化，close fence 满足 | saving，执行一次 end；当前 `advanceNaturalInputPipeline` 的 live guard 必须同步适配，不能先改 saving 又令 flush/end 永远不能执行 |
| saving | end 回执合法 | 保存阶段坐标，进入 batch discovery / acknowledgement；无新增 end |
| ack 进行中 | ack 合法完成 | 同 batch admission；UI 可显示 queued，但内部阶段不得混淆 |
| admission 进行中 | admission 被持久接受 | 先持久化 follow-up，再转交 outbox 责任，开始 status observation |
| queued/organizing/retryWaiting/statusUnknown | status.notReady，job pending/notCreated | queued，安排下一次状态读取 |
| 同上 | status.notReady，job leased | organizing，继续观察 |
| 同上 | status.notReady，job retryWait | retryWaiting，尊重 retryAvailableAt，显示重试状态，不手动执行 Worker |
| 同上 | status.notReady，job unknown 或 succeeded 但 review 状态未就绪 | statusUnknown，继续有限频率观察；job succeeded 本身不能当 reviewReady |
| 同上 | status.reviewReady | pendingReview，显示“可在待确认记忆中审核”；不等于正式记忆已写入 |
| 同上 | status.noCandidates | empty，按服务端真实语义显示无待审核新增；不能由候选总数自行推断 |
| 同上 | extractionFailed 或失败终态 | terminalFailure，显示明确失败；不显示成功或一直保存 |
| 同上 | extractionQuarantined | quarantined，不自动解除隔离或重放 |
| 任一非终态 | 临时网络/超时/未知状态 | 有限退避并保留恢复坐标；显示暂未确认状态，不回退 saving |
| 任一阶段 | 登出、账号/空间更换、authority 变化、恢复策略禁止 | 停止旧作用域请求和渲染；保留隔离数据，交由合法重新进入处理，不越权重新绑定 |
| 业务完成 | 本地清理失败 | 业务终态和 cleanupPending 分开；不能把服务端已完成改成仍保存，也不能伪造“清理已完成” |

成功业务状态以当前 batch 的经过鉴权、合同校验的 status 为准。ack 201、admission 201、extraction job succeeded 或通知出现都不是正式写入成功。

### 4.4 观察器、乱序与前后台

1. 每个工作流同一时刻最多一个 ack/admit 动作、一个 status 请求和一个后续 poll timer。重复通知不得启动第二套。
2. 每次重建观察器递增 `observerGeneration`；响应同时校验协调器身份、账号租约、batch、请求代次和当前阶段。旧 queued 响应不得覆盖已消费的 reviewReady。
3. 晚到 continuation、ack/admit 的失败只影响其仍拥有的阶段；业务已推进时不能把新阶段设为 unavailable。

### 4.5 持久化交接与恢复

当前 `persistFollowUpThenBeginObservation` 实际顺序是 `followUp.upsert → outbox.remove → status`。保留“先建立下一阶段责任，再释放上一阶段责任”，不要被旧注释误导成已经覆盖所有窗口。

局部扩展现有持久工作流元数据，至少覆盖 end、ack、admit 的待发命令与已接受坐标。可扩展文件型 outbox envelope 或增加同一受保护目录中的小型 completion checkpoint，不能用 UserDefaults 的 set 返回值宣称严格磁盘提交完成。推荐与现有文件存储一样原子写入；版本读取兼容本机已有 v1，不能清空旧记录。

保存内容限于 productSessionID、访谈 thread/session、冻结序号、batch、阶段、**精确的待发 commandId/版本前置条件及已验证回执所需最小元数据**；不要新增 transcript 副本或保存 credential。关键约束：

- 发出 end/ack/admit 前先记录同一个命令，丢响应或重启时重试原命令，不每次生成新 UUID。服务端既有 command receipt / by-batch 去重是最后保护，不能以新命令碰运气。
- end 已接受但客户端未保存回执：凭持久命令重获同一回执，不能走只查 active 的 current-session 路径来创建新会话。
- ack 已接受但 admission 未发送：凭持久 ack 命令/回执继续同 batch；不能只查 pendingAcknowledgement，因为此 batch 已不在其中。
- admission 已接受但回执或本地存储失败：使用原命令或已知 batch 的 status 核验；不得重新创建 Source/批次。
- 已有 follow-up 的恢复是只读 status，不走录音/start/end/重新抽取。只有 outbox、没有新 checkpoint 的旧记录不得猜造命令；用现有合法只读接口核验，无法确定则明确恢复待核验，保留数据并记录兼容限制。
- 同时存在 outbox 和 follow-up 时，以可验证的已持久阶段决定责任；同 batch 不建立两个 coordinator。逐个崩溃点测试写入失败、移除失败、进程退出。
- 当前 follow-up 按 subject/vault/authority 隔离。认证凭据合法轮换不改变历史归属；**authority 不同不能扫描、搬运或重新标记旧记录**。不做历史批量修复。
- 本地清理是正常已完成任务的生命周期，不是删除生产候选/历史。只允许清理已验证完成的本地工作流记录；未确认/失败/隔离任务不可直接清除以让 UI 好看。

若现有服务端命令重放不支持上述某个精确窗口，先用本地隔离存储/测试库证明，再报告为局部合同缺口；不得擅加生产重放脚本或放宽 authority 校验。

## 6. 安全恢复列表，不恢复旧审核权利

### 6.1 所有者和请求作用域

### 6.2 可恢复与不可恢复

| 变化 | 列表处理 | 旧审核内容处理 |

### 6.3 读取恢复流程

```text
用户刷新 / 已验证凭据更新通知
  → 主线程进入同一个 refresh single-flight
  → 校验当前 scope 与原页面连续性
  → 如需恢复：先 invalidate 旧审核树和回调 generation
  → 等待既有 auth single-flight 完成（不再造登录系统）
  → 必要时刷新对应 owner/cohort/build 的 policy/config
  → 捕获新 lease + 新 FeatureDecision，并执行原有门禁
  → 用新 UseCase 发一次候选 GET
  → transport / decode / commit / UI 再检查同一 scope 和 generation
  → 真实列表展示；用户重新打开预览才能确认
```

预算：每个用户读取意图最多一次凭据刷新恢复、一次必要策略/config 同步、一次候选重新发送；底层已有重试与上层共用预算，不能相乘。连续点击共享当前任务，必要时只排一个尾随刷新，不开无限队列。再次失败显示明确原因，用户可重新发起独立意图。

只给 `GET candidates` 等本次明确的只读流程增加恢复，不泛化到 `decisions`、关联组 confirm、Source 创建、admit 或其他写接口。不要修改全局 FeatureGate generation 定义来让所有旧决策都通过。

### 6.4 旧 Candidate/Proposal/Binding 失效细节

必须同时处理：

- UseCase 的 candidatesByID、orderedCandidateIDs、memoryRevision、batchCommandIDsByCandidateID。
- 单条详情持有的 Candidate、更正异步请求、服务端更正预览和 displayedBinding。
- 关联组选择、group proposal、组内更正/拒绝动作、group binding、确认闭包。

- 弹出的详情/预览/确认框须关闭或显示“账号状态已更新，请重新载入后审核”并禁用提交；不能只清主列表却留下可点的弹窗。

对**已发出的审核写请求**，失效的是继续操作权，不是既有请求事实：不能显示“肯定未写入”，不能自动补发另一个 command。保存最小结果核验坐标，重新鉴权后只读核验回执/审核历史；用户重新预览之前不得再提交。不会因为同一候选内容没变就自动重新授权旧 Binding。

### 6.5 错误分类与用户展示

新增或扩展局部 typed failure classification，至少分为 `accountChanged`、`authenticationUnavailable`、`permissionUnavailable`、`recoveryRestricted`、`networkUnavailable`、`serverFailure`、`contractMismatch`、`cancelledOrSuperseded`。unknown 可保留，不能都归 retryable。

| 分类 | 对用户的文案方向 | 恢复规则 |
|---|---|---|
| accountChanged | 账号状态已变化，请重新进入待确认记忆 | 旧树失效，不跨账号重试 |
| authenticationUnavailable | 登录状态暂不可用，请稍后重试或重新登录 | 仅走现有认证流程 |
| permissionUnavailable | 当前暂不能访问待确认记忆 | 不无限自动刷新，不描述成“空列表” |
| recoveryRestricted | 服务正在恢复，暂时无法读取待确认记忆 | 保留数据与真实门禁 |
| networkUnavailable | 网络连接失败，请重试 | 一次显式读取；不清候选 |
| serverFailure | 暂时无法读取，请稍后重试 | 保留错误码的安全分类 |
| contractMismatch | 记忆数据格式暂无法识别，请稍后重试 | fail-closed；不能删条目/放宽结构来通过 |
| cancelledOrSuperseded | 通常不额外弹窗，由新任务接管 | 旧任务不能覆盖新 UI |

页面 `emptyText/statusText/noticeText` 必须协同使用分类，避免上方有具体错误，下方仍显示统一“读取失败”掩盖原因。

```text
  → observerStarted → statusReceived → statusApplied → terminalRendered

CandidateInbox: inboxRefreshRequested → useCaseGateChecked
  → candidateClientEntered → authChecked → backendLeaseChecked
  → applicationLeaseChecked → recoveryChecked → featureRevalidated
  → transportCreated → transportResumed → responseReceived
  → jsonDecoded → inboxContractDecoded → scopeCommitted → uiRendered

任何节点失败：requestDenied / requestFailed / responseDiscarded
  必须包含对应阶段、原因与同一个随机 trace 标识
```

日志中的成功只表示本节点成功。`transportResumed` 不证明服务器收到，`uiRendered` 不证明用户审核，`terminalRendered=pendingReview` 不证明正式记忆写入。
