## 1. 结论与执行原则

1. **F1 存在可由当前源码确定的连续审核缺口**：A 审核成功后，UseCase 推进 `memoryRevision`，但保留 B 的旧 `proposedChangeSet.baseMemoryRevision`。B 再确认时，合法 Binding 校验会在发送前拒绝。应刷新 B 的正式预览并让用户重新核对，不能删除版本校验或偷偷改 Binding。
2. **F1 的“成功显示”必须另行定位**：代码中的普通失败状态会清空 `latestReceipt`，不能断言失败状态直接保留 A 的回执。已确定页面在发送审核意图前就返回列表，而且成功提示缺乏独立审核操作归属；具体是哪一个 UI 元素让用户看到成功，现有日志不足以还原，必须通过真实 UIKit 组合测试和下一轮可见页面证据确认。
3. **F2 根因已由日志与代码相互印证**：初始 FeatureGate 返回 `expiredPolicyCache` 时，适配器直接失败；已有恢复分支在 `requestJSON` 回调之后，既到不了初始失败，也未包含该原因，且只是重新捕获策略，不等于实际刷新服务端策略。
4. **F3 不能认定为 F1/F2 根因**：当前缺失检查点分支只报告该工作流被阻断，没有创建恢复协调器。当前版本本身存在 `markClosing` 先于 `prepareEnd` 的窗口，因此不必然是旧版遗留；真实历史记录的形成原因仍未知。
5. **补齐一个局部后端能力**：审核请求结果不确定时，需要按审核命令查持久结果的只读接口。当前历史列表不能精确核对该命令，不能用重发 POST 查询结果。F1/F2 主因在 iOS；这项新增读合同单独实现、测试和判定部署。

顺序：冻结证据 -> 建立红测 -> F1/F2 局部修复 -> 只读结果查询 -> F3 隔离验证 -> 本地门禁 -> 等用户授权安装/部署和逐步真机复测。不得把本地 PASS 写成 B4 已通过。

## 4. 先建立反例，再修改

以下为**应在冻结的当前代码上先执行的红测设计**，本次未执行。测试工具链/导入失败不得算业务红测。

### R-F1-01：两条 V5 的修订失配

构造同 vault 的 A、B，列表 revision=R，二者 proposal.baseMemoryRevision=R。使用真实 proposal builder 生成两条独立合法提案，不手拼绕过字段校验。真实 Controller 打开 A，用户确认，受控服务返回合法 A 回执和 revision=R+1。再次打开 B。

当前代码预期：没有自动取得 B 的新提案，B 确认在 `makeCommand` 被拒绝，第二次写调用数为 0。产品断言应是“自动刷新剩余预览；用户核对 B 的新预览后，可以发送并取得独立回执”，而不是“允许 R 的旧 Binding 在 R+1 上写入”。旧 Binding 拒绝的安全断言必须继续 PASS。

### R-F1-02：审核意图与可见结果脱节

保留 A 成功后的列表，打开 B 并在确认瞬间令策略门禁拒绝。真实 UIKit 记录确认前、意图送出、本地失败完成、下一次主线程渲染后的导航栈、候选关联状态和可访问性文案。断言：B 详情不能在结果产生前被当成完成而关闭，B 不能出现 A 的成功提示，本地失败可见且 B 保留。

现代码 `popViewController` 先于 `send` 可形成明确生命周期反例。另加一个保护测试：`transitionFailure` 后 `latestReceipt=nil` 且成功 label 隐藏；该项可能在修复前就 PASS，必须如实保留，不得人为改造成红测。如果用户所见的“成功”未被还原，记录为 UI 现场归因 NOT_RUN，不能宣称已经精确复现。

### R-F1-03：写入与读刷新竞争 / 401 重发

受控网络挂起 A 的 POST，触发列表刷新，再返回 A 的成功。当前共用 `operationGeneration` 可能使回执被丢弃；测试必须观察持久写操作结果，而非只检查列表内容。另对真实 BackendClient 的单条审核制造 POST 401 + 合法凭据更新，断言 POST 只执行一次；不能只测 helper 或关联组另一条写链路。

### R-F2-01：初始缓存过期

真实 `FeatureGateEvaluator` + 隔离的 `ReleasePolicyStore` + 可控时钟；合法同主体账号租约，候选功能已开启，但缓存到期。通过真实 UIKit -> UseCase -> BackendClient，受控网络提供一份新的合法策略及候选响应。

当前预期失败：在 `featureInitial` 结束，没有触发策略 fetch 和候选 GET。目标断言：一次实际策略刷新，然后同一读取意图自动 GET，不需手动刷新。不得使用 QA gate 常开、直接 stub `.allowed` 或在进页面前手动刷新来让该测试通过。

### 5.2 必须修复的三个独立问题

**剩余预览过时。** A 的成功会改变 B 做事实比较的基础。即使 B 本身的 candidateVersion 没变化，B 的旧 ChangeSet 也不能当成新版本上的正确差异。应使 B 暂时不可确认，自动读回正式构建的 B 新提案，而不是修改其本地 baseMemoryRevision。

**写结果生命周期被列表生命周期控制。** `refresh` 和 `submit` 都递增全页 `operationGeneration`；`receiveDecision` 首行按该 generation 丢弃回调。读刷新只能隔离旧读结果，不应抹除已发出的审核命令结果。另一方面，当前 `submit` 没有可靠的 per-command 防重复入口，UI 的禁用不能覆盖重复闭包、测试调用和生命周期竞态。

**显示/导航没有和本条持久结果绑定。** 当前详情提前关闭，列表用全局成功提示，`relatedGroupNotice` 还有更高展示优先级。这是待修复的结果归属风险，但本次没有证据说明关联组提示参与了现场。正确修复是每个操作结果明确归属候选，不是简单清空所有全局文案后宣布根因已解决。

## 6. F1 修改设计：不可变操作与真实结果

### 6.1 最小新增类型与所有权

在既有 OwnerTruth 审核模块内新增或扩展以下类型，不建立通用任务框架：

| 类型（建议名） | 职责 |
|---|---|
| `CandidateReviewOperationContext` | 不可变审核意图：subject/vault/合法 lease、授权代次、candidateID/version/hash、action、proposal/changeSet/hash/baseRevision、previewID、commandID、operationID。更正 payload 仍使用现有规范化合同，不把正文写日志。 |
| `CandidateReviewOperationState` | 独立写状态及证据强度；与列表 loading/ready 分离。 |
| `CandidateReviewTransportOutcome` | 区分明确未发送、可能发送但未知、明确业务拒绝、合法持久回执。不能把所有 Error 映射成同一个“提交失败”。 |
| `CandidateReviewPendingResultStore` | 只保存查询所需的受保护命令/绑定元数据与进度，不保存认证凭据，不重放写 payload。跨页面或重启后仅查询已发命令的结果。 |

先复用已有相同职责的类型；若新建本地存储，使用受保护的 app-private 文件和原子写入，与 Live outbox 完全隔离。测试用临时目录。不得把命令存储做成自动提交队列。

同一个 vault 同时最多一个主动审核写操作；每条候选拥有独立操作上下文和结果。另一个候选在前一个正在提交/结果待核实期间可查看，但不能隐式排队提交。用户需在它获得最新可确认预览后重新点击确认。不同候选不得共享 commandID。

### 6.2 审核写入状态机

| 状态 | 进入条件 | UI 与允许行为 |
|---|---|---|
| `previewReady` | 当前作用域、最新 proposal 与展示 Binding 相符 | 可由用户确认；不能显示本条成功 |
| `checking` | 捕获本次不可变意图，检查 lease、策略、恢复门禁、版本及在途占用 | 禁止重复按钮；不关闭详情 |
| `notSent(reason)` | 有确定的本地门禁失败，且没有交付给可能发送的 transport | 明示“本条未提交”及准确原因；保留候选，修复条件并展示新预览后由用户重试 |
| `submitting` | 持久记录已准备，请求交给 transport | 显示“正在提交本条”，不等于成功 |
| `outcomeUnknown` | 可能已发送后的断连、取消、超时、非合同 5xx、回执解码/绑定不确定、进程中断 | “暂无法确认本条提交结果，正在核实”；不得显示确定未写入或自动重发 |
| `checkingResult` | 同主体重新合法鉴权后执行结果 GET | 只读、有界；保持原 commandID；不能自动生成新的写意图 |
| `serverRejected(reason)` | 取得可验证且具有“本命令未提交”语义的业务拒绝 | 显示冲突/权限等原因；冲突要求新提案、再次确认 |
| `committed(receipt)` | 获得并核验本命令对应的持久审核回执、合法 activation | 按具体 decision 显示结果；accepted/corrected 满足既有 MemoryVersion 合同时才显示“已纳入正式记忆” |
| `blockedByAccount` | 账号/主体/权限不再允许查看结果 | 清除当前页面私有内容；不展示旧账号结果，也不把可能写入改成“未写入” |

`superseded` 只能描述某个 UI 展示/预览过时，不是已经发出的命令被取消。列表刷新不得把 `submitting/outcomeUnknown/committed` 覆盖成另一条候选的状态。HTTP 200/201 本身仍需 typed 合同和绑定校验；响应损坏不能直接改成“服务端没有写”。

### 6.3 提交步骤

1. 打开 B 详情时清除 A 的临时全局成功提示；若保留历史结果，必须明确标明对应 A，不能出现在 B 的确认结果位置。
2. 点击确认后，捕获不可变 context；校验当前账号、策略、恢复门禁、candidate/version/hash、完整 proposal 和展示 Binding。失败原地显示，不先 pop。
3. 同候选重复点击合并到现有 operation；已有不确定写结果时禁止创建新的 commandID 逃过防重。同 vault 其他审核明确提示等待，不悄悄发送。
4. 创建一次 commandID。将最小待核实记录原子落盘后才能放行 transport；持久化失败则 `notSent(localPersistenceUnavailable)`。这仅影响审核按钮，不进入 Live 热路径。
5. 扩展审核 service 方法，显式传入 accountLease、operationContext、诊断 trace 和不重发策略；不要从全局账号重新推断本次审核主体。
6. 分离 `readRequestID/readGeneration` 与写 `operationID`。写回调按本操作和作用域核验、保存结果，再决定是否更新当前页面；页面已经离开也不能遗失可查询的操作。
7. 合法成功后只移除回执对应候选，更新本地 `minimumKnownMemoryRevision`，失效所有依赖更旧正式修订的剩余 V5 preview/Binding/selection/确认闭包，自动读取新列表一次。
8. 新列表或预览未完成时允许看到 B 的只读卡片并显示“正在更新审核内容”；不能继续确认旧 proposal。新提案到达后重新展示差异，用户自行确认 B。旧 alert 晚到一律拒绝。
9. 按 action 和真实 activation 显示结果；拒绝不显示“已纳入”，不可用/冲突不显示成功。保持八种 ChangeSet 操作及关联组的既有合同，不通过统一文字把不同结果混淆。

回执核对必须区分命令的 `expectedCandidateVersion`（提交前）与回执 `candidateVersion`（决定后），按现有后端行版本推进合同验证，不能直接要求两者相等。`candidateBeforeHash` 要与本次展示候选的原 hash 匹配；正常 POST 的结果必须来自该操作捕获的请求完成回调，查询结果还需 command/proposal 绑定匹配。正式记忆写入成功与投影/向量稍后完成是两个状态，不能用 Worker 尚未完成否定真实写入，也不能以真实写入替代投影验收。

### 6.4 刷新乱序与版本冲突

- 读返回 revision 小于 `minimumKnownMemoryRevision` 时不得提交到可审核 UI；清晰记录 `snapshotBehindCommittedRevision`，最多再读一次，仍落后则阻断审核，不无限轮询。
- 同主体合法凭据更新、策略更新、事实修订更新分别触发 review preview epoch 失效；不把它们一律当“账号换人”，也不因此抹除在途写的结果记录。
- 已发写的回执即使晚于新读结果，仍按 operationID 记账；不能让 A 的晚回执覆盖 B 的详情或成功状态。
- PG CAS 冲突必须保留。收到明确冲突后刷新 proposal，展示新的完整 typed 差异；用户再次确认才能生成新命令。
- 关联组使用同一失效机制，但保留既有原子提交、成员集合和绑定检查。普通单条修复不得将关联组拆成逐条 POST。

### 6.5 禁止自动重试审核写

[reviewOwnerTruthCandidate](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DreamJourneyBackendClient.swift:8762)当前调用 [requestJSON](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DreamJourneyBackendClient.swift:14162)未禁用默认刷新/重试；其 401 分支会在合法 successor/refresh 后递归请求。

修复应使用明确的 `requestSemantics = nonReplayableReviewWrite`（或等价现有参数），关闭该审核写的 `allowsRefresh` 后重发及 `allowsRecoveryRefresh` 后重发，核查 Alamofire interceptor/redirect 和其他包装层没有隐式重试。认证可以为后续只读核实刷新，不能再带原 POST 自动走一遍。不要全局禁用 Live 或其他只读请求的认证恢复。

在 transport 已获得请求之后，除非能够可靠证明没有发送，均按可能发送处理。`taskCreated` 不是发送证据，但“未记录 taskResumed”也不是确定未发送的证明。本地判断应来自结构化 transport outcome，而不是读日志推断。

## 7. 不确定写入的只读核实合同

### 7.1 为什么需要后端局部补充

现有 [candidate-review-history 响应构造](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/main.py:5123)面向历史展示，不提供足以精确绑定该次 command 的结果。现有 [decision 响应](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/main.py:5160)可以正常返回持久回执，但客户端断连后无法按 command 重新读取它。

仓储 [_receipt_by_command](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/services/owner_truth_candidate_review.py:3665)是内部写事务查询并带锁；不能直接开放成接口，更不能调用 `decide_and_activate` 来取得“查询结果”。历史同一 candidate 已 accepted，也不自动证明是本次命令提交。

### 7.2 建议新增接口（待实现，不是现有 API）

```http
GET /v2/vaults/{vaultId}/candidates/{candidateId}/decision-result
X-DreamJourney-Review-Command-Id: <本次高熵命令ID>
```

命令 ID 放专用 header，避免进入默认 URL 访问日志；它不是认证凭据，必须继续执行 Owner/授权范围、有效 lease、恢复状态和 candidate 所属 vault 校验。禁止默认记录该 header。需要撤权后恢复查看时，只允许按现行授权返回最小结果，不能泄露历史正文。

响应 schema 建议 `owner-truth-candidate-decision-lookup-v1`，区分：

| result | 合同 |
|---|---|
| `found` | 本主体、vault、candidate、command 唯一匹配的持久 receipt；附 expectedCandidateVersion、candidateBeforeHash、expectedChangeSetId/expectedProposalHash（适用时）、原决定及 activation 身份。与本地不可变意图逐项核对。 |
| `notObserved` | 本次一致性读未观察到该命令的持久结果，不证明原 POST 将来不会提交；继续 `outcomeUnknown`，不能自动补发。 |
| 权限/作用域错误 | 标准受控错误，不泄露候选是否存在；不是 `notObserved`，更不是确定未写入。 |
| 持久回执存在但 activation/绑定不完整 | 明确 `inconsistentResult`，客户端保持阻断并报告；不得制造成功。 |

`found` 的正式版本、回执内容来自原事务已提交记录，不重新生成版本、不重新触发 projection、不刷新事实、不入队。当前 vault revision 若同时返回，应命名 `currentMemoryRevision`，不能冒充该命令原提交修订；只有能从权威持久记录恢复原修订时才返回 `appliedMemoryRevision`，不得猜测。

若原正式版本后来被更正，区分“这条审核曾成功”和“目前有效的正式版本”；不要为了查询原回执要求旧版本仍为 current，也不将已撤回版本重新恢复为 current。

实现只读 service/repository 方法，使用已有 command hash 规范，按 vault/Owner/candidate/command 条件查询，在短生命周期的一致性只读快照内取得 receipt/activation，避免 `FOR UPDATE`、advisory lock、激活/写函数。返回前继续遵守现有授权有效性检查，不为查询旧结果扩大权限。现有回执已存 command/payload hash 与 proposal 绑定信息；预计不需要新增表或数据迁移。若发现必需字段无法从持久记录可靠获取，单列合同缺口并停止该项，不能临时修改生产 schema 或填造字段。

首次未知后可以自动发一次结果 GET；仍 `notObserved` 时明确提供“核实结果”，允许有界的用户触发 GET。查询失败/超时释放查询占用，但保留未知写状态和 command。缺少安全的“原请求已终止且未提交”证据时，不提供自动重新提交。产品体验可能暂时阻断这条审核，这是比重复写入/假成功更安全的结果，需在交付风险中列明。

## 8. F2 实际调用链与局部恢复设计

### 8.1 已证实的断点


代码定位：[只读入口及初始 guard](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DreamJourneyBackendClient.swift:8173)、[FeatureGateService](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DreamJourneyBackendClient.swift:426)、[FeatureGateEvaluator](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/ReleasePolicyStore.swift:320)、[缓存到期判定](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/ReleasePolicyStore.swift:634)。

当前 adapter 回调仅对 `accountGenerationChanged/capturedPolicyExpired/policyVersionChanged` 做一次 recapture。初始 guard 在此之前返回，`expiredPolicyCache` 也不在列表中；重取本地 decision 不能替代 [fetchReleasePolicy](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DreamJourneyBackendClient.swift:7372)。这是前序“策略重新获取”测试没有覆盖的入口。

### 8.2 增加候选只读 preflight 结果，禁止放宽 gate

建议局部 `CandidateInboxReadGateOutcome`：`allowed(context)`、`needsPolicyRefresh(expiredPolicyCache)`、`denied(reason)`。保持真实 FeatureGate evaluator 的所有拒绝规则；不是把 `.allowed` 改成 true。

顺序固定为：

1. 验证同主体 AccountLease 和 vault，确认该读取意图仍拥有页面 requestID。
2. 检查当前认证及恢复门禁；跨主体/退出/注销/不允许的恢复状态直接阻断。
3. 初始 FeatureGate 为缓存过期，且属于同账号已知策略失效时，进入一次策略刷新；功能明确关闭、scope/audience 不匹配、未知策略原因不得按“缓存过期”放行。
4. 通过现有受认证策略读取路径取得新策略，重新验证账号、scope/audience、策略有效期和功能许可，再捕获新的 request decision；不能复用原 expired decision。
5. 再次进行 request-time 认证、lease、恢复、feature revalidation，才创建候选 GET；typed decode 和 UI commit 再校验当前所有权。

UseCase 的布尔 gate 如先截断请求，应改为传递上述 typed 结果或交给统一候选读 preflight 协调，而不是另开永远允许的入口。只给候选只读入口恢复资格，不给审核写入口套用同样自动继续规则。

### 8.3 单飞、预算及 attempt

延用 `OwnerTruthCandidateInboxReadContext/Outcome`、`CandidateInboxReadAttemptState` 和 requestID 所有权；新增局部 policy-refresh port，生产调用现有策略 API，测试注入真实 store/evaluator 与可控网络。不得另写一套策略判断。

| 层 | 规则 |
|---|---|
| 读取意图 | 同一用户首次进入/当前刷新意图持有稳定 trace、requestID、deadline、预算对象。策略恢复不能伪装成一个全新成功意图。 |
| attempt | 初始 preflight 为 1；恢复后重新评估并继续原读为 2。认证恢复若再发生，单调递增；页面/解码取实际完成的 attempt，不能回到 1。 |
| 策略请求 | 使用原 trace，并记录 `purpose=policyRefresh`、实际 attempt、独立 requestID；它不是候选 GET 次数。 |
| 总预算 | 一个意图最多一次实际策略 fetch、一次合法认证恢复、最多两次候选 GET。多个恢复层共享预算，禁止递归嵌套把上限相乘。 |
| 超时 | 建议策略恢复 15 秒、总意图 30 秒的可测试上限；由注入 Clock/现有超时配置实现，若项目既有更严格上限则保持。上限不是用 sleep 延迟掩盖问题。 |
| 多次刷新 | 活跃恢复期间合并为同一意图；最多一个尾随刷新标记，完成后确有新读取需求才另启意图，禁止每次点按都递归新增。 |
| 策略 single-flight | 按主体作用域、feature、策略 audience/cohort 及有效认证代次复用。不同主体/不合法代次不共享结果；同主体合法 successor 须通过现有验证。 |
| 释放 | 只由仍拥有 requestID/attempt 的完成或超时路径释放；旧 attempt 的 defer/取消回调不能清掉新 attempt。每意图完成一次。 |

### 8.4 旧审核授权失效，但不取消合法读取

进入恢复时旧 Candidate 可暂作不可操作的列表内容，必须撤销旧 proposal、displayed Binding、selection、详情确认闭包和关联组 preview 的确认权。更新后即使账号 subject 未变也不能复用旧确认。

失效事件要带 reason 与新的 preview epoch。不得把“使审核上下文过期”和“撤销当前只读 requestID”合并为同一全页 generation，否则刚恢复好的 GET 会被自身失效动作丢弃。

合法策略响应只更新正确作用域的缓存；迟到的旧请求不能使策略版本倒退、恢复旧审核权或提交到新账号页面。新候选 GET 完成后才赋予新预览确认权。此前已经发出的审核命令仍按第 6–7 节保留结果核实，不自动重试。

### 8.5 准确错误展示

区分 `policyRefreshFailed`、`policyRefreshTimedOut`、`policyStillExpired`、`featureDisabled`、`authenticationUnavailable`、`accountChanged`、`recoveryRestricted`、`networkUnavailable`、`contractMismatch`。用户文案保持简短，例如“权限信息更新失败，请重试”与“当前账号暂不可使用此功能”，诊断保留真实枚举原因。

401 成功刷新只是中间事件；策略返回 200 但无效/过期也不能继续 GET。超时后缓存合法更新不等于已失败的旧读取可以迟到成功；用户再刷新应正常创建新意图。失败不能吞掉占用，不能无限旋转或永久合并刷新。
