## 3. 已证实的问题

### 3.1 P1：六处插值丢失，用户无法看清写入预览

文件：[MemoryArchiveViewController.swift](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Archive/MemoryArchiveViewController.swift:7995)。

HEAD 中确实存在以下普通字符串，而不是 Swift 插值：

```swift
"基于正式记忆第 (proposal.baseMemoryRevision) 次修订快照"
"目标：正式记忆第 (targetVersion) 版"
"确认前：(beforeText)"
```

## 4. 正常链路与不能误判的部分

### 4.1 实际数据流

```text
Live 一场会话结束
  -> 已保存的用户轮次与会后整理
  -> Candidate（尚非正式记忆）
  -> GET candidates 获取候选及 proposedChangeSet
  -> iOS 校验候选版本 / contentHash 与 proposal 的绑定
  -> 候选原文 + 服务端预计写入差异
  -> 用户明确确认 / 更正后确认 / 拒绝
  -> decisions 携带预览绑定参数
  -> 服务端重新构建方案并在版本锁内校验
  -> 审核回执 + 按操作合同更新正式记忆
  -> 异步投影 / 向量就绪
  -> 文字问答及新 Live 会话使用已确认事实
```

### 4.2 后端存在 before/after 和预览绑定，不应重写整条链路

在 [memory_changeset.py 的 _proposal_operation_payload](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/domain/owner_truth/memory_changeset.py:663) 中：

- add、temporalChange、dispute、correct 的 after 取目标候选的结构化内容。
- refine 的 after 是与目标正式事实进行无损补充后的结果，不一定等于候选全文。
- addEvidence、duplicate 等的 after 使用既有事实；noPersonalFact 可以合法为空。
- before、after、目标版本、字段差异和证据差异参与服务端方案构造与摘要绑定。

[OwnerTruthCandidateInboxItem](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:1052) 校验 proposal 的 `candidateVersion` 和 `candidateContentHash` 与候选一致。`OwnerTruthJSONValue` 保留 before/after；没有发现这两个字段被解码成占位符的代码。

[PostgresOwnerTruthCandidateReviewRepository._assert_proposal_binding](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/services/owner_truth_candidate_review.py:2643) 在正式记忆修订锁下重新计算方案，并检查 revision、ChangeSet ID、proposal hash；不匹配即冲突。内存实现也有对应校验。

因此，**代码与本轮自动化支持“绑定机制已存在”的结论，但尚未取得该手机候选的实时响应作为逐字段证明**。Sol 在 A 阶段应使用经授权的只读接口核对当前候选；不得为了拿证据直接确认它。

### 4.3 术语必须跟真实合同一致

本项目当前八种 operationKind 是：

`add`、`addEvidence`、`refine`、`temporalChange`、`correct`、`dispute`、`duplicate`、`noPersonalFact`。

问题记录中的 `merge`、`supersede` 不是当前两个额外 operationKind。合并证据/补充内容由已有操作表达；版本替代是激活结果。不要按问题单中的泛称硬造新枚举或数据库操作。

## 6. 修改设计

### 6.1 单一、确定性的预览展示

优先保留现有 helper；补充一个小型、可测试的预览展示状态或等价局部方法，让详情、修改确认和关联预览共同使用同样的有效性规则。不要另建事实存储或引入 LLM 来生成确认文案。

展示数据必须直接来自绑定的 `proposedChangeSet`：

- 修订号：`baseMemoryRevision`。这是整个正式记忆集合的修订号。
- 目标版本：`targetMemoryVersion`。这是目标单条记忆的版本，不能与修订号混用。
- 确认前/后：分别来自 `factDiff.before/after`。不得在 after 缺失时用 `item.primaryValue` 偷补。
- 字段差异：来自 `factDiff.changedFields`，提供用户可理解的字段名与原始值。
- 证据计数：来自服务端差异，标明是方案预览，不是已经写入的计数。

示意显示，数字仅为测试样例，不得硬编码生产值：

```text
本次确认将如何更改正式记忆
基于正式记忆第 12 次修订快照
新增一条正式记忆
确认前：无对应正式记忆
确认后：用户的测试阅读计划代号是青禾，以青禾为准，蓝桥作废。
证据：0 → 1 条
```

对于真实候选，应显示服务端的真实字样。示例“青禾”不能成为生产替换规则。

### 6.2 操作语义与空值规则

| operationKind | 预览要求 | 不允许的做法 |
|---|---|---|
| add | 显示真实 after；没有 before 时说明新增 | after 为空仍放行，或拿候选正文伪装 after |
| correct | 明确目标版本、真实 before/after 和关键变更字段 | 隐藏将被修订的目标事实 |
| refine | 展示服务端合并后的 after，保留未改动事实 | 直接把候选原文当成最终结果 |
| addEvidence | 正文不变、补充证据及目标版本清楚 | 误称“新建独立事实” |
| temporalChange | 展示原事实及新事实的时间范围/限定关系 | 说成覆盖所有历史事实 |
| dispute | 显示存在冲突及预期冲突记录状态 | 表达为已经消除了冲突或新事实自动成为唯一正确答案 |
| duplicate | 明确没有新增正式记忆版本 | 强制期待 revision 增加或宣传新增 |
| noPersonalFact | 明确只完成审核、不新增跨会话正式事实；after 可为空 | 因 after 为空一律报错，或显示“新建正式记忆” |

对未知操作、必需 target 不完整、必需 after 空白/不具备可展示结构、关键差异无法理解的方案：显示“变更预览不完整，请重新载入后再确认”，禁止当前写入动作。保留候选，不伪造空内容、不静默跳过操作。

校验必须在 UI 和提交 UseCase 同时有效，不能只把按钮置灰；测试直接调用提交意图也应失败。沿用当前拒绝动作的鉴权及绑定规则，不另开绕过版本校验的拒绝接口。

只有有效的“无变化”操作可以使用对应空值语义。不要引入全局 `after != nil` 规则。

### 6.3 V5 facets 支持及更正副作用

`OwnerTruthMemoryFacetsState.resolve` 对 V5 使用保留的 facets 结构解析，沿用既有字段验证与置信度要求：

- 有效非空：正常显示值与证据属性。
- 合法空集合：显示未提取到线索，不标作“不支持格式”。
- 缺失/畸形：明确数据不完整，不伪造“分析完成”。
- 未知未来版本：保持 unsupported。

**需要同时检查更正行为：** 当前 `submitCorrectionTapped` 在 facets 为 available 时会收集所有输入框，而 `ownerCorrectedJSONValue` 会把提交的线索视为本人确认。打开 V5 支持后，不得因为用户仅修改一句正文，就把未修改的模型推断线索全部自动升级为本人陈述。

Sol 应按现有后端 `reextract_owner_corrected_memory_payload` 行为验证：只发送用户实际修改的线索；没有修改线索则传 nil。若传整组是现有协议要求，应保持条目的原证据属性，或要求用户明确确认这一整组，不能默认为全部主动修改。先用测试固定预期，再做最小改动，不重写事实抽取体系。

### 6.4 展示与提交绑定

既有服务端 CAS 是最后保护，但它不能替代“提交的就是用户刚看到的方案”。

对单条审核在页面打开时保留以下展示身份：账户租约、candidateID、candidateVersion、candidateContentHash、proposalHash、changeSetID、baseMemoryRevision。

确认时与 UseCase 当前项比较；不一致则停止提交，提示重新加载并重新确认。可以扩展现有 intent 携带展示绑定，或用等价的不可变 review snapshot，不必改后端 API。

更正流程继续先取得对应 correctedValue 的服务端预览，再展示、二次确认，并提交该预览的绑定参数。网络返回顺序不能把旧的更正预览覆盖到新输入上。

收到 `ownerTruthCandidateReviewConflict` 等过期错误，刷新后显示新差异，由用户再次确认；不要自动以新的 hash 重试写入。网络结果不确定时应先查回执/终态，沿用相同命令语义，不能显示“肯定没写入”后重复生成新写入。

当前 proposal 合同没有 expiresAt，不要为了“过期”新增一个任意 TTL。这里的过期主要是 candidate、正式记忆 revision、来源资格或授权改变，由既有服务端合同核验。

### 6.5 多操作与关联预览

关联按钮数量必须是真实选择数。组内确认、更正、拒绝要逐条显示真实动作；拒绝条目明确不新增事实，不能照抄其候选 add 预览误导用户。

单条更正超过三项或组内包含多项操作时，应让所有将提交的变更可见、可滚动查看。优先复用现有滚动详情；若当前不支持该形状，明确阻断，不能仅显示前三项后确认全量。

不得把关联组的原子提交改成逐条请求。现有批量逐项审核与关联组原子审核是不同入口，保留其合同区别。
