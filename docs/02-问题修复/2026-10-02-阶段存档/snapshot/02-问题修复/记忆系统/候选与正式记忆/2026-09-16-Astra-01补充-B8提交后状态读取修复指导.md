### 2.1 建立本场精确 plan 与 followup 保全

正常入口必须已经完成：admission typed receipt 验收 → `acceptAdmission` 成功写入 admitted checkpoint → 本场 followup upsert。plan 绑定原 `AccountLease`、productSession、精确 reviewBatchID、实际本地 revision；来源只填写确实存在的 followup/checkpoint。不得生成随机 batch、借用“最近一条”或将 readContext trace 当业务身份。

已有 followup 与 checkpoint 坐标冲突时停止读取并报告 bindingMismatch，不自动选任意一个。已有 committed receipt不能因读失败退回 acknowledged/admissionPrepared，更不能借 retry 再发 ack/admit。

若 followup 落盘失败，保留已经写好的 admitted checkpoint 与原 outbox，不清理最后恢复坐标。可以从这份实际存在、已验收的 admitted checkpoint 建只读 plan；无法建立可信 plan 就保持 statusUnknown，不重做 admission、不伪造 followup 成功。跨进程仍交给现有只读发现流程。

同场成功后的清理遵守现有业务完成条件，并增加明确的终态观察持久化结果。当前 child 的 `finishTerminalRound` 在 recorder 失败后仍返回业务终态，而 parent 的现有完成清理会删除 followup/checkpoint；不能直接拼接这两段行为。

child 必须向 parent 返回“服务器业务终态已核实”和“该终态观察已持久化”两个独立结果。后者失败时可以保留前者的真实显示，但不得进入删除最后恢复坐标的清理分支；保留 `cleanupPending` 或等价状态，后续仅重试本地维护，不重发业务请求。读取超时、取消、策略拒绝、token freshness 或相同 phase 回调不得触发任何 followup/outbox/checkpoint 删除。terminal observation recorder 只写同场匹配记录；存储失败记录安全诊断。

## 3. 一次 read intent 的授权、预算与生命周期

### 3.1 fresh current read authorization，不复用 POST authority

现有 B6 bounded reader 会先看旧 route，并只对3种过期原因捕获 fresh。这个顺序还覆盖不了“旧 route 最初 denied、但当前有效政策已经 allow”。对资源 `.liveMemoryRecoveryStatus`，主方案是：**在本次明确的只读 intent 内首先捕获 fresh request decision**，使用当前经过 scope/appBuild/audience/cohort/时效验证的缓存。沿用 `freshRequestFeatureDecision(.ownerTruthCandidateReview)`；不刷新全局 route，也不修改 FeatureGateEvaluator 的旧快照拒绝语义。

- fresh/current policy 明确 allow：用该 decision 发原 batch 的 GET，requestJSON 仍严格 revalidate；它不来源于 admission POST authority。
- fresh/current policy 明确 deny：零 status GET，返回白名单拒绝原因；不能回退旧 allow、QA override 或无限 fetch直到允许。
- 当前缓存缺失/过期等确属可刷新元数据状态：可按白名单原因进行一次有界只读 policy fetch，仍使用同一 ReadContext/attemptState 的预算；成功后 fresh capture，并再次验证原 lease/deadline。不要仅按旧 route 的 deny reason 决定当前政策永远被拒绝。
- scope不匹配、account/authority失效、真实撤权：停止，不用 fresh 捕获把旧场移入新作用域。
- late refresh成功、callback重复：已取消/到期的 intent 零 GET、零 UI/磁盘提交。

这个修改会同时影响 B6 对**同一个 status资源**的读取，必须跑它的定向回归；不因此扩大全部 Candidate GET、其他 OwnerTruthReadResource 或全局 FeatureGate 的行为范围。

### 3.2 预算不得因轮询重建

复用已有 B6 的 `OwnerTruthReadContext`：原 trace、intentStartedAt、deadline、resourceGETCount、policyFetchCount、authRecoveryCount、runtimeRecoveryCount 贯穿整个轮次。当前默认轮次30秒、status GET上限6；policy/auth/runtime恢复各沿用现有 attemptState预算，不新增隐形重试。

首次 admission 成功后的观察是一个新 read intent。child 只 `.start()` 一次。后续 pending轮询只 `verifyStatus(startsNewRound:false)`，接收 `outcome.readContext` 后继续，不能每次新建 coordinator/context 或无条件 `startsNewRound:true`。

预算/截止用完即结束本轮并保留 statusUnknown/真实已知处理中状态，不通过新定时器立即开启另一轮。新的明确“核实本场状态”操作、合法前台恢复可创建新读轮次；同一前台事件链的 willEnterForeground/didBecomeActive 必须去重，不能双开预算。页面重绘、重复订阅和同 phase callback不属于新意图。

`startsNewRound:false` 必须要求原轮次仍活动，并核对调度时捕获的 roundID/trace 与 generation；context 缺失、轮次已暂停/取消或替换、预算耗尽、到期均直接停止，不得借这些条件创建新 context。仅明确的新读意图可以开启新轮次。现有 `scheduleNextReadIfPossible` 的 poll closure 需要补此入口栅栏；网络结果的 generation/requestID 检查不能替代它。取消后旧 poll 即使在原 deadline 之前被调用，也必须零新增 GET。

### 3.3 所有权和取消

parent 持有自己的 child 和 token；child持有自己的 read handle、deadline/poll work item。替换、账号切换、parent销毁、明确取消时先递增generation，再unsubscribe/suspend/cancel并清空引用。网络底层即使迟到返回，也必须通过现有 generation/requestID/lease fencing被忽略；不能假称取消一定阻止服务器收到已发出的GET。

App进入后台时暂停当前 child，取消本轮后续poll；回前台由既有单次生命周期恢复点决定是否开新只读轮次。不要同时由 parent旧poll、child B6 poll和全历史恢复链读同一场。

当前 capture coordinator 仍被 retained 时，现有 `trackedProductSessionIDs` 排除集合可避免后台全历史扫描重复认领。若 parent退出并移交冷启动发现，要先suspend/unsubscribe自己的child，再释放拥有权；磁盘followup/checkpoint保留。禁止为了接手调用全历史 UI `retainLiveMemoryRecoveryCoordinator` 来竞争当前文案。
