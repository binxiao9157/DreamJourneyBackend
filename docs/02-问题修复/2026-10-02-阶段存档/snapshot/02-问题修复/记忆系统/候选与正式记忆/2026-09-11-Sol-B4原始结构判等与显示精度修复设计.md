## 3. 已证实的代码原因

### 3.1 判等用错了依据

[OwnerTruthStructuredFieldChange](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:883) 当前将 `hasChanged` 定义为：

```swift
var hasChanged: Bool { beforeText != afterText }
```

`OwnerTruthStructuredDiffPresentation.compare` 随后通过 `result.filter(\.hasChanged)` 删除“未变化”的行，`reviewability` 再根据 `hasActualChange` 决定更正等操作是否可以审核。

因此，原始结构不同、展示字符串却相同的字段，会被错误删除。如果还有另一项可见修改，整个操作仍会放行，形成隐藏修改。

### 3.2 可信度展示丢失精度

[ownerTruthCompletePreviewText](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:1080) 的 facet atom 分支将 confidence 乘以 100 后四舍五入成整数。

`0.721` 与 `0.724` 因此均显示为 `72%`。修复不能只把百分比改成固定一位小数：`0.72101` 与 `0.72102` 仍可能再次显示相同。

同一判等缺陷还可用纯展示样例复现：一个元素的数组 `["甲，乙"]` 与两个元素的数组 `["甲", "乙"]` 当前均显示为 `[甲，乙]`。这是同一根因的防御性回归，不另起一个业务改造项目。

## 4. 最小修改方案

### 4.1 结构判等与显示彻底分开

沿用现有 `OwnerTruthJSONValue`、递归 compare 和展示模型。在构建一行变化时，用成对的原始 typed value 计算语义变化，再生成 beforeText/afterText。

可以让 `OwnerTruthStructuredFieldChange` 保存原始成对值，或保存由内部构造过程确定的只读变化标志。具体实现遵循现有模式，但不能再从文字、翻译、百分比或排版结果计算 `hasChanged`。

判等规则：

- 对象比较键和值，键顺序不代表事实变化；展示顺序保持确定性。
- 数组比较元素、顺序和数量，不自动排序、去重或按语义合并。
- 类型参与比较，字符串 `"1"` 与数字 `1`、字符串 `"无"` 与 null 不能被展示别名合并。
- 若当前 typed 输入可区分缺失和显式 null，则保留区别；不声称恢复 API 或解码已经归一掉的信息。
- 使用当前数字合同的值等价规则；不新增 epsilon、精度阈值或舍入容差来删除变化。数字字面量写法差异不必被当成事实变化。
- 原始值相同，即使因展示格式变化而文案不同，也不应产生新的事实修改。

`hasActualChange` 必须来自真实结构变化；`isComplete` 表示所有必要修改已经能够完整、无歧义地查看。二者继续分离，不能用其中一个替代另一个。

保持现有八操作对目标、before/after、activation 和 binding 的校验，不通过全局放行更正解决误拦截。

### 4.2 显示精度和冲突消歧

可信度变化必须能看到实际不同的值。最小可靠方案是显示原始数值，例如 `0.721 -> 0.724`；也可以显示百分比摘要并附可查看的精确原始值。

要求：

1. 不限死为整数百分比、固定一位或两位小数。对不同的已解码有限数值，提供可区分、能够往返该数字合同的表示。
2. 优先使用标准的数值字符串能力，避免自行构造高精度数学系统。此处不要求迁移 `Double`，也不要求还原解码前 JSON 数字的字面写法。
3. 若百分比缩略展示相同，必须在同一次绑定预览中明确展示不同的原始数值，不能只加一句“有变化”却让用户看不到差别。
4. 字符串与 null/空值/布尔值的文案冲突，用类型标签、引号或等价的结构化排版消歧。
5. 数组中的文本含分隔符时，用带转义的字符串边界、元素编号或分项展示保留元素个数和原值，不能靠无边界字符串拼接。
6. 若原始值不同但当前呈现无法让用户区分，预览不完整并阻止当前确认；不能因 `hasChanged=true` 就强行放行。

纯展示过程不能更改原始 JSON、confidence、evidenceMode、proposalHash、candidate version、base revision 或提交内容。

### 4.3 同时验证三个入口

详情、更正和关联组已经使用共享展示，应保留这一设计。修改共享逻辑后，在三个真实入口分别验证 B4-P02：

```text
正文：保持原文
有效时间：2016年 -> 2018年
习惯线索可信度：0.721 -> 0.724
证据方式：仍为系统推断，不升级为本人表达
```

允许用其他等价排版，但两项变化都要可见，非首关联成员也不能漏掉。保持可滚动预览、固定操作区、原始 binding 和提交前重复校验。

## 6. 两个反例的准确构造方式

不能只改 `facets` 后直接拼一个候选，必须通过现有 `enrich_memory_payload_v5` 同步其派生语义，再交给真实 builder。否则 `inconsistentSemanticProjection` 是 fixture 未正确构造，不是本轮要修复的后端缺陷。

使用 `habits`，而非用其他派生展示可能碰巧显示完整精度的维度替代。以下命令只生成本地合成 proposal，不调用模型、不连接生产库、不写入正式记忆：

```bash
cd /Users/gaominge/Documents/Codex/Video/DreamJourneyBackend
STORE_BACKEND=memory PYTHONDONTWRITEBYTECODE=1 .venv/bin/python - <<'PY'
import json
from copy import deepcopy
from uuid import uuid4
from tests.test_owner_truth_memory_changeset import OwnerTruthMemoryChangeSetTests
from app.domain.owner_truth.ontology import enrich_memory_payload_v5
from app.domain.owner_truth.contracts import MemoryKind
from app.domain.owner_truth.memory_changeset import build_memory_changeset_proposal

x = OwnerTruthMemoryChangeSetTests()
x.setUp()
results = []
for label, change_time in [("confidenceOnly", False), ("timePlusConfidence", True)]:
    before = x._content()
    before["facets"]["habits"] = [{
        "value": "喜欢清淡饮食", "evidenceMode": "inferred", "confidence": 0.721,
    }]
    after = deepcopy(before)
    after["facets"]["habits"][0]["confidence"] = 0.724
    if change_time:
        after["qualifiers"]["validTime"]["expression"] = "2018年"
    before = enrich_memory_payload_v5(
        kind=MemoryKind.KNOWLEDGE, payload=before,
        memory_subject_id="person-owner", claim_subject_id="person-owner")
    after = enrich_memory_payload_v5(
        kind=MemoryKind.KNOWLEDGE, payload=after,
        memory_subject_id="person-owner", claim_subject_id="person-owner")
    current = x._current(content=before, source_id=str(uuid4()))
    candidate = x._candidate(
        content=after, review_mode="correction",
        correction_of_memory_version_id=current.memory_version_id)
    proposal = build_memory_changeset_proposal(
        candidate=candidate, current_memories=(current,), base_memory_revision=4)
    results.append({"case": label, "proposal": proposal.payload()})
print(json.dumps(results, ensure_ascii=False, indent=2))
PY
```

将生成的完整 proposal 输入实际 Swift 解码、展示与校验类型，再进入实际页面和提交 UseCase 测试。不能用手写等价算法替代待测实现，不能改 fixture 预期掩盖错误。

正式 fixture 采用现有确定性 ID/时间策略；此处随机 ID 只用于便捷复现。保存修复前结果和修复后结果，原始失败证据不覆盖。
