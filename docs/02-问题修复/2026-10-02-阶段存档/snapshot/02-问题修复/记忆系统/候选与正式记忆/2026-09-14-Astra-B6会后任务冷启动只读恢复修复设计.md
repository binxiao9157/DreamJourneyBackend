## 1. 问题及验收边界

### 1.1 本轮只解决什么

Live 已结束，后台接受了原任务，用户在 queued/organizing 阶段关闭 App。后台在 App 关闭期间完成后，新的进程必须凭原账号作用域内的磁盘坐标发现原批次，合法只读查询，并在回响页显示准确结果。

成功不是“发现了旧记录”，也不是 HTTP 200，而是：**发现原工作流 -> 合法读取原批次 -> 严格解码/校验 -> 正确状态落盘 -> 新页面展示完成态；全过程没有恢复性业务写请求。**

### 1.2 明确不包含

- 不分析或修改其他验收阶段、候选审核、更正预览、正式记忆列表读取及其历史问题。
- 两条同文候选已证实来自两次不同 Live，每场一条。本轮不得将其改写为单场重复缺陷。
- 不改整理规则、正式记忆、向量模型、文字问答或火山原生 Live 的声音、低延迟、持续聆听、打断、正式记忆绑定。
- 不恢复 ASR -> DeepSeek -> TTS 串行链路；不自动开麦；不把新话语写入旧关闭场次。
- 不操作生产候选、正式记忆、审核历史或 Dead Letter；不替用户审核。

### 1.3 只读恢复的能力边界

“后台已经完成”与“用户退出时后台还没有接受某个写命令”必须分开。

前者必须自动收敛完成；后者只能核实已有事实，不能通过 end/ack/admit 自动补发来保证整理完成。若 ack 或 admit 从未被接受，显示明确的待核实/尚未进入整理状态并保留记录是正确结果，不得伪装成完成。

本轮不设计手动补发命令的产品入口。“核实状态”按钮只读。若未来希望未接受的关闭流程也自动推进，需要另行设计服务器持久工作流，不属于本次修复。

### 3.1 现场已证实事实

| 编号 | 证据内容 | 可以推出什么 |
|---|---|---|

### 3.2 静态核查已经证实的缺陷机制

**C01：临时访问不可用与任务业务终态被合并。**

`OwnerTruthInterviewCandidateProposalStatusUseCase.beginRequestOrFail()` 先调用布尔 `releasePolicyAvailable()`；false 直接变成 `.unavailable(.releasePolicyDisabled)`。租约失效也进入 unavailable。接收结果时还会再次检查策略和租约。

`EchoLiveMemoryCaptureCoordinator.receiveCandidateReadinessState()` 对 `.unavailable` 不区分 notice，直接设置 `EchoLiveMemoryCaptureState.unavailable`；该状态 `isTerminal == true` 且不再允许观察。定时器取消，页面 `retainLiveMemoryCaptureCoordinator` 随后移除 coordinator。访问失败因此被展示为任务“无法继续整理”，原批次即使随后完成也没有活动观察器收敛。

这是已证实的代码机制，**不是已经证实现场首次失败一定是策略过期**。实际 notice 还可能是 staleAccountLease、contentUnavailable、contextChanged 等。

另一个必须区分的分支：旧 checkpoint 恢复在 queued 之后还可能执行 acknowledgement/admission，其失败也会设为 unavailable。因此，仅凭 queued -> unavailable 不能证明现场已经执行到 status UseCase；新增日志必须标明发现来源和当前 stage。

**C02：恢复触发没有覆盖前置条件合法就绪后的闭环。**

页面在 `viewDidAppear` 发现旧任务；`viewWillAppear` 启动异步策略刷新，两者没有“策略已就绪再观察”的协调。`refreshOwnerTruthInterviewNaturalInputProductEntryPolicy()` 完成后只更新入口可见性，没有接回原恢复任务。`rebindEchoAccountScope()` 也未直接调用会后恢复入口。已有前后台通知只让仍存活且处于 awaiting 状态的 coordinator 再读，无法恢复已被当成 terminal 移除的对象。

**C03：冷启动复用带写能力、且构造即执行的 capture coordinator。**

`EchoLiveMemoryCaptureCoordinator.init` 立即执行 `restoreCompletionCheckpointIfNeeded()`，否则恢复 outbox。恢复 checkpoint 的 endPrepared、ended、acknowledgementPrepared、acknowledged、admissionPrepared 分支会走原 end、ack、admit 写链路。现有测试甚至明确要求 crash 后重放这些原命令。

这与本次“冷启动恢复只读、不重发 end/ack/admit”的合同冲突。幂等命令不等于只读恢复。它不是此次现场重复写入的证据，但必须隔离，不能继续从恢复服务实例化带写副作用的对象。

**C04：发现顺序不是真正的合并，存在恢复所有权隐患。**

恢复服务依次读取 checkpoint、follow-up、outbox；只要存在 checkpoint，就跳过相同 productSession 的 follow-up，并在扫描过程中构造执行器。它没有先核对两种记录是否同批次、哪一种是已证实的更后阶段。follow-up 分支构造对象时也可能先命中残留 outbox。页面外没有工作流级单飞注册表，当前排重依赖该页面保留的对象集合。

**C05：暂时失败记录通常仍在，但缺少有效只读重试入口。**

admit 成功后，`persistFollowUpThenBeginObservation` 先写 follow-up，再删除 outbox/checkpoint，再观察状态。因此重启恢复可能只有 follow-up，这是正常情况，不能强制要求所有三个文件同时存在。unavailable 分支并不主动清理 follow-up，后续可能重新发现，但当前页面不会因策略/账号恢复自动复核，也没有本任务专用只读核实按钮。

**C06：现有超时不是完整的有界恢复预算。**

30 秒计时只将 UI 变为 statusUnknown；轮询超过原次数后改为每 15 秒继续，没有总截止时间。UseCase 已有 operationGeneration、coordinator 已有 observerGeneration，不能说完全没有防旧回调；但它们没有实现跨页面同工作流执行权、统一恢复预算以及页面焦点归属。

### 3.4 已排除或不能成立的推断

- 外层完全没有 lease 时，`resumePendingLiveMemoryOrganizationsIfNeeded` 直接返回；**单独一条 leaseUnavailable 不能解释随后某任务 queued -> unavailable**。还需要后续捕获租约、创建 coordinator 或 commit 时失效的证据。
- AppCoordinator 正常冷启动先完成在线认证、激活记录，再显示主页面；不能宣称正常流程必然让回响在账号激活前出现。账号晚就绪是必须测试的竞争边界，而非已锁定现场根因。
- 当前客户端已有 `reviewReady -> pendingReview` 和 `noCandidates -> empty` 映射，不能把问题简单归为“没有实现 completed 映射”。
- `ownerScopedMemoryMounted` 不证明 feature policy、authority、当前请求授权都已就绪；status 200 不证明 UI 使用了它。
- 暂无证据证明服务器漏整理、checkpoint 已永久丢失、用户数据损坏或同场重复创建。

## 5. 建议结构与状态机

### 5.1 分离三种事实

1. **持久关闭阶段**：原 end/ack/admit 命令及已验证回执，是现有 journal 的事实，不由网络失败改写。
2. **恢复执行状态**：等待账号、等待策略、只读查询、暂时未知、访问阻断。这不是后台任务失败。
3. **后台业务状态**：排队、执行中、待确认、无待确认、业务失败/隔离，仅由合法原批次结果确定。

建议新增局部类型 `EchoLiveMemoryRecoveryState`，不要将访问错误继续塞入原 capture 的 `.unavailable`：

| 状态 | 含义及 UI | 是否清除检查点 |
|---|---|---|
| discovered | 已发现原会后任务 | 否 |
| waitingForAccount / waitingForAuthority | 等待当前账号安全状态就绪；不显示业务终态 | 否 |
| waitingForPolicy | 正在恢复读取权限 | 否 |
| checking | 正在核实上次整理结果 | 否 |
| queued / organizing / retryWaiting | 服务端确认处于对应阶段 | 否 |
| statusUnknown(reason) | 暂未能核实；显示“核实状态”只读按钮 | 否 |
| actionRequired(stage) | 已核实流程尚未进入后续整理；本轮不自动补发 | 否 |
| accessBlocked(reason) | 登录失效、实际拒绝、作用域不匹配；不得声称任务失败 | 否 |
| contractBlocked(reason) | 结构损坏或校验失败；保留原记录并提供准确提示 | 否 |
| completedPendingReview | 已进入待确认记忆；不显示已成为正式记忆 | 先落盘完成观察记录，按既有安全清理规则处理 |
| completedNoPendingReview | 整理已完成，暂无待确认内容 | 同上 |
| failed(code) / quarantined | 原批次明确业务失败或隔离；不是网络失败 | 保留诊断与坐标，不自动重试业务写 |

等待和读取失败不是业务终态；可暂停当前执行，但不能消灭任务可恢复性。完成态必须来自同一 workflow 的有效结果。历史完成提示再次展示前需合法作用域；其待审核数量等动态信息可只读刷新，不据旧快照宣称“当前仍待审核”。

### 5.2 建议的局部模块

- `EchoLiveMemoryRecoveryService.discoverPlans`：纯发现与合并，不创建 capture、不联网、不写业务命令。
- `EchoLiveMemoryRecoveryPlan`：不可变的作用域、原工作流标识、记录来源、已知 batch/命令坐标和完整性检查结果。
- `EchoLiveMemoryRecoveryCoordinator`：只注入窄的只读端口、磁盘 store、时钟和 readiness；禁止持有 NaturalInput/ack/admit 写协议。
- `EchoLiveMemoryRecoveryRegistry`：按账号作用域与 productSessionID 单飞，生命周期高于页面；页面只是订阅者。
- `EchoLiveMemoryRecoveryReadContext`：固定 owner scope、当前合法 lease、工作流、trace、attempt、budget、requestID。
- `EchoLiveMemoryRecoveryReadiness`：提供可分类的账号/authority/策略状态及就绪事件，不能只返回 Bool。

这些都是建议新增类型，不代表当前已有实现。可放在 Echo 模块新文件中，原 capture 不进行无关拆分或重构。

### 5.3 正常 cold restart 时序

```text
新进程 -> 账号激活 / 作用域挂载 -> readiness 就绪通知
       -> 读取并合并磁盘记录 -> 注册唯一 recovery owner
       -> 先挂页面订阅，再 start（构造函数无副作用）
       -> 若策略临时缺失：刷新一次，重验 lease/authority/gate
       -> 使用原 reviewBatchID 发只读 GET
       -> 严格解码、请求/结果所属校验
       -> 将有效完成观察结果原子落盘
       -> registry 发布当前状态 -> 新 EchoViewController 显示完成
```

磁盘保存失败不能伪造“下次启动也可恢复”：本次收到的服务端成功仍是真实成功，但同时报告本地保存异常、保留旧坐标，不做清理。下次按旧坐标重新只读核实。

## 6. checkpoint、outbox、follow-up 的合并及所有权

### 6.1 作用域

持久主键使用现有语义：`subject + vault + authorityEpoch + productSessionID`。批次 ID 是该主键的绑定坐标，不能拿全局“最近一个批次”代替。

runtime generation/session 是本次请求的执行凭据，不应使同一合法作用域下重启后的磁盘记录不可发现。重新捕获当前 lease 不等于复用旧授权：每次读取及提交 UI 都重新验证；账号/vault/authority 真正变化时隔离旧任务。不能把 unresolved epoch 当通配符，也不能为恢复扫描其他账号目录。

### 6.2 必须先合并，再执行

对同一 scope 串行读取三种 store，按 productSessionID 分组。磁盘只读扫描返回 `valid/absent/unreadable/decodeInvalid/schemaUnsupported/scopeMismatch`，不可把损坏解释成空列表，也不能使用可能因重复 key 崩溃的 `Dictionary(uniqueKeysWithValues:)` 直接吞并。

| 记录组合 | 决策 |
|---|---|
| 仅合法 follow-up | 已知原 batch 的正常恢复入口；不要求 checkpoint/outbox 仍在 |
| admitted checkpoint | 使用其中合法 admittedReviewBatchID，只读状态 |
| follow-up + 较早 checkpoint | 验证已知 thread/session/batch 坐标不矛盾；follow-up 作为已持久入队观察坐标，禁止执行早期写阶段 |
| follow-up + outbox 残留 | 不重放 turn；只读 batch 状态；完成前不丢弃残留证据 |
| 多个相同 product 记录、相同 batch | 合并为一个读取计划、一个执行权 |
| batch/thread/session 明确矛盾 | `contractBlocked(bindingMismatch)`，不得“取较新时间”任意选择 |
| 只有 closing outbox、无可靠命令/批次坐标 | 保留并隔离；不创建新 session，不补造 checkpoint，不妨碍其他任务 |
| 磁盘损坏或 schema 不支持 | 只阻断对应任务；原文件不删除、不覆盖为成功 |

记录时间仅用于排序，不作为服务器业务完成或命令已接受的证明。合并计划需带 localRecordRevision；执行前校验该版本，避免扫描同时正常会后流程仍在更新记录。

### 6.3 各退出阶段的只读计划

| 本地阶段 | 允许的恢复动作 | 不能做什么 |
|---|---|---|
| endPrepared，无 batch | 合法读取 pending review-batch handles，严格匹配原 thread/session 与关闭触发类型；唯一匹配才记录 batch 并读 status；无匹配则 notObserved/待核实 | 不重发 end；不把查询为空当作 end 确定未接受 |
| ended，无 batch | 同上；端已结束回执不能代替后续 ack/admit 回执 | 不自动进入 beginAcknowledgement |
| acknowledgementPrepared | 从原命令取得 batch，直接 GET status | 不重发 ack，不因 pendingAcknowledgement 自动补发 |
| acknowledged | 从原 ack 回执取得 batch，GET status；readyForAdmission 表示未观察到 admission | 不自动 admit |
| admissionPrepared | 用原 admission 命令 batch GET status，已 admitted 则观察结果，否则保留待核实 | 不重发 admit |
| admitted / follow-up | 原 batch GET，直到有效完成或本轮读取预算结束 | 不请求 current session，不重建 session/source/batch |

现有 pending batch GET 只列等待 acknowledgement 的句柄，不是全量历史，也不是 command-result 查询。匹配不到不能证明无批次；多于一个匹配不能随意取第一条。这里的 pending review batch 不是用户最终审核候选，本文不改其生成或确认规则。

不得在正式恢复中启用 QA header 调用 `fetchOwnerTruthInterviewSessionState`：该客户端方法当前是 QA-only。`interview-sessions/current` 只用于活动可继续会话，不能可靠查旧已关闭批次；outcome read 主要提供计数/呈现，也不能冒充原命令回执。

**可达性限制必须体现在验收：**在 end 未接受、批次不可定位或 ack/admit 未接受时，只读恢复可能停在 notObserved/actionRequired。这是“不允许恢复写”的正确边界，不是该场已完成。已 admitted 的本问题主场景不能停留在此状态。

### 6.4 持久化与重复 ended receipt

- 保留正常当场关闭流程的 prepare -> 合法 receipt -> 下一阶段机制及原幂等键。本轮只拆掉冷启动、重建页面触发的写恢复入口。
- 同 command、同身份的重复 ended receipt 必须 no-op；不得让 queued/organizing/completed 回到 saving，不得再发 ack/admit。
- 同 product 下 command/receipt 身份矛盾必须拒绝并保留记录；不得用“阶段较大者优先”掩盖不匹配。
- 原 checkpoint 阶段应单调；重复 acceptEnd/acceptAcknowledgement 不得覆盖更后阶段。当前 setter 直接赋 phase 的行为需增加单调性测试和精确相等校验。
- follow-up 当前在 UserDefaults，且解析失败返回空。建议扩展该 store 为原子文件 V2，实现结果型扫描与最小完成观察记录；不要再另建互相覆盖的第二套进度来源。
- V2 最小保存：schema、scope、product、已知 thread/session/batch、原命令标识（有则保留）、localRecordRevision、业务观察状态及时间。不保存 token、音频、Prompt 或新增会话正文。
- 老 V1 follow-up 只有 product/batch 也是合法输入。不能伪造已被正常清理的原命令 ID；按其原 scope 和 batch 执行只读，标记 coordinateSource=legacyFollowUp。
- 迁移采用“读旧 -> 校验 -> 原子写 V2 -> 回读校验”，失败保留旧记录。本轮不靠删除旧记录消除 UI 问题。已验证的完成记录可阻止残留旧阶段再次抢占。
- UserDefaults 写入完成不应被测试当成进程终止后的耐久性证明；真正重启测试必须读取新进程磁盘。

## 7. 账号、authority 和策略恢复

### 7.1 就绪触发，不靠固定延时

AppCoordinator 的 `validateCachedPrivateAccess` / `activateVerifiedLogin` 已有 accepted active receipt；在现有成功激活、作用域挂载完成的接入点向 B6 registry 发出安全就绪信号。不能提前发布 active 或修改账号激活顺序。

Echo 的 `viewDidAppear`、合法 `rebindEchoAccountScope`、前台事件只是幂等触发/订阅，不直接实例化一个新的带写 capture。若扫描先于 lease，记录全局 waitingForAccount 请求，合法 active 后再扫描原作用域，不提前枚举私人目录。authority 未解决时等待；明确的新 authority 不得自动“认领”旧 epoch。

策略刷新完成后，必须针对实际读取接口重新捕获 gate 决策。只刷新 echoTextInput 入口可见性，不能代表 ownerTruthCandidateReview 状态读已获授权。

### 7.2 只读恢复规则

- missing/expired cache 等暂态：在合法同主体 lease 下允许一次策略刷新，仍走真实 policy store、evaluator、authority 检查，然后继续原读取意图。
- 明确服务端禁用、版本不支持、主体/vault/authority 不匹配：停止，展示准确阻断原因；不得循环刷新撞开权限。
- 401：允许现有认证服务完成一次合法凭据更新，但共享本轮恢复预算；只有成功验证的同 scope successor 才能重新构建只读 attempt。原 lease 的回调作废，旧门禁 decision 不继承。
- 认证失效/账号切换：取消执行权、隔离数据，不自动改登录态或展示旧账号任务。原账号后来合法返回可重新只读发现，不重放命令。
- DNS/TLS、离线、超时、5xx：未知/暂时读取失败；保留 checkpoint；不能标业务 failed，也不能降级 TLS。
- 403/404/410/409：保留细分白名单 reason；权限拒绝、资源失效、状态未观察到和合同冲突不可互换。单个 404 不证明从未生成任务。

## 8. 单飞、预算和旧回调隔离

### 8.1 所有权

Registry 主键是 workflow scope，不是 Controller 地址。每个执行 owner 有 `recoveryGeneration`，每次读取有唯一 `requestID` 和递增 `attempt`。页面另有 subscriptionID 和选中的 workflowID。

合并刷新请求只增加订阅，不创建第二个请求；老回调只有在 workflow、owner generation、requestID、当前 lease 和 record revision 全部匹配时可提交。释放在途锁、清理 timer 也必须 compare-and-release，不能无条件把全局 busy=false。

新 Live 与旧恢复使用不同 productSessionID、不同 coordinator。旧恢复结果只进入它的会后结果显示区域；不能覆写新 Live 状态、开关麦克风或转用新场次 ID 查询旧 batch。多个历史任务不得争用同一无归属 status label。

### 8.2 默认预算（建议值，属于新设计，不是现有性能结论）

- 每次自动恢复 round：最多 30 秒；最多 6 次业务只读 HTTP 尝试（含401后的重读和可选句柄发现）。
- policy refresh 至多 1 次，auth refresh 至多 1 次；二者都计入 round 总时限，不允许底层各自重置预算。
- 单次网络截止上限 8 秒且不超过 round 剩余时间；明确超时则撤销该 requestID。
- 尚未结束的业务状态可以有限退避轮询，遵守 retryAvailableAt；等待时间超过剩余预算则结束当前 round，保留真实进度及只读按钮。
- 相同 readiness epoch 下的连续 viewDidAppear/刷新/前台事件合并，不能重置已耗尽预算制造无限轮询。新账号/策略就绪事件或用户明确“核实状态”可开启新 round。
- 后台暂停读取并撤销旧请求提交权；前台按保留状态开始或接回唯一合法 round。页面消失只取消订阅，不丢磁盘记录。

30 秒是资源边界，不是“等待30秒后假装修好”。有效成功应立即展示。时钟和调度器必须可注入，测试不依赖实际 sleep。

### 8.3 迟到结果

区分“UI提示等待较久”与“请求已硬超时撤销”。前者若 requestID 仍有效可接收迟到完成；后者一律丢弃迟到 200，新的 attempt 再合法 GET 得到结果。

已完成记录不能被同轮旧 queued、旧 unavailable 或另一 Controller 的回调降级。授权撤销不等于业务结果被改为失败：隐藏旧作用域结果即可。后续业务变化仅允许新的合法只读结果按明确状态合同更新呈现。

## 11. 安全日志和验收证据

### 11.1 事件和关联

新增 `EchoLiveMemoryRecovery` 白名单事件：

`scanStarted / scanCompleted / planMerged / readinessWaiting / readinessChanged / recoveryClaimed / readAttemptStarted / requestDenied / taskCreated / taskResumed / transportCompleted / httpResponse / decodeCompleted / resultValidated / resultDiscarded / observationPersisted / uiCommitted / roundSuspended / roundFinished`。

同一逻辑恢复使用一个trace；attempt从1递增，软重试不生成无关联trace。新进程可以生成新trace，使用经脱敏的稳定workflow关联码联结前后两次运行。日志必须明确processRun、requestID和recoveryGeneration，不记录原始账号session。

taskCreated不等于发送；taskResumed也不保证服务端已接收。HTTP响应与服务端访问日志匹配是另一个证据层级，不可混写。

### 11.2 可记录与禁止记录

可记录：记录来源/phase/schema、结果枚举、allowlisted reason、attempt、状态码、耗时、计数、作用域/原batch是否匹配的布尔值、只读/业务写method类别。

workflow/batch/command仅使用现有合规脱敏关联机制；需要持久关联时采用受保护密钥的HMAC或经确认可跨进程关联的安全实现，不能自己截断原hash冒充脱敏。日志不记录完整原始hash、UUID、文件内数据、URL路径中业务标识、token、密钥、Prompt、正文、音频、完整请求响应或error.localizedDescription。

reason采用显式枚举：`accountActivating`、`leaseUnavailable`、`staleLease`、`authorityUnresolved`、`scopeMismatch`、`policyMissing`、`policyExpired`、`policyDenied`、`policyRefreshFailed`、`authFailed`、`offline`、`dnsFailure`、`tlsFailure`、`timeout`、`notObserved`、`bindingMismatch`、`schemaInvalid`、`staleAttempt`、`budgetExhausted`、`storageUnavailable`。未知错误统一unknown，不动态拼接正文。

### 11.3 收敛证据链

必须能回答：发现哪类本地记录 -> 对应哪个脱敏workflow -> 为什么等待 -> 哪次合法恢复 -> 哪个attempt查原batch -> 解码出什么业务态 -> 为什么允许提交 -> 哪个当前页面实际显示。

成功证据还必须包含恢复业务写次数0、自动开麦次数0、新旧Live身份不混用，以及该workflow只有原候选集合。后台候选数量只是最后一条佐证，不是UI恢复的替代品。

## 15. 交付摘要
