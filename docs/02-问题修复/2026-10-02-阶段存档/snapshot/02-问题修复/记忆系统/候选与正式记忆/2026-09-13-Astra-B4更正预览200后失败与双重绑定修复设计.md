## 1. 结论与交付边界

找到可确定性复现的合同语义冲突：

```text
原候选内容 C0，列表 contentHash = H0
用户更正输入 I -> 后端确定性归一化得到 C1，哈希 H1
后端更正 Proposal.candidateContentHash = H1
iOS previewCorrection 要求 Proposal.candidateContentHash == H0
真实更正通常 H1 != H0 -> 即使 HTTP 200、解码成功，预览仍被拒绝
```

这不是应该删除的安全检查，而是两个不同对象被放进了同一个比较关系。必须分别绑定 **原候选身份/版本/内容** 和 **本次用户更正输入/归一化结果/Proposal**。

第二个同类出口位于 `OwnerTruthCandidateReviewBinding.matches`，只修预览 guard 会把失败推迟到最终确认。修复应贯通编辑、二次预览、用户确认、严格服务端 CAS 和持久结果验证，不自动提交。

**生产和本地预览 builder 与 ontology 指纹相同，单纯部署当前本地后端不构成此问题的修复。** 推荐最小增量是预览响应增加独立 correctionBinding，保留现有 Proposal v1 的语义和哈希算法；客户端增加更正专用绑定，不改变普通接受/拒绝的绑定规则。

## 5. 修复合同：分开绑定，不重定义旧哈希

### 5.1 必须保持的对象

- `SourceCandidateBinding`：vault、candidateId、candidateVersion、**原** contentHash；来自本次读取的原候选。
- `FrozenCorrectionInput`：请求实际提交的 correctedValueSchemaVersion 和 correctedValue，包含用户明确编辑的内容；一经请求冻结，不从正在变化的 TextView 重读。
- `ResolvedCorrection`：服务端既有归一化结果，其哈希为现有 Proposal.candidateContentHash。
- `VerifiedCorrectionPreview`：原候选绑定、冻结输入、Proposal、revision、页面/请求/账号所有权全部校验通过后的不可变对象；不能由 UI 随便拿一个裸 Proposal 构造。

普通接受/拒绝仍要求列表 Proposal 对原 Candidate hash 相等。不得把 `OwnerTruthCandidateReviewBinding.matches` 全局改成忽略 hash，或把所有预览都按“更正”放宽。

### 5.2 推荐的最小后端增量

保持当前 URL、请求字段白名单、envelope schema 和 **Proposal v1 内部字段/哈希/ID 计算**。仅在请求包含更正输入时，响应增加带独立版本的 `correctionBinding`：

```text
schemaVersion: owner-truth-candidate-changeset-preview-v1
vaultId, candidateId: 既有路由响应归属
proposedChangeSet: 既有 Proposal v1，语义不变
correctionBinding:
  schemaVersion: owner-truth-candidate-correction-binding-v1
  sourceCandidateVersion: 原 Candidate row_version
  sourceCandidateContentHash: 原 Candidate content_hash
  submittedCorrection:
    correctedValueSchemaVersion: 实际验证过的请求值
    correctedValue: 实际验证过的请求对象，深复制
  resolvedContentHash: 同一次构建中更正 canonical content 的哈希
```

约束：

1. sourceCandidate 字段必须来自本次授权事务内实际使用的原 Candidate，不信任客户端提供的“源哈希”。原 Candidate、binding、proposal 必须出自同一次一致读取，不另外查询后拼接，避免竞态。
2. resolvedContentHash 与内部 proposal.candidateContentHash 严格相等。不要单独再次归一化来生成不同结果；复用此次 builder 的已确定结果。
3. submittedCorrection 是服务端验过的原请求输入，不是润色结果、不是模型生成文本。客户端进行完整 typed 等值检查，区分缺失、null、空数组、布尔和数值；不能只对主文本或显示字符串判等。
4. 采用 typed 输入回显是为了不新增 Python/Swift 通用 JSON 哈希算法和规范化差异。**不允许在客户端用原始输入的 SHA-256 替代更正 canonical hash**，两者可能不同。
5. 回显只用于响应合同与原请求配对，不是权限票据；HTTP 认证、lease、服务端 CAS、最终 Proposal hash 重算全部保留。客户端不能把回显伪造成写权限。
6. 没有更正输入的列表/预览继续原合同；无需给历史 Proposal 补字段，不改历史 payload、proposalHash、ID 或审计表记录。
7. 服务层可增加小型 immutable result/envelope 类型以携带原 Candidate 绑定。不要为取 source hash 在请求外额外读数据库，不重写整套 repository。已有组级 builder/结果恢复保持语义不变。

替代方案“把 Proposal.candidateContentHash 直接改回原候选 hash”不采用：会改变已持久化 v1 合同和 proposalHash/ID/recompute，扩大历史回执和关联组兼容范围。只改 iOS 为无条件接受不同 hash 也不采用。

### 5.3 iOS 合同与校验顺序

新增 typed correction preview response，网络层不能继续只返回裸 `OwnerTruthCandidateChangeSetProposal`。预览输入显式传递本次 application AccountLease、主体、冻结 Candidate 绑定及诊断上下文。

按以下次序校验并分别记录失败 reason：

1. envelope schema、vaultId、candidateId 和 correctionBinding schema；更正响应缺少新 binding 时明确 `correctionBindingMissing`，禁止回退裸 Proposal。
2. JSON 与 Proposal typed decode；版本、hash 格式、operation/dependency 边界保持原规则。
3. requestID、编辑代次、页面所有权、operationGeneration 及当前账号 lease 仍对应本次预览；合法凭据轮换也不能复用旧审核授权。
4. 当前 Candidate 仍存在且未决；原版本/原哈希与请求冻结值一致。
5. correctionBinding 的原候选版本/哈希严格匹配冻结值，proposal.candidateVersion 严格匹配原版本。
6. submittedCorrection 完整匹配本次冻结输入；resolvedContentHash 严格匹配 proposal.candidateContentHash。
7. proposal.baseMemoryRevision 与当前被确认的列表 revision 一致；不把 69 硬编码。若 revision 已变，废弃预览，提示重新读取和再次预览，不静默改写旧 binding。
8. reviewability 完整且可审核；未知 operation、缺 target、差异不完整、预算超限等继续 fail closed。
9. 输出 VerifiedCorrectionPreview，并且二次确认页实际使用它渲染。正文更正后的归一化可能调整派生线索，须完整展示实际差异，不谎称“只改了文本”；不改变本轮既有归一化产品规则。

判等关系变为 `binding.sourceHash == candidate.H0` 和 `binding.resolvedHash == proposal.H1`，而不是删除哈希校验。没有任何证据允许 H0/H1 随意错配。

### 5.4 最终提交必须同步修复

- `openCandidateDetail.onCorrect`、更正 intent、`makeCommand` 接收 VerifiedCorrectionPreview 或等价不可变绑定，使用冻结输入生成命令，不重新拼接旧 item + 裸 proposal 充当“已审核”。
- 普通 accept/reject 继续现有 matches；V5 correct 使用更正专用匹配器，完整验证 SourceCandidateBinding、FrozenCorrectionInput、Proposal/revision/lease/代次。裸 Proposal 不足以确认更正。
- 最终命令继续携带原 expectedCandidateVersion、expectedMemoryRevision、expectedChangeSetId、expectedProposalHash，以及冻结 correctedValue/schema。不绕过服务端重算，不将 expected revision 修改成刚读取的值而不重展示。
- 用户必须在“核对更正方案”页明确点“确认写入”。取消、编辑变化、预览失败或回调过期均不能产生审核 POST。
- 新更正的未决记录可以增加可选 `expectedCorrectedContentHash`，只存哈希不存正文，用于对成功回执 candidateAfterHash 的核对。新流程必须赋值，旧记录保留原格式/既有核实规则，不补写历史、不删除不认识的记录，也不得将旧记录当作新更正预览使用。
- 原命令的 before hash/版本、回执动作和 after hash 不一致时不得提示成功，保留未决并只读核实。不得重发审核 POST；沿用现有明确未发送/未知/拒绝/持久成功分类。

## 6. 状态机、并发和失败恢复

```text
editing -> previewRequestFrozen -> requestingPreview
  -> transport/contract/context failure -> previewFailed 或 contextStale
  -> verifiedPreview -> awaitingExplicitConfirmation
  -> 用户继续编辑/取消/换账号/上下文刷新 -> previewInvalidated
  -> 用户确认 + 所有绑定仍合法 -> reviewSubmitting
  -> notSent / serverRejected / outcomeUnknown / committed（沿用现有状态）
```

| 事件 | 必须动作 |
| --- | --- |
| 连点预览 | 相同冻结草稿单飞；编辑变化产生新 requestID，旧回调不覆盖新状态 |
| 编辑内容/线索改变 | 使旧预览确认能力失效，即使正文显示相同但 typed 内容不同也不能复用 |
| 请求前策略过期 | 有界恢复认证/策略及只读列表可复用既有能力；废弃旧审核上下文。不能把候选只读自动恢复扩成自动审核 POST |
| 预览 POST 已发送但响应未知 | 不进入“已写正式记忆”，不生成审核未决记录；提示预览未完成，用户可主动重试预览。服务端可能已有预览审计，不能宣称数据库完全无变化 |
| credential rotation | 显式传入 lease，返回时检查 allowed 和 sessionRotated；合法轮换重新建立只读上下文，旧 Candidate/Proposal/确认闭包作废 |
| revision/候选已变 | 保留用户草稿与安全提示；重新读取后由用户核对新候选、再发预览，不自动替用户把草稿套到另一条候选 |
| 确认页已显示后更新上下文 | 禁止旧确认闭包提交；明确提示重新预览，不能静默关闭并显示成功 |
| 账号/vault 改变 | 不跨主体重放草稿或展示私有预览，不仅靠 subjectId 字符串判断 |
| 最终审核未知 | 使用前序未决持久化与 GET 核实，不能重新 preview/POST 作为查询 |

预览网络调用当前默认允许通用恢复。局部修复应显式审计允许重试的边界：发送前可恢复门禁；发送后不要隐式重复 POST，除非未来另有经过验证的预览幂等合同，本轮不引入它。不得为修预览改动所有 requestJSON 调用的全局行为。

## 7. 白名单安全诊断

新事件族建议 `CandidateCorrectionPreview`，复用现有隐私工具和网络阶段，不引入另一套日志框架。一个用户预览意图一个随机 trace；每次尝试有 attempt、requestID 安全关联，UI/UseCase/FeatureGate/lease/HTTP/typed decode 使用同一上下文。旧回调丢弃记录其自身 trace，不冒充当前尝试成功。

事件顺序：`previewIntentCreated -> scopeChecked -> featureChecked -> requestCreated -> taskCreated -> taskResumed -> transportCompleted -> httpResponse -> envelopeDecoded -> proposalDecoded -> bindingChecked -> reviewabilityChecked -> previewPresented`。任务创建不等于真正发送；服务端 200 不等于客户端 decode。

| 层 | 固定 reason 示例 | 可记录字段 |
| --- | --- | --- |
| 传输/门禁 | transportFailed、httpRejected、policyUnavailable、leaseRejected | HTTP status、固定错误类别、attempt、duration；不输出 response |
| envelope | envelopeInvalid、envelopeVaultMismatch、envelopeCandidateMismatch、proposalMissing、correctionBindingMissing、bindingSchemaUnsupported | presence/type 布尔、合同版本白名单 |
| decode | proposalDecodeFailed、operationDecodeFailed、dependencyInvalid | 固定 fieldCode、operationIndex；不得直接 dump Error.localizedDescription |
