## 1. 先读结论

1. **优先修复启动配置，不要先接回旧的逐轮检索函数。** 当前 iOS 最终 JSON 为 `dialog.dialog.system_role`；官方 StartSession 合同的字段为 `dialog.system_role`。同一个包装错误还影响 `dialog.extra.model` 和根级 ASR 配置。
2. **现有测试把错误层级锁定成了“正确合同”。** 当前测试接受双层包装、拒绝官方所示单层结构。修复必须更换测试的独立判据，不能继续让构造器和校验器相互证明。
3. **逐轮正式记忆注入确实没有被调用，但它不是已证明的必要修复手段。** 若当前 65 条合格事实在启动时正确进入模型，四个基础问题不应依赖每轮重新检索才能回答。
4. **旧 RAG 发送实现本身也不符合公开合同。** 当前发送 `{"content":"..."}`；官方 ChatRAGText 使用 `external_rag`，其值是包含 `title/content` 条目的 JSON 数组字符串。不能直接复活旧代码。
5. **ChatRAGText 不是已证明的“生成前补充背景”接口。** 它可以触发外部知识总结语音。默认原生模式中，ASR 结束后 Provider 可能已经开始生成，异步检索再到达会产生时序竞争。
6. **本次推荐主链：正式事实快照在启动前绑定一次，火山原生 S2S 完成每轮回答。** 保留低延迟、连续收音、原生播放和打断；文字继续 DeepSeek，不朗读。
7. 若正确启动合同下仍不能稳定回答，再执行本文的长度/位置对照实验及 RAG 能力验证；不能把未经验证的逐轮 RAG 接入当作已经完成修复。

**交付目标是“火山实际回答采用正确正式事实”，不是“某个方法终于被调用”。**

### 3.5 R5：现有本地轮次 Gate 不等于 Provider 轮次 Gate

- `EchoTurnKnowledgeContextGate` 有本地 turnID、身份、生命周期与重试保护，但没有 Provider questionID/replyID。
- `parseASRResult()` 返回的只有文本和 isFinal；`SEEventASREnded` 当前只写日志。
- Chat 回调也没有按 Provider questionID/replyID 建立与 Context 的完整关联。
- 当前 `ASRInfo` 处理把它主要当作文本事件；公开合同中它可以只有 questionID。新增关联时不能因没有文本就丢弃这个控制事件。
- 原重试是 0.12/0.24 秒的本地再次发送，不能证明第一次请求没有被 Provider 处理，更不能证明重试仍属于同一轮。

这些不足在当前未启用 RAG 时不必导致 B1 四轮失败，但它们使“直接接回旧 RAG 函数”的修复不安全。

### 3.6 R6：结构化偏好强度在角色文本中有遗漏

后端 `_typed_fact_context()` 保留 `strengthExpression`，但 [_provider_fact_line()](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/services/formal_memory_conversation_snapshot.py:260) 没有输出该字段。

## 5. 火山合同核对结果与版本限制

本次读取官方页面正文，而非仅依赖搜索摘要。官方 iOS 页面目前展示版本 `0.0.14.7`；项目锁定为 `0.0.14.6.1-bugfix`。因此要区分：公开服务协议、公开 SDK 示例、锁定 SDK 实际出站、真实模型输出，四类证据不得替代。

### 5.1 StartSession

官方 iOS 文档要求 StartEngine 入参参考服务端 StartSession，示例把 bot_name 放在根对象的 `dialog` 内，没有额外包装。服务端规定 `system_role` 位于 `dialog` 下，O 系列使用此类角色配置，SC 系列使用不同角色字段。参考：[iOS SDK：启动引擎](https://www.volcengine.com/docs/6561/1597646)，[实时语音 API：客户端 StartSession](https://www.volcengine.com/docs/6561/1594356)。

本次期望形状如下，全部为合成占位；实际值必须来自当前运行合同，不从示例覆盖用户配置：

```json
{
  "asr": {"extra": {}},
  "dialog": {
    "bot_name": "寻梦环游",
    "system_role": "服务端生成并绑定哈希的正式事实角色文本",
    "speaking_style": "运行配置中的表达风格",
    "extra": {"model": "1.2.1.1"}
  },
  "tts": {
    "speaker": "当前已验证音色",
    "audio_config": {"speech_rate": 0}
  }
}
```

示例里的 speech_rate=0 不是要求改语速。实际仍使用当前验证过的值。不要把 `asr/tts/dialog` 的 SDK 参数与服务负载混写到同名对象中。

### 5.2 ChatRAGText

最小合成负载：

```json
{
  "external_rag": "[{\"title\":\"已确认正式事实\",\"content\":\"合成人物本科毕业于甲大学。\"}]"
}
```

应两次使用 JSON 编码器：先编码条目数组为字符串，再编码外层对象；禁止手工拼接/转义。公开合同限制该 RAG 输入整体不超过 4K 字符，不能把 8,088 字符的全量角色原文直接塞进去。服务端事件名为 ChatRAGText，SDK 指令名为 `SEDirectiveEventChatRagText`。参考：[API：事件 502 及补充说明](https://www.volcengine.com/docs/6561/1594356)，[iOS SDK：发送 RAG Query](https://www.volcengine.com/docs/6561/1597646)。

### 5.3 同轮与播放控制的事实边界

公开 API 的 502 入参未提供显式 question_id；Provider 在 ASRInfo、Chat、TTS 等事件中提供关联 ID。iOS SDK 另有委托播放选择机制，但**控制采用哪路 TTS 不等于控制模型何时开始推理**。默认原生模式不能仅凭一次本地异步 HTTP 请求保证 RAG 先于默认回答生成。参考：[API：服务端事件](https://www.volcengine.com/docs/6561/1594356)，[iOS SDK：客户端/服务端触发 TTS](https://www.volcengine.com/docs/6561/1597646)。

不能把新版 RTC、全双工新品、其他 SDK 或其他模型的能力直接套用到本项目锁定版本。需要升级或切换协议时另列收益、成本、风险并取得用户确认。

## 6. 本次确定采用的修复主链

```text
用户开启 Live
  -> 服务端鉴权并确定当前人物
  -> 读取唯一正式记忆的当前合格事实投影
  -> 生成完整 providerRoleText，保留事实限定，绑定角色哈希和正式修订
  -> iOS 按正确 StartSession 字段发送
  -> SDK/Provider 会话建立
  -> 每轮用户音频由火山原生 S2S 回答，使用会话已绑定的正式事实
  -> 每轮转写继续独立持久化
  -> 用户关闭整场会话后，整理一次，进入待确认/无新增/明确失败终态
```

### 6.1 必须保持的产品边界

- 正式记忆只来自用户审核后的统一 Authority；不能用 Source、Candidate、本地 Archive、KBLite、旧对话摘要或模型猜测补正式事实。
- 本场用户新表达可以作为未审核的对话语境被回应，但不能声称已经成为正式记忆，也不能自动覆盖现有正式事实。发生矛盾时区分“本场新说法”和“已有已确认记录”。
- Live 答案与音频继续由火山生成；禁止恢复 `ASR -> /echo/answers -> DeepSeek -> ChatTTSText`。
- DeepSeek 仍负责文字问答和会后整理；不能为了增加 Live 检索而调用 DeepSeek 生成一份答案，再要求火山照读。
- 维持同一场持续麦克风和播放器/AEC，不按问答轮次 stop/start，不等待整理完成才允许下一场。
- 原权限失效、正式修订失效和会话租约校验继续有效。当前设计在正式快照变化时中止失效租约；不得悄悄继续用旧快照，也不得偷偷把新版本与旧版本混合。

### 6.2 为什么主链不强制增加逐轮 RAG

B1 测试的四项依据应已包含于当前全量快照。启动前注入不增加逐轮检索网络等待，也没有“RAG 比默认回复晚到”的竞态。

主链成功的逐轮验收记录应是 `groundingMode=sessionSnapshot`，并关联会话角色哈希与正式修订。此模式每轮无需出现 contextBuilt/3009；不能伪造这些事件，也不能把缺少这些事件继续视作必然缺陷。

相反，若选择 `turnRag` 模式，则必须完成第 9 节更严格的检索与轮次验收，不能拿 sessionSnapshot 模式的 PASS 覆盖它。

## 8. 接口与数据合同：主路径无需新数据库或新服务

### 8.1 继续使用的现有接口

| 接口/边界 | 本次要求 |
| --- | --- |
| `/voice/realtime-token` | 保留鉴权、人物、productSessionId、短期代理凭证、当前快照和角色哈希绑定；不向客户端发长期 Provider 密钥 |
| `sessionContext.providerRoleText` | 仅由服务端生成；iOS 发送正文必须等值，不能客户端截断/拼接后仍用旧哈希 |
| `formalMemorySnapshot` | 当前合格正式事实的只读派生快照；不变成第二份事实 Authority |
| WebSocket 代理 | 保留一用凭证、权限复核、帧/流量预算。当前是透明转发，不应声称它已经校验了最终 Provider JSON 的字段或正文 |
| `/echo/answers` | 文字继续使用；Provider-owned Live 不调用它生成回复 |
| Live 转写持久化/会后整理 | 维持逐轮耐久写入、整场一次整理的现有合同；本次不重放历史失败批次 |

客户端内存校验不能作为恶意客户端边界。如果增加代理侧 StartSession 字段/哈希核验，只针对已验证协议的控制帧，失败拒绝，不重新生成正文；音频仍按原链路透传。该强化必须补二进制、压缩、边界和性能测试，不可为 B1 偷改所有音频转发规则。

### 8.2 长度与格式预算

本地现状：快照日志约 42,750 字符，角色文本约 8,088 字符；两者不是同一份发送材料。`FormalMemoryConversationSnapshotService.build()` 当前不按传输字符预算裁切 coreFacts；`bind_provider_role_text()` 才对最终 role 做字符上限判断，超限报错，不静默截断。

`32,768` 是本项目角色字符阈值，不是 Provider 模型 token 容量；15,310 字节也不是 15,310 tokens。不能用“没超过本地阈值”推断模型肯定能完整采用。官方当前文档列出 O2.0 上下文为 12K，并且上下文还包含其他输入与对话历史。参考：[模型能力与上下文](https://www.volcengine.com/docs/6561/1594356)。

必须分别计数：eligibleFactCount、includedFactCount、omittedFactCount、roleUnicodeScalarCount、roleUTF8Bytes、可获得时的 Provider token 用量。Swift String.count 与 Python len 的 Unicode 单位不同，诊断中明示计数单位，**正文等值以 UTF-8 字节哈希为准**。

采用策略：

1. 先修字段，再在同一模型配置下测实际长短效果；不要把未知失败直接归因于 8,088 字符太长。
2. 可做确定性紧凑序列化，去重复格式和无用标签，不能删除事实值或关键限定。角色哈希必须对应压缩后的最终文本。
3. 不采用模型自由摘要来替代完整事实。若预算不足，必须明确范围或返回超限，不能只塞最近若干条却说“全部正式记忆”。
4. 事实放头部/中部/尾部均要有测试，长会话后另做 B2 覆盖。检验成功不只看句子相似度，要看学校、学历、时间、职业状态和偏好强度的事实蕴含。

## 9. 条件性逐轮 RAG：需要时怎样做，不作虚假保证

本节是启动修复后仍有采用不足、或未来正式事实超出已验证预算时的执行分支。**不是要求无条件开启 RAG。** 未启用时在交付写“本次采用 sessionSnapshot；turnRag 未启用”，不能写 turnRag PASS。

### 9.1 不允许的简单修复

```text
ASR final
  -> 异步 /context/build
  -> 不论 Provider 是否开始回答都发送 3009
  -> SDK 返回 0 即标记同轮成功
```

这条链不能保证同轮，不能上线。首音未到也不代表模型尚未生成；本地 turnID 相等也不能消除网络在途时新问题到来的竞态。

### 9.2 先执行独立能力探针

必须使用锁定 SDK、合成事实和真实 Provider 验证，普通业务流保持关闭：

1. 正确 external_rag 指令最终编码到服务端事件 502；产生 `tts_type=external_rag` 的可听回答。
2. 精确记录 questionID、replyID、ASREnded、502 发出、550/350 到达的关系。
3. 在检索人为延迟 50/200/800/1500ms、默认回答先到、用户抢话、连续同问、断网重连条件下观察是否重复回答或污染下一轮。
4. 明确区分默认推理、RAG 推理、客户端/服务端 TTS 选择。SDK 委托播放模式只算候选能力，不因其名称相近就切回本项目 `.dreamJourneyBackend` 分支。
5. 若供应商没有可验证的等待、提交、取消或轮次指向合同，不得承诺“回答生成前绑定同轮”。将该能力标 `BLOCKED_PROVIDER_TURN_CONTRACT`，继续已验证的 sessionSnapshot，不用延时或暂停麦克风伪造保证。

若证据仅能证明“RAG 产生的新答案被选为可听输出”，应如实写“输出选择保证”，不能写“默认答案从未开始生成”。该语义差异须先向用户说明，不能悄悄替换验收要求。

### 9.3 只有能力验证通过，才接入带会话租约的检索

复用现有 PostgreSQL/pgvector/BGE-M3 检索能力，不新增数据库、消息中间件或第二个生成模型。

现有 Owner `/context/build` 可以作为检索逻辑参考，但它没有绑定 Live productSession/providerGeneration 的完整合同，不能直接等同 Live 专用检索入口。建议新增或明确扩展一个窄接口，路径可按仓库惯例调整，例：`POST /voice/live/context`。这是**拟议合同**，不是已存在接口。

请求字段：

| 字段 | 约束 |
| --- | --- |
| productSessionId | 必须由当前登录者拥有，关联服务端授权目标 |
| providerGeneration / providerSessionBindingId | 服务端签发的当前活跃连接绑定；客户端整数不是授权依据，不重复消费一次性 WebSocket ticket |
| clientTurnId、turnSequence | 本地幂等标识和顺序，不当作 Provider 同轮保证 |
| providerQuestionId | 只能作当前 Provider 会话关联；若服务端没有可信事件观察就标客户端关联，不能伪称已验证 |
| query、queryRevision | 本轮实际用户最终文本；设长度限制，重复 id 不允许换问题正文 |
| expectedMemoryRevision、projectionCheckpoint、authorityEpoch | 只用于一致性条件，服务端重新读取/验证；不能由客户端指定任意人物、事实或权限 |

响应字段：`outcome`、以上会话/轮次绑定、`queryHash`、`memoryRevision`、`projectionCheckpoint`、`authorityEpoch`、`rightsRevision`（已有服务可取得时）、`groundingMode=turnRag`、`facts[]`、`sourceMemoryVersionIds`、`retrievalReceiptId`、`contentHash`、`expiresAt`、长度及覆盖计数。

要求：

- `facts[]` 只包含本次合法正式事实及完整限定，最多为 Provider 预算内可完整容纳的相关事实，不返回原始 Source/Candidate。
- 无依据、权限失效、修订变化、检索失败、超时必须区分。失败不回落 KBLite/Archive，不调用 DeepSeek 生成替代答案。
- same session/turn/query/revision 的重复请求返回同一逻辑结果；同 id 不同 query 明确拒绝。使用现有会话/幂等存储，不能把进程内 map 当跨进程可靠保证。
- Family 复用已验证的目标授权与范围，不调用 Owner 私人入口绕过权限；授权无法对应时拒绝。
- 检索中发生正式 revision 变化时，拒绝旧结果并按现有会话更新策略处理，不能拼接新旧事实。
- 尽量预取与缓存同权限/同修订结果，但 partial ASR 的预取不能直接触发 502，final 更正后必须重新校验 queryRevision。

### 9.4 时序状态机及失败规则

建议每轮键：`(productSessionId, providerGeneration, providerQuestionId, turnSequence, queryRevision, authorityEpoch, memoryRevision)`。

```text
LISTENING -> QUESTION_OPEN -> FINAL_OBSERVED -> RETRIEVING
 -> CONTEXT_READY -> PROVIDER_COMMIT_WINDOW_CONFIRMED -> SUBMITTED
 -> MATCHING_REPLY -> AUDIO_PLAYING -> TURN_FINISHED

任一阶段新 question / 打断 / 重连 / 切人 / 撤权：INVALIDATED
检索超时或提交窗口关闭：NOT_SUBMITTED
提交返回不确定：SUBMIT_UNKNOWN，禁止盲重发
```

- `PROVIDER_COMMIT_WINDOW_CONFIRMED` 必须来自实测且有协议依据的控制机制，不能只用本地计时器创造。
- 所有 Provider 指令在同一串行发送/协调通道执行；不能在 SDK 回调线程直接重入 send。
- 新问题在 ASRInfo 就使旧轮查询/提交失效，不能等新 final 才取消。旧在途结果即使成功返回也丢弃。
- 同一轮最多提交一次；没有 Provider 幂等保证时，本地 ACK 不确定禁止重发 502，避免重复生成。
- 若默认 ChatResponse 已到而无可验证的替换机制，不向该轮继续注入，也不把它偷偷留给下一轮。
- Provider replyID/questionID 与预期关联不符，不能宣称本轮 grounded。是否能在不破坏原生音频的情况下阻止错误输出，必须在能力探针验证，不能只拦截字幕。
- 麦克风一直保持，检索/播放故障不自动关麦；严重权限失效按已有明确退出策略处理。
- 不用任意 sleep、重复 ClientInterrupt、每轮 stop/start、切 push-to-talk 来实现等待。

**当前公开合同与本地代码不足以证明上述 Provider 提交窗口存在。Sol 不得用本地 Gate 实现代替这项证据。**

### 12.4 B1 核心复测

## 13. 性能与不回退验收

沿用原文档 DFX 原则，不引用豆包/GPT 未公开 SLA：

- sessionSnapshot 主链不增加每轮 DeepSeek、embedding 或检索 HTTP 等待。
- 修复前后在相同设备/网络/模型/音色/VAD条件下比较：点击到会话可用、用户说完到首音、打断到停播、停播到下一次语音被采纳。
- 至少30个有效样本/条件报告p50/p95、绝对耗时和失败率。若没有修复前可复现基线，明确不能声称“开销不足20%”。
- 延迟增量目标仍按原约定不超过同条件基线20%；任何固定增加的3秒停顿、每轮关麦/开麦或默认答+RAG重复答都是回归。
- 角色预算不能只看单次开场；B2长对话后要重新问基础正式事实。
- 会后整理不阻塞收音或新场开启；对话持久化不得因检索/诊断同步耗时阻塞SDK回调。
- 原角色从错误路径移到正确路径后可能首次被模型有效使用；因此语气、音色兼容、响应长度和安全拒答也需回归，不能假设只是一个无行为影响的JSON修正。

## 14. 失败回退方案

| 失败情形 | 正确处理 | 禁止处理 |
| --- | --- | --- |
| 正确单层负载被锁定SDK拒绝 | 保留合成帧和安全错误码，核对该版本实际合同；隔离分析，必要时提出SDK升级评审 | 把双层路径重新称为“官方正确”或直接升级到最新 |
| 短合成事实也不采用 | 检查model/资源/角色语义，提交真实Provider案例，B1保持FAIL | 写死学校/职业答案；改用户正式记忆 |
| 短成功长失败 | 做位置/预算对照，确定性紧凑编码；不满足则明确限制 | 删掉事实、用未审核摘要或忽略未知题 |
| RAG竞态/双回复/无声 | 禁用turnRag，退回已验证sessionSnapshot；若后者也失败则B1继续FAIL | 恢复ASR→DeepSeek→TTS或暂停麦克风隐藏竞态 |
| 新版本破坏播放/打断 | 停止B用例，按已保存构件回退应用；状态记录为回退后仍待修复 | 将旧已知“不知道”版本标记B1通过 |
| 后端角色格式改动失败 | 回退兼容应用/配置，重新签发匹配会话；不回滚正式数据 | 修改数据库revision/ready字段伪造健康 |
| 撤权或正式修订失效 | 拒绝旧上下文，按既有显式会话重建策略处理 | 为保持声音继续输出旧私人事实 |

回退不清用户数据，不删审核历史，不重放Dead Letter，不更换模型/供应商/凭证。涉及新权限、费用、SDK升级或额外生产变更时先确认授权。

## 15. 隐私安全日志要求

### 15.1 可记录的最小事件

建议统一事件名；以下为拟议诊断，不宣称当前已存在：

| 事件 | 最小字段 |
| --- | --- |
| liveSessionBindingValidated | build/adapter、groundingMode、事实计数、revision、租约有效布尔值 |
| liveStartFrameObserved | sdkVersion、event=StartSession、fieldPath、roleBytes、hashMatch、modelFieldPresent |
| liveProviderSessionStarted | 与本地会话的匿名关联、耗时；不表示记忆采用 |
| liveQuestionOpened / liveASRFinal / liveASREnded | sessionGeneration、turnSequence、匿名questionID、单调时间 |
| liveReplyObserved / liveFirstAudio / livePlaybackEnded | 匿名questionID/replyID、ttsType、单调时间、关联结果 |
| liveFactAnswerEvaluated | 测试caseID、supported/refused/incorrect/unknown、人工或合成自动评价类型 |
| liveTurnContextBuilt / Submitted / Dropped | 仅turnRag模式：匿名receipt、检索耗时、字节数、计数、SDK指令名+编号、原因为何丢弃 |

诊断必须区分：本地构造、SDK接受、出站捕获、Provider会话建立、事实语义正确。没有可观测事件就记 NOT_OBSERVED，不补造 ACK。

### 15.2 哈希不是匿名化许可证

- 合成输入可以记录全文SHA供复现；真实短问题/低熵事实直接SHA可被字典猜测，普通日志优先按场/按运行密钥HMAC或不记录该字段。
- 协议绑定所需完整providerContextHash保留在安全内部合同；普通日志只输出匿名关联或hashMatch，不必暴露原合同值。
- 同轮时序使用同一进程单调时钟。跨手机/服务端时钟没有同步误差评估时，只比较相关事件/往返耗时，不宣称精确网络先后。

### 15.3 禁止记录

正式role正文、正式事实值、手机号/账号、访问令牌、长期凭证、完整Provider请求/响应、用户转写正文、音频文件、未经脱敏的query字符串、带ticket的URL。

不要打开SDK TRACE或原始录音保存。当前 DEBUG `DialogPromptDebugRecorder` 会在内存保留prompt，仅允许在明确的合成测试路径使用全文检查；正常真机诊断用元数据，不把lastSnapshot导出。完成会话/退出诊断时释放临时引用。

T06允许的合成受控WS捕获必须与正常用户模式明确隔离；不得把真实用户正式记忆发到任意自建公开接收端。普通日志采集从源头白名单化，不能先把敏感完整流写盘再靠事后脱敏补救。
