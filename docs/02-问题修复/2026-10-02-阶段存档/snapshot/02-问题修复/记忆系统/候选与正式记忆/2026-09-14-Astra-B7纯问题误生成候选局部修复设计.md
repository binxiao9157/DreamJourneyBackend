## 5. 局部修复设计

### 5.1 产品语义合同

候选资格按**有上下文的用户表达片段**判断，不能按整个 turn 是否含问号判断。以下例子是待测合成验收标准：

| 用户表达 | 结果 |
|---|---|
| “我的阅读清单代号是什么”；“能告诉我代号吗” | 纯查询，0 候选；无问号也同样处理 |
| “难道我的代号不是晨星吗？” | 单凭反问/预设不足以新增事实；需看上下文中是否另有明确自述，不能由问法推定 |
| “我不是 2020 年去的，是 2021 年，这次记清了吗？” | 保留明确纠正为 2021，不因结尾疑问删除整句 |
| “我昨天问老师‘什么时候开学？’，后来去了图书馆。” | 可保留明确自述的真实事件/时间；不把引号内未知开学日期造出来。此处叙述历史询问行为与把本次查询自动改写为“用户问过”不同 |
| “我 2021 年搬到苏州。能帮我查一下学校吗？” | 保留搬家事实，过滤查询子句 |
| “我 2020 年搬家，不对，是 2021 年。” | 同轮纠正取最终 2021；保留修正依据，不产两个并列事实 |
| assistant：“你在杭州工作？”；user：“对” | 含糊附和不独立采纳助手具体命题；若用户明确“我目前在杭州工作”，按实际自述处理 |
| “以前在杭州，现在住苏州”；随后补充“从去年九月开始” | 保留历史/当前限定并合并时间，不丢掉补充或强行只取最后一句 |

问句仍原样保存为会话上下文；候选不应记录“此次用户提出查询”这一元事件。用户主动叙述自己过去询问某人的经历，可以是事实，需按语境判断。任何正式写入仍由现有用户审核合同决定；修复不能自动确认。

### 5.2 推荐实现：生成后、真实 builder 前的专用语义支持关口

只为已封口的 Live conversation Source 增加一个小范围的 validation 模块。它不改 ontology 全局规则，不新建长期事实库，也不向火山逐轮插入调用。

1. **固定输入。** 从当前 Source 的不可变 conversationTurns 和用户证据窗口构造规范序列，保留 owner/assistant、顺序、分段映射、终稿来源与 Source hash/version。维持现有最后序号封口验证。角色或窗口损坏报合同错误，不“尽力猜测”。
2. **明确生成约束。** 更新 Live organizer prompt/version：只提取用户主动表达的事实、感受、观点、时间补充和纠正；纯查询、确认问法、助手回答与“用户问过”式当场查询转述不能生成事实。保留空结果路径。提示词变更必要但不作为唯一修复。
3. **独立支持复核。** organizer 给出草案后，用独立的受控语义复核请求读取原始用户终稿、必要 assistant context 和草案，不把 organizer 自报“用户证据”当事实。输出版本化内部结果：用户片段的言语类型（assertion/correction/timeSupplement/query/quotedSpeech/ambiguous）、候选逐命题支持片段、supported/unsupported/uncertain、纠正/撤回关系及片段覆盖。此合同是新增设计，不是假称现有字段。
4. **确定性关口。** 程序验证复核结构、全部 user span 覆盖、准确文本范围、仅 user 可作证据、命题与证据 ID/Source 绑定、同轮/跨片裁决完整，之后才调用现有 `enrich_memory_payload_v5 → CandidateProposal`。任何用户 span 仅被判为查询不能支持该候选；assistant context 不能充当支持片段。仅 quote 存在、仅 confidence 高、仅 user role 都不够。
5. **空结果也要复核。** organizer 返回空并不证明没有事实。全部用户终稿被可靠分类为无需提取时，才允许 `succeeded + 0 → completedNoChange`；若漏掉事实、覆盖不全或纠正未裁决，不得以空结果假成功。可在现有有界预算内进行一次修正请求并重新全量校验，仍不成立则进入明确合同失败/隔离状态。
6. **整场最终裁决。** 长会话可继续分片，但必须保留 original turn/span 对应关系；第二遍在整场范围处理同一事实的补充、否定、撤回和纠正，再输出最终候选集合。不能只做字符串去重、只读尾句或按“最后出现者总胜”覆盖所有事实。跨片冲突无法在预算内裁决时阻断该场最终发布；不把部分结果标全场成功。
7. **错误处理。** 无可靠支持的候选不能通过“等待用户审核”放行。复核明确所有片段为纯问题时正常 noChange；semantic uncertain/Provider 错误/schema 错误保持真实失败/受控重试，不调用原文拼接 fallback，不静默丢弃真实事实后宣称成功。
8. **保持写边界。** V5 候选外部合同、Source 原文/版本/hash、authority、lease、CAS、Binding、候选审核合同保持。语义内部结果如无需落入候选 payload，避免新 API/DB 字段；只记录安全版本/计数/原因。如果实现必须持久化新证据结构，先给出最小 schema 变更和旧读者兼容证据再实施。

独立复核也依赖模型语义能力，不能声称是数学证明。其效果必须由真实 Provider 的固定语料、多次复现和人工标准判定验证；不得仅 mock 一个 `supported=false` 就宣称语义问题已修。新增调用发生在会后 Worker，影响整理延迟/成本，应测量并纳入现有租约心跳和总预算，不影响原生 Live 的实时回答。

## 7. 真实组合怎么搭与本地门禁

1. 从真实 iOS append payload 和后端冻结 batch/source builder 取得合成结构；保留 question、assistant、后续用户新事实/纠正的位置。实际 PostgreSQL 测试必须从 natural session 写入口构建，不能仅 seed 一条抽象 Source 代替全链路。
2. 受控模型替换 HTTP 边界，真实 `build_request/normalize/parse`、Live extractor、V5 enrichment、CandidateProposal、ExtractionService、Worker 均运行。必须同时控制 generator 与 verifier 输出，证明坏 generator 会被实际 verifier/关口拒绝，并证明错误 verifier/字段不完整会 fail closed。另设真实 Provider 门禁，不能将这两层合并。
3. PG 只用独立库与合成 vault；核对 conversations、review batch、Source、admission、extraction、candidate、effect/lease/consumer、通知和正式 revision。纯问题允许存在原始 Source 与成功空 extraction，不允许新增候选或正式事实；不能用删除 Source 消除问题。
4. 真正走 `/v2/vaults/{vault}/candidates` 和原 batch status 读取。使用真实后端 builder 导出的响应、真实 iOS BackendClient/evaluator/账户作用域和 UIKit。比较新增 candidate ID 集合、来源归属、正文与 UI；总数不变但错换内容仍须失败。
5. 真实 Provider 只使用新合成语料，在获授权的测试目的地执行；不读取或外发生产私人原文。本地固定验收集至少覆盖 T05–T09，每例建议三次独立运行，所有关键反例及正例均通过才能放行；三次是起始实验门禁，不代表普遍正确性保证。记录新增会后耗时、token/cost 与总超时/心跳，不调整原生语音实时链路。
6. 保存修复前后同组断言、代码指纹、实际 runtime/config/prompt/validator 版本、日志与 PG 关系快照。先修真实业务红例，再跑相关 backend 测试和 iOS OwnerTruth/终稿保持性；只有 iOS 改动时追加必要构建，锁定依赖不升级。
7. 隔离 PG、真实 Provider、UIKit 或真机未执行，逐项标 `NOT_RUN` 并说明条件；不能拿 R01 的内存 Worker 或现有空输出测试代替。所有要求的本地门禁通过才可记 `B7_A_LOCAL_PASS / READY_FOR_B7_DEVICE_RETEST`，现场仍待真机闭环。
