## 5. 最小修改方案

### 5.1 恢复入口与职责

推荐把恢复调度接到现有列表 `refresh` 的未决检查位置，扩展它识别单条和关联组记录。初始化、手动刷新和“核实结果”使用同一调度路径。可以提取小型恢复组件，但不能另建一套通用任务队列。

对返回已有列表页面的 `viewWillAppear`，仅在有未决记录且没有该作用域活动操作时触发一次有界核实；避免 `viewDidLoad` 与首次 `viewWillAppear` 双触发。不得使每次重绘/弹窗关闭都自动查询。

组级恢复应暴露不依赖 Proposal 的窄入口，概念合同为：

```text
输入：原主体合法 AccountLease、磁盘 PendingGroupRecord、readIntent/requestID
必要字段：record.commandID、record.binding、record.subjectID、record.vaultID
输出：核实中 / 已核实 / 尚未核实 / 授权阻断 / 本地记录异常
副作用：只有合法 found 后解决对应本地未决记录；不发业务写请求
```

方法名称可以沿用项目风格；不得用 `confirm(proposal:)` 当恢复 API，也不得伪造完整 Proposal 以适配旧函数。现有 `lookupOwnerTruthCandidateChangeSetGroupDecisionResult(... expectedBinding:)` 已接受持久 Binding，优先复用。

### 5.2 列表与未决查询的关系

- 未决记录的作用域是主体/vault，不是当前列表或 sourceIDFilter。来源过滤页、空列表、旧组成员不在列表时都必须能恢复。
- 发现合法组级未决记录时先进行一次有界查询；查询期间不开放该作用域新审核写。普通内容可只读展示，但不能将旧列表可见解释为可确认。
- found 验证和本地记录解决成功后，将 appliedMemoryRevision 纳入已知最低版本，再通过现有列表刷新逻辑获取最新 Candidate/Proposal/Binding。
- 刷新成功且该作用域全部未决问题解决后，才允许新的用户确认。不能先放开旧 Binding 再异步刷新。
- 列表刷新使用既有版本追赶和预算，不重新引入无限追赶；一次核实成功只能触发一次必要刷新，不能 query -> refresh -> query 循环。
- 多条异常未决记录或单条/组记录并存时，不得静默只解决第一条便开放写入。保持整个作用域写保护，给出可诊断状态；仅允许有界只读核实，不清理或猜测其他记录。不得以本轮为由新增自动历史重放。

### 5.3 复用同一条组级结果处理链

当前 confirm 后立即核实和重新进入后核实，应复用同一 Binding 校验与本地记录解决代码，避免出现两套成功标准。

合法 found 至少保持现有 `OwnerTruthMemoryChangeSetGroupCommitResult(expectedBinding:)` 的 Proposal ID/hash、base revision、成员 ID/顺序、决定、终态、activation 校验，且请求命令、响应归属和原持久记录一致。

存储原记录中的 base revision 是核实原事务的依据，不能用当前最新 revision 改写它。核实历史结果不要求重新生成现时 Proposal，也不重新确认一次。

## 6. 状态机与结果规则

| 状态/事件 | 处理 | 审核写是否允许 |
| --- | --- | --- |
| 无未决记录 | 走现有合法列表读取/预览流程 | 其他门禁均满足后允许 |
| 发现组级未决记录 | 保留原命令，进入 checking | 不允许 |
| checking | 同作用域同命令核实单飞；页面可返回 | 不允许 |
| found 且绑定合法 | 解决精确记录，刷新到足够新的正式修订与候选上下文 | 刷新和全部门禁完成前不允许 |
| notObserved | 表示查询时未观察到，不代表没有提交；保留记录 | 不允许 |
| 超时/网络失败/503/接口不存在 | 保留记录，准确提示，可手动再次只读核实 | 不允许 |
| found 但绑定不符/解析失败 | 不宣称成功，保留记录，报告结果不一致 | 不允许 |
| 查询前或返回时账号不合法 | 停止对旧主体的操作；页面结束等待，不显示旧主体私有内容 | 不允许使用旧上下文 |
| 本地文件损坏、不可读或移除失败 | 不按“无记录”放行，不删文件，准确报告 | 不允许 |
| 页面退出/进程结束 | 不删除记录，不自动重发写；后续由合法入口核实 | 不因退出而恢复 |

“已核实关联审核结果”不一定等于每个成员都新增了正式记忆。复用已验证回执区分确认、更正、拒绝和不新增事实等结果；不能对整组一律提示“全部新增正式记忆”。

## 7. 账号、单飞和迟到回调

1. 请求开始、响应处理、UI 提交都验证当前账号租约和作用域，不能只比较 subjectID 字符串。
2. 同主体合法凭据轮换可在现有受控机制下重新核实，但旧预览/选择/确认闭包必须失效。不同主体不得自动读旧主体文件、查询或显示旧结果。
3. 以 scope + 原 command 的安全关联身份识别核实操作，requestID 标识具体尝试；页面实例/代次决定谁可以接收 UI 完成。
4. 复用现有主线程/串行执行域，使未决检查、核实占用、记录解决与写门禁一致。两个列表实例或刷新连点不能产生重复查询风暴。
5. 同一查询在途时合并入口；notObserved 或失败后停止自动查询。用户再次点击“核实结果”可创建新的只读尝试，不产生新 command。
6. 设置可测试的整体查询期限，沿用不宽于已有 30 秒约束；到期只结束一次等待并释放本次读取占用。不得删除原未决记录或开放写入。
7. 迟到回调不得移除新记录、完成新页面的其他操作，或释放新 requestID。不同主体和已过期请求不能提交 UI；本地持久状态的变更也必须通过合法的作用域/命令校验。
8. 当前进程中关联组写仍在途时，不要把磁盘记录误当成无人负责的重启恢复任务；共享该作用域的活动状态，禁止另一路绕过写保护。

- 在待确认记忆列表的既有状态区域显示“有关联审核结果待核实”，提供明确“核实结果”动作；无需新页面或装饰性卡片。

- 保持 VoiceOver 标识与可操作状态；真实 UIQA 要检查返回可用、核实动作可达、写按钮受保护。
