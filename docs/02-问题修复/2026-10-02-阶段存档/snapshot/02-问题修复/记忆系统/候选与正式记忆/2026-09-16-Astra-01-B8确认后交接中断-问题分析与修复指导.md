## 结论与证据等级

当前源码存在一条已经用真实源块运行复现的确定缺口：candidate admission 的刷新适配器刷新了缓存，却继续复用旧 route decision。旧 decision 过期或最初 denied 时，新缓存已经允许也仍会得到 false。随后 admission use case 将它合并为 `releasePolicyDisabled`，Echo 将各种原因合并为 `unavailable`。BackendClient 的 admission 首层同样重新取得旧 route，因此只把页面里的一个 Bool 改为 true 并不能完成修复。

另有一项确定的失败分类缺口：若 ack 已收到 `.committed` typed receipt，但随后 `receipt.matches` 失败，会变成 `.contractMismatch`；Echo 又将这个 notice 默认持久化为 `.notSent`。发送后回执无法绑定不等于未发送，必须修正为保留 unknown 的只读恢复状态。

这是**确定的当前源码机制和局部反例**，目前还不是**该次真机唯一根因**。原问题记录和后来恢复的原任务现场输出均没有给出 ack 的绑定验证事件、磁盘 phase、admission notice 或命令关联的具体拒绝原因。不得只依据相邻 policy 请求认定该真机命中了旧 route 缺口。

还有一个必须校正的表述：即使有 `ack HTTP 201 + typed decode succeeded`，也不等于客户端已进入 `.acknowledged`。真实代码在解析后还验证账号 lease 和 `receipt.matches(command)`；这一步失败也会产生相同的 `queued → unavailable`，且没有 admission 请求。因此定位必须从 ack 回执验收到 admission 首次 transport 边界完整覆盖。

本轮未修改业务代码，未连接手机/生产，未运行手机或模拟器测试，未重放历史写入。本轮运行了合成源块 probe，以及 5 个既有后端内存测试；完整 UIKit/真实磁盘/BackendClient/网络组合与修复后真机均为 `NOT_RUN`。DJ-B8-DEVICE-01 继续保持 `FAIL`。

## 4. Sol 的最小修改指导

### 4.1 先把第一次失败定位到阶段，保留细分原因

仅在文字关闭的 coordinator/use case/typed BackendClient 链增加 `B8CompletionStage` 和白名单失败摘要，不再只记录 captureState。每个事件带同场安全 correlation hash、原 command hash、单次 attempt、阶段、允许/拒绝结果、checkpoint phase、曝光分类。不得打印原 subject/vault/session/batch/command ID、正文、token、URL 完整路径或后端原始 error detail。

最少区分：ackDecoded、ackBindingChecked、ackCheckpointCommitted、admissionCommandPrepared、admissionPolicyChecked、policyRefreshStarted/Finished/TimedOut、clientLeaseChecked、requestRuntimeChecked、requestFeatureChecked、requestCreated、taskResumed、transportClassified、admissionReceiptChecked、admissionCheckpointCommitted。

ack binding 报告四个布尔值与版本关系（gt/eq/lt），不输出原业务坐标。账号报告 AccountLeaseValidationReason 白名单；磁盘报告 missing/decodeInvalid/schemaUnsupported/phaseMismatch/commandMismatch/storageFailure。policy 报告 feature、reason、旧/新revision、expiresAt和request purpose，不输出 accountGeneration 原值。

修改 `receiveAcknowledgementState/receiveAdmissionState` 时保留 notice 和安全失败阶段；修改 use case `receive` 保留 notSent(Error)/serverRejected 的白名单具体原因。特别要区分发送前 command 不合法与收到 committed/曝光后 receipt 无法绑定：当前 ack use case 在 receipt.matches 失败时产出 contractMismatch，而 Echo 默认把它映射 notSent。后者必须是 `outcomeUnknown + receiptBindingMismatch`，不得将已曝光业务写持久化为未发送。admission 对应回执分支也按同一规则检查。允许界面沿用现有稳定错误文案，但本场诊断必须能回溯，不在本项重构全局状态展示。

trace 应在 client 首层 guard 之前建立；只有进入 requestJSON 才创建 trace 会遗漏最关键的拒绝。`requestJSON` 中 runtime policy deny 当前没有对称的明确 stage 事件，也要在该真实早退记录白名单原因。

### 4.2 修复 candidate admission 的授权准备，不放宽全局规则

推荐一个窄接口：`prepareCandidateAdmissionAuthority(accountLease:command:deadline:completion:)`，返回 `Result<CandidateAdmissionAuthority, B8PreparationFailure>`。authority 至少携带确切 FeatureDecision、原 lease 和本次准备 generation；它不是一个可随意复用的 Bool。命名可调整，但职责必须明确。

1. 原 ack 已绑定验收，先原子保存 admissionPrepared + 原 command；保存失败零业务请求。保留现有 B8 顺序。
2. 检查原 lease、同场关闭意图、operation generation、准备 deadline。先用现有 `freshServerPolicyManagedRequestDecision(.ownerTruthCandidateReview)` 捕获当前 request authority。
3. 缓存缺失/过期/版本需要更新时，允许一次有界**只读** policy refresh。fresh request 仍明确 deny 则停止，不无限刷新到允许。复用已有 30s timeout 和 generation fencing，超时或取消后的成功回调零写。
4. 刷新后重新核对相同账号/authority，并从最新合法缓存 fresh capture；不要重新问旧 route。不要修改 captured expiry、绕开权限 deny、借 echoTextInput 许可给 candidate admission。
5. typed `admitOwnerTruthInterviewCandidateProposalWrite` 接收上述明确 decision，并检查它的 feature、scope 和期限，再把同一 decision 传入 requestJSON；requestJSON 继续严格 revalidate。不能在中间又调用 requestFeatureDecision 取旧 route。
6. 保留原 commandID、reviewBatchID、expectedReviewBatchVersion；授权刷新不新建命令。不要为了通过 CAS 去把 ack fence 改成当前任意批次版本。
7. 只有若具体现场 reason 证明 runtime/auth preflight 也需要恢复，才用现有受限只读准备能力补对应原因。不要把 admission POST 的 `allowsRefresh/allowsRecoveryRefresh` 全局改成 true 来隐式重放业务写。

若采用更小的替换方案，至少同时覆盖 Echo 的 available、refresh callback、BackendClient typed write 三个点；并用同一组合测试证明 fresh decision 没被下层覆盖。仅在测试里 `candidateReviewPolicyAvailable: { true }` 不是修复。

### 4.3 保留磁盘与未知写边界

- `acknowledged` 只意味着 ack receipt 已在本场 checkpoint 持久化。`admissionPrepared` 只意味着原 admission command 已落盘，不能推断未发送或已发送。
- 本进程有真实 preflight 拒绝且未曝光证据时可记 notSent；日志缺失、进程中断或回执不可绑定时必须 unknown。已曝光后的网络错误、解码错误、账号切换等不得自动转成 notSent。
- 当前 exposureTracker 是内存状态。若增加跨进程曝光证据，必须先原子记 mayExpose 再允许 task resume；两个动作间 crash 保守 unknown，禁止重启时从“没有 taskResumed 日志”倒推出未发送。
- 结果 unknown 后只读读取原 batch 的 status/orchestration/已有精确结果，保持 B6 冷启动零业务写。禁止在恢复 reader 中再次 `.admit`，禁止新 commandId 和新 batch。
- 磁盘保存 ack 失败时保留原 acknowledgementPrepared 与原 command，用只读确认 ack；保存 admission receipt 失败时保留 admissionPrepared 与原 command，用只读确认 admission。不能清空 outbox/checkpoint 来解除 unavailable。
- 若只读状态表明 acknowledged/readyForAdmission，但无法证明原写未提交，不由后台自动续写。用户是否另起明确受权恢复操作是独立合同，本项先保留可定位、安全的 actionRequired，不把它伪装为自动恢复成功。
