## 4. 已证实根因

### 4.1 B4-S01：将合法对象误判为不可读

代码位置：[OwnerTruthContracts.swift](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:895)，`OwnerTruthJSONValue.ownerTruthFieldPreviewText`。

当前 `.object` 分支仅支持两类对象：存在 `statement/event/...` 等摘要字符串，或存在字符串 `value`。普通嵌套对象直接返回 `nil`。

随后 `OwnerTruthCandidateChangeSetOperation.reviewability` 检查所有字段差异；只要有一个值不能展示，整个操作就成为 `.incomplete`。

后端实际在 [memory_changeset.py](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/domain/owner_truth/memory_changeset.py:663) 的 `_proposal_operation_payload` 中，将真实 before/after 的 `qualifiers` 对象放入字段差异。`build_memory_changeset` 的时间变化分支合法地使用 `changed_fields=("qualifiers",)`，不是后端返回了损坏数据。

因此，“以前喜欢某食物，现在不喜欢”的合法时间变化，可能被客户端禁止审核。**校验需要保留，应该补齐的是合法结构的呈现能力。**

### 4.2 B4-S02：把事实摘要误当作完整字段差异

同一个 `.object` 分支在找到 `statement` 后立即返回，不再处理 `qualifiers`、`facets` 等其他字段。

后端 `correct/refine` 等操作可以返回 `path="content"`，其中 before/after 是完整内容对象，而非仅正文。复现样例正文均为“我在杭州时喜欢吃东坡肉”，但 `qualifiers.validTime.expression` 从 `2016年` 改成 `2018年`。

真实结构已经变化；当前客户端却产生相同的正文摘要和相同的字段展示字符串，仍将操作标为可审核。此时用户无法知道将批准什么修改。

三个入口必须一起修：

- 详情页：`makeChangeSetCard`、`fieldDiffText` 使用了上述有损 formatter。
- 更正确认：`correctionPreviewMessage` 同样依赖该 formatter。
- 关联组：`relatedGroupPreviewText` 仅使用 `groupFactSummary` 输出正文，没有字段级差异。多操作数量完整不等于每项变化展示完整。

### 4.3 为什么已有测试没有发现

[测试 fixture](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourneyTests/OwnerTruthContractsTests.swift:10196) 除了一个 `facets.emotions` 样例外，多数操作共用 `path="content"` 和简单正文对象，通过切换 `operationKind` 覆盖八种名称。

## 5. 修改设计

### 5.1 分开“正文摘要”和“结构化变化”

保留 `ownerTruthFactPreviewText` 作为卡片正文摘要，不再用它证明整个内容对象已经完整展示。

增加一个局部、可测试的成对差异呈现能力，由当前 typed before/after 生成展示结果。建议包含：字段路径、字段名称、before 展示值、after 展示值、完整性状态及失败原因。可使用现有类型扩展或小型展示模型，不建设新的通用 JSON 编辑器。

必须满足以下关系：

```text
绑定的服务端 proposal
  -> 完整性和操作语义校验
  -> 同一份结构化差异展示结果
  -> 详情 / 更正预览 / 关联组预览
  -> 携带原始 binding 提交
```

展示模型只负责格式化，不生成事实、不改变 proposal、不计算一个替代服务端合同的新写入方案，也不调用 DeepSeek 或其他模型润色审核内容。

### 5.2 嵌套对象与 content 的处理规则

1. 当 `path="content"` 时，对 before/after 的实际结构作确定性比较，展示发生变化的字段。不能遇到 `statement` 就提前结束。
2. 当 `path="qualifiers"` 或其他合法结构对象时，继续向下展开到有意义的字段，保留有效时间、适用范围、地点、极性等实际差异。
3. 对象按两侧键的并集比较，处理新增、删除及类型变化；输出顺序固定，可按产品字段顺序再按稳定键顺序排列。
4. 数组不能先排序、去重或按语义合并再比较。没有合同保证的稳定元素 ID 时，按索引或整体 before/after 展示，保留顺序和所有发生变化的值。
5. 不硬编码“只有正文、时间值得显示”。证据模式、可信度、人物归属及其他已支持 schema 内的语义字段发生变化时，也必须可见。
6. `factDiff.changedFields` 是服务端提供的变更范围。可在一个粗粒度路径下展开，不得凭客户端推测新增其他写入动作。`evidenceRefs` 的变化按现有 `factDiff.evidence` 合同展示，不伪装为一个内容字段。
7. 对 known schema 中未映射中文名称、但值可完整解释的字段，可展示清晰的原字段路径作为兜底；未知 schema/operation 或无法解释的关键结构保持不可确认。

示例仅用于合成测试，生产页面必须取实际 proposal：

```text
操作：更正已有正式记忆
确认前正文：我在杭州时喜欢吃东坡肉
确认后正文：我在杭州时喜欢吃东坡肉

发生变化的字段
有效时间：2016年 -> 2018年
```

这是一项有效更正，不得因两段正文相同而显示“没有变化”，也不能用一模一样的两段正文代替时间差异。

### 5.3 空值、类型和完整性

| 情况 | 处理要求 |
|---|---|
| 显式 null | 使用合同允许的“未设置/无”等文案；不得伪造不存在的事实 |
| 字段不存在 | 若原始合同/解码可区分，显示未提供；若已被解码或后端归一为 null，不声称还能区分，两者按该合同处理 |
| 空对象、空数组、空字符串 | 在合法字段差异中明确展示“空对象/空集合/空字符串”等状态，不静默丢失；必需正文为空仍不合格 |
| bool、number | 确定性展示；不把 bool 当数字，不做可能越界的无保护 `Double -> Int` 转换，不擅自舍入改变含义 |
| 嵌套或大内容 | 允许分组、换行和滚动；若超过安全预算而无法完整呈现，显示具体原因并禁止当前确认，不截断后放行 |
| 未知操作、缺失必要目标、缺失必要 after | 继续关闭写入动作，保留候选并允许按既有流程重新载入 |

实现中不能用 `compactMap` 丢掉不可展示的子项后把剩余部分当成完整预览。用于排版的截短摘要可以存在，但完整差异必须在同一次绑定预览中可访问；提交门槛依据完整性，而不是摘要非空。

若需要限制深度、节点数、文本长度，采用现有响应预算或记录明确本地限制，并对边界做测试。无需为了本次问题引入新服务或外部依赖。

### 5.4 八种操作保持真实语义

| 操作 | 必须看见的内容 | 不得误判 |
|---|---|---|
| `add` | 新增后的真实事实与结构化信息，说明原来没有目标事实 | 不强制要求 before 存在 |
| `addEvidence` | 目标版本、正文未改及证据计数变化 | 不伪装成新增独立事实 |
| `refine` | 服务端合并后的 after 及完整字段差异 | 不把候选原文直接当最终内容 |
| `temporalChange` | 前后事实、时间与适用性变化，说明关联新时间事实的语义 | 不将合法 qualifiers 判为坏数据，不说成抹去全部历史 |
| `correct` | 目标版本及真实修改字段，正文可相同 | 不因为正文相同而隐藏修改 |
| `dispute` | 冲突内容、限定条件与预期冲突状态 | 不宣称冲突自动解决 |
| `duplicate` | 无新增正式记忆版本的结果说明 | 不强制期待产生新版本 |
| `noPersonalFact` | 不新增跨会话正式事实的说明 | 不因为 after 合法为空而失败 |

沿用服务端实际的 `anticipatedActivation`：`create`、`revise`、`createRelated`、`createContradictory`、`noNewVersion`、`notApplicable`。测试 fixture 不得对所有操作统一填 `revise`。

### 5.5 三个入口与提交校验必须共用结果

- **详情页**：正文摘要下展示完整字段变化，字段标签可中文化，值不得润色；保持修订号、目标版本、证据和操作说明。
- **更正预览**：必须来自服务端针对更正生成的新 proposal；展示其真实 before/after 及结构变化，保留现有异步 generation 防乱序和 binding。
- **关联组**：显示全部成员、每个成员全部操作及其结构化变化；不能只显示 `正文 A -> 正文 B`。拒绝成员明确不新增事实，不制造 after。
- **提交 UseCase**：单条和关联组都必须验证同一套完整性与原始 binding。不能仅通过 UI 隐藏按钮；直接调用接受/更正提交也要拒绝不完整预览。
- **拒绝路径**：维持原有鉴权、版本和绑定约束；不为拒绝创建新的事实，也不另开绕过校验的接口。

如果关联组内容已经不适合 `UIAlertController` 的长消息，复用现有可滚动预览容器或局部增加一个滚动详情。不要修改整个记忆档案布局。完整展示不要求用户强制滚过每个字，但不能有被省略、无法查看的修改。

原始 JSON、proposal hash、candidate version、changeSet ID 与 base revision 不因格式化而改变。展示完成后方案发生变化时，应要求重新预览，不能把旧页面的同意用于新方案。
