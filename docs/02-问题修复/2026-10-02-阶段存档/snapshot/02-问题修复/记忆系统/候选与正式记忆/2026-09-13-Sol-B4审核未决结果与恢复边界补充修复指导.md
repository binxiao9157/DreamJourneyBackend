## 4. S1：结果未知期间必须禁止新的审核写意图

### 4.1 定位与反例

[submit](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:16231)仅检查 activeReviewOperationID 和活动读取，没有检查 activeResultLookupCommandID 或持久未决记录。[receiveReviewTransportOutcome](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:16883)先清空 activeReviewOperationID，再进入查询；notObserved 保留候选和记录，但详情 [onReviewOperationOutcome](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Archive/MemoryArchiveViewController.swift:7954)把 unknown 与普通失败一起恢复交互。

现有 `testCandidateReviewNotObservedRemainsUnknownAndNeverReposts` 只在 unknown 后调用 refresh，未再次调用 accept，不能证明重复确认安全。

先建反例：真实 UIKit 点击 A -> POST 断连 -> 查询 notObserved -> 关闭提示 -> 再点击 A 确认。记录每个 commandID 和 POST 数；使用每次生成不同 ID 的 factory，不能固定同一 command 掩盖问题。补充查询仍在途、返回 503、重进详情和换另一条 B 确认的变体。

### 4.2 修改规则

1. 同 vault 只允许一个尚未解决的主动审核写操作。任何新的 accept/correct/reject，以及会产生审核写的批量/关联组入口，都必须先检查该作用域的未决写状态。关联组继续保持原子提交，不拆分。
2. `pending/outcomeUnknown/checkingResult/blockedByAccount` 未解决时，不允许创建新 commandID、不覆盖旧记录、不重新发送原 command；用户再次点击也不是安全重发授权。
3. 详情将 unknown 与 notSent 分开：unknown 仅提供“核实结果”和返回查看，确认/更正/拒绝禁用；notSent 在合法新预览就绪后允许用户重新确认。
4. 待核实记录读取失败、损坏或本地锁状态无法确定时 fail closed，不能按“没有待核实记录”继续写入。
5. 写提交前检查与占用获得在同一串行执行域完成；不能先 await 再抢占。优先沿用现有 actor/主线程约定，确有跨 Controller 多实例时增加作用域共享的最小协调器，不建立全局通用队列。
6. 命令状态与 UI 生命周期分离。页面消失、重新创建 UseCase、同主体凭据更新，不会授权新写或遗失原 command。

成功退出条件：获得匹配的持久结果，或证明原意图明确未交给可能发送的 transport。查询 `notObserved` 不是退出条件。保留旧记录后再次刷新只允许 GET。

## 5. S2：用实际请求阶段分类结果，不按 Error 名称猜测

### 5.1 定位与反例

[classify](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:15341)将 accountScopeChanged、sessionUpgradeRequired、recoveryAccessDenied 等直接映射 notSent；然而 [requestJSON 响应处理](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DreamJourneyBackendClient.swift:14775)在收到网络响应之后，也会因提交时账号检查失败返回 accountScopeChanged。UseCase 随后可能走 removePendingRecord。

先建两组真实 BackendClient + 受控网络测试：

- 发送前账号/策略拒绝：POST=0，结果 notSent。
- transport 已接收请求，服务端合成事务成功但响应尚未交 UI，随后账号变化：即使 Error 名称相同，也必须保留原账号的待核实记录，不显示成功、不归为 notSent、不再 POST。恢复到合法原主体后只能 GET 核实。

### 5.2 修改规则

为这条审核写接入结构化请求执行信息，可扩展已有 requestJSON 内部合同或提供窄的审核写包装，禁止复制整个 HTTP 引擎。

| 实际证据 | 结果 |
|---|---|
| 在交付 transport 前已拒绝，可靠证明没有发送可能 | notSent，可结束该命令占用 |
| 已交付 transport，后续丢连接、取消、超时、主体变化、解析失败或回执不匹配 | outcomeUnknown；保存 command，按现行授权决定是否允许结果 GET |
| 收到经过验证、具有明确未提交语义的后端业务拒绝 | serverRejected；不得仅凭任意 4xx 或网关文案推断事务未执行 |
| 合法作用域内收到绑定正确的持久结果 | committed |

关键约束：

- `reviewOwnerTruthCandidateWrite` 必须把捕获的 accountLease、subject/vault、操作身份传到底层请求。目前先检查 lease 再调用不带它的旧方法不够。
- transport exposure 在可能启动网络前记录；taskCreated/taskResumed 只是诊断，不能用“日志没出现”推断 notSent。
- 新主体不显示旧主体正文或回执，不自动查询旧主体。保留最小受保护 command 元数据不等于向新账号开放数据。
- 若结果已经核实成功而本地删除记录失败，保持可再次只读核实的安全状态，不能静默丢失所有权后开放重复写。
- 401/策略/恢复后的审核 POST 自动重发继续关闭；本轮不能修回旧串行语音链路或修改普通 Live 请求语义。

## 6. S3：所有本地拒绝都必须结束对应的页面等待

### 6.1 定位与反例

[详情 onAccept](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Archive/MemoryArchiveViewController.swift:7908)先 `setReviewSubmissionInFlight(true)`；其实现会禁用整个 view 并隐藏返回按钮。submit 的 candidate 缺失、在途读取、makeCommand/Binding 失败等分支只 transitionFailure 后 return，没有向详情发送操作结果。

### 6.2 修改规则

1. 用户确认时先分配轻量 `intentID`，即使前置校验失败也有明确接收者；只有通过未决互斥与合法预览校验后才分配/落盘可写的 command。
2. 建立一个局部统一完成入口，所有 guard、makeCommand 失败、本地持久化失败、明确拒绝、unknown、committed 都回传对应 intent/operation 的结果，恰好一次。列表状态不是详情完成通知的替代品。
3. 回调至少绑定 intentID/operationID、candidateID 和 preview epoch，不能只按 candidateID 让旧操作改变新详情。
4. 重复点击同一个正在提交的操作应合并到原操作状态，不发失败回调把原提交按钮重新启用；另一个操作被拒绝，只影响另一个意图。
5. 普通 notSent/冲突：解除整页等待、保留详情、错误可见；冲突后旧确认仍禁用，取得新预览并再次核对后可确认。unknown：返回可用但写按钮保持禁用，只允许核实。
6. 用户退出页面可以结束 UI 等待，但不能取消可能已写入的结果追踪。不要通过超时后自动弹“成功”恢复交互。

## 7. S4：旧版本自动重读必须真正有界

### 7.1 定位与反例

receiveInbox 在收到 revision 低于 minimumKnownMemoryRevision 时把 snapshotBehindRetryCount 从 0 改为 1，并标记 hasTrailingInboxRefresh；[completeInboxRefresh](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:16876)又将该计数清零。下轮持续旧版本会再次被当成第一次重试。

先建反例：A 已确认 revision=R+1，候选 API 连续返回 R。使用可控异步回调逐次释放两次响应，然后检查不得创建第三次自动 GET。禁止同步无限递归导致测试栈溢出；第 3 次请求若出现，由测试立即记录失败并终止本地桩，不用延长等待掩盖循环。

### 7.2 修改规则

- 将版本追赶预算保存在当前读取意图，内部恢复保持原 trace、请求所有权和预算，attempt 单调递增。
- 最多一次因版本落后而追加的读取；第二次仍旧时结束该意图，显示“审核内容尚未更新，请稍后刷新”，保持候选不可审核。
- `completeInboxRefresh` 只负责完成/尾随意图调度，不重置当前意图尚未结束的追赶预算。区分用户明确新刷新与内部重试，不能把每次内部重试包装成新意图。
- 旧 attempt 的完成/取消不得释放新 attempt 或恢复旧确认权。只有新用户意图可以获得新预算；刷新连点仍应合并，不能绕过同一意图上限。
- 与 S6 共用总体候选 GET 上限。若策略/认证恢复已耗尽预算，版本追赶不能再无限借用新预算。

## 8. S5：校验服务端实际返回的决定版本

### 8.1 定位与反例

[validateDurableDecisionBinding](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:17087)只核对 response.candidateID、beforeHash，再比较 command 与本地 pendingRecord 的 version/proposal。这不等于核对 response.receipt.candidateVersion。

先建反例：预期 candidateVersion=N，返回 candidateID/action/beforeHash 均正确、其余 activation 合法，但 receipt.candidateVersion=N+2 或任意较大的正整数。当前 typed decode 只验证它是正整数，结果校验未拒绝。目标是不显示成功、不移除待核实记录，进入受控核实/不一致状态。

### 8.2 明确版本合同

现有 PG [bind_vault_authority 触发器](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/db/migrations/0011_owner_truth_core.sql:243)在 Candidate UPDATE 时使 row_version 加一；审核 pending->terminal 在当前路径进行一次该 UPDATE，返回 updated row_version。因此本轮标准单条审核合同是：

```text
expectedCandidateVersion = N       # 用户实际审核的候选版本
receipt.candidateVersion = N + 1    # 本次决定完成后的候选行版本
```

这与正式记忆的 vault revision、MemoryVersion.versionNumber 是不同量。不得要求 receipt.candidateVersion==N，也不得拿正式记忆 revision 来比较。对八种操作和拒绝均沿实际后端 builder/事务验证，不硬改 fixture 让错误合同通过。

修改要求：

- 正常 POST 和只读 found 都验证候选决定版本、action、beforeHash、适用的 ChangeSet/proposal 及 activation；核对的是服务端结果，不只是两份本地请求的相等。
- deduplicated/found 的结果代表原命令，不要求它重新增加一次版本，也不重新写入。
- 后端当前 terminal candidate 有不可变保护；不要为测试历史版本稳定而放开它、禁用触发器或伪造生产行。验证已有结果查询的 candidateVersion 与持久 expected_candidate_version 的关系，memory 和 PG 实现一致。
- 若隔离 PG 合同证明某条现有合法路径不是 N+1，先提交具体事务证据并明确该路径专属合同，不扩大为“任意正整数都接受”。
- 保留 accepted/corrected 的正式 activation 要求与 rejected 的 notApplicable 合同；回执版本错误不能通过宣称“后端肯定正确”而省略验证。

## 9. S6：真实策略请求、预算、单飞和 trace

### 9.1 已发现的验收缺口

[T10 当前测试](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourneyTests/OwnerTruthContractsTests.swift:1393)使用真实 evaluator，但通过 candidateInboxPolicyRefresher 直接替换局部 FeatureGatePolicySnapshot；URLProtocol 只收到一个候选 GET。它验证了“刷新回调成功后继续”，没有验证实际 release-policy 请求、合同解码及缓存保存。

生产 [refreshCandidateInboxPolicy](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DreamJourneyBackendClient.swift:8435)调用共享 FeatureGateService，后者调用 [fetchReleasePolicy](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Services/DreamJourneyBackendClient.swift:7401)。这条策略 HTTP 请求没有继承候选读取的 trace/attempt/恢复预算。

CandidateInboxReadAttemptState 当前主要保存 latestAttempt 和一次策略刷新标记，不代表原设计要求的完整 deadline、auth/GET 共用预算已经实现。不得把系统默认网络超时或某个回调测试解释为总意图超时与组合预算验证。

### 9.2 最小接线方案

在现有候选读取模块内提供窄的策略读取 port / dependency context，生产默认仍走现有策略实现；测试可注入隔离真实 ReleasePolicyStore、时钟、认证提供者和受控 transport。不要新增另一套权限规则。

上下文需要包含：scope（主体/vault/认证代次/audience/cohort/build）、rootTrace、intentID、attemptState、deadline、预算、当前 owner requestID。策略调用、HTTP 回调、解码、缓存作用域验证及 UI 提交均由它传递或校验。

- 同一意图最多一次实际策略 fetch、一次合法认证恢复、两次候选 GET；版本追赶、policy recapture、401 都消费同一个预算，不能各自产生新的全额预算。
- 策略恢复建议 15 秒、总读取意图 30 秒的明确可测上限，或保留项目更严格的既有上限。超时只能结束/隔离当前意图，不自动发审核写。
- 同 scope 的策略请求单飞；不同主体、无效认证代次不能共享。旧回调可在仍合法时被缓存层按现有规则处理，但不能重新完成已超时的旧 UI 意图，也不能倒退缓存版本。
- 缓存刷新成功不自动等于功能允许：重新检查 audience/cohort、有效期、功能开关、lease 和恢复门禁，重新捕获 request decision。
- 策略版本变化必须撤销旧 Proposal/Binding/选择/确认闭包及关联组预览；不能因“subject 没变”复用旧确认。
- 正在查询未知审核结果的命令仍受 S1/S2 保护；只读策略刷新不能成为自动重发审核的入口。

### 9.3 必须建立的真实组合测试

组合：真实 Controller -> UseCase -> BackendClient -> 真实 FeatureGate evaluator + 隔离 ReleasePolicyStore -> URLProtocol 策略响应 -> 真实 decode/save -> 候选 GET -> typed decode -> UI。
