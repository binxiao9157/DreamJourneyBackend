## 1. 评审结论

### 1.1 总判断

**保留 B 方案，但把它从“多维分类和混合检索”补强为“多人提供证据、按人物归属、经过审核形成统一正式记忆”的模型。**

产品真正需要的不是一个把聊天塞进向量库的工具，而是同时回答下面六个问题的系统：

1. 这句话是谁说的，原话在哪里？
2. 这句话讲的是谁？是本人经历、家人观察，还是转述别人的话？
3. 说的是哪个时期、场景，以及多确定的判断？
4. 它与已经确认的记忆是重复、补充、变化，还是争议？
5. 谁可以确认、查看、引用或者撤回它？
6. 用户换一种问法，是否还能找到，并以不夸大事实的方式回答？

目前代码已具备 Source、Candidate、MemoryVersion、审核回执、投影和异步任务的基础，不宜整体推倒。主要短板在**入口语义不一致、来源身份传递不完整、语义归并弱、检索仍以文本匹配为主、消费端资格不完全一致**。

### 1.2 本次最重要的发现

| 优先级 | 发现 | 证据性质 |
|---|---|---|
| P1 | 家人提交的 Source 带 `familyReport/reported`，通用整理器却生成 `firstPerson/recalled` 候选 | 已读代码并通过替身模型/确定性提取器两条本地探针复现 |
| P1 | 逝者专用控制者和贡献体系只有 shadow 边界，不等于现有“在世 Owner 接收家人贡献” | 模块说明、路由和持久化边界核对 |
| P1 | 以前喜欢、后来不喜欢，同一偏好会被当作不能引用的冲突 | 非重叠时间样例本地复现 |
| P1 | “饮食偏好”“爱吃什么菜”等改述会漏召回 | 本地检索探针复现；不是线上用户故障定责 |
| P1 | 本人 Live/文字沉淀仍依赖客户端内存队列；Family Live 没有自动接入相同沉淀协调器 | 客户端静态链路核对，未做断网/杀进程真机复现 |
| P1 | 不同消费者对争议事实的处理不同；Live 快照仍包含争议原文，维度摘要未逐条携带争议状态 | 快照构建与搜索过滤代码对照 |
| P2 | “归纳”主要靠规则分组和代表记录，不等于持续维护完整个人知识和情感结构 | 归并/画像代码核对 |
| P2 | 家人图片、文档、语音、聊天采用不同的整理载荷；部分来源元数据不能完整进入候选 | 媒体转换与候选提取代码核对 |
| P2 | 一些画像文本可能把历史情绪写成现在仍有的感受；性格推断依据还较粗 | 模板和推断代码核对，未认定为实际用户库污染 |

没有证据证明所有用户数据都已出错，也没有运行生产数据审计。本专项不据此宣称当前线上有越权或既有事实已被篡改。

### 1.3 推荐落地形态

```text
本人文字 / Live / 素材        家人贡献 / 逝者生前资料
           \                  /
          授权后的来源与证据登记
                    |
        统一提取：人物、断言、时间、出处
                    |
      与当前正式记忆匹配，形成待审核变更集
                    |
         本人 / 合法控制者审核确认
                    |
       单一正式记忆权威，原子提交新版本
                    |
        可重建、带版本和权限的派生视图
        /             |             \
   整体文本/自传   文字混合检索    Live 授权上下文
```

这是逻辑数据流，不代表新增这么多个独立微服务。实现仍放在现有模块化后端、PostgreSQL、对象存储和 Worker 中。

## 2. 先把容易混淆的概念拆开

### 2.1 五种身份不是同一个字段

| 概念 | 含义 | 示例 |
|---|---|---|
| 登录者 `actorAccountId` | 本次操作的账户 | 女儿登录 App |
| 档案主体 `memorySubjectId` | 这份人生档案属于谁 | 已故父亲 |
| 原始表达者 `speakerPersonId` | 原话真正是谁说的 | 女儿；或录音中的父亲 |
| 提交者 `contributorAccountId` | 谁上传这份材料 | 女儿上传父亲录音 |
| 控制者 `controllerAccountId` | 谁在当前权限下管理/审核 | 已登记的档案管理者 |

事实还可能涉及其他人物，例如母亲、老师和同事。必须另有 `claimSubjectId`，不能把材料里每个“我”都替换成档案主体。

**逝者档案应是一个被管理的人物档案，不是假装逝者本人还能登录的账户。** 在世本人和逝者可以复用记忆模型，但不能复用“本人确认”的身份语义。

### 2.2 正式不等于客观真理

“正式记忆”意味着完成规定审核、允许按政策使用，不代表平台验证了绝对事实。

- 本人说“我记得 2016 年毕业”：保存本人回忆及不确定性。
- 女儿说“父亲可能 2015 年毕业”：保存女儿对父亲的转述，不变成本人自述。
- 母亲说“那次搬家让我很难过”：情绪属于母亲，不能写成父亲难过。
- 模型认为“这体现了他很内向”：属于推断，不是已确认的人格事实。

审核可以确认“这是家人的这段回忆”，却不能把“听说”“可能”自动升级为“已经证实”。

### 2.3 一份正式记忆不等于一条数据库记录

一个人物应只有一个当前权威版本入口。它下面可以包含多个事实、时间阶段、证据和合法的不同观察角度。

过去喜欢东坡肉和现在不喜欢可以同时正确；两个家人对同一事件有不同记忆，可以在同一份档案里标为争议。**不要为满足“一份”而删除历史、强选一个答案或把多人观点混成共识。**

整体文本、搜索索引、自传稿、Live 快照都是这份权威的派生物，不能各自成为可独立写入的“另一份人生”。

## 3. 所有记忆来源途径盘点

以下区分“代码具有路径”与“当前部署已开放”。本次未查询生产配置，不能把路径存在等同于普通用户可用。

| 来源 | 当前实现情况 | 正确入库规则 | 主要风险 |
|---|---|---|---|
| 本人记忆档案新增文字 | 有 Source -> 整理任务 -> Candidate 路径 | 原文证据、结构化变更、本人审核 | 新增时没有充分匹配既有事实 |
| 本人 Live 对话 | 有最终转写捕获、逐条提交、结束整理 | 稳定产品会话，逐回合可靠落盘；整场一次审核批次 | 客户端内存队列、续会话身份、结束失败 |
| 本人文字回响 | 有回答与本人沉淀协调器 | 和 Live 同一沉淀合同，输入类型不同；问句不凭空产生新事实 | 目前复用 `.live` 模式，通道标识与产品会话语义不清晰 |
| 专门访谈/补充追问 | 有访谈 Session、ReviewBatch、Candidate admission | AI 问句提供语境，只有用户明确断言可当个人证据 | 首个助手问题可能未保留，“是的”等回答失去指代 |
| 本人图片 | 有媒体上传、处理和候选路径，受能力门控 | 区分 OCR 原文、视觉观察、用户说明、身份确认 | 看见两个人不等于父子，笑容不等于幸福 |
| PDF/DOCX/文本等资料 | 有文档解析和 Import Source 路径，入口受门控 | 页码/段落证据、作者、材料时间、被描述人物 | 文件上传者不一定是作者；文件内容不一定属于他 |
| 上传录音/历史音频 | 有处理适配接口；默认 ASR 可为 disabled | 音频时间段、说话者、转写置信、用户校正 | 枚举/接口存在不等于 ASR 已启用；不能混同 Live |
| 上传视频 | 存储入口有代码；处理器明确 `videoProcessingNotApplicable` | 未来分轨提取音频/画面，再统一证据 | 当前“上传成功”不等于“已理解并生成候选” |
| 在世 Owner 的家人文字贡献 | 有授权、提交、材料审核、生成 Source | 保留贡献人和被描述人，审核后仍注明转述 | 通用整理器把 reported 固定改成 firstPerson |
| 在世 Owner 的家人图片贡献 | 有上传和材料审核后排处理 | 贡献来源贯穿媒体 -> 提取 -> 候选 -> 正式事实 | Import 元数据没有完整携带家人来源身份 |
| 切换家人后用 Live/文字补充故事 | 文字无答案可跳转贡献入口；本人捕获协调器显式跳过 Family | 独立 `familyContribution` 会话，结束送目标控制者审核 | 不能假定家人对话已自动沉淀；不能直接写对方私人记忆 |
| 家属为逝者提供生前照片、录音、信件、回忆 | 有 Memorial shadow 合同；未形成实际专用完整链路 | 先有代表人物及控制权，再接入统一证据/审核 | 以在世账户冒充逝者、贡献者等同本人、控制权争议 |
| 多个家属讲述同一事件 | 可提交多份材料；缺少完整多人证言归并 | 保留独立证言、共同事件和差异，不按多数票认定事实 | 相同转发资料可能被当成多份独立佐证 |
| 正式记忆更正/补充 | 有更正、版本与审核路径 | 基于目标版本生成修订，不覆盖原始证据 | 从普通新增入口说“之前说错了”尚不等于调用更正链路 |
| 历史数据迁移/导入 | 有迁移模块和历史 schema | 分清曾审核、未审核、AI 生成；保留原凭证 | 旧库中的“已存储”不能等同“用户已确认” |

### 3.1 这些不应自动成为正式记忆

| 内容 | 可以做什么 | 不能做什么 |
|---|---|---|
| AI 回答、Live 数字人口述 | 保留上下文、帮助理解用户回答 | 当作档案主体经历或证词循环入库 |
| 自传/“Ta 的故事”生成稿 | 引用正式事实写作；检测需补充之处 | 反向把文学句子写成新的正式事实 |
| 用户在自传里改写的一句新事实 | 建立独立更正提案、标明人工输入部分 | 把整本 AI 生成书稿当本人原始证据 |
| 头像、昵称、账户资料、家人列表 | 辅助身份解析与管理 | 自动确认为人物人生事实，或者推导查询授权 |
| 查到的百科/网络资料 | 经允许提供外部常识，并标外部来源 | 变成“这个人知道、经历或相信”的个人记忆 |
| 用户问题“我是不是北大毕业？” | 用正式记忆核对 | 因问题包含学校名就生成毕业事实 |
| 时光信、延迟回复等历史入口 | 按现行产品门控处理 | 因代码残留或枚举存在就自动重新开放 |

## 4. 当前问题与成因

### 4.1 家人材料的来源身份在提取层丢失：P1，已复现

`owner_truth_family_contribution.py` 给 Source 写入 `familyReport/reported`，并保留贡献授权、提交记录等引用。但 `ModelAssistedOwnerTruthSourceExtractor` 在建立每个 Candidate 时固定使用 `FIRST_PERSON/RECALLED`。确定性兜底也如此。

因此问题不是没有字段，而是**字段没有贯穿各层**。Source 的 `familyReport` 也不是 Candidate `PerspectiveType` 的合法枚举，应显式映射为 `reported`，不能原样拷贝。

提取调用只传正文给整理模型，没有明确传入叙述者/档案主体。即使模型恰好保留“女儿说”，结构字段仍可能把它标作本人回忆。后续审核也不应掩盖这一错误。

修复方向：提取输入必须携带服务端解析的身份与来源合同；Candidate 的字段不能由模型自由设置为更高确定性；增加从家人提交到正式读取的全链路测试。

### 4.2 逝者是新的管理模式，不是新增一个 Family 标签：P1，功能缺口

现有正式家人贡献针对“Owner 现有私人 Vault”。Memorial 模块明确说明无路由/无持久化，仅为默认关闭的边界判断。

应新增或扩展人物档案管理关系，而不是要求亲属注册一个虚构的本人账户。人物死亡状态、管理授权、材料贡献授权、查询授权、声音/肖像使用授权各自独立。已有 shadow 合同可作为边界参考，但不能当成功能实现证据。

### 4.3 时间变化被误判为事实冲突：P1，已复现

当前偏好规则抽出 `preference:东坡肉 = positive/negative`，冲突判断没有比较事件时间和适用场景。

本地样例：2016-2018 年喜欢；2026 年起不喜欢。结果是一个冲突组，并从部分回答投影中排除。实际上应该保存为偏好演变，而不是不可回答。

另一方面，不同人物、不同语境可能被错误归并；不同 `perspectiveType` 的矛盾又可能完全不进入同一冲突比较。统一主键并不能解决这些语义问题。

### 4.4 “多维”存在，但“多维语义检索”尚未完整实现：P1，已复现部分症状

已有三类 MemoryKind、十类 semantic facet 和若干具体字段，不能说现在只存原始文字。但当前检索模式明确为 `deterministicTextFallback`，`semanticRankingAvailable=False`，本地未找到实际向量数据库/Embedding 接入。

最小样例“我在杭州的时候特别喜欢吃东坡肉”：

| 提问 | 当前探针 |
|---|---|
| 我最喜欢吃什么 | 命中 1 条 |
| 我有哪些饮食偏好 | 命中 0 条 |
| 我爱吃什么菜 | 命中 0 条 |
| 我在杭州时喜欢吃什么 | 命中 1 条 |

所以不能武断认定用户之前那一次“最喜欢吃什么”失败就是某个确定的搜索函数错误。真实事件还可能涉及当前版本、索引、权限和 Live 快照。但**改述召回不足**已得到本地证据。

### 4.5 目前的归并不等于维护整体人生认知：P2，代码确定

现有合并靠语义槽正则、字串和相似度分组，代表记录主要取较长文本。认知投影根据重复 facet 生成 inferred mental model。

这有一定展示价值，但缺少：新事实与旧事实的明确更新操作、时间适用性、证据独立性、多证人对同一事件的视角，以及整合后逐句事实引用。还可能搜索文本来自组内其他记录，最后只返回代表记录的版本引用。

应把“分组”降为候选匹配手段，最终提交的是经过审核的结构化变化；文字画像是可重建结果，不是另一个 AI 维护的事实库。

### 4.6 三条本人入口和家人入口还没有统一沉淀合同：P1/P2，静态风险

当前文本素材与会话整理输出结构不同；媒体又有独立的提取形态。入口差异应只发生在证据获取，不应决定最终正式事实能保存哪些语义。

追加探针还确认：带 `origin=mediaSourceObjectProcessing` 的文档 Import，即使文字语义整理开关开启，也会被路由到 Live 提取器；没有对话 turns 后再回退到确定性摘要，生成 v2 本人回忆候选，未调用文字整理模型。这能解释为什么“能解析文件”不等于“和手写文字获得同等结构化效果”。

客户端会话记录存在内存队列；网络失败和停止轮询会进入终态，不能代替持久 Outbox。恢复当前访谈主要比较 entryMode，而非同一个 productSessionId，有混入旧产品会话的风险。

这不表示后端没有持久化或重试：已进入后端异步任务的部分有租约和重试。风险重点是**提交到后端之前、回执丢失、结束未完成以及新旧会话绑定**。

### 4.7 情感的“主体、对象、发生时间”还需成为硬结构：P2

当前有 Emotion 类型和 facets，但并非每条路径都完整保存触发因素、归属人物、时间。画像模板存在“回想起来，我仍会感到…”这样的表达，可能把过去感受带入现在。

家人回忆尤其要区分：父亲当时的感受、女儿现在的怀念、女儿对父亲感受的猜测。这三项不能写入同一个 emotion 标签。

### 4.8 Live 上下文不能靠无限增加长度解决：P1/P2

当前快照遍历正式投影条目，核心事实和维度摘要有重复内容；超过字符阈值报错，不是经过语义压缩的稳定人物背景。

更重要的是，搜索投影会排除 conflict 分组，Live 快照却仍加入这些条目，只在核心事实标状态，维度摘要又拼接其原文。**同一权威不代表消费者获得了同一套可使用事实。** 需要统一 eligibility 规则。

当前 Family Live 在委托授权后，以目标 Owner 上下文读取快照。若产品未来支持逐条事实/敏感范围授权，仅有这一步粗粒度授权不够。此处是边界升级要求，不是本次已证实的越权事故。

### 4.9 版本一致性不能只理解为“最新”两个字：P2，方案约束待统一

单次回答应基于一个明确的记忆版本，不能边生成边混入另一版本。Live 开始时拿到版本 V，并不意味着对话持续半小时仍自动拥有 V+1。

之前 Live 设计允许一场内固定快照、下一场再取最新；用户又要求尽量使用最新正式记忆。必须明确产品取舍，见第 8.3 节和决策表。撤权、删除与普通内容更新的处理不能相同。

## 5. B 方案应怎样升级

### 5.1 保留什么，不增加什么

保留：PostgreSQL 正式权威、JSONB 类型化载荷、Source/Candidate/审核、对象存储、现有 Worker、火山 Live、DeepSeek 文字与会后整理。

补强：人物身份、证据、结构化断言、时间、审核变更集、实体别名、混合检索、增量整体文本、各端统一事实资格。

暂不引入：独立 Neo4j/FalkorDB、第二套正式记忆数据库、Kafka、Kubernetes、每个人一套服务、每维度一个 Agent、自动人格诊断、每轮 Live 串行经过多个大模型。

**B 是应用级个人记忆模型，不是训练出一个新基础大模型，也不是完整复制一个人的心智。**

### 5.2 十个内容维度，三种结构用途

十个维度用于组织产品内容，不要求建十张孤立表，也不能让一条事实只能属于一个维度。

| 内容维度 | 典型事实 | 必要语义 | 必须避免 |
|---|---|---|---|
| 身份与背景 | 学历、职业、出生地 | 人物、实体、角色、时间 | 名字相同就合并成同一人 |
| 人生经历 | 求学、迁居、重要事件 | 事件、参与者、地点、时间、结果 | 不同人的经历合并 |
| 家庭与社会关系 | 父女、师生、朋友 | 关系两端、方向、阶段、依据 | 关系数据直接给予访问权限 |
| 知识、技能与经验 | 专业方法、生活经验 | 领域、适用条件、例外、学自谁 | 说过知识就被认定精通 |
| 偏好与兴趣 | 喜欢东坡肉、爱听民乐 | 对象及类别、倾向、强度原话、场景、时间、是否明确“最” | 喜欢推成最喜欢、过去推成现在 |
| 习惯与生活方式 | 晚饭后散步 | 行为、频率、条件、时间段 | 一次行为推成长期习惯 |
| 情感与情感联结 | 怀念外公、毕业时紧张 | 感受者、对象、触发事件、情绪、时间、直接表达或转述 | 家人的情绪写给逝者 |
| 价值观与原则 | 重视诚实、家庭优先 | 表达者、适用场景、证据、是否自我认同 | 一次选择推成终身原则 |
| 性格与应对方式 | 自认内向、遇事先列清单 | 自述/他评/模型假设、情境、持续性 | 从悲伤诊断疾病、强贴 MBTI |
| 目标、计划与当前关切 | 想转行、准备退休 | 目标状态、期限、意愿强度、取消/完成 | 曾考虑创业写成已经创业 |

这十类里真正的存储基础可收敛为少数结构类型：`attribute`、`event`、`relation`、`knowledge`、`preference`、`habit`、`affect`、`value`、`traitReport`、`goal`。实际枚举须版本化并有 unknown/other，不要求每条记录填写所有字段。

三个用途分别是：**证据事实用于核对，理解层用于关联，表达层用于阅读。** 它们不是三份可独立改写的正式记忆。

### 5.3 六组跨维度元数据

| 元数据 | 建议内容 |
|---|---|
| 人物与作用域 | tenant/vault、memorySubjectId、claimSubjectId、speakerPersonId、contributorAccountId、reviewer |
| 证据 | sourceVersion、原文片段、音频起止/页码/图像区域、原始作者、派生链、独立来源组 |
| 时间 | 事件有效时间、记录时间、精度、是否开放区间、原文时间描述；需要纠错时另存系统版本时间 |
| 认识状态 | 本人自述、目击、家人转述、文档记载、机器观察、推测、不确定；可信程度和真实性不画等号 |
| 生命周期 | pending/accepted/rejected、当前/被替代/争议/已撤回，版本和变更依据 |
| 使用权限 | 可审核者、可读范围、用途、敏感性、撤权版本、引用时是否允许披露贡献者身份 |

不要只用一个 `confidence=0.9` 代表全部质量。至少区分转写质量、提取确定性、证据表达确定性和审核状态。审核通过不把置信度自动改为 1.0；“不知道”和“没有”也必须可区分。

### 5.4 建议逻辑存储结构

下表是目标逻辑结构，不是要求立即新增十几张表。可以扩展现有表，只有生命周期/约束明显不同才拆表。

| 对象 | 建议存储方式 | 是否事实权威 |
|---|---|---|
| 人物与控制关系 | 独立人物 ID + 账户管理关系表，逝者无登录凭据 | 身份/管理权威，不等于人生事实 |
| Source 与原始证据 | 现有 sources + 私有对象存储；补 speaker/author/contributor/subject 和片段证据 | 原始证据权威，不直接用于普通回答 |
| Candidate / ChangeSet | 现有候选与审核批次，增加匹配目标、操作类型、基础版本、证据 | 待审核，不是正式事实 |
| Claim/MemoryVersion | 现有 memories/memory_versions 演进为类型化断言，核心键为关系字段，类型体用 JSONB | 是 |
| ClaimEvidence | 多对多证据关联，包含角色、支持/反驳、片段、独立来源组 | 事实的证据依据 |
| Entity/Alias | 稳定人物/学校/地点/菜品实体与有作用域的别名 | 经过确认的解析关系；其他只作索引提示 |
| MemoryRelation | 扩展现有 memory_relations，按需关联同一事件、变化、更正、支持、争议 | 关系本身新增事实时也需审核 |
| 当前聚合版本 | 复用/增强 projection checkpoint，唯一 current manifest | 选择当前事实集，不重复保存第二套事实 |
| 画像/维度文本/自传事实底稿 | 投影及来源版本集合、句子引用、生成版本 | 否，可重建；事实性修改需走 ChangeSet |
| 搜索文档及向量 | PostgreSQL 文本检索列 + pgvector，绑定事实版本和 embedding 版本 | 否，可重建 |
| 会话/Outbox/Job | 已有会话与任务表 + 客户端持久 Outbox | 会话证据与工作状态，不直接成为正式记忆 |

关系字段应承载过滤、权限、版本和关联；JSONB 承载类型细节。不是把所有人物和整个人生塞进一个不受约束的 JSON，也不是用户一条输入就永久新增一份完整人物画像。

### 5.5 示例：东坡肉应怎样保存

以下为设计示意，不是当前数据库实存，也不是最终 DDL：

```json
{
  "memoryId": "preference-001",
  "memoryVersion": 1,
  "memorySubjectId": "person-owner",
  "claimSubjectId": "person-owner",
  "type": "preference",
  "dimensions": ["preferences", "lifeEvents"],
  "statement": "本人回忆，在杭州时特别喜欢吃东坡肉。",
  "predicate": "likes",
  "object": {
    "entityId": "food-dongporou",
    "label": "东坡肉",
    "category": "food"
  },
  "qualifiers": {
    "strengthExpression": "特别喜欢",
    "superlativeAsserted": false,
    "place": "杭州",
    "validTime": {
      "start": null,
      "end": null,
      "precision": "unknown",
      "expression": "在杭州的时候"
    },
    "currentApplicability": "unknown"
  },
  "provenance": {
    "mode": "selfReport",
    "speakerPersonId": "person-owner",
    "sourceRef": "source-123:v1#turn-7"
  },
  "review": {"state": "accepted", "receiptRef": "review-456"}
}
```

“东坡肉属于食物”可以来自受控知识分类，作为检索辅助；它不代表模型推断出了用户更广泛的饮食习惯。

回答“我喜欢吃什么”时可以说：“你提过，在杭州的时候特别喜欢东坡肉。”

回答“我最喜欢吃什么”时可以说：“你说过在杭州时特别喜欢东坡肉，不过还没明确说过它是不是你最喜欢的。”

不要把“杭州”设为查到这条偏好的必要条件；也不要因为命中了食物分类就去掉原来的地点和时间限定。

### 5.6 示例：逝者家人提供材料时怎样保存

女儿说：“爸爸在杭州时特别喜欢东坡肉。每次想起他，我就很难过。”至少包含两个不同归属：

| 项目 | 父亲的饮食偏好 | 女儿现在的情绪 |
|---|---|---|
| 断言主体 | 父亲 | 女儿 |
| 表达者 | 女儿 | 女儿 |
| 来源类型 | 家人转述 | 本人表达 |
| 情绪/偏好时间 | 过去在杭州时 | 本次表达时，持续性未知 |
| 目标存储 | 父亲档案的待审核家人贡献 | 默认只留在本次会话；明确选择后进入女儿自己的待确认 |
| 审核者 | 父亲档案的有效控制者 | 女儿 |
| 对外说法 | “家人的回忆中，他那时很喜欢东坡肉” | 不应以父亲口吻说“我现在很难过” |

同一段 Source 可以支持多个断言，但不能因为文件存于父亲档案，就把整段内容全部视为父亲的人生。若要跨档案派生，须有独立授权和去除无关第三方内容；不共享可被任一方修改的全局事实行。

## 6. 从输入到统一正式记忆的完整处理

### 6.1 来源接收

服务端解析操作者、目标人物、贡献授权和用途。客户端声明只是请求参数，不是最终身份依据。登记 Source、材料版本和处理任务；UI 显示“已接收/待整理”，不是“已成为正式记忆”。

音频/图片/文件的内容识别结果必须保留原始定位，原始内容由保留策略控制。证据记录版本化不意味着用户删除后永不清理数据。

### 6.2 会话可靠记录和结束

一个产品会话从用户开启到用户关闭/经明确规则超时结束，包含多次问答。provider 重连不新建产品会话；切换人物必须结束或暂停原会话并重新绑定。

最终用户转写及已发送的助手文字以 `productSessionId + turnId + sequenceNumber` 去重，先入加密短期 Outbox，再异步提交。助手开场问题也保留为上下文，不能作为独立事实。

结束流程使用 `lastSequenceNumber` 或等价水位：服务端缺少消息时进入 `awaitingTurns`，补齐后再建一次整理批次。确认回执丢失时重放同一幂等键，不创建第二个批次。

“整场只整理一次”是一个产品结果，不等于长会话只能调用一次模型。内部可以分块提取，但需有跨块实体统一、证据合并和重复提案归并，最后呈现一个可审阅批次。

### 6.3 提取：先识别断言，再贴维度

统一提取合同优先处理人物、原文断言、谓词/对象、肯否、时间、场景、来源、证据，再生成维度标签。

问句、建议、假设和助手补写不变成个人事实。“我想去北大”是目标，不是学历；“我是不是北大毕业”是查询，不是确认。

身份模糊时宁可提出少量澄清。例如家人说“当时我很紧张”，不得自动把“我”指向当前选择的逝者。不能为消除歧义而编造姓名或亲属关系。

若模型不可用，保留已接收原文和可重试任务。原文兜底候选可以作为产品选项，但必须标“未完成结构化”，不能标成与完整整理同等级成功。

### 6.4 与现有事实对齐：生成变更集而非盲目新增

先在同一授权人物范围内找少量相关事实，再比较结构与语义。只给整理模型必要的既有事实，避免每次重写整个人生。

| 结果 | 含义 | 行为 |
|---|---|---|
| `add` | 首次出现的新事实 | 新增待审核断言 |
| `addEvidence` | 同一事实的新证据 | 更新支持关系，不重复新增人生内容 |
| `refine` | 补充原先未知时间、地点等 | 显示字段变化，确认后生成新版本 |
| `temporalChange` | 喜好/工作等随时间改变 | 记录分时状态和关联，不消灭过去 |
| `correct` | 明确表示之前记录错误 | 指向目标版本，审核更正 |
| `dispute` | 同一主体/时间/场景下证词矛盾 | 保留来源和争议，要求澄清或暂不用于确定回答 |
| `duplicate` | 相同材料/重复转写 | 幂等去重，不制造更多佐证 |
| `noPersonalFact` | 只有问题或闲聊 | 整场完成但没有新候选，明确告知 |

合并判据不能只有向量相似度。必须同时考虑主体、命题、对象、时间重叠、场景、肯否、表达来源和材料独立性。

家人重复转发同一封信只增加传播链，不算三份独立证词。两人都说“我觉得他很严厉”是两份观点，不足以证明普遍的人格事实。

### 6.5 审核与原子提交

用户应看到“将新增什么、修改什么、替代什么、哪些仍有分歧”，并能看出处，不必阅读数据库字段。

家人材料现有两次审核分别是“允许处理这份贡献材料”和“确认其中的事实变更”。可以统一在一个工作台减少跳转，但不应让一次“接收图片”默默批准图片 AI 的全部猜测。

提交携带 `baseManifestVersion`、目标 memoryVersionId、证据引用和 reviewer 权限。事务内重查权限与基础版本，写新版本、当前指针、审核回执及 Outbox。并发两人审核时一个旧提案必须重新校对，不能最后写入者获胜。

已有 MemoryVersion 体系继续是权威。未经再次确认，不应让投影任务偷偷生成具有新含义的永久事实。

### 6.6 增量生成整体文本

正式页展示连贯的人生概况与维度内容，不展示技术 JSON，也不只是把单条记录按标签排队。

- 只重建受本次 ChangeSet 影响的维度及关联段落。
- 每个文本段落/事实句有 supportingMemoryVersionIds；事实指代、时间和不确定性必须保留。
- 模型新增的人格评价、未证实因果进入待审核提案，不进入默认画像。
- 生成失败时事实仍已保存，但 UI 明示“正式记忆已更新，概览整理中”；不能显示旧概览却宣称最新。
- 第二页面保留每次输入、处理批次与修改历史，满足追溯。

**不润色正式记忆**的含义是不得美化或改写事实；中性重排、去重和有证据的合句可以做。文学表达只在自传，温柔口语只在回复层。

## 7. 记忆与情感如何支持交互

### 7.1 检索不是只有向量

推荐同一 PostgreSQL 中提供四路受控召回：

1. 结构化：人物、学校、食物类别、时间、关系、偏好状态。
2. 关键词：人名、校名、年份、菜名；中文分词/别名需要专项验证，不能把英文全文搜索配置直接当中文 BM25。
3. 向量：处理“爱吃什么菜”和“饮食偏好”等语义改述。
4. 有界关系扩展：同一事件、人物别名、前后状态及支持证据，默认最多 1-2 跳并限制候选量。

融合排序后必须回源当前有效事实、重新校验授权和版本，再生成带引用的 Context Packet。不能把整库所有向量搜完之后，仅在 UI 隐藏其他家庭的数据。

每条向量需带源事实版本、contentHash、模型版本和索引版本；更换模型必须重新索引，禁止不同维度/模型的向量混算。候选与正式索引必须有不同的服务端读取边界。

### 7.2 归属与情感优先于修辞

| 场景 | 允许的回应方式 | 不允许 |
|---|---|---|
| 本人问喜好 | 依据偏好事实，保留时期和“可能” | 只有一项喜欢就说“你最爱” |
| 家人问父亲过去喜好 | 有证据的第一人称表达可用于经批准的角色体验；保留来源提示 | 转述或争议被说成“我亲自确认过” |
| 女儿刚说很难过 | 回应女儿此刻表达，不需要等待审核 | 把这种感受写给父亲或做诊断 |
| 询问逝者现在想法 | 说明没有本人新表达，可基于已记录往事交流 | 编造逝者当前意愿、情绪或新的承诺 |
| 两个家人记忆矛盾 | 说明现有记载不一致，可分别看来源 | 声称系统比家人更知道真实历史 |

当前会话中新表达可以用于当场上下文，这是短期对话状态；只有审核后才进入跨会话正式记忆。模型“能安慰”不等于有权形成用户心理画像。

## 8. Live、文字、自传如何使用同一份事实

### 8.1 统一的是事实服务，不是统一回答模型

用户已确定：Live 使用火山实时语音，文字问答使用 DeepSeek 且不朗读。该分工不变。

```text
同一正式记忆 Manifest + 同一权限/有效性判断
       |                            |
Live 预生成上下文                文字按问题混合检索
       |                            |
火山原生连续语音                  DeepSeek 自然文字
       \                            /
        会话证据 -> 同一整理/审核合同
```

相同事实允许不同表述，不允许学校、时间、人物、否定状态或证据确定性不同。

### 8.2 Live 采用分层上下文，不重建串行慢链路

第一层：当前授权人物的稳定基本事实、重要偏好/关系、回答边界。正式记忆变化后预生成，不在打开麦克风时调用 DeepSeek 压缩。

第二层：按维度生成紧凑事实摘要，保留证据 ID、时间、转述和不确定性。摘要不应重复完整事实正文。

第三层：只有详细事实不在快照时，才按当前火山 SDK 实际支持的工具/上下文更新机制调用自有正式记忆检索。这里的“RAG”就是对我们自己的正式记忆检索，不是另建外部百科库。

第三层目前只是设计方向：必须用现有账号、SDK、模型验证支持能力。**未验证工具能力之前，不能承诺任何详细问题都能查到，也不能退回每轮 Live ASR -> DeepSeek -> TTS。** 若不支持，第一版需明确上下文覆盖范围/容量，并用自然的说明或提示补充替代编造。

不在 Live 热路径做情感人格抽取、全库归并、画像重写或同步上传大文件。录入可靠性采用异步持久化解决。

### 8.3 “始终最新”的可实现合同

建议产品接受：

1. 每个文字请求从当前已提交 manifest 读取；单个回答固定版本。
2. Live 开始读取最新已提交 manifest。普通事实更新在自然回合边界更新，前提是 provider 支持且验证成功。
3. 若 provider 不支持安全更新，保留本场版本并提示有新记忆，下一场生效；不得宣称本场已刷新。
4. 删除、撤权、身份切换立即提高权限 epoch 并阻断后续使用；若无法清除 provider 已注入内容，应结束并重建会话，不能只依赖“忽略旧内容”提示词。
5. 任何派生索引/概览不得用旧内容伪装最新；索引落后时从已授权当前权威小规模读取或明确报告更新中。

因此“最新、无缝不中断、供应商不支持更新”三项不能无条件同时保证。这是需要产品显式选择的限制，不应埋进实现。

### 8.4 自传与整体正式记忆不同

正式记忆概览是中性事实整合；自传是文学写作作品。自传可固定写作快照，保留其引用和“基于哪个版本”。事实更正/撤回后应标记相关章节需更新或按权限阻止旧内容展示。

自传稿不反向喂回正式记忆。编辑时新增的事实应单独提交候选，不能把 AI 已生成内容重新确认为证据。

## 9. 家庭与逝者的权限、分歧和删除

### 9.1 建议权限组合

| 操作 | 本人 | 档案控制者 | 获授权贡献者 | 查询者 |
|---|---|---|---|---|
| 新增本人/目标材料 | 本人授权范围内 | 目标范围内 | ContributionGrant 范围内 | 无，需另给贡献权限 |
| 审核目标正式事实 | 本人 | 有效控制权范围内 | 默认无 | 无 |
| 查询私人内容 | 本人 | 按控制关系与内容政策 | 不因能贡献就能读 | QueryGrant/发布副本范围内 |
| 撤回自己贡献 | 本人的材料 | 不冒充其他贡献者 | 可发起自己的材料撤回流程 | 无 |
| 发布、克隆声音/肖像 | 分别授权 | 分别审查 | 不随贡献权自动获得 | 不随查询权自动获得 |
| 处置争议/争权 | 依据当前主体状态与政策 | 可处理内容但不能删掉合法争议证据冒充无争议 | 可提出争议 | 可举报，不能改事实 |

查询授权撤销、贡献材料撤回、事实更正、整个账户删除是四种不同动作，不能共用一个模糊“删除”字段。

### 9.2 多人证言不做自动投票裁决

同一事件有多个叙述时，保留 `assertedBy` 和证据独立性。控制者可以决定当前产品展示采用哪个版本或暂不采用，但系统不得把这写成“所有家属一致确认”。

存在潜在管理权争议时，可冻结发布或敏感使用，而不是删除所有私人资料。冻结的操作范围、提出者、复核者和恢复条件应有明确记录。

### 9.3 删除必须沿派生关系传播

贡献撤回触发检查：原件、派生文本、候选、正式事实证据、搜索文档、向量、整体概览、自传、发布副本及仍在运行的会话。

如果一条事实还有独立有效证据，不等于必须删除该事实；应移除已撤证据并重新评估可使用性。若唯一来源被撤回，不能继续把生成摘要当作“新的独立证据”。具体保留例外由政策决定，不能由模型裁定。

数据库历史记录可保留最小审计标记，不代表必须永远保留可读原文。清理异步执行但访问先阻断，未拿到对象/供应商清理结果不得显示完全清理。

### 9.4 法律边界：有亲属关系不等于获得无限用途授权

中国《个人信息保护法》第四十九条为近亲属基于自身合法、正当利益行使死者相关个人信息的查阅、复制、更正、删除等权利提供了规定，并保留生前另有安排的例外。不能从该条直接推出“账户持有人当然继承所有 AI 模拟/公开传播许可”。[个人信息保护法全文](https://www.samr.gov.cn/wljys/gzzd/art/2023/art_3ef1e889c1e644d4b65b5f5c7f432386.html)

《民法典》第九百九十四条还规定了死者相关人格利益受侵害时特定近亲属的救济权。因此技术上不能将“最先创建账户”视为排除其他相关权利的充分证明。[最高人民法院：民法典全文](https://www.court.gov.cn/zixun/xiangqing/233181.html)

以上是架构风险识别，不是业务合法性结论。地域、材料权利、生前安排、家属争议及供应商允许范围仍须专业法律审查。私有文字纪念档案与声音/肖像模拟分开决策，避免后一项拖住前一项的数据模型建设。

### 10.1 核查口径

以下为 2026-09-07 获取的 GitHub 页面快照；星数为网页近似值，会变化，不是质量评分。没有部署这些项目，没有跑本产品中文、多家属、审核和删除用例，也没有对比供应商宣传的性能数字。

| [Hindsight](https://github.com/vectorize-io/hindsight) | 约 23.0k；MIT | retain/recall/reflect 分工，事实/经历与证据支持的观察分层，多路检索 | Agent 自身经验不能当人的经历；自动 reflect 不能产生未经审核的人格事实 | 优先做有限的检索/观察层 PoC，非直接上线接管写入 |
| [Graphiti](https://github.com/getzep/graphiti) | 约 30.7k；Apache-2.0 | 时间化关系、实体消歧、随时间变化的事实 | 额外图数据库及维护成本；冲突规则仍要适配家人多视角 | 借鉴时间与关系语义，暂不新增图数据库 |
| [Mem0](https://github.com/mem0ai/mem0) | 约 64.8k；Apache-2.0 | 多信号召回、实体关联、记忆接口和评测思路 | 当前 README 将 Agent 生成事实作为同等信息；与本产品证据红线不符 | 比较检索算法，不复制自动对话写入策略 |
| [pgvector](https://github.com/pgvector/pgvector) | 约 22.9k；PostgreSQL 风格许可 | 在现有 Postgres 内做向量检索并与文本查询融合 | 向量相似不等于事实正确，更不等于权限验证 | 第一版最值得直接验证并集成的底层组件 |

星数更高的 Mem0 不一定更适合本项目；Memobase 的产品形态更接近整体画像，Hindsight 更适合参考事实/观察分层和检索，Graphiti 补足时间关系思想。

### 10.2 需要特别纠正的选型认知

Mem0 当前 README 已说明新算法为 ADD-only，并区分托管平台和开源 SDK，平台基准含专有优化。不能再按旧版本的 UPDATE/DELETE 流程笼统描述它，也不能把托管指标当作接入开源包后的性能承诺。[Mem0 当前 README](https://github.com/mem0ai/mem0#new-memory-algorithm-april-2026)

Graphiti 当前依赖图后端；它是有价值的参考，但引入它意味着新增运行组件，不是一个无成本的 JSON 解析库。[Graphiti 安装依赖](https://github.com/getzep/graphiti#installation)

pgvector 支持和 Postgres 文本查询融合；近似索引在过滤条件下可能减少召回，需测试租户过滤与索引策略。初期每个人几千条事实可先测“按人物范围过滤后的精确向量搜索”，不能只因使用向量就默认上共享 HNSW。[pgvector 混合检索](https://github.com/pgvector/pgvector#hybrid-search)、[过滤与多租户](https://github.com/pgvector/pgvector#filtering)

### 10.3 推荐组合

**业务权威和审核留在 DreamJourney；画像组织借鉴 Memobase，证据支持的观察和召回借鉴 Hindsight，时间关系借鉴 Graphiti，数据库扩展优先评估 pgvector。**

不是安装四个记忆中间件串联运行。首先实现必要的来源/审批领域逻辑，再用同一批中文用例比较自有检索与一个候选开源实现。

评测接入必须锁版本，核对许可证及依赖、中文实体识别、API 兼容性、备份与删除、遥测和出网、迁移方式、最近发布与维护情况。本次未完成各项目 commit/release 级审计；除页面可见信息外，不作维护稳定性保证。

## 11. 成本、性能与运维复杂度

### 11.1 初期建议部署

优先保留模块化单体 API + 少量同代码 Worker + 一个 PostgreSQL（含向量扩展）+ 私有对象存储。已有 Redis 可继续做可丢弃缓存，不作为唯一记忆或唯一任务凭证。

“同一数据库技术”不等于“只有一台不能故障的机器”。可使用托管 PostgreSQL 的备份/恢复能力，生产可用性根据实际目标选择主备；是否购买高可用规格是成本决策，不虚报现有部署已有主备。

### 11.2 避免成本爆炸的措施

- 会话逐回合持久化，但整理按整场批次，不为每次问答重算画像。
- 先增量匹配相关事实，不每次将全库发送给 DeepSeek。
- 不为十个维度分别发十次模型请求；一次提取多类型，疑难冲突才追加分析。
- 只为新增/变更事实生成 embedding；由 contentHash 和模型版本去重。
- 一次审核后合并刷新受影响的视图，避免多 Worker 重复重建整个人物。
- 每个 Vault 限制同时整理数量并公平排队；长文件不占满短文本队列。
- Provider、数据库连接池、令牌预算及后台任务分别限流。独立语音配额不消除后端资源竞争。

### 11.3 不给虚假的延迟和费用保证

总耗时至少分为：证据接收、排队、模型提取、语义匹配、审核等待、正式提交、索引/概览刷新。用户审核时间不能算作服务端性能退化。

建议压测起点，不是实测生产承诺：100 个在线用户、峰值 20 次检索/秒、5 次提交/秒、3 个后台整理并发；每人物 5,000 条事实，300 人共 150 万条，再用 3 倍数据量测退化。在线人数不直接等于 QPS。

向量存储估算：150 万条 x 1,024 维 x 4 字节约 6.1 GB，仅向量正文；不含索引、元数据、历史版本、WAL、备份和媒体。模型维数必须由实测效果选择，这里只是容量例子。

模型费用按实际输入/输出 token、embedding token、重试、媒体解析及语音分钟统计；没有锁定模型和供应商报价前不提供“每人固定几元”的保证。

### 11.4 AI 辅助运维可以做什么

AI 可以生成和分析告警、写测试、形成恢复操作建议、执行已批准的幂等重试和索引重建。但不能独自决定删除、控制权争议、生产权限扩大、不可逆迁移及合规结论。

需有一个明确的人类负责人；工具权限最小化，危险动作需审批。监控面板至少包含：未收齐会话、最老待整理任务、提取失败、待审核数量、索引落后版本、删除传播积压、每人物资源占用和模型费用。

## 12. 实施优先级与验证策略

这是一版完整交付中的工作顺序，不是把用户需要的核心效果拆成四个遥远发布阶段。

| 工作包 | 内容 | 依赖 | 完成凭证 |
|---|---|---|---|
| 来源与主体合同 | 修复家人来源降级，统一 speaker/contributor/subject；补人物管理模式 | 产品确认逝者角色及权限 | 家人和逝者归属端到端测试 |
| 可靠会话与统一入口 | 持久 Outbox、稳定产品会话、整场一次批次；Family 单独贡献路由 | 身份合同 | 断网、杀进程、回执丢失、换人物测试 |
| 结构模型与变更集 | 十维内容、少量类型、时间/肯否/来源、与旧事实匹配 | 身份与证据合同 | 重复、变化、更正、争议测试 |
| 审核与原子版本 | 差异确认、并发版本检查、唯一当前集、权限 epoch | ChangeSet | 并发审核和重放测试 |
| 混合检索 | 中文结构/关键词/向量/有界关系，回源与引用 | 正式版本与实体 | 多种问法召回、删除、跨家庭隔离 |
| 整体视图和消费统一 | 中性整体文本、Live 上下文、文字事实上下文、自传影响检测 | 当前权威与引用 | 同事实多端一致、争议不误用 |
| 数据校正与回归 | 检查历史 firstPerson 标记、错误冲突组、老 schema 和孤儿任务 | 前述能力 | dry-run、差异报告、备份恢复、人工复核 |

开始编码前，先用当前 Source 和审核回执做只读盘点。已审核数据中能从不可变证据确定的纯格式转换可以自动迁移；涉及叙述者、含义、冲突选择的变化必须可复核。用户只有一个测试账户也不等于授权清空全部正式记忆。

最终验收不以“数据库有记录”通过，而以“同一事实在不同问法、不同入口、不同人物权限、不同时间下均正确使用”通过。完整矩阵见配套文档。

## 13. 需要产品确认的决策

| 待确认内容 | 建议决定 | 原因 |
|---|---|---|
| 逝者应建账户还是被管理档案 | 建人物档案，实际亲属用自己账户管理 | 防止操作人和被模拟人物混为一人 |
| 家人提供的内容算什么事实 | 可正式收录为带来源的家人转述，不能伪装本人自述 | 保留真实来源，不妨碍积累资料 |
| 家人对话中自己的经历/情绪是否入库 | 默认仅会话使用；明确选择后写自己的待确认 | 避免污染目标人物及意外跨库 |
| 家人材料审核是否两次 | 一个工作台承载材料处理授权与事实差异确认；不得隐式合并权限 | 减少操作但不跳过事实确认 |
| 两个家人说法冲突怎么办 | 保留争议和各自来源；暂不作确定回答，控制者可选展示策略 | 不用多数票或最后写入抹平差异 |
| 第一人称回答是否保留 | 可按既有产品决定保留，但转述/争议明确限定，逝者无“当前新感受” | 角色表达不能改变事实性质 |
| 人格与价值观推断能否进入正式记忆 | 只自动形成假设/提案，明确确认后才能成为自我认同记录 | 不把算法判断当人格事实 |
| Live 中途正式记忆更新 | 优先回合边界刷新；不支持时提示下一场生效；撤权/删除立即阻断 | 避免虚假“永远最新”承诺 |
| 没有新事实的会话怎么显示 | 显示整理完成、无新增内容；不制造空候选 | 消除用户误以为沉淀失败 |
| 整理降级时能否显示原文候选 | 允许则明确未完成结构化；默认可重试，不谎报完整整理成功 | 防止长期积累未经处理的碎片 |
| 贡献撤回后已有事实保留条件 | 检查独立证据与使用授权；无合法有效依据则停止使用 | 不把派生摘要当新证据 |
| 原始会话与媒体保留期限 | 分离短期转写/原件/审计，提供明确用户设置与清理策略 | 不用“永久记忆”暗示永远保存所有原文 |

## 14. 最终建议

**第一版应该做完整的“可靠来源 -> 统一语义 -> 差异审核 -> 当前事实集 -> 可解释检索/交互”闭环，而不是先换一个更复杂的数据库。**

B 增强版的价值，是在现有后端和数据库基础上把记忆的真实性、归属和使用方式做正确。它比只增加向量检索更完整，也比同时引入多套记忆框架更容易维护。

是否进一步引入完整时序图引擎，应由真实多跳查询、消歧和时间推理测试的不足触发，不由 GitHub 星数或“模拟大脑”名称触发。
