# Live 与文字对话：记忆调用复核与体验保留要求

日期：2026-09-07。状态：方案补充，未修改业务代码、未部署、未做真机验收。

本次实施讨论暂不包含逝者场景。本人 Live、文字、素材和在世 Owner 授权接受的家人贡献仍需统一记忆规则。较早专项中的逝者内容保留为历史评估，不进入本次开发范围。

## 1. 先看结论

**保留现在已经满意的交互，修改它们与记忆模型之间的连接方式。不是重做 Live。**

- Live 仍由火山原生语音对话负责，保留快速回复、连续聆听、随时打断。
- 文字仍由 DeepSeek 回复，不朗读；保留自然、友善、温柔的表达。
- 两者共用同一套正式事实与访问规则，不要求使用同一个生成模型或同一个 HTTP 接口。
- 新说的内容可以在本次聊天中接着讨论，但只有审核后才能变成长期正式记忆。
- 整场聊天结束后整理一次，进入一个审核批次；批次里可以有多条候选，不是每问一句就整理一次。

**以上是开发必须通过的验收要求，不是“尚未开发就已经保证没有性能退化”。**

## 2. 当前两条链路

本人 Live：开启会话 → 后端读取正式记忆投影并生成快照 → iOS 放入火山启动提示 → 火山持续听、说、处理打断。正常原生 Live 的用户转写不会再逐句调用 `/echo/answers`。

本人文字：输入问题 → `/echo/answers` → 按当前问题检索正式记忆 → 将检索结果和最近对话交给 DeepSeek → 展示文字，不播放声音。

因此，**并不是一个用了正式记忆、另一个完全没用，而是读取、筛选、传递和更新方式不同**。静态代码只能证明准备了快照，不能证明火山实际完整接收、理解并正确使用了它。

## 3. 本次发现的问题

| 问题 | 用户可能感受到什么 | 证据与处理方向 |
|---|---|---|
| 文字检索只拿当前问题，不拿前文消歧 | “我的大学是什么？”之后追问“哪年毕业的？”可能找错或找不到 | 代码确定；先解析本场人物、话题和指代，再检索 |
| 是否需要个人记忆主要靠固定词组判断 | 同一意思换个说法，走入普通问答分支 | 本地函数复现：“我的大学是哪所？”为 true，“我爱吃什么菜？”为 false；分类不代表最终模型回答必错 |
| Live 快照仍以原文和拼接摘要为主 | 模型可能忽略过去/现在、本人/转述、喜欢/不喜欢等限制 | 代码确定；快照须保留 B 模型中的事实限定信息，而不是只放一段总摘要 |
| Live 与检索对争议事实的处理不一致 | 同一条矛盾在文字侧不引用，在 Live 侧却可能作为事实说出 | 快照包含带争议状态的事实，摘要又未逐条标状态；统一可引用资格，并实测模型行为 |
| Live 主要在开场绑定记忆，文字按请求取上下文 | 聊天期间纠正事实后，两端可能暂时回答不同版本 | 开场绑定已确认；热更新能力和真实运行行为未验证，需版本失效与 SDK 验证 |
| 当前提示词对“正式事实”与“本场新表达”区分不够清楚 | 刚说“今天去了杭州”，接着聊时仍被当成“记忆里没有” | 提示词风险，未做真实模型定责；允许引用本场用户表达，但不得宣称它已入正式记忆 |
| 会话沉淀仍有客户端内存队列、恢复和完成状态问题 | 聊得好，但结束后没有候选，或误显示整理失败 | 既有专项静态发现；与本次记忆升级一起修可靠持久化和整场整理 |

补充：文字有普通问答分支，Live 提示却泛称“事实问题只能使用正式记忆”，两者范围不一致。个人经历、身份、偏好必须有依据；通用知识不应要求用户先存入自己的记忆。不能靠放宽个人事实约束解决普通聊天问题。

## 4. B 方案要一并补齐的设计

### 4.1 统一事实读取规则，保留两个对话引擎

在现有后端内部抽取共享读取合同，不新增独立微服务。读取先绑定访问者、目标人物、权限范围、正式记忆版本和投影就绪状态，再产生不同消费者需要的上下文。

每条可引用事实至少带：事实 ID、版本、人物归属、具体断言、时间/场景、肯否与程度、证据类型、来源引用、审核及争议状态。已撤回、被替代和无权访问的事实不能进入回答材料；有争议的内容不能被断言为确定事实。

文字使用该合同做问题相关检索，Live 使用该合同构建会话背景。向量检索只能帮助找到候选，不负责决定真假、授权或覆盖旧事实。

### 4.2 将三类上下文分开

1. **正式记忆**：已审核，可跨会话作为个人事实引用。
2. **本场用户表达**：本次聊天里刚说的内容，可立即回应和追问，标明尚未确认，不自动升级为正式事实。
3. **助手回复**：用于理解指代和聊天进展，不是新增个人事实的证据。

例如用户刚说“今天在杭州吃了东坡肉”，可以回答“今天那顿吃得怎么样？”；不能因此长期记录成“最喜欢的菜是东坡肉”。若与旧记忆不同，可以了解变化，生成待审核变更，不自动覆盖。

### 4.3 文字补上下文检索，不靠无限加提示词

检索前结合服务端已接收的本场对话，解析目标人物、话题和时间。对“那是哪一年？”先明确问的是毕业还是入职；存在歧义时澄清，不自行猜。

优先使用有界的会话状态与实体解析，必要时再评估模型消歧，不默认每轮新增一次串行大模型调用。已有客户端最近消息限制为 6 条、每条 500 字、合计 2400 字，不能把它当作完整长期会话记忆。

“是否涉及个人事实”不能只靠固定词命中；检索无结果也不能一律终止自然对话。回答可明确“你之前提过在杭州时喜欢东坡肉，但没说它是不是现在最喜欢的”，不能把“喜欢过”升级为“现在最喜欢”。

### 4.4 Live 使用有版本、可验证的记忆背景

核心事实预先形成紧凑、可追溯的背景，不等待用户每句话说完再找 DeepSeek。压缩必须保留人物、校名、时间、否定、程度和适用范围；记录覆盖情况，不能把漏掉的事实说成用户没有记录。

先验证当前火山 SDK 对启动上下文的真实接收、容量和回答使用情况。需要更多细节时，只有经过该 SDK 的工具调用/动态上下文 PoC 后，才确定补充查询方案；不能默认供应商已经支持。

正式记忆更新后使相关快照失效，目标是在下一次个人事实回答前使用最新有效版本。撤权/删除不能等待下次开场才生效。需要已确认的热更新或停止引用旧事实机制，不能悄悄重开麦克风、丢掉聊天上下文。

若 SDK 无法同时满足连续 Live 和版本更新要求，该项必须标为未通过并回到架构评审，不能降级成旧式逐轮 DeepSeek 链路，也不能把仅下次开场刷新宣称为实时更新。

### 4.5 沉淀与实时回应解耦

使用独立且稳定的产品会话 ID，包含本人/家人目标及输入通道。供应商重连不新开整理批次；用户主动新开会话不能错误续接已结束的旧批次。

按回合异步持久化，带 turnId、sequenceNumber 和幂等键；本地持久发送箱与服务端接收水位处理断网/回执丢失。回应不等待 DeepSeek 整理任务，但未确认上传的数据不能显示“已保存”。

用户关闭或满足已确认的自动结束规则后，形成明确的结束水位；缺回合时等待补传或显示部分保存，不静默生成“完整”总结。整场幂等创建一个整理任务/审核批次；重试不重复生成候选。轮询超时与真实任务失败分开显示。

### 4.6 在世家人场景仍需单独验权

当前文字端有 Owner 私人、Visitor 发布副本、Family Contribution 等路由；Live 家人分支有自己的委托授权。不能因为界面都叫“家人”就默认事实范围相同，更不能将家人的全部私人记忆直接注入。

两端必须按同一有效授权范围读取。Visitor 查询的是获准的发布版本，不应私自追随 Owner 的未发布修改。在世家人的聊天沉淀应进入贡献审核，不自动写入对方正式记忆。逝者控制者及授权机制暂不实现。

## 5. 验收底线

| 验收项 | 必须满足 |
|---|---|
| Live 体验 | 保持原生连续听说，至少 10 个连续回合、多次打断、长回复后接话；无“声音还在播但会话已结束”及播放后收不到话的回归 |
| 文字体验 | 仍由 DeepSeek 回复、不朗读；温柔自然，不强制每轮追问，不把正式记忆润色后写回 |
| 事实一致性 | 两种入口测试校名、毕业时间、近义问法、连续追问、历史偏好与当前偏好；同一授权及版本下事实一致，措辞可以不同 |
| 本场新内容 | 新话题能持续聊，AI 推测不变成事实；结束后一个可追踪审核批次，确认前不进入正式记忆 |
| 变更与授权 | 纠正、删除、撤权、切人物和索引延迟均有测试；不得串人或静默引用过期事实 |
| 性能 | 先测现有版本基线，再同设备/网络/数据量 A/B 测首音、打断停播、续听和文字首字的 P50/P95；记忆改造引入的延时相对增幅目标不超过 20%，绝对上限依据基线另行定稿 |
| 容量与成本 | 长记忆量、并发、模型上下文用量和持久化积压有实测；不能靠无限塞全文、每轮重复总结或多装几套服务达成效果 |
| 证据 | 区分“已检索”“已注入”“回答受事实支持”“已播放”，不能用一个 grounded 标记宣称全部完成 |

上述性能比例是验收目标，不是已测结果；即便比例达标，若基线本身迟钝，也不算用户体验合格。事实正确性及授权限制不能为了速度放宽。

## 6. 本次做了什么

- 只读核对后端和 iOS 的两条实际调用链，没有修改业务功能。
- 运行 Echo、正式记忆 Context Authority、Live 快照相关测试共 31 项通过，其中 5 项快照测试与上一轮检查重复。
- 运行本地个人记忆意图分类探针，确认不同问法的分类缺口。
- 未调用真实 DeepSeek/火山，未查生产私密原文，未做真机或压测。因此没有宣称已修复，也没有重新判定学校问题的线上根因。
