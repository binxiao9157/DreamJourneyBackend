日期：2026-09-20。主问题：**DJ-LIVE-LONG-MEMORY-02**，关联现场 DJ-LIVE-L20-01。\
用途：交给 Sol 完成本地实现、组合验证和交付；当前真机验收目标为 20 分钟，后续另行执行超过 1 小时的压力验收。\

## 1. 已确认的产品要求与完成条件

### 1.1 用户最终应得到的行为

1. Live 持续记录用户说过的内容。整理速度和模型失败不得阻塞录音、语音回答、正文落盘或已授权的同步。
2. 会话过程中，服务端把已经可靠收到的内容分成小批整理，形成**内部草稿**；这些草稿不出现在待确认列表，也不成为正式记忆。
3. 用户停止后，沿现有 end → ACK → admit 完成正式 Source 封定；补齐尚未整理的内容，对整场内部草稿统一处理重复、补充、纠正和撤回，再发布完整待确认候选。
4. 第一批说一件事、最后一批又提到它：重复不新增；补充并入同一件事；明确纠正更新被纠正的内容；同一人发生的不同事件仍分别保留。不能按“最后一句总是正确”处理矛盾。
5. 保留经历、知识、情绪等记忆类型，以及现有 dimensions、facets 等多维属性。同一原子事实不能因为属于多个维度而复制多条；独立事实也不能为了节省名额硬塞成一条。
6. 候选发布后仍由用户审核。只有确认操作才能形成正式记忆；拒绝或尚未确认的候选不能自动进入正式记忆。
7. 不能再把“每次最多 8 条”变成整场最多 8 条。单次模型请求可以有小容量上限，整场必须通过多个有限请求处理。

**本轮不能只实现会后分片而声称实时预整理已完成，也不能只做后端草稿而遗漏会后候选发布和正式记忆回归。**开发可分阶段，但下面的本地完成条件全部满足后才交付 LOCAL_PASS。

### 1.2 本地、供应商和真机严格分离

本次顺序：保全当前工作区 → 建立旧代码红测 → 开发 → 本地受控 HTTP / PostgreSQL / 模拟器组合测试 → 受影响回归 → 交付并结束任务。

- 不检测、连接、安装、启动或等待手机。手机未连接不构成阻塞；用户之后主动发起真机测试。
- 不调用真实 DeepSeek 或火山做付费测试，不访问生产，不部署，不处理历史失败任务，不审核真实用户候选，不 commit/push。
- 之前获准的最多 8 次合成 DeepSeek 诊断已全部执行完毕，**不构成本轮新增模型调用授权**。
- 本地隔离数据库中的合成审核写、正式记忆写、迁移和恢复测试是本次开发的必要组成部分。

## 3. 架构边界：一次产品会话，分批内部处理，一次可见发布

```text
现有 Live 正文持续落盘、上传
          ↓ 读取服务端连续持久化前缀，原文不改写
内部 run → 小片事实提取 → 独立小片复核 → 持久草稿和覆盖台账
          ↓ 会话期间持续推进；失败/积压不阻塞采集
用户停止 → 现有 end / ACK / admit → 最终不可变 Source
          ↓ 校验所有前缀与 Source 一致，补齐尾部
跨片关系核对 → 合并、补充、纠正、撤回 → 有界候选支持复核
          ↓ 全部工作单元完成，机械检查覆盖与证据
原子发布候选和同场完成状态 → 用户审核 → 现有正式记忆与回查
```

### 3.1 实时草稿不能伪装成已结束的 Source

当前 `owner_truth_conversation.py` 只保存会话与消息；`owner_truth_interview_candidate_proposal.py::admit_review_batch/_prepare_from_batch` 在 ACK 后生成 Source。必须保留这个边界。

- 增加 **Live 专用私有预整理通道**，读取本场已经连续持久化的、最终正文可用的消息前缀。不得提前创建 Source、ACK、admit、用户可见 review batch 或 Candidate。
- Run 稳定键为 `(owner, vault, productSessionId, productCaptureGeneration, pipelineVersion)`；逻辑 captureGeneration 不因刷新、重连或进程重启变化。authorityEpoch 是固定权限栅栏，技术 sessionId 是经过校验的来源绑定，不是重建 Run、刷新预算的理由；查历史“最近任务”不能代替精确绑定。
- 原 append 返回和事务不执行模型；通过提交后的可靠调度信号/持久扫描水位唤醒内部 Worker。遗漏唤醒可被同场水位扫描补回；禁止只靠进程内回调。
- 默认触发条件：累计 8 条尚未处理的已确认 user final，或正文容量达到小片预算，或最早未处理 final 等待 30 秒；这是调度条件，不是固定延时修复。停止后必须立即登记尾部可处理工作，不再等凑满。
- 仍在说话的 interim、未上传、乱序空洞后的尾部不得当成已可靠保存；既有 canonical/partial 规则保持。
- 实时模型请求要有独立、显式的 Live 整理授权与 FeatureGate 检查，并受当前 owner/epoch 控制。已有“关闭后 admit”不能被拿来授权提前传输。未授权预整理时，持续保存，关闭获准后走同一分批链补齐；不能悄悄发送。
- 草稿运行时失效不反向影响已成功正文事务；系统停机或预整理未开启，关闭后仍能从完整 Source 启动同一算法。
- 会话期间也推进内部关系核对、候选草稿和局部支持证明，而非把全部关系计算拖到会后。新补充/纠正到达时只使受影响证明失效并重验；正式Source未封定前仍不得发布候选。会后统一是统一冻结与校验，不是第一次才开始去重。

### 3.2 会后绑定与发布边界

正式 Source 建立后，逐消息校验身份、顺序、内容 hash 与文本区间，绑定 Source ID/version/hash、最终连续水位。前缀中不在正式 Source 窗口的上下文不可成为候选证据。任何不匹配草稿不能直接复用，应在同 run 的受预算控制的新输入版本上重算相关部分。

预整理 index 不得直接视作最终 `sourceTurnIndices`。显式建立映射，沿现有用户原文拼接方式计算 Source offset；上下文重叠不能造成重复证据或重复事实。

本轮只处理**同一产品场次内部**重复和纠正。与之前会话、已有正式记忆的合并或改写继续遵守现有审核合同，不能自动修改历史记忆。会后另开一场的补充也不能偷偷写回已经发布的旧 manifest。

### 3.3 Live 长正文的Source封存合同

当前CreateTextSourceCommand最多20000字符。F-DENSE/F-65不能只直接构造Extractor输入绕过它，必须从真实已ACK批次走admit到Source。

新增服务端受控的Live专用Source容量合同/类型，只有真实已ACK、正确captureMode、owner/epoch及冻结窗口通过的admission可使用。普通文字、导入和旧调用方保留原20000字符限制；不得允许客户端靠伪造metadata或传一个large=true提权。

本轮Live初始包络为：用户Source正文最多100000字符、全部conversationTurns正文合计最多200000字符、完整序列化Source内容及metadata最多2MiB；逐项检查，任何一项超限保留已有对话正文并准确报告容量未完成，不截尾、不假成功。单条消息现有20000字符上限保持，本轮测试长turn为4000字以上但在该消息限额内。

使用原Source writer、稳定command/Source身份、内容hash、authoritative epoch与receipt；只扩展经过验证的Live创建合同及一致的读写校验，不直接绕过领域校验写库。仍是同场一个正式Source，不拆成多个可见Source规避限制。原文投影、候选证据span、审核和重建读取必须支持这个包络。

Sol须沿真实admit、Source仓储、job输入、候选构造和API读取查找其他重复长度/数量限制，补齐最小一致适配及回归。改变共享验证器需明确调用方范围，不能全局把常量放大后声称非Live未受影响。

## 4. 持久结构、身份与隐私

允许增加 Live 专用表/repository 和版本化协议，优先复用现有 UoW、lease、安全读取及候选提交能力，不建设通用工作流平台。建议逻辑结构如下；表名可按仓库规范调整，字段语义与约束不能省略。

| 对象 | 必需内容与约束 |
|---|---|
| Run | 归属字段；pipeline/prompt/schema/budgetPolicy 版本；已持久前缀水位；最终 Source 绑定；当前计划版本；累计预算；冻结 manifest；终态；同产品场次同 pipeline 唯一 |
| WorkUnit | 稳定 ID、种类、输入 hash、所有权片段与只读上下文引用、依赖、generation、状态、lease/fencing、计划执行及失败恢复次数、输出 hash、安全失败原因；确定性唯一键 |
| ProviderAttempt | 所属 run/unit、请求参数 hash、调用前持久额度预留、曝光/响应/落盘状态、耗时、usage、实际 model、finishReason；重启不抹除可能已发生的调用成本 |
| EvidenceSegment / Atom | message ID、顺序、role、原文 hash 和精确区间；原子事实、类型、多维属性、证据、独立复核；可存于单位结果但要可独立查询验证 |
| Relation / Coverage | duplicate/supplement/correction/retraction/distinct/unresolved 等关系及证据；每个原子事实最终去向；被排除内容的理由；关系版本及待核对边 |
| PublicationManifest | 冻结候选集合、证据映射、覆盖摘要、最终 Source hash、所有完成单元的 hash、稳定排序和 manifest hash；绑定唯一最终提取结果 |

必须新增内存与 PostgreSQL 实现、SQL 迁移及仓库要求的对应迁移清单。迁移只在隔离本地库运行，生产迁移作为后续发布材料准备。

草稿、原子事实和证据均为私密业务数据，采用与 Source 一致的 owner/vault/epoch、撤权、删除与保留策略；不能变成不受删除控制的第二份记忆库。生产历史清理不在本轮范围，新增数据生命周期要有隔离测试。

偏移统一采用服务端固定版本的 Unicode 字符索引规范，保存原文 hash；不要混用 Swift UTF-16、UTF-8 字节和 Python 字符下标。最终导出旧 Source span 时显式转换；中文、emoji、换行与组合字符均测试。

## 5. 同时约束输入容量、事实容量和输出容量

### 5.1 先形成原子事实台账，不按对话轮数估算事实数

一次用户发言可含 0、1 或多条事实，必须保留事实级证据。组织器不能仅返回“这轮被引用了”就视作覆盖整轮。

1. 按稳定原文区间建立 ownership segment，所有用户正文区间有且仅有一个归属片段；邻近上下文可重复读取，但标为 `contextOnly`。
2. 逐片提取原子事实及语用类型：用户陈述、明确观点/感受、纠正、时间补充、撤回、纯问题、引述、歧义。区间内混合类型可并存，不能“一轮有问号就整轮排除”。
3. 独立复核请求必须读取该片原文及必要上下文，检查是否漏事实，而不只检查组织器自己列出的列表。助手正文只作理解上下文，不成为个人事实证据。
4. 同一事实可以依赖多个证据片段；一个片段也可以支持多个事实。跨句指代保留引用依赖，不能因切片把“不是周六，是周日”误判无事实。
5. 台账检查证明结构闭合；模型复核提供语义判断。二者都不能宣称对任意自然语言绝对无遗漏；测试用独立人工制定的真值集合验证。

### 5.2 本轮明确采用的有界处理方式

每种请求都有独立的完整 prompt 输入预算、预计输出预算、最大对象数和实际网络 deadline。不能只统计用户正文而漏掉 JSON、提示词、上下文和证据字段。

- 初始事实提取片：至多 8 个 user final，单个 ownership segment 初始不超过 2000 字符；先按句界切分，超长句按可逆区间切分并携带邻接上下文。
- 一次事实提取/复核最多处理 16 个原子事实；完整维度候选生成每请求至多 4 条；关系筛查每页至多 8 个新atom × 32 个既有组，实质关系证据核对每请求至多 8 对；最终候选支持复核每请求至多 4 条。关系页返回至多64条关系，饱和则缩页继续，不截断。
- 这些是**单请求工作容量**，不是整场总条数。关系、候选和证据过大都继续分页，不能截尾或只取 top-K。
- 初始本地容量配置：完整 prompt 估算预算 16384 tokens。输出按阶段预留：事实提取/独立核对4096、关系页筛查2048、实质关系核对4096、完整维度候选生成8192、候选支持4096 tokens；每种请求均能因预算缩小实际工作页。必须使用对应 tokenizer 或有安全余量的保守估算，并标记估算方法；不能把字符数直接当 token。真实 usage 只用于观测和后续校准，不伪造为历史数值。
- 每次请求前验证输入加输出预算不超过配置的供应商窗口；本轮不因官方上限很大而取消应用边界，也不强制更换既有模型别名。
- 达到对象上限、输出 length、独立复核发现遗漏或已知预算装不下时，不能“返回前 N 条即完成”。细分 ownership 范围，或者把已识别事实集合按稳定 ID 拆成更小的候选生成单元。所有子单元继承同 run 的额度、输入归属与父子关系。
- 请求容量拆分属于显式计划变更，必须证明子片并集等于父片且没有遗失；完成后父片被子片覆盖，不能同时作为第二套事实发布。
- 对“单个最小片含很多事实”继续按证据子区间拆分；若无法不损失语义地细分，保留 unresolved/明确容量原因，不能抛弃内容或并入无证据大摘要。
- 长证据组按原子断言和证据页核验，形成可组合的支持记录；最后仅做确定性集合校验，**禁止末尾再次发送全场全文、全部草稿或无界关系组**。

模型输出 count 小于上限不代表完整；达到上限也不自动证明确有遗漏。都需要独立覆盖判断。对有效拆分应有稳定停止条件、最大深度/单位数和全场预算，不能递归无限请求。

## 6. 跨批次去重、补充、纠正：保留事实与维度

### 6.1 合并规则

| 情形 | 必需处理 |
|---|---|
| 相同事件、相同原子断言重复 | 一个最终断言，合并全部有效证据，不因批次不同新增候选 |
| 同一事件追加人物、地点、时间等 | 更新同一事件的属性和证据；保留原信息，没有证据不自行补齐 |
| 明确“刚才说错了，是……” | 建立旧断言到修正断言的有证据替代边；最终不同时发布互相矛盾的版本 |
| 明确撤回 | 记录撤回及其指向，不发布被撤回断言，不用“曾经说过”绕过撤回 |
| 同一人、同一地点、不同时间的不同事件 | 分别保留，不能仅因主题/实体相似而合并 |
| 经历附带用户明确感受 | 沿既有类型与原子事实规则表达；同一事实的多维标签不复制候选，独立感受不被去重吃掉 |
| 用户过去偏好与现在偏好 | 保留时间适用性；不把有时间差的变化一律当口误 |
| 说法矛盾但没有明确纠正、指代不清 | 保留 uncertainty/待解析关系，不能简单最后一句覆盖前句；不能伪造确定事实 |

示例：开头说“周六和女儿去杭州看展”，最后说“时间说错了，是周日；我们还看了兽首”。结果应只出现正确时间的事件表达和有依据的补充；不能留下周六/周日两条冲突候选，也不能丢女儿或擅自补展馆名称。具体是否将独立展品经历另列，依据预先定义的原子事实规范，不能为满足候选数硬合并。

### 6.2 跨片关系必须可追踪，不能靠一次总摘要

建立基于实体、事件、谓词、时间与显式指代的候选关系索引。相似度或关键词只用于缩小查找范围，不能证明不存在其他关系；尤其省略主语、别名与隔很久的纠正必须处理。

本轮基准实现采用分页矩阵：一批最多8个新atom，对既有事件/事实索引每页最多32组进行一次筛查，不是每一对事实单独发一次请求。索引页带稳定ID、完整结构化原子断言投影、时间/主体/别名及证据引用；不能只用一句有损主题摘要。每个新atom的已扫描页范围必须完整记录，模型不能只返回top-K命中就算检查完毕。

筛查中的 possible/uncertain 关系必须取原文做小批证据核对；只有独立证据核对支持才可合并/替代。否定关系也保存判断覆盖；显式纠正无命中时执行全索引分页与原文回查，不能静默新建无关事件。索引过长先分页而非截尾，跨页关系稳定去重；超预算不把尚未检查的组默认distinct。

每批新atom之间也必须做批内关系检查，不能只比较已有索引。并行处理按稳定事实顺序及索引版本冻结计划，两个同时到达的新批不能相互不可见而漏掉关系；去重或重投不能跳过这条验收。

容量核算必须覆盖最坏的“300个相互独立事实、无法靠事先distinct短路”的计划：在所有实际页能装下时，8×32分页约需190次筛查，而逐对16项一请求会需要2804次，后者不符合本设计。实际次数还要计提取、复核、候选生成及证据回查，用真实序列化planner测量，不能把这个粗估当验收通过。

对同一关系组逐步更新**带原文引用的原子断言集合**；摘要只作索引，不作最终证据。聚合状态仍要分页，不能把前面压缩摘要当全部事实然后丢弃原子记录。每次合并必须保留输入 atom 到输出的映射，重新核验变更部分。

duplicate 等价关系与 correction 有向关系分别处理；拒绝替代循环、自引用、指向不存在事实、跨 owner/epoch 或不一致输入版本。一个事实不能同时被两个无关系的最终候选认领。跨页修改应使受影响支持证明失效并重验，而不是沿用旧“通过”标记。

## 7. 有限调度、恢复预算与原子发布

### 7.1 预算必须持久，正常工作不等于失败重试

新 pipeline 使用 Live 专用、版本化 Run/WorkUnit 调度；旧 extractor 与旧 job 的 maxAttempts、契约修复资格保持。不能让每一页推进都消耗一次现有 job 的失败 attempt，也不能给每个新子 job 一份无限重新开始的预算。

预算分为四类并分别持久计数：已登记的正常工作量、容量拆分新增工作量、失败恢复调用、整个 run 的 Provider 请求/输入/输出总预算。会话期间按已确认的新正文按规则扩充正常工作计划，关闭后冻结上限；仅重启/重调度/换 lease/换 Source 绑定不得扩充额度。

本地初始资源配置如下，属于应用资源策略，不是供应商官方限制，也不是无限会话承诺：

| 配置 | 初值与约束 |
|---|---|
| 支持测试包络 | 65 分钟、至少 120 个用户回合；另有 20 分钟 100+ 用户回合密集数据；超过 200 总 turns / 30000 字 / 32 最终候选 |
| 单场最大工作单元 | 2048，含拆分及关系分页；不能用丢弃工作满足上限 |
| 单场模型请求硬上限 | 512 次，所有阶段与恢复共用；预算按实际暴露请求记账，调用前原子预留 |
| 单场输入/输出累计预留上限 | 输入 4,000,000 tokens、输出 2,000,000 tokens；输入按实际完整prompt估算、输出按阶段上限预留，不能每次机械预留16384/8192；无 usage 的未知请求保守消费，不能退款后无限重发 |
| 单元额外请求 | 契约修复或transient恢复合计最多1次，共用名额；原因分类与策略不同，不得各领一份；不能重新跑完整会话 |
| 单场恢复额度 | 最多 32 次且同时受 512 总额约束；拆分前已消耗的调用和恢复不得清零 |
| 单场并行 Provider 请求 | 最多 2；账号全局并发另设限制，不将供应商最大并发直接当应用配置 |
| 请求 deadline | 独立配置整体 deadline 与 HTTP 分阶段 timeout；默认单次整体 90 秒，超时不误称响应成功 |
| 后台期限 | 关闭后600秒无已验证的持久进展才触发无进展终止；另设关闭后3600秒绝对上限。它们是故障保护，不是健康场次的目标等待时间，也不靠重启刷新 |

以上是本轮可编码的初始保护值。Sol 必须用规定压力夹具报告计划单元数、实际调用数、token 预留峰值和最坏页数；若健康样本触及保护值，先优化分页与工作计划，不能删除事实或直接把上限翻倍。确需调整资源策略，应在本地交付前给出测量和明确变更说明，不能把未知费用当作已批准外部调用。

新v2的32次共享恢复池是对多工作单元的新有限策略，**不声称沿用了旧整场一次契约修复的数字**；旧pipeline不变。每个工作单元带稳定 `budgetLineageKey`，组织修复改变输出hash所导致的后续复核也属于同一恢复链、扣共享恢复池；不能把它改名成新正常unit重新领修复额度。网络自动隐式retry关闭或计入同一本账。新增正文和合法有限细分才允许增长正常计划；schema/语义错误本身不能随意增长plannedCalls。

必须测量停止时剩余任务与关闭后耗时；实时正常推进和完全没有预整理的会后补算都需完成。以受控HTTP延迟证明健康夹具不会被无进展/绝对期限误杀，真实供应商吞吐和关闭后等待时间另验。不得为了避开超时保护制造虚假“进展”。

候选发布事务与内部推理完全分开：ProviderAttempt 标记的“可能已调用”不等于业务候选已经写入。未知模型响应若以后重新推理，必须计为新的预算消耗；不能声称供应商调用 exactly-once。Live start/append/end/ACK/admit 的未知写仍按原保护执行，绝不因此重放。

### 7.2 lease、调度与最终 job

内部 WorkUnit 使用独立的短任务 lease 与 fencing，复用现有 async outbox/kernel，新增一个 Live 专用 `ownerTruth.liveMemory.unit` job类型即可，不另建通用DAG调度器。每个可执行单元一个稳定intent，payload只带不透明关联和hash；依赖完成才enqueue；单位结果、receipt/completion及下游稳定intent同事务落盘。扫描只补漏掉的同一intent，不改变计划或预算。成功单元以相同输入 hash 和版本复用；每次模型等待在数据库事务外，保持 heartbeat；落盘前重新核对 owner/epoch、输入版本、generation 与 lease。job attempt与实际Provider曝光数分别记录，单元重领不能越过其额外请求额度。

admit 仍产生唯一正式 Source 与其原有最终提取 job。在admit的同一UoW内，将Run与Source/version/hash和稳定publication operation ID一对一绑定，早于outbox可被分发，禁止抢跑窗口；此时不创建新Run或重置预算。

候选Worker增加typed `claim_next_candidate_extraction_ready()`：在claim SQL递增attempt**之前**，排除已绑定但尚未readyToPublish/terminalFailure/cancelled的Live Run。未就绪的正式job保持pending、attempt=0，不占lease；ready/失败的Run都可被领取并登记相应结果。无Run的旧Source保持旧领取行为，但新pipeline Source必须原子绑定Run，不得漏绑后误走旧链。

这只是候选Worker的就绪筛选扩展，不增加通用kernel工作流状态。以Run状态可靠持久化加轮询领取/扫描完成恢复，覆盖丢唤醒、并发就绪、旧版本兼容及普通Source不被饿死。不得先claim再release_retryable耗尽预算，也不得提前写成功receipt。

正式 job 只校验冻结 manifest 并执行已有候选提交。若预整理未发生，则同样登记 Run 后等待；不能回退到全量单次模型路径。后台超时/预算终结时可靠唤醒正式 job 写真实失败；保留 Source、草稿进度和恢复依据。

### 7.3 发布门禁

冻结 manifest 前机械检查：

1. 最终 Source 的所有用户 ownership segments 完整覆盖，无漏片、越界、重复归属或 hash 冲突；contextOnly 不混入新增事实。
2. 每个片段有独立原文复核；每个事实有且仅有一个合法终态：最终表达、并入一个最终表达、被有证据的纠正替代、被明确撤回。
3. 所有纠正/合并的目标存在、无循环、无未检查关系；纯问题等排除有语义判断和出处，不能把漏事实改为排除。
4. 所有最终候选及多维属性有用户原话支持；没有 unresolved、悬空事实、未完成单元或过期证明。
5. current authority、Source/version/hash、最终水位及 publication generation 全部匹配。

通过后，用现有 `OwnerTruthCandidateExtractionService.record_in_unit_of_work` 及其正式事务装配原子提交候选、ExtractionResult、consumer receipt 和 job completion；manifest 与结果建立稳定绑定。必要扩展只能加强绑定，不能绕过现有服务直接 INSERT 候选。

任何候选提交中途错误整批回滚；已发布 manifest 的重投只读回原结果，不追加第二组候选。候选 ID 不能依赖模型返回顺序或每次重试随机 UUID；以已冻结并落盘的 manifest 和稳定项 ID 为依据。

合法纯问题场可成功完成且候选为 0；有明确事实但整理未完成不能冒充 empty/reviewReady。待确认状态必须与同 Source 可查询候选一致。用户确认后仍走原审核、版本、幂等、正式记忆读取链。

## 8. 客户端观察与超过一小时的边界

### 8.1 只调整本场即时观察，不改历史任务仲裁

当前 `EchoViewController.swift` 会在约 6 次 GET 后停止即时观察；分批整理可能耗时更久，必须纳入本轮受影响范围。

- close/ACK/admit 成功与“已产生候选”保持区分，现有 saving/organizing/失败文案依据真实阶段，不增加掩盖失败的新成功状态。
- 后端同场状态读取必须识别已绑定的新Run：正式Source job在就绪筛选中仍是pending，并不代表未开始整理；用Run的真实工作/等待/失败状态映射既有公开状态。只有最终候选事务完成才能返回reviewReady，不能把内部readyToPublish提前映射成功。读取join严格限定本场Source/owner/epoch，不查历史最近Run。
- 增加绑定本场 workflow/Source、owner/epoch、observer generation 的有界只读观察。建议退避间隔 1、2、4、8、之后 10 秒；前台自动观察上限 180 秒，由注入时钟测试。
- 单次 GET 超时/暂时网络失败不改变后台业务结论。自动观察到期保留已知阶段及恢复坐标，停止转圈/活跃请求；不能伪称成功或业务失败，也不删除任务。现有“核实整理状态”只查绑定本场。
- 180 秒是客户端跟进预算，不是后台失败 deadline；若后台尚在执行，显示既有真实状态，后台继续至自己的期限。下次页面重进/回前台或用户核实可用新 fresh read authority 发有界 GET，不能重发业务写。
- 当前观察只允许本场结果提交页面；旧场或旧 observer callback 立即丢弃，不取消新 observer，不触发历史自动修复。
- 页面离开/账号切换取消本地 observer，不能取消后台 Run；冷启动从本场持久坐标只读恢复。UI 不再持有观察器不能导致服务端候选丢失。

历史任务优先级/全局 UI 仲裁仍独立；如红测证明共享函数影响当前场绑定，做最小修复并列入 IR 回归，不能顺便重写全局历史恢复策略。

### 8.2 未来 65 分钟能力需解除本应用 60 分钟配置门槛

当前 `app/core/config.py` 的代理连接期限为 3600 秒；`realtime_voice_proxy.py::consume` 会将其固定在 lease 中。它不是供应商时限，不应隐藏。

本轮增加显式开启的**新Live专用资源profile**，在经过验证的Live用途与新能力开启时选择 **7200 秒**代理连接期限，并固定进票据/lease；旧Live与其他实时语音保持原3600秒/512MiB共享默认。不得让客户端任意声明profile越权扩大资源，也不得关闭总时长保护。既有产品场次 ID、消息全局序号、捕获 coordinator 不随代理连接重建而重置。未部署环境仍保留原生效值，报告不能写生产已支持两小时。

单帧 2 MiB 保护保持。全场字节预算需要按实际双向编码与采样率计算 65 分钟上界并留余量；新Live profile采用 1 GiB 的有限上限，其他profile不变，测试合法累计流量及越界关闭。不要把只测空帧的逻辑时钟当流量验收。65分钟本地组合同时跨令牌/FeatureGate凭据有效期，恢复后继续采集及end/ACK/admit；明确deny或账号变化仍禁止新增请求，不能让受控网络永远无条件成功。

不改声音播放、打断、麦克风 ownership 或 SDK 的实时模型上下文，不做车机专用代码。真实供应商若在 65 分钟前主动断开，现场另行定位；不能预先声称透明续连已验证。连接恢复若走现有路径，必须保留同产品场次并遵循原未知写/迟到 final 保护；本轮不凭猜测新增音频自动重连状态机。
