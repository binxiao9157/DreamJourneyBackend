# 修改报告：主题争议提案缺少变更字段

日期：2026-10-08。**本文为待实施的修改方案，不是代码已修改或验收通过报告。** 用户本轮要求分析和报告；当前仅归档文档及离线诊断脚本。

## 1. 目标与范围

让同源、同版本、相同明确正文的重复事实在有限条件下只补充证据；让仍需保守审核的争议提案包含真实差异，使客户端能够完整审核。不得用关闭客户端审核保护解决问题。

| 范围 | 计划与风险 |
|---|---|
| 后端 memory_changeset.py | 主要修改点：同源重复识别及兜底差异字段；这是三个输入入口共用的确认规则，影响不局限于 Live |
| 组预览和确认 | 原则上只补测试；预览、加锁重算、实际激活必须沿同一规则，保持原子性和幂等 |
| iOS Contracts / 主题页 | 原则上只补真实响应和 UI 回归，不改审核保护；不新增内部字段展示 |
| 短场、长场、文字、添加记录 | 保存与发布实现不变，但必须回归其确认链，防止共用规则引入回归 |
| Live SDK、开麦、音频、十分钟告别、收尾调度 | 不改实现；重点回归 |
| 旧记忆、历史候选、任务、数据库 schema | 无批量重写、无迁移、无历史任务重试 |

不扩大到另一条“室内” temporalChange 的关系策略，也不同时修复短场问答召回观察项。它们保留独立记录。

## 2. 第一步：最小业务修复和离线验收

### A. 收窄识别 unknown/positive 的同源重复

在现有 `_is_same_source_repetition` 中增加明确、局部的 polarity 兼容条件：仅在字段差异集合为 unknown 与 positive 时允许继续核对；不能简单跳过整个 polarity 字段。

必须继续满足现有完整判定：同账号与主体边界、同 Source/版本、合法且非空的证据范围、完全相同的明确正文、没有明确时间变化、其他 qualifier 检查通过、业务正文内容一致。只要存在明确正反矛盾、跨 Source/版本、不同主体、具体地点/场景变化、明确日期或新增业务内容，就不能通过新增规则。

结果按证据集合选择 addEvidence 或 duplicate。addEvidence 只合并证据引用，保留目标已审核业务内容，不将 unknown 自动升级为 positive，不覆盖旧正文。必须测试两种输入顺序，不能依赖候选或 UUID 排序偶然避开问题。unknown/negative、unknown/neutral 本轮不新增宽松规则；沿既有规则且保障提案完整。

### B. 修复保守 dispute 兜底的差异契约

`sameAssertionCannotSafelyMerge` 是前面 polarity 相等分支之外的兜底；至少已知两端 polarity 不同。为该操作显式提供实际变化的 `qualifiers.polarity` 路径，由统一序列化器生成 before/after，不凭空填写差异，也不能只写空字符串或改名为 add 来获得通过。

实施前以所有可进入该兜底的合法 polarity 组合证明路径成立。若其他业务差异也会被该分支携带到 after，应一并提供对应真实、必要的差异，不能只列 polarity 而隐藏实际正文改动。比较和路径生成应排除纯证据位置、派生索引等内部噪声；不得通过清空 candidate 内容实现。

为所有会修改内容的操作加入测试契约：refine / correct / temporalChange / dispute 至少有一项真实可展示变化，两个 changedFields 表示一致，目标版本完整。不要贸然对全部旧操作构造器增加会改变运行时控制流的全局异常。

客户端继续严格拒绝 malformed/incomplete 提案。确认弹窗保留必要的内容差异说明，不能把 polarity、ID、置信度、原始 JSON 作为新增用户字段展示；若现有通用渲染对新的兜底响应会暴露内部字段，应先报告具体 UI 影响并纳入有限展示修复，不能靠隐藏真实内容变化绕过审核。

### C. 真实样本与反例

保存本次输入的未改原件；供仓库测试使用时脱敏账号、Source 和候选标识，保持正文、字段差异、证据范围关系。实际故障重现必须先红，修改后用相同断言变绿。

| 用例 | 必须证明 |
|---|---|
| 本次真实 unknown→positive 同源事实 | 修前 dispute+空差异；修后 addEvidence；目标正文不变、两处证据保留 |
| 反方向及相同 evidence | 不受顺序影响；相同证据不重复生成正式版本 |
| positive↔negative | 仍为可审核争议，不吞掉否定事实 |
| 其他未放宽 polarity 组合 | 保守兜底不能再返回空差异；不把 unknown 一概当作 positive |
| 跨 Source/版本、跨主体、地点/时间/正文变化、明确更正 | 保留各自原有保护，不能套用同源重复例外 |
| 23 成员真实主题组 | 全组提案经实际 Swift 类型审核可读；所有成员有明确结果，没有静默遗漏 |
| 预览后版本变化、旧提案提交 | 正确冲突并要求新预览，不用旧 hash 强行提交 |
| 组中途失败、重复确认 | 回滚不留半组；相同命令幂等，不重复增记忆或证据 |

第 A、B 部分和以上离线门槛通过后才能进入第二步。新增测试不能只有“后端 operationKind 正确”；必须将真实后端响应交给现有 Swift 解码和 reviewability。

## 3. 第二步：持久化、三入口与真机回归

1. 隔离 PostgreSQL 中使用正常 API/组审核服务完成待确认→预览→确认→正式记忆→重建/新进程读取。数据库确认数不必等于 23 条独立记忆：重复事实应合并，但所有候选必须有对应决定、回执和证据归属。
2. 验证重新预览会重算新提案并产生新 hash/ID，旧提案保留不可变；旧 expected hash 提交必须被拒绝，已成功提交的旧命令重放仍读原回执。
3. 三入口至少覆盖：文字输入/编辑/草稿恢复/确认；添加记录/确认与拒绝；Live 短场保存、待确认及正式确认。分别核对归属和实际记忆调用；召回失败单独记，不能冒充保存失败。
4. 跑开麦时间与失败恢复、音频播放/打断/恢复、正常关麦和十分钟告别重点回归。对比最终源码指纹，相关依赖改变后重新冻结，不能复用不匹配的短场凭证。
5. 用户发起部署和设备验证后，先用保留的本场 23 成员主题重新预览并确认，不重开 Live、不重做对话、不绕过客户端。另一个 3 成员主题独立验证。如果提案指向历史记忆，先核对新提案的具体影响，不能沿用旧核对结论。
6. 新一轮设备回归按 **独立短场→十分钟场**。每次长场前短场必须通过；不恢复 65 分钟压力要求。已授权的 ASR 轻微差异按用户逐场确认记录，不修改原始日志。
7. 首错后在既有安全边界内继续观察保存、收尾、候选发布和只读状态，记录失败是否局部、其余内容能否完成；不得未经分析自动重发未知写入。发布完成不等于正式确认完成。

没有手机时完成所有本地工作。真实 Provider 新调用、部署和设备测试在实施后按当次授权执行；本报告阶段全部未执行。

## 4. 发布兼容与回滚

共享确认规则变更会影响单条及主题组预览；不得在生产热改部分进程。部署时核对参与相关业务的 API/Worker 版本，保留一个可回滚发布与数据库备份。

现有组预览服务每次调用 `_build_fresh_proposal`，提案 hash 参与提案 ID；设计上可保留旧提案并生成新提案，无需删除旧表记录。仍必须以隔离 PG 实证确认旧命令与新逻辑的冲突、幂等和回滚行为，不能仅凭阅读宣布兼容通过。回滚程序不能撤销已确认记忆；不得把代码回滚等同于数据回滚。
