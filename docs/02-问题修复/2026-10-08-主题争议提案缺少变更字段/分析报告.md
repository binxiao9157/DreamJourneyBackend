# 主题争议提案缺少变更字段：分析报告

日期：2026-10-08。范围：本场待确认主题无法确认进入正式记忆。状态：本次直接根因已离线复现；未修改产品、未部署、未重新调用模型或操作手机。

## 1. 结论

本次是内部确认规则与前后端契约的组合缺陷，不能归因于火山网络、DeepSeek 超时、模型容量，或语音转写失败：

1. 同一场对话两次提取出相同正文，但结构字段 polarity 分别为 unknown 和 positive。
2. 后端同源重复判定只宽容“新值缺失”，不宽容“旧值缺失、新值明确”的反方向，因此同一句事实未被识别为重复补充。
3. 后续兜底分支将其归为 dispute，但没有填写 changed_fields；提案序列化也不会自动补差异。
4. iOS 要求争议提案具有至少一个真实、可展示的变更；这个要求没有得到满足。
5. 主题使用整组审核，任一成员不可审核就阻塞整组。因此一条异常提案阻塞了该主题全部 23 条候选。

后端对本次真实候选和目标重放后，生成的**单成员提案哈希与现场完全一致**。原样抽取现有 Swift 领域代码在 Mac 离线执行，23 个成员中只有索引 8 不可审核。以上不是仅凭错误文案推测。

## 3. 具体是哪两条

Source：`dc1dee18-d2ef-5d6a-adc8-2519dc2202a7`。

| 字段 | 同组先前事实 | 后加入事实 |
|---|---|---|
| 候选 ID | ef1cc9a8-7d05-55a8-aac2-7bb43fe6f1da | efed3e57-2c30-5c19-aeff-8a3d70e16690 |
| 正文 | 我先记录阳台薄荷的新叶数量。 | 我先记录阳台薄荷的新叶数量。 |
| polarity | unknown | positive |
| sourceTurnIndices | 25 | 45 |
| 地点正文 | 阳台 | 阳台 |

25、45 是保存正文中的索引，不应称为第 25、45 个用户回合。facets.places 中的证据轮次也相应变化。新增引用带来一份新证据，其余核心表述没有改变。

提案操作目标是同一主题内先前拟新增的虚拟记忆，不是历史正式记忆。这来自组预览的虚拟顺序执行：先模拟新增，再让后续候选与模拟后的当前集合比较。该机制用于保证预览与最终原子提交一致，本身不应删除。

## 4. 实际执行链

### 4.1 同源重复识别的方向不对称

[`_is_same_source_repetition`](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/domain/owner_truth/memory_changeset.py:458) 检查同 Source、版本、合法证据范围、完全相同正文、时间和业务内容。循环比较 qualifiers 时：

- 新值为 unspecified，则跳过；
- 新值明确而与旧值不同，则返回 False。

所以 incoming=unknown、existing=positive 可以继续判重复，而 incoming=positive、existing=unknown 被拒绝。这里 unknown 是结构信息未明确，不等于用户表达了反对。

### 4.2 空变更字段是代码遗漏

[`build_memory_changeset`](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/domain/owner_truth/memory_changeset.py:890) 的本次路径为：同 assertion → 相同 scope → 非已知正反冲突 → 同源重复不匹配 → 内容结构不完全相同 → polarity 不相同 → `sameAssertionCannotSafelyMerge`。

最后这个分支构建 DISPUTE 时漏传 `changed_fields`，默认值为 `()`。该分类由本地确定性 Python 代码产生，**确认阶段没有请求模型来判定 dispute**。

[`_proposal_operation_payload`](/Users/gaominge/Documents/Codex/Video/DreamJourneyBackend/app/domain/owner_truth/memory_changeset.py:731) 只遍历 operation.changed_fields 生成 factDiff，因此正文和 qualifiers 即使有结构差异，也会输出两个空数组。后端操作构造器目前也没有为争议建立“必须存在可审核差异”的约束。

### 4.3 客户端正常执行了既有保护

[`reviewability`](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Domain/OwnerTruth/OwnerTruthContracts.swift:1192) 对 refine、temporalChange、correct、dispute 要求至少一项 hasActualChange；空数组使结果为 incomplete。组审核要求成员全部可审核。

普通主题页的 [`preview`](/Users/gaominge/Documents/Codex/Video/DreamJourney_dev/DreamJourney/Sources/Modules/Archive/MemoryArchiveViewController.swift:21135) 也会停止在“确认信息不完整，暂不能提交”。因此不能通过放宽自动化工具的 add-only 规则解决，更不能跳过普通客户端保护来宣称通过。

## 5. 离线复现及最小对照

执行的是当前未改动后端领域函数，不使用假模型返回，不联网、不写服务器。

| 输入控制 | 输出 | 说明 |
|---|---|---|
| 完整真实输入：旧 unknown，新 positive | dispute；两个差异数组均空 | 提案哈希完全匹配现场 |
| 仅把旧 polarity 改为 positive | addEvidence | 改一个字段即可避开失败 |
| 仅把新 polarity 改为 unknown | addEvidence | 同样恢复重复识别 |
| 旧 positive，新 unknown | addEvidence | 证实方向不对称 |
| 旧 negative，新 positive | dispute，包含 polarity 差异 | 真正明确正反矛盾仍有保护 |

单成员现场哈希：`1f4f58317b2c7db0a393a9eff5fab1d4193e2b6baf20aa8cb4f6ac07b29c7c35`。

Swift 离线探针直接复制未改动的 JSON 解码、FactDiff、结构展示和 operation.reviewability 声明，记录原文件行号和片段哈希。23 条中 22 条可审核、索引 8 不可审核。它是 **Mac 领域代码执行证据**，不是新增模拟器、真机或按钮点击验收。

同时重跑现有 `test_owner_truth_memory_changeset` 和 `test_owner_truth_same_source_repetition`：20 项全部通过。已有测试覆盖相反 polarity、若干同源抽取漂移，但这两个测试模块没有覆盖本场 unknown→positive 的真实响应与 Swift 审核闭环。不能把这 20 项通过当成问题已修复，也不声称穷尽全部历史测试。

## 6. 与这次 UI 和第三方的关系

- 后端 `memory_changeset.py`、组预览领域逻辑和组审核服务与当前 HEAD 相同，本轮 UI 部署未修改这些文件。
- iOS Contracts 的未提交差异仅在日期投影；上述 reviewability 逻辑未改。主题确认仍执行该保护。
- 因而有证据表明这是本轮发现的既存确认缺口，并非本轮 UI 日期展示修改直接造成；不据此推断全部历史故障同根因。
- 已知两份最终提取结构存在差异，但本轮没有逐一重建上游原始模型响应与规范化过程。ontology 也可能将缺失或非法 polarity 归一为 unknown，因此尚不能说 unknown 一定由 DeepSeek 原文直接返回。
- 定位并修复当前确定性确认缺口不需要额外模型调用。上游为何产生差异可以后续调查，不应以模型随机性掩盖内部处理缺陷。

## 7. 修复判断

推荐先修复严格条件下的同源重复识别，使本次重复事实只补证据、保留既有正文；同时补齐保守 dispute 兜底的真实差异表示，避免其他输入再次产出不可审核提案。客户端审核保护、整组原子性、正式记忆权限与幂等规则继续保留。

没有必要重写 Live 收尾、重新提取整个场次、删除主题或要求用户重聊。修复后应通过正常“重新预览→确认”流程处理本场未决主题，旧提案继续作为审计证据保留。
