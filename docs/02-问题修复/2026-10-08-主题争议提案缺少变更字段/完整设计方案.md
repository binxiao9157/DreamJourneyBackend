# 同源重复确认修复与自然长场测试设计

2026-10-08。用户已批准实施。本文件是本轮实现和验收依据；原分析、失败日志保持不变。

## 一、问题和目标

同场相同正文的两条提取事实，旧 polarity=unknown、新 polarity=positive，未被同源重复规则识别，落入缺少 changed_fields 的 dispute 兜底；一条不可审核提案阻塞 23 成员主题。真实数据和原 Swift 领域代码已经离线复现。

目标：本次重复只补证据；真正争议仍明确展示差异、仍由用户确认。自然十分钟测试以新内容为主，不再循环十条固定句子凑时长。专项重复/补充/更正/矛盾测试与自然验收分离。

## 二、影响范围

1. 后端 `app/domain/owner_truth/memory_changeset.py`：同源重复 polarity 兼容和兜底差异字段。这是文字、Live、添加记录共享的确认路径，三入口都要回归。
2. iOS 仅允许小范围修正确认差异的 polarity 自然语言展示，避免将新可达兜底的 unknown/positive 等枚举暴露给用户；不改变 reviewability、确认提交、权限、版本绑定或页面结构。
3. 主测试工具 `tools/live_device_lab`：替换 short/10m 的循环内容生成器，增加可检查的事实预期清单与独立语义专项计划。旧场 manifest、录音和结果不可覆盖。20/40 历史压力能力保留，本轮不启动；不重新引入 65 分钟。
4. 不改 Live SDK、开麦/音频、十分钟告别、采集落盘、收尾和候选发布实现；不改检索和模型提示词；不做数据库迁移、历史重跑、数据清理或当前场强制确认。

## 三、业务修改规则

### 3.1 同源重复

保留原账号、主体、Source/版本、证据范围、完全相同正文、无明确时间、其余限定条件和业务内容检查。仅对 polarity 的 {unknown, positive} 组合增加兼容，不放宽 negative/neutral，不忽略整个 qualifiers。

通过后按新证据集合返回 addEvidence 或 duplicate，保留目标业务内容。不能自动把 unknown 改成 positive，更不能覆盖已有明确否定、地点、日期或更正。测试正反顺序；结果不依赖 UUID 排序。已有 unknown 输入的宽容语义不额外扩大。

### 3.2 保守兜底的可审核差异

兜底 `sameAssertionCannotSafelyMerge` 必须给出实际变化路径。明确列入 polarity；若有其他原始业务字段变化，逐字段纳入，以原 before/after 生成差异。排除 provenance、sourceTurnIndices、semantic、facets、dimensions 等证据或派生噪声；不删除真实 after 内容。与原分支相比只补差异描述，不改变该分支的争议操作类型、目标、激活行为。

不能使用虚构变化、跳过客户端审核、把全部争议改成新增、拆开原子组强行确认。对尚不可完整展示的提案保留拒绝，并如实记为失败。

### 3.3 展示边界

现有 UI 会把 polarity 枚举显示为“倾向：unknown→positive”。对该路径改为自然语言说明“原记录未明确是否肯定这件事 / 本次明确表示这件事成立”等，不新增技术字段。其他内容差异继续按既有精简展示，审核仍基于完整原响应。

### 3.4 旧提案兼容

预览和确认共用重算逻辑；新逻辑改变 hash 后必须重新预览，旧提案和回执保留。旧 expected hash 被拒绝，已经成功的命令仍走幂等回执。先在隔离数据库验证，不直接操作现场未决主题。

## 四、测试内容设计

自然短场使用两条易识别的新内容，十分钟场使用同一新主题下不少于 30 个有意义的输入，最多少量标明的重复/补充，正文不机械循环。主题从有限场景库轮换并带本场身份；不得只随机换数字而仍把它当旧项目改名。所有必需校验词必须真实存在于对应输入。

自然脚本是预设的顺序输入，不伪称能够理解模型回复的自适应对话；模型回复实时性与稳定性由现有工具验证。产品自然告别可能早于计划全部轮次，验收只要求实际已完成并保存的回合所对应预期，不要求未发送内容生成记忆，不为凑轮数延长 Live。

另出短语义专项清单：原话重复、同义重述、补充细节、明确更正、真实矛盾。为每条输入记录稳定 factKey、预期动作与关联目标。语义预期必须用生成内容逐项核对，不能只用候选数>0 或数据库存在宣布通过。没有完整语义自动评判器时明确标为待人工/模型证据核对，不能把清单生成当成专项通过。

每场保留 manifest/源码和工具指纹/实际转写/Source/候选/确认与正式版本证据。用户接受的 ASR 差异单独记录；原 FAIL 不删除。旧测试记忆清理由既有按 Source 归档后清理流程执行，本轮不为写测试计划触碰现场数据。

## 五、实施与验收顺序

1. 冻结源码和已有未提交修改，保留 UI 日期修改；新增真实脱敏样本和业务断言，先取得修前红。
2. 后端最小修复，真实候选对修后 addEvidence；全部 23 成员组重算后交实际 Swift 解码/reviewability；保留正反冲突与跨身份/来源反例。
3. 预览→确认→正式读取、重复确认幂等、并发版本冲突和回滚由既有组服务和隔离 PG 测试验证；三个入口的本地 API/Worker 链及短A→逻辑十分钟→短B继续执行。
4. iOS 执行确认展示、草稿与三入口相关回归，以及开麦、故障恢复、PCM、打断、告别与尾部保存重点测试。实际读取 xcresult，不以构建成功代替测试。
5. 工具生成器新增单测：固定种子可重复、不同种子换场、自然脚本不循环、必需词来自原句、事实目标有效、预期仅覆盖实际回合。准备一套新场计划但不启动手机。
6. 上述完成后冻结最终指纹和交付。部署/现场确认/真实 Provider/新短场→十分钟场为下一轮，不能记成本轮通过，也不能复用旧版短场凭证。
